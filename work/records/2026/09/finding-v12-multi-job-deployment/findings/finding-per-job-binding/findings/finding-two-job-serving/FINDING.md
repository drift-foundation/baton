**Two global fallbacks survive in the serving path, found by reading the tree
rather than by driving it.** Both are inside the authorized two paths.

1. `Integration.account` proves the integration settlement against
   `self.required_tests()` with NO Job id. That overload selects "the one
   implementation worker", so under a `/2` deployment with two producers it
   refuses -- the terminal completion check of EITHER Job would fail for having
   more than one producer configured. The required-test selection is already
   per Job everywhere else in this module through the binding's
   `source_worker_id`; this one call site was left global. Fix: pass this
   stage's own bound Job id, the same `_bound_id` the two lines above it use.

2. The integration runtime port is ONE injected object for the whole
   deployment, and `integration_worker.IntegrationRuntimePort` is constructed
   over ONE accepted `line_id`, ONE `proposal_id` and ONE `canonical_target_id`.
   Those are per-Job facts. A `/2` deployment handed a single port would run a
   second Job's integration against the FIRST Job's line and target -- the
   global fallback this campaign exists to remove, reached with a candidate
   already published. Fix: `operations_from(integration_port=)` accepts a
   MAPPING of bound Job id to port, `Integration` selects by the stage's own
   Job, and a `/2` deployment binding several Jobs REFUSES a single bare port
   rather than reusing it. One binding keeps the single-object spelling exactly
   as it is, so `/1` and every accepted case are unchanged.

   This composes no new provider, driver or profile: it is the same accepted
   port, supplied once per Job by the same operator that supplies one today,
   and the acceptance for this Work names the port among the operands to bind
   per Job.
