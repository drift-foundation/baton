## Findings

### P1 — canonical-unavailable status reports an unfinished ending as completed

The gate run exposed a source defect which `PROGRESS.md` reports but dismisses
as outside this Work. It is inside the accepted W81857 status boundary and is
the read-only form of the freeze-window defect fixed in pass 2.

`projection._ending_owed` returns true only when it can read an exchange whose
state is `answered`. The read-only `job_manager status` surface deliberately
has no deployment exchange reader and reports `exchange: null`. Once output is
frozen, `_observed_state` therefore skips the ending-owed rule and projects the
frozen disposition as terminal even when the manager's own cleanup axis is
still unsettled. The result is a stage reported `completed` while intake,
retention, Authority pass, or cleanup can still be owed.

`/tmp/repro-w81857-status-no-exchange.py` holds the same frozen output and
`cleanup: null` on both reads and changes only exchange availability:

```text
{'with_exchange': 'answering', 'without_exchange': 'completed', 'reported_exchange': None, 'canonical': False, 'cleanup': None}
```

This contradicts the pinned status matrix's canonical-unavailable and
post-answer-ending cases, the `/3` decision that an absent exchange read must
not invent progress, and the correction that frozen output is only step three
of seven. `exchange: null` usefully reports that nobody looked, but it does not
make a false terminal stage state truthful.

Derive the owed ending from the manager-owned frozen output plus unsettled
cleanup when the exchange read is unavailable. Preserve `exchange: null` as
the availability fact. Add positive controls for no exchange read before any
answer, and settled-cleanup controls that still project the frozen disposition;
add a negative case proving frozen plus pending/unset cleanup cannot complete
the stage or open a dependent gate.

### P1 — the real-container helper records observations but does not enforce its gate or bind the image to the reviewed source

`evidence/gate-real-container.py` computes the important acceptance members,
but it never validates them before printing JSON and returning zero. A run with
`provider_turn_began_after_the_commanding_manager_exited: false`, a nonempty
`ExecIDs`, multiple commands/receipts, staging residue, no output, an
exceptional final state, a surviving runtime, or a surviving/recreated exchange
would still exit successfully. A file named an acceptance gate must fail closed
on every acceptance member; otherwise command success does not mean the gate
passed and a later run can silently bless the regression it was added to catch.

The evidence also records the immutable image ID but no source binding. The
script accepts any `--image`, and neither the JSON nor the image configuration
records a hash of `/opt/baton/baton_worker.py` that can be compared with this
proposal's accepted candidate digest
`sha256:da34aa2c1dff8b9f25d748db79fc078c6082de9a13e5908c2cf247b99753a923`.
The package therefore proves that *an* immutable image ran, not independently
that the image contained the worker bytes signed off in pass 4.

Add a fail-closed acceptance check covering every claimed boolean/state/count,
while still printing useful failure evidence. Bind the run to the source-
approved proposal `sha256:93535b7e861faa2ed70bb0af5f1ad7b54b39dc95303410719d08be35f02d131b`
and record an independently measured content digest for the worker file inside

gate is meant to exercise.
