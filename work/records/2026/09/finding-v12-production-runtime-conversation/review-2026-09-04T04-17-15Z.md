## Findings

### P1 — worker event schema identities are accepted but never validated

`worker_manager.exchange._event` passes each receipt, state, and terminal
through `_decoded` and `_correlated`. `_decoded` checks only the closed member
set and scalar bounds; `_correlated` checks only session, attempt, sequence,
and command digest. Neither compares the document's `schema` member with
`RECEIPT_SCHEMA`, `STATE_SCHEMA`, or `TERMINAL_SCHEMA`.

Consequently a closed document explicitly identifying itself as another
protocol is accepted as this one. `/tmp/repro-w81857-event-schema.py` writes a
receipt whose schema is `somebody.elses.receipt/9`; the candidate prints:

```text
{'state': 'working', 'receipt': {'accepted_at': '2026-09-04T00:00:01.000Z'}, 'unreadable': None}
```

The pinned regression matrix requires wrong versions and foreign worker
documents to refuse. Schema identity is the type/version discriminator, not a
decorative bounded string. Check the exact expected schema for every event
kind before projection, and add wrong-schema receipt, per-operation state, and
terminal controls alongside the positive cases.

### P1 — a terminal can become answered success without the durable receipt/state chain

`exchange.observation` reads receipt, each state, and terminal independently.
If a correlated terminal exists it assigns the terminal ending regardless of
whether the receipt or the state events exist. Thus a worker/provider that
writes only an answered terminal skips the pre-dispatch replay fence and the
declared operation evidence yet is projected as a successful answer.

`/tmp/repro-w81857-missing-receipt.py` writes only the terminal and prints:

```text
{'state': 'answered', 'receipt': None, 'terminal_ending': 'answered'}
```

This directly contradicts the pinned matrix: receipt, state, and terminal
files are a correlated sequence; missing, reordered, or replaced documents
must refuse or project incomplete, and none becomes success. It is especially
unsafe for the receipt because that file is the durable proof that dispatch
was fenced before the provider ran. Enforce the causal prerequisites for a
terminal and the exact state evidence appropriate to its completed operation
list. Add omission and reordering controls for receipt, state events, and
terminal, including an answered terminal with no receipt and with incomplete
or impossible operation state.

### P2 — an ordinary command write/fsync failure strands its unique staging file

Manager `_publish_once` enters the staging-unlink `finally` only after
`_write_whole`, `fchmod`, and file `fsync` all succeed. An exception in any of
those operations closes the handle in the earlier `finally` and exits without
unlinking the partial staging file. Unique names prevent the old permanent
wedge, but repeated transient failures leak one file each and contradict this
function's stated invariant that ordinary failure paths leave nothing behind.

`/tmp/repro-w81857-write-failure-staging.py` injects a partial write followed
by `OSError` and prints:

```text
{'failure': 'injected write failure', 'staging': ['.sequence-2fe0dc3b28748780dace88a87ea9af53.json.2.82404cf97d669479.publishing'], 'staging_survives': True}
```

Put creation, write, mode, file sync, final-link/directory-sync, and close
failure handling under one cleanup boundary without weakening durability or
no-clobber semantics. Add injected write and sync failure cases that assert no
ordinary-failure staging residue. Apply the same audit to the worker publisher.
