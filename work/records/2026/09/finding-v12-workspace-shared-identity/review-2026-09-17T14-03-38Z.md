## Decision support: observation placement may move; freshness cannot disappear

**Confirmed:** `single_worker.effective_engine_run(None)` selects `_engine_run`,
which uses `subprocess.run`. `worker_preflight` is called from bootstrap
composition, staged worker composition and result-judgment composition. Its
current documentation already identifies configuration side effects; it is not
a generally read-only function. `configure_workspace_group` records configuration
and does not itself run an engine. Therefore, the proposed phrase "at the same
point ... a real engine is already in use" does not yet identify an actual
observation producer or prove that the new design covers every startup path.

**Clarification of earlier reviewer direction:** requiring enforcement during
preflight/start did not require starting a probe from every composition call.
The PLAN's former wording that combines observation with that precise preflight
location is superseded by the placement flexibility below. Moving observation
to an explicit deployment activation boundary and consuming its result before
affected execution is within the existing scope. No new owner permission is
needed solely for that choice. A test reaching an uninjected live runner shows
a test-boundary problem; it does not alone establish that deployment-time
observation is inherently incorrect.

**The proposed durable tuple alone is insufficient.** Journal/projection
agreement proves what was recorded, not that the current engine connection,
identity mapping or workspace filesystem still matches it. A store can retain
the same UID/GID while the engine/context, mapping or mount is replaced. Merely
calling `configure_identity_mapping(store, identity, observed_identity)` and
checking those numbers on restart would recreate the previously rejected stale
reuse defect. No unconditional acceptance of that design is given.

Implementation may choose either a startup-scoped observation capability or a
durable record with sufficient provenance and invalidation. Pin the chosen
producer/consumer flow in FINDING/PLAN before implementing it:

1. Name the exact explicit activation entry point and ordering for bootstrap,
   pooled and judgment execution, including custody use of the same mapping.
   Observation must precede affected Job execution; ordinary composition must
   not silently acquire an unbounded engine side effect.
2. Bind accepted evidence to the actual engine connection/deployment and
   workspace mount context, requested non-root identity and relevant runtime
   configuration. Refuse missing, malformed, mismatched or obsolete evidence.
   If continuity cannot be verified across a restart/reconfiguration, observe
   again at explicit activation rather than trust old recorded numbers. A
   startup-scoped capability avoids requiring a new durable schema solely to
   cache this result. Exact representation remains an implementation choice.
3. Exercise the real producer-to-consumer path with a deterministic engine at
   its normal boundary. Record-only fixtures may test consumers but cannot be
   the sole acceptance proof. Include matching acceptance; absent/mismatched
   refusal; engine/context/workspace change; restart/reuse; failed observation
   or cleanup; and no affected launch following refusal. Preserve the helper's
   verified cleanup and caller-visible unresolved diagnostics.

Then complete private HOME/cache, owner-only access both directions, compatibility
conclusions and written unexecuted update/recovery instructions. This is a bounded
implementation continuation, not another design-only approval round.
