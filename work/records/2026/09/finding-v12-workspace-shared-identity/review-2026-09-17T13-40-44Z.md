## Findings

1. **Inspection failure is classified as absence.** `_reclaim_probe` returns
   True for every nonzero inspect status. A daemon connectivity/permission error
   is not evidence the object is missing. Independent simulated inspect returns
   status 1, stderr `Cannot connect to engine daemon`; the observer returns a
   matching identity, performs no removal and records nothing unresolved while
   the modeled object remains. Require positively established absence using the
   engine boundary; ambiguous/nonzero errors must fail closed. The fixture's
   only nonzero inspection currently means `No such object`, so it misses this.
2. **Ownership inspection and removal target different objects under a race.**
   The nonce check uses a name, then rm --force uses that mutable name again.
   The independent engine model replaces the object immediately after returning
   the authentic nonce; removal deletes the unrelated replacement and the
   observer succeeds. Read the immutable object ID with the authenticated label
   and target that exact ID for cleanup. Do not solve this with another name-only
   inspection; the name can change after it too. Preserve wrong-owner objects.
3. **Directory cleanup failure does not affect acceptance.** `_remove_probe`
   catches an unlink failure, appends UNRESOLVED and returns. The caller ignores
   the cleanup outcome and returns its already-computed identity. A deterministic
   PermissionError leaves the file/directory present, yet the predicate accepts
   the returned identity. Propagate failure or an explicit settlement result;
   do not treat adding a diagnostic to a global list as enforcement. Surface
   unresolved resource identity through the actual caller-facing failure path.
4. **Original acceptance remains incomplete.** The production mapping gate is
   still disconnected, and private HOME/cache, restrictive-file checks in both
   directions, compatibility decisions and written update/recovery instructions
   remain outstanding. Fake-engine support and these changes are already
   authorized; finish them without creating another approval gate.

## Required outcome matrix

Accept only when run, observation, engine cleanup and filesystem cleanup all
satisfy their contracts. The following are existing requirements, made explicit
to avoid correcting one error shape while silently accepting another:

| Outcome | Required result |
| --- | --- |
| Valid run/file; positively established engine absence; directory removed | Matching observation may proceed |
| Authenticated owned engine ID remains; that exact ID removed successfully; directory removed | Matching observation may proceed |
| Run failed or timed out | No accepted mapping, even if cleanup succeeds |
| Inspection unreachable, denied, malformed or otherwise ambiguous | Refuse; retain actionable resource identity |
| Wrong nonce or name replaced by another object | Preserve other object; remove only authenticated owned ID if appropriate |
| Removal fails or its outcome is unknown | Refuse unless subsequent evidence positively settles exact absence |
| Owned filesystem cleanup fails or resource identity is uncertain | Refuse with diagnostic; do not return usable identity |

Use deterministic engine fixtures for every row and the recorded interleavings.
No live-engine run is needed to test these control-flow failures.
