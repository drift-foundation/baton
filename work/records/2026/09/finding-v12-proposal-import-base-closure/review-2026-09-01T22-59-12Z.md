## [P1] The mandatory base bundle contradicts the later Git input-delivery ruling

The live `FINDING.md` supersedes complete-directory staging for Git-backed
Work: input identity is an exact repository locator plus an exact base commit;
the Git-aware worker resolves that locator and clones or fetches the commit,
while a bundle or cache is only an optional transport optimization. The
retained proposal implements the opposite contract:

- `git_work_profile.INPUT_MEMBERS` has `base_commit` and `base_bundle`, but no
  repository locator;
- `held_input` requires `base_bundle == "base.bundle"`;
- `GitAgent.work` can only open that staged bundle and clone from it; and
- `EFFECTIVE-BATON-GIT.md` tells operators every assignment ships its objects
  in `base.bundle`.

This is mandatory protocol vocabulary and a correctness dependency, not an
optional provider optimization. It also means the worker never proves that it
resolved the repository locator the assignment declared, because no locator
can be declared. The candidate's PLAN therefore cannot mark item 5 done
against the current dossier.

Required correction: make repository locator plus immutable commit the input
identity at both held ends; make the Git-aware runtime resolve a supported
read-only local or remote locator into its private workspace and verify the
exact commit before writable execution. A bundle/cache may accelerate or
enable a deployment's transport, but it must not replace the locator in the
contract or become mandatory protocol vocabulary. Update the guide and the
append-only plan/progress history to reflect the current ruling, and cover
both direct resolution and optional transport with refusal cases for a wrong
commit.

## [P1] Changed-path decoding silently rewrites provider-controlled names

Both `v12/python/tools/git_work_profile.py:_out` and
`v12/worker/git_agent.py:_out` call `.strip()` after strict UTF-8 decoding.
Their changed-path readers feed `git diff --name-only -z` through that scalar
helper before splitting on NUL. Consequently leading whitespace in the first
changed path is removed. A leading newline is removed before the path-policy
check too, bypassing the explicit newline refusal.

The focused suite misses this because all fixture names begin with ordinary
letters. A direct probe of the retained host reader demonstrates the loss:

```text
_held_changed(CompletedProcess(..., stdout=b" leading.txt\0"))
=> ['leading.txt']
```

The worker and reviewer share the same defect, so `verify_proposal` can agree
with the worker's false list while the retained Git range changes a different
legal filename. That defeats the proposal's claim that review compares the
declared paths with the exact range and can misdirect later path-sensitive
review or integration.

Required correction: decode NUL-delimited path output without trimming any
byte or character; keep scalar object-id output on a separate helper. Preserve
allowed path names exactly and reject disallowed names before any
normalization. Add real-Git cases for a leading-space path and for a
leading-newline path that must be refused at both worker publication and
independent review.

## [P2] The closed-document readers accept an ignored suffix past one MiB

`git_work_profile.read_result` and `git_agent._work_input` each call
`read(1 << 20)` once and never test EOF. A file can therefore contain a valid
JSON document padded with whitespace through byte 1,048,576 followed by
arbitrary retained bytes. The parser and hold accept the prefix while every
reader of the complete file sees a different, invalid document.

A direct retained-code probe wrote a valid no-proposal result, padded it to
one MiB, appended `ignored-tail`, and `read_result` accepted the 1,048,588-byte
file as job `w62098-tail`. This breaks the closed-document and exact-custody
claims at the worker-to-reviewer boundary.

Required correction: state an exact document-size bound, read at most that
bound plus one byte, and refuse overflow before JSON parsing at both ends.
Add boundary cases proving a document at the limit has one interpretation and
that any byte beyond the limit is refused.
