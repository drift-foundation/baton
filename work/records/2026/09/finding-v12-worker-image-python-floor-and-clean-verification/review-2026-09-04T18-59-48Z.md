## Finding

### P1 — a surviving provider descendant can replace a verifier root after revalidation

`v12/worker/claude_agent.py:542-548` validates child roots by pathname, and
`_verify()` passes those same pathname strings to `_ran` at lines 851-855.
There is an unavoidable check/use interval between the final `lstat`/`realpath`
and the verification child resolving `HOME`, `PYTHONPYCACHEPREFIX`, `TMPDIR`,
or `XDG_CACHE_HOME`. The provider runs as the same uid and can write the whole
private scratch. More importantly, this module already records at lines
628-639 and 703-709 that a provider may leave a long-lived descendant after
its direct process exits. Such a descendant can wait until the pathname check
has passed, replace a verified directory with a symlink to `candidate`, and
let the verification child follow it.

A focused interleaving against the exact packaged `claude_agent.py` replaced
the verified `PYTHONPYCACHEPREFIX` only after
`_revalidated_environment()` returned and then ran the real
`python3 -m compileall -q probe.py`. Verification returned status 0 and wrote
44 `.pyc` files beneath `candidate`. The retained reproduction is
`/tmp/w85497-review-race-7ky_8jr_`. This is the same containment failure as the
prior provider-symlink P1, at a later interleaving; creating the predictable
roots earlier and checking them immediately before launch narrows the window
but does not close it.

Eliminate provider-descendant concurrency before verification, or bind the
verification child to stable directory objects that cannot be redirected by a
provider-writable pathname. Add a deterministic regression that performs the
replacement after the final validation and proves verification neither
follows it nor writes into `candidate`. A static replacement before validation
is still useful coverage but does not discriminate this race.
