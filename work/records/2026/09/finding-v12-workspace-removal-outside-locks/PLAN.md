# Correction plan — F2, workspace removal outside database locks

Bound to v11 Work W270664. Written under claim 272502 by baton.claude. This is a plan, not
a record of work performed; PROGRESS.md says what was actually done.

## The shape the correction has to take

The existing serialization is a real property obtained by an impermissible mechanism, so
the mechanism is replaced and the property is kept. The discipline is the one already
accepted in W257624 for restoration, reused rather than reinvented — owner 270664 says
"Existing lifecycle machinery must be assessed first", and this is that machinery:

1. **A SHORT COMMITTED OWNERSHIP TRANSITION BEFORE ANY REMOVAL.** One
   `BEGIN IMMEDIATE`, doing only database work: read the custody holds for BOTH roots from
   the journal, and — in the same transaction — commit a removal-ownership record naming
   this assignment, both roots, the pinned object identities and this act's nonce. A hold
   committed before it wins; a hold attempted after it sees the ownership record. Nothing
   in this transaction touches a filesystem.

2. **EVERY FILESYSTEM OBSERVATION OUTSIDE EVERY TRANSACTION.** `realpath`, the mount-table
   read, the tree walk, the permission changes and the `unlink`/`rmdir` all run with no
   transaction open, while the ownership record stands. The object identities the removal
   acts on are pinned in step 1 and compared here, so the act is bound to the objects it
   was authorized for rather than to their names.

3. **COMPLETION CONDITIONED ON THAT OWNERSHIP.** A second short transaction records what
   was removed, revalidating in PURE SQL that the ownership record is still this act's and
   that no hold arrived for either root. If either changed, the act refuses and stays held.

4. **UNCERTAINTY HELD, NEVER PRESUMED.** An ownership record with no completion behind it
   holds later removals of the same roots. The existing asymmetry stays: an absent home is
   the state the caller asked for and answers `False`; an interrupted removal is not.

5. **ONE MECHANISM FOR BOTH ENTRIES.** `intake._settle`'s call must not run removal under
   the cleanup transaction. Either the cleanup's removal moves out of that transaction
   (preferred: the cleanup's own completion already tolerates a replayed removal, per its
   comment at intake.py:4540ff), or the cleanup splits into
   authorize-outside-remove-outside-commit. The nested `in_transaction` branch at
   workspaces.py:1793 is then removed rather than kept as a shortcut, because after this
   correction there is no legitimate caller inside a write transaction.

## Evidence obligations, from owner 270664 verbatim

"Require focused deterministic evidence for both entry paths, competing removal/hold/reuse,
interruption/retry, stale completion and unrelated DB progress during paused filesystem
work."

Concretely, and each as its own case:

* **Both entry paths** — `discard_workspace` and `discard_execution_roots` standalone, and
  the same removal reached through `intake.authorize_cleanup` → `_settle`.
* **No transaction open at the external boundary** — the owner connection's
  `in_transaction` observed FALSE at every filesystem call the removal makes, in the style
  of `AnOpenTransaction` in W257624's selector.
* **Unrelated database progress while the filesystem work is paused** — a second handle
  commits an unrelated write while the removal is blocked mid-tree.
* **Competing removal** — two callers, one removal, exact answers: the loser is refused or
  answers its own truth, and never a replay of the winner's answer.
* **Competing hold** — a `custody_act` hold committed before the ownership transition
  refuses the removal; one attempted after it is excluded.
* **Reuse** — an allocation or adoption of the same roots during the removal.
* **Interruption and retry** — a removal that dies mid-tree leaves the act HELD, and a
  retry proceeds only after the ownership question is answered.
* **Stale completion** — a caller whose ownership was superseded records nothing.
* **Both roots and alias identity** — a symlink component and the result-root-inside-
  workspace overlap, preserved from the current code's own cases.

A stat or a timeout moved outside the lock proves nothing on its own; the audit says so and
it is right.
