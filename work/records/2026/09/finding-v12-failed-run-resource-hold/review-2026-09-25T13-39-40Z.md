## P1: confirmed runtime observation does not discharge an outstanding submitter

§1b says a delayed start is safe because admission is discharged by confirmed
runtime termination. §3 then proposes that recorded quiescence discharges the
start admission. Neither states how the old manager/engine request is prevented
from creating or starting a runtime AFTER the observation. An admission holder
paused before adapter.start, or a delayed daemon request, is precisely why an
absence/termination observation alone cannot prove the submission has finished.
Keep the reservation held until both the submitting effect cannot continue AND
all runtimes it produced are positively accounted for. State the exact supported
evidence for that transition or conservatively make it an unresolved held outcome;
do not infer that runtime termination also terminated its launcher.

The claimed completed producer trace also omits a material precondition:
attempts._quiescent at3446 requires a terminal worker disposition, not merely a
quiescent runtime. A deadline-cancelled worker that never answered cannot use
finalize_quiescent_assignment as a universally “necessary” release proof.
request_cancellation at2757 instead journals attempt.cancel then fences and orders
quiescence; its docstring expressly says ordering is not positive absence.
Separate successful checkpoint finalization from unanswered cancellation and
unknown-start recovery. Name the appropriate evidence owner for each, leaving
unknowns held. Add one forced delayed-submitter schedule to the planned start
cases: observation occurs while an admitted submitter is paused, replacement
must remain refused, then release that submitter. No test execution selected.
