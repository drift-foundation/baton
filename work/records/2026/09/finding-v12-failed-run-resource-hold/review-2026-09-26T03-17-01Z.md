## Lock proposal: necessary constraints before enabling settlement

The proposed lock is a candidate exclusion mechanism, NOT yet a proven cessation
boundary. In particular, availability of a manager-held lock proves only that the
lock is available. It proves all external effects ended only if every effecting
executor participates for its entire lifetime. `checkpoint_profiles.py` actually
delegates `reset` and `clean` to the supplied runner (`_run`, `restore_checkpoint`);
it has no current lock-ownership propagation in that interface. A manager can
exit while a child command survives, and a delayed invocation can be before lock
acquisition. These are concrete lifecycle windows the new implementation must close,
not assumptions supplied by calling a successful lock probe an absence observation.

Required invariants for the proposed implementation:

- Acquire the same durable lock object before effect eligibility/claim decisions,
  re-read completion and ownership after acquisition, and retain exclusion through
  the effect and relevant settlement/release decision. No probe-and-drop window.
  Acquire/probe/create filesystem objects outside DB transactions; short DB checks
  still bind the exact ownership generation.
- Bind lock identity to the actual store/resource/recovery ownership and protect
  against path replacement, symlinks and independently opened competing lock files.
  Do not unlink/recreate a lock still usable by another participant. An episode-only
  file must not let retry2 bypass live episode1. Absence of an old lock for a legacy
  episode is not evidence that episode ended.
- Establish the effect lifetime: a detached child still writing must keep settlement
  held even after its parent dies, or a supported supervisor must positively end and
  reap/fence it before release. Exception unwinding or parent-only close is not this
  proof. Restrict unsupported profile/runner lifecycles to held rather than assume.
- Prove bounded stopped execution followed by successful fresh retry, unresolved
  effect holding, late prior completion, actual cross-process post-settlement retry,
  and completed replay. Preserve successor bytes and no-I/O-under-DB-lock coverage.
  A supported positive settlement should not require pretending a fresh manager is
  the previous incarnation. Unknown historical/executor identity remains held.

These are conditions on the same owner-selected recovery guarantee, not a global
lease redesign or a mandate to add a specific mechanism. A supported alternative
that establishes them is acceptable. The earlier dossier wording that automatic
lock release on manager death itself proves effect cessation is explicitly NOT
accepted as a design premise.
