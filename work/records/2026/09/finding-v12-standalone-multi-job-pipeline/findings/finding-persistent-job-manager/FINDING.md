# Build the persistent v12 Job manager and submit/status API

Ledger Work: W71875

Parent: `work/records/2026/09/finding-v12-standalone-multi-job-pipeline/`

## Confirmed scope

Build the persistent host-side control plane that accepts a bounded multi-Job
submission and advances each Job through ordinary v12 stages without an
operator issuing every transition command. This leaf owns Job/submission and
stage-state persistence, restart reconciliation, the manager process boundary,
and documented CLI/JSON submit and read-only status surfaces.

The control plane composes the existing public Worker Manager and authority
operations. It does not duplicate offers, claims, attempts, runtime sessions,
output freezing, intake, retention, cleanup, or receipts with a second state
machine. It does not interpret Git, copy a source tree, implement worker-pool
selection, review policy, or integration policy. Those are separate leaves or
existing contracts.

## Observed baseline — 2026-09-02

- `v12/python/src/baton_v12/worker_manager/schema.py` persists manager
  operations, offers, attempts, sessions, outputs, intake, retention and
  runtime lanes, but has no Job, submission, stage queue, review, or
  integration scheduler relation.
- `offers.py`, `attempts.py`, `sessions.py`, `output.py`, and `intake.py`
  expose restart-safe bounded operations for the individual lifecycle steps.
- `v12/python/tools/dogfood_operator.py` is a supervised one-attempt command.
  It consumes operator-prepared grants/evidence and hands the result back to a
  v11 route; it is not a persistent scheduler and has no submit/status API.
- `v12/python/tools/parallel_test.py` is a test runner, not a product manager.

## Acceptance

- One documented JSON submission atomically records at least two Jobs, their
  immutable input identities, stage-scoped dependencies, requested runtime
  profiles, bounded test-change scope, and terminal policy.
- A long-lived manager process resumes that submission after restart and
  derives the next eligible act from persisted state rather than operator
  memory or a shell transcript.
- Every act delegates to the existing canonical Worker Manager/authority
  operation and records the returned identity/receipt; no shadow claim or
  lifecycle state can advance independently.
- The status command projects queued, offered, claimed, running, reviewing,
  changes-requested, integrating, completed, and exceptional states, runtime
  identity, dependency gates, and safe relative artifact/log locators.
- Replaying the same submitted intent is idempotent. Conflicting reuse of a
  submission or Job identity refuses.
- Restart tests stop the process at representative stage boundaries and prove
  that reconciliation neither repeats a committed act nor skips an owed act.
- No command-capable TUI, Git operation, source-tree walk/copy, or policy-driven
  acceptance/integration decision is added by this leaf.

## Confirmed correction ruling — 2026-09-02

The review above offered two acceptable mechanisms for the adoption finding.
The one taken, and pinned here so it is not re-litigated: **a manager proves
the intent; the two stores are not paired.**

`delegation.check_binding` compares the six offer operands this leaf owns and
persists — `offer_id`, `work_id`, `runtime_attempt_id`, `input_digest`,
`policy_digest`, `profile_digest` — against the operands `issue_offer` signed
into the `offer.issue` record. A mismatch refuses `refused/operation-collision`
and is neither recorded as `adopted` nor projected; a signature this build
cannot read refuses `integrity/schema` rather than being read as agreement.

Durable store pairing was REJECTED as the mechanism, for a reason that will
still hold later: it has to be configured, an operator can still point
`--store` and `--control` anywhere the CLI's own operands allow, and an
operation namespace made unambiguous by construction still collides when two
Job stores choose the same submission and Job identities. Proving the act is
the property that holds however the two paths were selected. Pairing remains
available as an ADDITIONAL guard for a later pass; it is not a substitute for
the proof and must not be introduced as one.

**The offer is the binding, so one check covers every act.** Both derived
identities are keyed by the offer id, `offer.settle` can only be journalled by
settling that one offer row, and the canonical observation is keyed by the
attempt id the offer froze. `offer.settle`'s own signature carries no Job
facts, so proving the claim through its offer is not a convenience — it is the
only place the intent exists. The proof therefore lives in
`projection.stage_states`, the single pass the sweep's adoption, the owed-act
derivation and the status document all come through, with a re-proof in
`manager._delegate` before it adopts instead of performing.

The scope finding is settled by reuse rather than by a second rule:
`documents._paths` applies the existing public `contracts.check_relative_path`
to every entry and refuses duplicates through the same `_unique` helper the
rest of the document uses, so one bounded test-change authority has one
durable spelling of each repository-relative path.

## Confirmed correction ruling — 2026-09-03 (pass 2)

**Obtaining a canonical row and proving it are ONE act.** This does not
supersede the 2026-09-02 ruling above; it completes it. That ruling settled
WHAT proves an act — the six offer operands, compared against what
`issue_offer` signed, with the offer as the binding for every act. It placed
the proof in `projection.stage_states` with a re-proof in `manager._delegate`.
What the re-review found is that placing a proof at a *pass* rather than at a
*read* leaves the reads that happen afterwards unproved. So the rule is now
stated at the read: `manager._proved` performs the journal read and proves
whatever it returns, absence stays absence, and every canonical read in
`manager.py` goes through it. `check_binding` is unchanged — it re-reads the
`offer.issue` row itself, so calling it at a later instant proves the row as it
stands at that instant; the defect was the set of call sites, not the check.

Two consequences are pinned so they are not re-litigated:

- **`_delegate` makes ONE acquisition after the delegated call**, whichever way
  the call answered. Two post-call read sites — one after a durable refusal,
  one after a returning call — were what let one of them go unproved. The call
  now decides only whether a *missing* row is `deferred` or a derived-identity
  fault; the row itself is obtained and proved once.
- **`_adopt` proves at its own read** and no longer inherits `stage_states`'
  proof. The review named `_delegate`; the identical fail-open was one pass
  earlier. A stage whose offer is absent when `stage_states` looks is answered
  `None` there — absence is the ordinary state of an unstarted stage — so a
  foreign row committing before `_adopt`'s read was written as this store's
  `adopted` receipt on the strength of a check that ran before the row existed.
  The review's own acceptance forbids a foreign winner being reported as
  performed, **adopted**, or refused, so this is inside the bounded correction
  and not an expansion of it.

**Open concern, recorded and deliberately NOT taken in this pass — the
projection's own read window.** `projection.stage_states` proves the binding
and then calls `operations.observe(stage)`, which reads the manager keyed by
`attempt:{stage_id}` — derived from the Job id and stage kind exactly as the
offer id is. A foreign attempt materializing between that proof and that read
would be projected once by `status`. It is narrower than the corrected defect
and durably harmless: nothing is recorded, and the next sweep's
proof-at-the-read refuses. Closing it means re-proving after the observation,
which changes the projection pass this FINDING deliberately placed — a redesign
the bounded correction was told not to make. It belongs to a NAMED later pass
and is not on this leaf's critical path.

## Confirmed correction ruling — 2026-09-03 (pass 3)

Slawomir approved the bounded correction: **an attempt-keyed observation is
usable for a Job stage only when it is bound to the offer identity already

## Correction taken, pass 3 — 2026-09-03

The pass-3 ruling above is implemented by making the observation's ACQUISITION
its binding, and by deleting the boolean that made the defect invisible.

**`claimed_by` replaces `claimed`.** The canonical observation reported whether
*some* offer held this attempt's claim. "Somebody claimed it" and "this stage
claimed it" are different facts, and a flag cannot tell them apart — so the
reader answers WHICH offer holds it, from the manager's own
`claimed_offers_for`, and this leaf compares that against the offer identity it
proved. `_one_claim` refuses `integrity/schema` rather than letting row order
choose between two claimed offers in a store written before
`offers_one_claim_per_attempt`.

**`delegation.observation_of` is the one operation.** It proves the offer
binding and binds what the reader returned to it, and
`projection.stage_states` makes that one call where it made two. There is no
unqualified attempt-id read left in this leaf for a later caller to reach — the
structural half of the ruling. A foreign holder refuses
`refused/operation-collision` naming both offers and the attempt; the refusal
comes out of the single pass `status`, `owed_acts` and `sweep` all use, so it
is never projected, never recorded, and never answers an act this Job still
owes.

**An unclaimed attempt carries no facts for this stage.** The claim is the only
thing the manager holds that ties an attempt id to an offer: the runtime, the
activity and the frozen result carry the attempt id and no offer at all, and it
is the manager's own `activate_assignment` that refuses to run an attempt for
anything but that attempt's committed claim. So `_bound` answers absence for
all four members when nothing claims the attempt, rather than reporting
observations nothing has bound to this Job. This is the half that keeps the
correction from being a single comparison somebody can later route around.

`check_binding` and `manager.py` are unchanged. The pass-1 and pass-2 rulings
are neither narrowed nor reversed: the offer remains the binding for every ACT,
and what this pass adds is that an attempt-keyed OBSERVATION is not covered by
that proof, because it is reached by a different derived identity.

**Open concern, recorded and deliberately NOT taken — the claim call's own
window.** A sweep now refuses before deriving or delegating anything when a
foreign offer holds this stage's attempt, so `_delegate` cannot reach
`submit_claim` under a known collision. A foreign claim committing between that
projection and this store's own `submit_claim` is not closed here. It cannot
falsify this pass's acceptance and is not the shape the ruling is about: the
manager's `offers_one_claim_per_attempt` unique index rejects the second claim,
so the outcome is a hard integrity error from the manager's own boundary rather
than a false projection or a shadow receipt — no durable state at all. Closing
it means holding a lock across another package's transaction, which is a
redesign of the delegation seam this bounded correction was not asked to make.
It belongs to a NAMED later pass. This is a genuinely narrower concern than the
one PLAN item 13 parked and item 14 superseded, and it is recorded with that
history visible rather than as a fresh observation.
