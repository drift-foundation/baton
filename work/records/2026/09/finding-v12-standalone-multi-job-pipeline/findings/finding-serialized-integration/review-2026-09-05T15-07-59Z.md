## Findings

### P0 — the proposed store cannot enforce the required lock domain

The proposed schema-5 integration tables live in `JobStore`. W83781 binds each
such store to one Authority UUID and makes an open under another Authority
refuse. A live-target unique index in that database is therefore unique only
within one Authority. Two Authorities configured for the same checkout can each
hold a lease in separate stores, violating W71878's explicit cross-Authority
serialization requirement and queue-key acceptance test.

Owner action is required: introduce one target-global coordinator/transaction
domain independent of an Authority-bound Job store (recommended), or narrow and
mechanically enforce the deployment model to one Authority per target while
explicitly superseding the current cross-Authority contract. Implementation
cannot choose this silently.

### P1 — object colocation does not make three durability domains indivisible

One injected composite profile may be a useful wiring unit, but placing policy
reads, filesystem import and Authority completion on one object creates no
atomicity across scheduler SQLite, target filesystem and Authority SQLite.
The record must retain explicit durable cutpoints and reconciliation between
preflight, import, verification and receipt completion. The claim that one
object makes the sequence indivisible is rejected.

### P1 — a serializable fence is not a live lease capability

Supplying a lease id and monotonic generation to a profile does not prove the
lease remains live; those values can be replayed. The target-store owner must
supply and re-evaluate the live grant against the exact target, entry, lease and
fence before canonical mutation and before Authority completion. Uncertain work
must prevent lease release. The boundary also needs a fixed participant-bound
integration Session and must validate its returned proposal/receipt documents;
the generic Worker Manager `AuthorityPort` should remain unchanged.

## Disposition

**Changes requested; owner ruling required before implementation.** The
integration-profile direction is acceptable only after the lock owner and live-
lease mechanism are corrected and the atomicity overclaim is removed. No
implementation bytes or test changes are approved by this review.
