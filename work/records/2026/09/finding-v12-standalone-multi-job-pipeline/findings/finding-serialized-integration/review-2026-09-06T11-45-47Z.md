## [P1] A sound replay is proved across multiple database snapshots

**Observed.** `IntegrationStore.transact` calls `replay` before
`BEGIN IMMEDIATE` and returns immediately when it finds the operation.
`_recorded` does the same for the fenced verbs. The newly required witness is
therefore semantically complete but not transactionally coherent:
`_proved -> _relationship` reads the target, entries, leases and journal in
separate autocommit statements.

Using two ordinary coordinator connections, the retained reproduction pauses
an exact enqueue retry immediately after its target-row read and commits a
valid grant through the other connection. The retry combines the earlier
target at fence 0 with the later lease and journal at fence 1, then reports an
`integrity.schema` corruption instead of replaying its first enqueue outcome:

```text
interleaved-sound-retry REFUSED integrity schema target 'target:mainline'
records fence 0 and the greatest fence in its durable history is 1
```

No persisted state is corrupt. This is a normal same-target schedule that the
coordinator exists to serialize, and an exact retry is required to return its
first owned outcome. The prior review required the materialized cross-binding
under the transaction's lock; adding the witness without moving the preflight
read into one snapshot leaves that part incomplete.

Correction boundary: every semantic replay proof must observe one SQLite
snapshot. A mutator may conservatively take the coordinator write lock for the
deciding replay, or use another transaction shape that proves the same
coherence, but it must not assemble one proof from independently committed
reads. Preserve the required ordering for fenced verbs — exact replay is still
decided before a now-ended live-grant check. Add a deterministic two-connection
regression that interleaves a valid grant between the replay projection's
component reads and proves the exact retry returns its first outcome without
altering either act.

## [P1] Refused journal rows bypass the semantic and order witness

**Observed.** `IntegrationStore.replay` branches on `state == "refused"` and
revives the sealed refusal before calling `witness`. `_history` likewise checks
the generic row and sequence position, then skips every refused row before
`_act` owns its kind, operands, derived identity and result variant.

The retained reproduction demonstrates both consequences:

```text
refused-retry-with-hole policy denied recorded refusal
ordinary-read-with-hole integrity schema this store's journal holds
'entry.enqueue:entry-2' at position 3 where its act number 2 belongs
unknown-refused-kind ACCEPTED
```

The first call is an exact retry of a well-formed refused enqueue after a prior
operation row was deleted. It returns the policy refusal without noticing the
journal hole or the now-unproven materialized entry; the immediately following
ordinary read detects both through the witness. In a separate sound target, a
schema-valid refused row carrying an operation kind this build does not own is
silently skipped and `target_of` succeeds. Thus “every retry is proved” and “a
kind this build does not own refuses the read” are true only for committed
rows.

Correction boundary: adopt every operation row before either outcome branch.
A refused act has no materialized effect to match, but its owned kind, complete
typed operands, canonical derived operation identity, dense position and
sealed refusal remain coordinator evidence and must be proved before replay or
before any ordinary relationship is returned. The exact retry must also prove
the surrounding journal/relationship in one snapshot. Add unknown-kind,
malformed/noncanonical signed-act and journal-hole cases through both ordinary
read and exact refused replay, plus the sound durable-refusal control.
