## Findings

### [P0] The live grant can end during producer revalidation and the port still mutates the target

`runtime.compose_assignment()` proves the grant at `execution.py:253`, but
execution then re-reads every producer, reads manager state, creates the
delivery and publishes the assignment before `port.run()` at line 267. There
is no second `live_grant()` at the pre-mutation cutpoint. The next grant check
is only in `settle_observed()` after the model has answered.

This is a real interleaving, not a theoretical width. The reviewer
reproduction at `/tmp/w101492_grant_gap.py` ends and abandons the grant from
the Authority target callback inside `_current()`, while returning the same
target revision. `_current()` succeeds, the port is asked, and `src/a.py` is
created with candidate bytes. Settlement then refuses because the lease is
abandoned. Output:

```text
model asked: [('attempt-1', 'entry-1')]
target changed: True
entry states: [('entry-1', 'held'), ('entry-2', 'queued')]
```

The new grant-race test ends the grant in `runs_after`, after the port has
already written. It proves the completion cutpoint and cannot detect this
missing start cutpoint. The parent contract requires the target-store owner to
re-evaluate the exact live target/entry/lease/fence immediately before
canonical mutation, not merely before a potentially long cross-store proof.

Correction boundary: after producer revalidation and assignment publication,
re-read the exact live grant immediately before the port receives writable
work. Add the deterministic interleaving above and prove an ended grant means
the port is never invoked and every target byte/mode stays unchanged. Retain
the existing post-run grant check independently; the two cutpoints answer
different races.

### [P0] `_startable` authorizes a writer behind an `uncertain` or cancelling runtime

`_startable()` rejects only `quiescent` and `destroyed`. It therefore calls the
port when the same attempt is `uncertain`, `cancel-requested`, `stopping`,
`start-requested`, or already `running`. Several of those states expressly do
not prove that an earlier writer is absent. The post-run `_quiescent()` check
is too late to prevent concurrent or unaccounted target mutation.

`/tmp/w101492_runtime_gap.py` records the granted attempt's manager state as
`uncertain` before `integrate_next()`. The current implementation asks the
port, creates candidate bytes, and only then refuses settlement because the
runtime is still uncertain:

```text
model asked: [('attempt-1', 'entry-1')]
target changed: True
entry states: [('entry-1', 'leased'), ('entry-2', 'queued')]
```

The corrected positive fixture also records `running` before
`integrate_next()` creates the delivery at line 264, while the accepted
`runtime.materialize_delivery()` contract says those fixed namespaces must
exist before the runtime starts. It therefore does not yet prove a realizable
delivery-to-start-to-quiescence sequence.

Correction boundary: define the exact manager state in which this assembly may
start one port invocation and refuse every state in which a current runtime may
already exist, be cancelling, or be unaccounted for. Materialize and publish
the delivery before that runtime starts; have the test port drive the same
attempt through the manager's legal start/running observation and only then to
quiescence after it writes. Add state-driven negatives, especially
`uncertain`, and assert the port and target are untouched. Merely checking
"not terminal before, terminal after" does not bind the writer interval.

### [P1] A stale ordinary preflight wedges the queue instead of refusing the entry

The parent finding's confirmed queue disposition says an ordinary current-
policy, scope or target failure before mutation terminally refuses the
immutable entry and moves the queue on; only integrity/digest/ambiguous-
custody failure holds the target. `_current()` describes its mismatch as
ordinary staleness, but its `_denied()` escapes after `grant_lease()` with no
coordinator disposition. The test
`test_the_stale_entry_keeps_its_grant_and_its_state` explicitly locks in
`entry-1=leased` and `lease-1=live` after Authority advances the target.

No target byte moved, so this is fail-closed, but it turns an ordinary stale
candidate into manual interrupted-integration recovery and prevents rank two
from progressing. That contradicts the recorded disposition rather than
implementing it.

Correction boundary: map execution-time preflight outcomes to the already
ruled coordinator verbs. An ordinary moved target/policy/scope account should
record a typed refusal through `refuse_entry` and release atomically; a genuine
integrity or ambiguous-custody account should block/retain. Add both branches
and prove bytes/modes unchanged and the next rank available only for the
ordinary-refusal branch.

### [P1] The replacement happy-path test still does not prove final-mode or verification evidence

The fake now writes real candidate bytes, which corrects the earlier no-op
happy path. Its result remains the constant
`verification={"final_bytes": "checked"}`, however; the port never reads the
final target back. `test_the_verification_observes_the_final_bytes` ignores
that verification document and independently checks only the imported path's
bytes after settlement. The newly created path's mode is captured by
`target_state()` but never compared with an expected ordinary mode. Because
`open(..., "wb")` uses the ambient umask, the test can pass with an unintended
mode.

Correction boundary: make the fake model's verification account derive from
the bytes and mode it reads after import, assert the persisted verification
against those exact facts, and assert the expected mode for every imported
path. Keep the explicit core limitation that this is the model's account, not
an independently invented coordinator verification.
