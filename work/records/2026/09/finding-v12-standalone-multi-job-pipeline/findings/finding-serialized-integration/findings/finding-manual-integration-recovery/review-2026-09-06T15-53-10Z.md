## Findings

### [P0] Abandonment ignores a newer `uncertain` manager observation

`abandon_held_lease()` calls `runtime.prior_runtime_witness()` and authorizes a
quiescent state, then immediately calls `_runtime()` for the runtime identity.
That is a second manager read. Its state is not compared with the witness and
is not checked for quiescence, so the operation can observe that the attempt
has become `uncertain` and still call `abandon_lease()` using the older proof.

The deterministic reproduction
`/tmp/w101493_abandon_observation_gap.py` returns `quiescent` from the first
manager read and `uncertain` from the second. The resulting status reports the
newer manager state as `uncertain` while the coordinator lease is
`abandoned`:

```text
newer manager state: uncertain
lease state: abandoned
```

That contradicts the acceptance boundary that explicit recovery refuses until
the prior runtime is positively proved unable to mutate, and repeats the
instant-binding defect corrected in W101492. The target remains blocked, but
ending its grant against an observation this same call already knows is
ambiguous corrupts the recovery account and weakens the gate later repair must
reason from.

Correction boundary: make one owned Worker Manager row the last pre-mutation
runtime observation, validate its execution state, and use that same snapshot's
runtime identity in the abandonment evidence. If two reads remain, the later
one must itself be quiescent and must agree with the proof being acted on. Add
the deterministic `quiescent -> uncertain` interleaving and prove the call
refuses with the lease still live.

### [P1] An invalid delivery is rejected only after the lease is abandoned

The delivery operand is not validated before `abandon_lease()`. It is first
read by the trailing `held_status()` call, after the coordinator mutation.
Passing `object()` as the delivery therefore raises the intended
`ContractRefusal` but leaves the lease `abandoned`:

```text
invalid delivery refusal: ContractRefusal
lease after refused call: abandoned
```

A public operation that refuses its input after performing its irreversible
coordinator transition makes the refusal falsely look non-mutating and loses
the typed-delivery boundary precisely on the operator action.

Correction boundary: own every caller operand needed by the action and its
answer before changing coordinator state. Add a negative case asserting an
invalid or foreign delivery refuses while the target remains blocked, the
entry held and the lease live. Preserve exact replay after a successfully
abandoned lease.

### [P1] Routine held status copies an untrusted block reason verbatim

`held_status()` deliberately omits block/result payload detail and exposes its
digests, but it still places `account["reason"]` directly in the returned
status. `block_target()` admits arbitrary text there, and an execution
runtime's valid `held` settlement can therefore place credential-shaped model
content in that field. A block with both reason and detail equal to
`credential-shaped-private-material` produces:

```text
secret projected: True
```

The existing privacy case covers only result detail before this leaf creates
its own fixed `runtime-interrupted` block, so it cannot detect an already
blocked execution result's untrusted reason. This violates the acceptance
boundary that routine status expose safe locators and identities without
credential content.

Correction boundary: expose only a leaf-owned closed classification for
routine status and retain arbitrary block reason/detail behind the existing
digest and evidence locator. Add an already-blocked case with credential-shaped
content in both fields and prove neither appears in serialized status.

## Accepted portions

`hold_interrupted()` turns absent, waiting, answered-looking and unreadable
delivery states into the exact coordinator block without settling or releasing
the entry, and a repeated hold reads the existing account rather than replacing
it. Status preserves exact target/entry/lease/fence/attempt identities,
manager-derived runtime and retained-file locators, while result and block
detail remain behind digests. The implementation invokes no retry, start,
acceptance, Authority completion, cleanup, output removal or reassignment.
