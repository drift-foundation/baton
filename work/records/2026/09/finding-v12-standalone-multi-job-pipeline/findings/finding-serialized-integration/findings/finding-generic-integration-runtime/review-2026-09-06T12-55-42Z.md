## Findings

### [P0] The assignment's attempt is not bound to the live grant

`compose_assignment` validates the caller's `attempt_id` and writes it into the
assignment, but never compares it with `held["attempt_id"]`. Only target, entry,
lease and fence are copied from the grant. A live lease for `attempt-1` therefore
successfully composes an assignment and delivery for caller-selected
`attempt-9`.

This violates the acceptance boundary's exact target, queue entry, attempt and
fence identity. The assignment must derive its attempt from, or exactly compare
it with, the live grant returned by the coordinator. Add a regression in which
every grant operand is current but the requested attempt differs.

### [P0] Caller-authored quiescence is treated as manager proof

`prior_runtime_witness` owns only the shape and static transition vocabulary of
a caller-supplied dictionary. It never reads the manager's durable attempt row.
Consequently a witness naming an entirely unrelated attempt as `destroyed`
authorizes writable access. Omitting `prior` authorizes it unconditionally; a
deterministic second-fence probe showed a later grant can omit its predecessor
and still receive `writable`.

The record correctly rules that agent/session state is not runtime quiescence,
but moving the same unsupported claim into a dictionary does not make it a
runtime observation. The positive answer must come from the Worker Manager's
durable state for the exact runtime whose ability to mutate is at issue (the
existing `attempt_runtime_of` is the public read), correlated with the exact
coordinator grant/predecessor relationship. Absence must likewise be observed
from durable state rather than asserted with `None`. Regression coverage must
include an unrelated witness, caller omission after a prior grant, a mismatched
attempt, each non-quiescent state, and restart adoption of the same durable
answer.

### [P0] The admitted profile kind is not bound to the runtime profile

The accepted coordinator correction under W101714 leaves `profile_kind` in the
entry's 14-member eligibility account and removes the two members with no
accepted producers. `compose_assignment` checks only the profile's integrator
participant against the lease. It does not read or compare the entry's accepted
`profile_kind`; a lease for the repository profile therefore composes a
`different.profile` assignment with arbitrary deployment version and
instructions.

`profile_version` and the instructions digest remain deployment wiring and
must not be reintroduced into candidate eligibility. The correction required
here is narrower: obtain the accepted entry's `profile_kind` as part of the
same coordinator relationship proof as the live grant and require the runtime
profile kind to equal it. A separate unsynchronised `entries_of` read would
weaken the one-snapshot property. Add the positive match and differing-kind
refusal cases against stored entry evidence.

### [P1] Assignment publication is the older unsafe algorithm, not the inherited mechanism

The finding promises `worker_manager/exchange.py`'s current publication rule,
but `publish_assignment` uses one fixed staging name, one unchecked `os.write`,
process-umask-dependent creation, and `os.rename` onto the final name.
Reproductions establish that:

- a stale `.assignment.json.staging` permanently wedges publication with raw
  `FileExistsError`;
- a one-byte short write is reported as successful and published as the final
  assignment;
- a restrictive umask produces a mode-000 final file despite the declared
  `0444` contract; and
- `rename` may silently replace a concurrent winner after the initial absence
  check.

The shared exchange code already fixes these exact cases with a unique staging
name, whole-write loop, descriptor `fchmod`, file sync, no-clobber hard-link
publication, winner comparison, directory sync, and staging cleanup. Reuse an
extracted shared primitive or preserve all of those current invariants exactly;
do not copy this superseded publication shape into a fourth delivery. Drive
short-write, umask, stale-staging, identical-race, and conflicting-race cases.

### [P1] Restart adoption does not prove manager custody

`adopt_delivery` uses `os.path.isdir` for the root and both namespaces. That
follows links and proves neither exact modes nor the configured workspace
group. A result namespace changed from the manager-established group-writable
mode to `0700` is accepted. The assignment namespace can likewise drift from
`0755` while the manager reports it as its own delivery.

The accepted exchange mechanism opens directories no-follow, proves directory
type and exact mode on descriptors, and proves the runtime-written namespace's
group against the manager-minted `WorkspaceGroup`. Integration delivery
adoption needs the same custody checks and therefore the same trusted group
input. Add symlink, non-directory, wrong assignment mode, wrong result mode,
and wrong result group regressions.
