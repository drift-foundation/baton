## P0 — a released integrated entry can be requeued and leased again

The claimed whole-graph validation checks:

- each lease names an entry on the target;
- at most one lease is live;
- a live lease has a `leased`, `integrated`, or `held` entry;
- every `leased` entry has a live lease; and
- held/abandoned states agree with target blocking.

It does not check a released lease against the state and settlement of its
entry, nor does it reject a queued entry that already has a lease history.
After a normal integration and release, the re-review changed only the entry
row to its schema-valid queued shape. All public reads accepted the released
`integrated` ending beside the queued entry, and selection leased the same
candidate again:

```text
released-integrated-as-queued/target ACCEPTED
released-integrated-as-queued/lease ACCEPTED
released-integrated-as-queued/entries ACCEPTED
released-integrated-as-queued/grant ACCEPTED entry-1
```

The result has both a released and a live lease for `entry-1`. This can repeat
an import whose durable lease account already says it completed, violating
idempotent recovery and the immutable one-place queue contract.

Correction boundary: make `_prove` enforce the complete per-entry lifecycle,
not selected state pairs:

- `queued` has no lease;
- `leased` has exactly one live lease;
- `integrated` has exactly one lease, live between settlement and release or
  released with the `integrated` ending afterward;
- `refused` has no lease when refused before selection, or exactly one
  released lease with the `entry-refused` ending when refused under a grant;
- `held` has exactly the blocked account's one lease, live before recovery or
  abandoned afterward; and
- the target fence equals the greatest fence it has granted (zero only when it
  has no leases).

No entry in the item-3 model returns to `queued` or acquires a second lease.
If a later repair/retry design needs either transition, it must introduce an
explicit reviewed state/account rather than weakening these invariants.

Add a table-driven corruption matrix at `target_of`, `entries_of`, `lease_of`,
and `grant_lease`: reset integrated/refused/held entries to queued; mismatch
released outcomes with integrated/refused entries; attach released leases to
queued or unrelated same-target entries; give an entry multiple historical or
live-plus-ended leases; and drift the target fence from its lease history.
Every case must refuse without moving rows or offering work.
