## Findings

### [P0] A stale schema-2 opener can replace the immutable Authority binding

`JobStore._adopt` reads the schema version before `_migrate` obtains its
`BEGIN IMMEDIATE` lock. `_migrate` then trusts that pre-lock value at
`store.py:348-375`. Two openers can therefore both observe schema 2. Opener A
migrates first and records Authority A; opener B then acquires the lock with
its stale `version == 2`, runs the empty 2-to-3 step, and executes
`INSERT OR REPLACE`, changing the binding to Authority B. The second open may
then succeed as B. Existing namespaced episodes still belong to A while every
future episode is derived in B's namespace—the exact cross-authority split
the immutable store binding was introduced to prevent.

The deterministic reproduction is
`/tmp/repro-w83781-stale-migration-rebind.py`. It opens two independent SQLite
connections that both observe version 2, serializes the two migration calls,
and reports:

```text
{'after_first': 'aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa',
 'after_stale_opener': 'bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb',
 'rebound': True}
```

Re-read and validate the live version/binding after obtaining the migration
write lock. A waiter that finds schema 3 must compare the recorded UUID and
either adopt the same binding or refuse the conflicting one without writing.
Do not use replacement semantics for an immutable binding. Add a deterministic
two-opener regression that proves the loser cannot change the winner's UUID,
version, episode identities, or bytes.

### [P1] The promised migration rollback evidence is absent

The finding and plan require a failed schema-1/schema-2 migration to roll back
the UUID and version stamp together. The implementation has a rollback path,
but the new migration tests cover successful schema-1/schema-2 migration only.
Add a failure vector after the migration begins and prove the prior version is
retained, no `authority_uuid` row survives, and existing identities/receipts
are unchanged. This vector should exercise the public `JobStore.open` boundary,
not merely assert the transaction text looks atomic.

### [P1] The OCI positive vector never performs the promised fresh start

`test_a_namespaced_attempt_does_not_select_the_other_authoritys` at
`test_oci.py:1111-1132` derives two distinct attempts and proves only that
`adapter.list(...)` returns `[]`. Its docstring says a start proceeds, but it
never calls `start`, and the manifest/PLAN acceptance explicitly requires a
fresh namespaced attempt to reach exactly one `run`. Use an engine double that
retains the old Authority's attempt and honors the attempt-id selector, drive
the fresh attempt through `start`, and assert one—and only one—engine `run`.
Keep the adjacent same-attempt/foreign-authority refusal proving zero runs.

### [P2] Newly added tests are below the direct-run entry point

Both `test_store.py:386-387` and `test_submission.py:225-226` call
`unittest.main()` before the new test classes are defined. Discovery imports
the modules and sees the cases, but invoking either test file directly exits
before defining them. Move each guard to the true end of its file so the
file's documented direct test entry point exercises the new regressions too.

### [P2] The persisted UUID is compared before its semantic type is owned

`JobStore._bound` reads the new durable UUID with `boundaries.text` and then
compares it. A corrupted schema-3 row such as `not-an-authority` is reported as
a valid store belonging to a different Authority (`refused/precondition`)
rather than malformed persisted state (`integrity/schema`). Run the persisted
value through the same `check_authority` rule used on input before comparing
it, and add the corrupt-meta negative case. This remains fail-closed today but
misclassifies the store's own invalid evidence at its receiving boundary.
