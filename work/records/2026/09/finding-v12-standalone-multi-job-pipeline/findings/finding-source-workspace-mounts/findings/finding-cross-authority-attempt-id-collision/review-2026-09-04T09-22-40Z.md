## Remaining findings

### [P1] The durable rollback vector fails before either value it claims to test is written

`test_a_failed_migration_rolls_the_uuid_and_the_version_back` patches
`_statements` to raise. `_migrate` calls `_statements(MIGRATIONS[at])` before
executing a migration statement, advancing `schema_version`, or inserting
`authority_uuid`. The test therefore proves only that an exception immediately
after `BEGIN IMMEDIATE` changes nothing. It does not prove that the two
required durable values roll back together, and it would still pass an
implementation that committed migration work before writing either stamp or
wrote the stamps outside the migration transaction. The proposal manifest and
PROGRESS.md description of a failure injected “mid-migration” overstate what
this case exercises.

Keep the public `JobStore.open` boundary, but inject the failure after both the
new schema version and the UUID are visible on the migration connection and
before `COMMIT`; then retain the current assertions for prior version, absent
binding, identities, receipts, byte equality, and a successful later
migration. The independent reproduction above demonstrates one deterministic
hook, but the regression belongs in the candidate's scheduled test file.

### [P2] The stale-opener regression omits the requested byte invariant

The prior P0 asked the competing-opener case to prove that the loser cannot
change the winner's UUID, version, episode identities, **or bytes**. The new
case proves the first three but takes no byte snapshot around the stale
opener's `_migrate` call. The separate wrong-UUID-open test covers a store that
was already current before that open; it does not cover the stale migration
path that caused the defect. Snapshot the winner's completed database before
the stale migration call and assert the same bytes afterwards.
