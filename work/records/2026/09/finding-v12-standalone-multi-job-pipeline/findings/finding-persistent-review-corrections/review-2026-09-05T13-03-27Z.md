## P0 — revoking the database writer does not fence its writable capability

`review_cycles.writer_boundary` returns an `AllocatedRoots` and
`SourceBoundary` that authorize the persistent line as writable `/output`.
`freeze_checkpoint` then changes only `line_writers.state` and
`review_lines.state` before calling the checkpoint profile. The already-minted
roots and boundary carry no line-writer identity or generation and consult no
store when `adopt_source_boundary` or `boundary_mounts` consumes them.

The reproduction composes the writer boundary, freezes the checkpoint, proves
the durable writer row is revoked, and then successfully adopts the old
boundary and recovers `(line_path, "/output", True)`. An already-running
container likewise retains its writable bind. The caller-supplied `quiescent`
predicate is evaluated before revocation, so a runtime may also start another
operation in the check-to-revoke interval; it is not an atomic fence.

This violates the confirmed revoke-before-freeze rule and means a reviewer can
receive a supposedly current read-only checkpoint while the old writer still
holds usable write authority. Correction must fence the actual assignment and
runtime/engine start boundary, then prove all supervised activity quiescent,
before freezing. A previously minted capability or remembered generation must
not remain sufficient to start, adopt, or retain a writable line mount after
that fence.

This defeats the Work's central rule that an independent verdict AND its logs

that never ran or still has live supervised work must refuse.
