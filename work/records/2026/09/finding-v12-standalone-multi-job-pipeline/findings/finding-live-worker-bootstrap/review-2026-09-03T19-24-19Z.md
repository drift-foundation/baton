## [P1] Post-start runtime naming is edge-triggered and skips contradictory launch material

`tools/single_worker.py:722-739` records `runtime.preparation-failed` before it
calls `_named`. That record immediately projects the Job stage as
`exceptional`, while `job_manager.manager._launch` calls the deployment only
for `claimed` stages. A process death or ordinary naming refusal between those
two acts therefore does not leave naming "still owed" as the comment at lines
730-732 claims: no later process or tick reaches it.

A focused probe stopped the process immediately after the preparation record
was committed and before `_named`, then resumed the same stores for six ticks:

```text
stage state: exceptional
attempt runtime id: None
preparation-failure record: present
later engine calls: 0
engine runtime id: runtime-single-1
```

The same orphaning is reachable without an injected crash. `launch.adopt` at
lines 706-708 may refuse a contradictory or partial existing delivery. That
exception bypasses `_stranded`, reaches the generic preparation recorder, and
again makes the stage exceptional without ever naming the live runtime. A
post-start launch root with a refused mode produced the same final state after
six ticks: the engine still held `runtime-single-1`, while the attempt held no
runtime identity and no later engine call occurred.

Make post-start identification a durable, level-triggered obligation whose
completion can be replayed after the preparation ending and which covers every
launch-adoption refusal, not only `adopt` answering absence. Add a crash
between ending and identification plus a contradictory/partial launch case;
both must converge to a named runtime without authoring launch bytes,
rereading a bearer, or starting a replacement.

## [P1] A pre-start launch adopted after a crash is never discarded

`_launch_document` returns `(delivery, False)` whenever it adopts a valid
launch at lines 706-710. The failure handler at lines 656-669 discards only
when `authored` is true. If the first process crashes after publishing the
launch but before credential materialization, the second process proves
`execution_runtime == not-started`, adopts that exact delivery, and then a
credential-source refusal ends the stage. No runtime can hold the launch
mount, but the terminal stage leaves its root permanently present.

The focused crash/restart probe observed:

```text
launch present before restart: true
stage state: exceptional
provider calls: 1
launch present after ending: true
engine starts: 0
```

Authorship in the current invocation is not the ownership boundary. Adoption
returns the exact `LaunchDelivery` capability, and the already-proved
`not-started` state establishes that no runtime received it. Dispose that
exact delivery after any later pre-start failure whether it was authored or
adopted, while preserving the prohibition on deleting a delivery after a
start was requested. Add the crash-after-launch/provider-refusal regression,
not only the same-invocation case.

## [P1] A bearer equal to durable attempt identity wedges the manager before cleanup

The credential provider's answer is explicitly untrusted, and the existing
section-13 suite deliberately uses a bearer equal to
`runtime_attempt_id` (`tests/manager/test_credentials.py:884-921`). In the
production composition, `CredentialHome.materialize` registers that answer
live. `_prepared` then leaves its cleanup `try` at line 669 and calls
`request_runtime_start`, whose first attempt-row read now correctly refuses:
the durable row contains the live bearer as its identifier. The outer handler
tries `attempt_start_failure_of` and `attempt_preparation_failure_of` at lines
613-615, which repeat the same refused read rather than settling the delivery.

A focused production-factory probe returned the stage's exact attempt id as
the provider bearer. No engine call occurred, but the section-13 refusal
escaped the sweep, the credential registration/root and launch root remained,
and no durable ending could be read or written in that process. This is the
same adversarial equality the engine-port regression already treats as valid;
random-looking provider output is not a proof that it cannot occur.

Keep the delivery's cleanup owner active across every pre-start manager
boundary that follows materialization, and ensure a colliding live value is
released only after its bytes are proved absent before durable state is read
or an ending is recorded. Add an end-to-end case returning the actual attempt
id as bearer and prove: no engine traffic, no bearer in output, successful
credential and launch disposal, one safe exceptional ending, and no retry.

## [P1] The preparation-failure record still has two contradictory meanings

The durable schema comment at
`worker_manager/documents.py:169-180` says `runtime.preparation-failed` means
"no start act happened and none ever will" and "this attempt will not run".
`attempt_preparation_failure_of` repeats that contract at
`worker_manager/attempts.py:350-358`, and the dossier's 2026-09-03
preparation-record ruling says there was no start act to name. Correction pass
4 now deliberately writes this record after a preceding process did perform a
start act and left a running runtime, then reconciles and attaches that
runtime. `DEPLOYMENT.md:85-100` additionally calls the sibling record a
"failed start" while describing the new post-start behavior.

Keeping this record separate from `runtime.start-failed` and granting it no
destroy authority remains sound; the false claim is that it proves no start
act or runtime can exist. Pin one coherent meaning before changing code:
explicitly supersede the obsolete dossier language and update the owning
schema/API/deployment text to say this is the deployment's post-claim
preparation/continuation ending, not an account of whether an earlier start
act occurred and not cleanup authority. The record's consumers and recovery
obligation must then be verified against that single meaning.
