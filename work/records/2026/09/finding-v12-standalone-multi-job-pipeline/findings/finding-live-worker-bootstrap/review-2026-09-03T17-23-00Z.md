## [P1] Restart adopts credential bytes before proving the live runtime and mounts

`tools/single_worker.py:478-495` reads the local credential lifecycle record
and calls `CredentialHome.adopt` directly. It supplies
`recorded["runtime_id"]` as the expected runtime id, so that comparison is the
record compared with itself. The composition never calls the existing public
`OciAdapter.recover_credentials` operation.

That public operation is the owner boundary for this exact restart question.
As documented and implemented at `worker_manager/oci.py:1826-1919`, it derives
the attempt's full label context, identifies exactly one live runtime, compares
the lifecycle record's runtime id with the engine's answer, inspects the
runtime's actual mounts, and only then calls `CredentialHome.adopt` to reread
and re-register bearer bytes. Ordinary `reconcile_runtime` does not perform
those credential/mount checks. The current code therefore re-registers secrets
from local files before proving that the live container is the one named by
the record or that it holds the intended mount. A stale or mismatched lifecycle
record is accepted at the very boundary the credential recovery contract says
must fail closed.

Compose the public credential recovery capability on the attached-runtime
restart path before adopting the delivery, and carry its proved delivery into
the adapter used for runtime reconciliation. Add cases for a lifecycle record
naming another runtime, a matching runtime with a mismatched credential mount,
and the exact successful recovery. The failure cases must not re-register the
bearer or accept output, and must preserve the recovery operation's bounded
stop/cleanup result.

## [P1] Workspace and input failures are outside the canonical failure ending

`tools/single_worker.py:505-534` performs attempt recording, activation,
workspace adoption, input adoption/composition, and manifest retention before
the `try` that begins at line 537. Only credential, launch-document, and adapter
construction refusals reach `_PreparationFailure` and the Worker Manager's
durable `runtime.start-failed` record.

Consequently a structurally foreign workspace, partial or contradictory input
root, changed source, assignment-manifest refusal, or retained-manifest
collision returns to `job_manager.manager._launch` with no failed-start record.
An ordinary `ContractRefusal` is reported as `deferred` and retried on every
tick; a durable refusal or ordinary fault aborts the whole sweep. Neither is
the accepted rule that a preparation/start failure becomes one exceptional,
non-retried stage while later independent stages remain observable. The crash
tests stop only after each completed checkpoint and do not exercise a partial
or contradictory boundary between those checkpoints.

Give every post-claim preparation boundary one owner-recorded exceptional
ending without requiring an input-root authorization that cannot yet succeed.
Then add at least partial-input and foreign workspace/input cases, with the
failing stage sorted before an independent one, proving exceptional status,
no retry, and continued service. Do not repair contradictory material or add a
shadow Job-store receipt.

## [P1] The partial-input branch raises an invalid refusal pair

`tools/single_worker.py:432-436` calls `_refuse` with
`category="refused", code="path"`. `path` belongs to the `integrity` category,
not `refused`, so `ContractRefusal` rejects the raising site itself with an
`AssertionError`. The focused probe was:

```text
PYTHONPATH=v12/python/src:v12/python python3 -c \
  'from tools.single_worker import _refuse; _refuse("partial input", category="refused", code="path")'

AssertionError: this build raised a refusal whose code is 'path', which is not
a refused code; the pairing is closed
```

Use a valid closed pair and add a regression through `_input` rather than the
private helper, so a process that finds non-empty incomplete input material
gets the intended typed refusal and the canonical exceptional ending described
above.
