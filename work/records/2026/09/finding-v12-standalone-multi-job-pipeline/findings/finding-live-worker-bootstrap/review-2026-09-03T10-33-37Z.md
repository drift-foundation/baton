## [P1] A real adapter fault still aborts the whole sweep

`job_manager/manager.py:186-195` catches only `ContractRefusal` and claims that
all launch failures are contained per stage. The public Worker Manager start
operation deliberately re-raises an ordinary adapter/transport exception
after it settles and journals the failed start. Such a failure therefore
escapes `_launch`, prevents later stages in the sorted sweep from being
launched, and terminates `serve` even though the canonical failure record now
exists. The new containment test at `test_launch.py:208-218` drives only a
typed refusal, so it does not exercise the production fault path.

Contain only a fault that the Worker Manager can prove it durably recorded;
do not turn arbitrary programming faults into success or transient refusal.
Add the real/fake fault regression with the failing stage sorted before an
independent stage, prove the first becomes `exceptional`, prove the second is
still launched/observed in that sweep, and prove the serving loop continues.

## [P1] A durable pre-start refusal is reported once but remains `claimed`

The same branch maps any durable `ContractRefusal` to a `refused`
`stage.launch` report without writing or observing a durable ending. Only a
failure recorded by `request_runtime_start` is visible through
`attempt_start_failure_of`; durable refusals from attempt activation,
workspace/input adoption, credential materialization, launch delivery, or a
pre-start Worker Manager check do not necessarily have that record. On the
next projection the stage is still `claimed`, so the manager repeats the same
settled refusal forever. The new test asserts only the one sweep report and
does not assert exceptional status or non-repetition.

The completed composition needs one canonical rule for every durable launch
ending. Prove that a durable preparation/start refusal projects
`exceptional` and is not retried, while an ordinary not-yet-ready refusal
remains level-triggered. This must not become an unowned shadow receipt in the
Job store.

## [P1] The new journal projection does not prove it read a failed-start row

`worker_manager/attempts.py:263-273` treats any committed non-null result
under the derived identity as a failed-start record. It neither verifies
`record["kind"] == "runtime.start-failed"` nor replays through the journal
with that kind, and it does not bind the returned record to the attempt,
assignment and start operation it is projecting. The existing failed-start
consumer in `worker_manager/intake.py:2129-2155` documents and implements the
required opposite rule: an identity is not a warrant, the kind must agree,
and the journal reader owns the committed answer before its members are
bound. The only new direct tests at `test_launch.py:266-278` cover absence;
none drives a genuine committed failure or a wrong-kind/mismatched record.

Make the public read follow the existing owner-record discipline and add
positive replay plus wrong-kind and mismatched-record regressions. A malformed
or colliding row must refuse; it must not falsely make a Job exceptional.

## [P1] Factory construction is still outside the release boundary

`tools/job_manager.py:210` calls `_operations_from` before entering the
`try/finally` at lines 211-231. If the production factory opens the Authority
and then fails while opening or validating another owned resource, no
operations object is returned and `_release` can never run. The nearby comment
and `PROGRESS.md` claim construction-failure cleanup that the code does not
provide. Either give factory construction a real context/cleanup protocol or
make the production factory atomically clean its partial acquisitions itself;
in either case test the failure after at least one acquired handle and prove
all earlier handles close without replacing the original failure.
