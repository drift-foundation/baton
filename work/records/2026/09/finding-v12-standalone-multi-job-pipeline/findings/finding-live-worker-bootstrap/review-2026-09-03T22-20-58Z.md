## [P1] The deployment removes mount sources from a live failed-start runtime

`tools/single_worker.py:699-716` computes `fresh` before
`request_runtime_start` and passes that stale value to `_unwound` for every
typed failure. A start can reach the engine, create a container, and then
report failure. `OciAdapter._undelivered` asks the engine, sees that live
runtime, and correctly leaves both delivery roots `unresolved`; the outer
handler nevertheless still has `fresh == True`, tears down the credential at
lines 756-759, and discards the launch root immediately afterwards.

The new `TheFailedStartEndingCommitsWithItsNaming` fixture reaches exactly
this production path and correctly asserts an exceptional stage, one named
runtime, and one start, but it does not inspect the paths mounted by that live
runtime. A focused extension of the fixture observed:

```text
stage_state: exceptional
engine_runtime_id: runtime-single-1
launch_root_exists: false
credential_root_exists: false
credential_lifecycle: null
credential_registered: false
```

The engine's recorded mount vector still names both deleted paths. This is not
later-pass hardening: it directly contradicts this dossier's pinned rule at
`single_worker.py:729-734` that neither delivery is removed after a start was
requested because a container may hold the mount. It also leaves the failed
worker live over storage the manager has already declared gone.

Carry the adapter owner's delivery settlement across the boundary as a
structured value or equivalent exact capability; refusal prose is not an API.
The deployment should unwind only where no runtime owner reached or decided
the boundary. Add regressions proving all three sides together:

- a created-then-denied runtime keeps both unresolved mount roots until its
  authorized failed-start cleanup;
- a refusal before the adapter/start boundary cleans both local deliveries;
  and
- the colliding-bearer path still releases its local delivery before durable
  state is reread, so it remains exceptional and non-retried.
