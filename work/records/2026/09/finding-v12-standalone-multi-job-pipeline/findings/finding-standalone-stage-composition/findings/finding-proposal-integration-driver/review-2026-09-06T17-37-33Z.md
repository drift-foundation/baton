## [P0] Admission replay hides the materialized terminal state

`driver.admit_accepted` takes `entry` from `admit_candidate`
(`driver.py:419`) and passes it to `_terminal` (`driver.py:432-434`). An exact
`admit_candidate` retry reaches `enqueue`, whose journal contract deliberately
returns the first enqueue result. The coordinator's own regression states that
exact replays return the first outcome (`test_coordinator.py:1892`); that
outcome has state `queued`, regardless of the entry's later materialized
state.

I measured the exact distinction after one complete integration: replaying
`enqueue` returned state `queued`, while `entries_of` returned state
`integrated` for the same `entry-1` (`queued integrated`). Thus a real restart
never enters the new `entry["state"] == "integrated"` branch. With an already
released lease it refuses because the stale entry looks queued; with the
settled/live lease this review is about, it follows the ordinary live-lease
path instead of draining the committed release tail.

The new regression hides the defect at `test_driver.py:498-499` by mocking
`admit_candidate` to return `copy.deepcopy(entry)`, where `entry` came from
`entries_of` and is already integrated. That proves the helper branch but not
the production restart route.

Refresh the exact current entry through the coordinator's semantic read after
admission replay, require exactly one matching `entry_id`, and cross-bind its
eligibility to the newly resolved accepted account before `_terminal`. Exercise
the live-tail and released terminal cases without mocking `admit_candidate` or
the enqueue replay. This fits the existing driver/test paths.
