## Findings

### P1 — restart does not revalidate principals for live prior generations

The accepted ruling requires trusted deployment to resolve persisted
worker/principal associations again on restart and fail closed on mismatch.
`activate_pool` revalidates only the ONE generation whose pool document it is
given (`scheduler.py:158-200`). `_required_workers` then adds workers from live
prior generations (`scheduler.py:137-155`), but
`PooledManagerOperations.__init__` accepts no resolved-principal evidence and
checks only each operation's participant (`scheduler.py:462-484`).

A claimed allocation from an old generation can consequently be launched,
dispatched, concluded or observed after its endpoint maps to another principal;
the later claim-answer comparison cannot protect a claim that was already
taken before restart. Require attachment-time Authority resolution for every
active worker and every live prior-generation worker, and refuse before any
stage operation on mismatch. Add a restart test with a live old-generation
allocation and a changed resolution.

### P1 — missing allocation silently selects the first worker

`_worker` returns `_first()` when no allocation exists
(`scheduler.py:497-502`). `launch`, `dispatch`, `conclude`, `observe` and
`refresh_runtime` all use that fallback (`scheduler.py:595-608`), although
`claim` correctly refuses the same condition. This erases reserve-before-offer
and participant/generation binding at the exact stage-specific seam.

The 3 -> 4 migration deliberately creates empty scheduler relations, so an
already admitted or claimed schema-3 stage is the important recovery case, not
an academic caller error. Every stage-specific operation must require its
exact allocation. The correction must also pin how a migrated in-flight stage
is stopped or recovered; it must never run through whichever worker sorts
first. The retained reproduction shows an unallocated attempt launching
successfully through that worker.

### P1 — a broad durable admission refusal releases capacity unsafely

`PooledManagerOperations.admit` releases the allocation for ANY durable
`ContractRefusal` (`scheduler.py:559-569`). Durability says that a refusal is a
recorded outcome; it does not prove that no offer or assignment exists.
`ManagerOperations.admit` commits `issue_offer` before invoking the injected
bearer-delivery capability, so a durable delivery refusal can occur after the
canonical offer exists. Releasing then lets unrelated work reserve the same
logical worker/principal while that offer may still be accepted.

The accepted settlement table permits release only after canonical offer
settlement proves no assignment exists, or canonical cleanup is complete or
retained. An uncertain post-reservation admission failure must retain or
quarantine capacity until that evidence is observed. The retained reproduction
shows a durable admission refusal releasing a reservation while its stage
episode has no ending.

### P1 — the 3 -> 4 migration does not validate the prior schema

The recorded schema ruling preserves complete-prior-schema validation. The
implementation validates meta/version and Authority binding, runs the migration,
then checks only that the final TABLE NAMES are present (`store.py:177-212` and
`store.py:446-459`). It does not prove schema-3 indexes, columns, constraints or
object closure before changing the version.

The retained reproduction removes `episodes_one_live_per_stage`, stamps the
test store as schema 3, and opens it successfully as schema 4; the critical
one-live-episode index remains absent. Validate the complete schema-3 object
set under the migration lock and roll back without changing the store when it
differs. Add missing-index, changed-column/constraint and concurrent migration
regressions.

### P2 — a historical pool variant cannot be activated again

Pool activation identifies both a configuration definition and the activation
act by the pool-document digest. `pool_generations.digest` is unique, and
`activate_pool` returns any historical row with that digest
(`scheduler.py:171-224`); `active_generation` and reservation nevertheless
select the highest generation. After activating primary generation 1 and
fallback generation 2, activating the primary document reports generation 1
while generation 2 stays active.

This contradicts the ruling that an explicit variant activation creates a new
generation for new work. Preserve exact retry of one activation while allowing
a later deliberate return to the same immutable configuration to create and
activate a fresh generation. Add primary -> fallback -> primary coverage and
restart coverage of the active selection.

### P2 — settled allocation replays bypass operand collision checks

`_move` returns immediately when an allocation is already in the requested
state or already released (`scheduler.py:382-391`), before constructing and
replaying the journal signature. Calling `release` first with one reason and
then with another therefore returns the first row instead of refusing the
changed operands, even though `reason` is explicitly part of the operation
signature. The retained reproduction demonstrates this mismatch.

Route exact replays through `JobStore.replay`; changed state/reason operands
under the same derived operation identity must refuse. Cover same-operand
replay, changed-reason replay, recovery-to-release and release-before-recovery
orderings.

### P1 acceptance gap — the four-principal claim boundary is not exercised

`test_two_implementation_and_two_review_capacities_are_live_together` creates
four Job-store reservations only. The alias case also stops at `reserve`.
`fixtures.FakeSession.claim_slots` was added to mimic Authority's one-live-claim
per principal rule, but the candidate has NO caller constructing a session with
that map. Thus the accepted positive proof of four simultaneous effective
claims, the negative Authority-level alias collapse, returned-principal
binding, and concurrent run path are not exercised by the 23 scheduler cases.

Drive two implementation and two review offers through acceptance and claim
using four participants, four principals and one shared claim-slot map, then
show the alias mapping refuses at the Authority-like boundary. Include launch
or the narrowest real composed operation that proves each claimed stage routes
through its reserved generation/worker, plus failure isolation and slot
settlement. W71879 still owns the real-container demonstration; that does not
make W71877's contracted fake boundary optional.
