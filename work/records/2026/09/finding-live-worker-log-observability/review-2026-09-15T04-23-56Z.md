## P1 — per-attempt admission still permits a replacement helper

Naming the helper and its admissions separately fixes terminology, but section2
still does not implement the selected no-replacement rule across recomposition.
Its retained key remains `(store path, attempt_id)`.

**Reasoned sequence:** composition C1 starts helper H1 over store S and admits
attempt A. H1 blocks in I/O; C1 close times out and keeps `(S,A)` occupied.
Replacement C2 over S starts helper H2 and admits B. `(S,B)` is free, so H2 is
allowed while H1 remains unresolved. Repeat with fresh attempt ids and more
helpers can accumulate. Keeping the64-attempt registration cap limits entries;
it does not make C2 start no helper, which is the retained acceptance rule.
The new same-attempt-only test would miss exactly this sequence. This is an
unimplemented-design counterexample, not an executed product defect.

**Exact correction to section2 and acceptance3:** acquire one helper-ownership
slot keyed by the held deployment/store identity **before starting the helper**.
Use a single process-wide registry shared by both factories. Conservative
`held control-store identity -> helper owner` is the already-proposed in-scope
choice; no attempt_id belongs in this helper key. The atomic acquisition never
waits and the registry lock is never held across I/O. If occupied, the new
composition starts no ingestion helper and suppresses all activity ingestion.
Keep the slot until positive helper termination, including timeout/unwind.
An acquisition followed by failure before any worker starts may release it.
Keep the selected64-entry bound as a registry bound distinct from file tracking.

Attempt_id and its root/identity fields remain in requests; separate per-attempt
admissions may exist if needed, but cannot substitute for helper ownership.
Planned acceptance must use distinct compositions over S and **different**
attempt ids A/B, asserting H2 never starts while H1 is unresolved. Once H1 is
positively gone, a subsequent composition may acquire and start one helper.
This is the same concrete correction requested by review174947, not a new
cross-process lock, scheduler feature or additional product boundary.
