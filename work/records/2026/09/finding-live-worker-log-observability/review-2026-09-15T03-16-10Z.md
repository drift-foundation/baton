## 1. [P1] The proposed experiment cannot select a real provider source

**Confirmed from retained evidence:** this dossier's FINDING, “Observed —
2026-09-01” and “Reviewer revalidation — 2026-09-01”, records that during
W52821 native JSONL showed ongoing messages/tool activity while container stdout
did not provide useful incremental output. The original independent review
retains that distinction. Canonical W52821 detail resolves its permanent record
to `baton:work/records/2026/08/finding-per-user-concurrent-credential-delivery`;
a targeted Markdown search there supplied no additional native-JSONL evidence.
The evidence actually reused here is the observation retained in THIS dossier;
no private transcript was read and no stronger measurement is invented.

Design section 2's “Nobody has made that observation in this tree” is too broad
and must be corrected. A scripted provider emits according to the script; its
arrival times cannot determine how the real Claude CLI behaves. Multiple
4096-byte reads can also all come from one final JSON payload. Neither selects
incremental stdout as a live source or proves growth before completion.

**Proposed correction:** take private native-JSONL metadata as the source to
design against, reusing the retained observation. State separately what is
still **Open** for the current supported profile: exactly how the adapter
identifies its own session file before completion. `_prepared_home` establishes
a private `.claude` directory, not a session-file identity. Specify bounded
discovery, directory/file type and link checks, binding to this invocation,
baseline handling, and replacement/truncation/rotation behavior. Do not count
credential files, arbitrary home growth or restored historical bytes. A missing
or ambiguous source leaves activity unknown; it is not a provider failure.

Deterministic fixtures should drive the real adapter's selected observation
boundary and prove propagation while completion is held back. Label that as
simulated-provider coverage. Only if retained evidence and source cannot settle
a necessary current-profile fact should a later scope proposal state that exact
provider-specific question and smallest finite qualification. This review does
not authorize such execution or require a fresh live run as a blanket gate.

## 2. [P1] Rewriting state-work.json can destroy terminal causality

**Confirmed code:** `baton_worker.serve_exchange` publishes dispatched, runs
the operation synchronously, then publishes answered (or `_faulted` publishes
faulted) before terminal publication. It has no periodic state writer today.
`_publish` uses separate staging files and atomic replacement, including file
and directory fsync. Atomic replacement does not order competing publishers.

**Inferred counterexample to section 4:** periodic writer captures dispatched,
stalls before replace; main worker publishes answered and terminal; periodic
writer resumes and replaces answered with dispatched. `exchange._caused`
rejects that history and `observation` drops the terminal as unreadable. The
same issue affects faulted endings. Existing test bodies
`test_an_answered_operation_still_dispatched_refuses` and
`test_a_faulted_terminal_whose_stop_says_nothing_refuses` in
`v12/python/tests/manager/test_exchange.py` already demand those refusals.
They were read, not executed in this review.

**Proposed correction:** keep activity out of lifecycle state documents. Use
one fixed count-only diagnostic document, with its own closed schema/version,
in the existing exchange event capability; keep receipt/state/terminal byte
contracts unchanged. Pin the document name, exact member set, maximum size,
integer bound and non-bool validation, and event-namespace allowance. Carry
the existing session, attempt, sequence, command digest, work operation and
operation-id correlation; validate them against manager-owned delivery rather
than merely accepting self-consistent worker labels. Activity conveys neither
an answer nor permission to extend deadlines or settle an attempt.

This is a concrete recommended transport direction, not an approved new wire
contract. The revision must also show that delayed diagnostic publication
cannot touch lifecycle files or a later attempt, and that missing/malformed
activity remains unknown/last-observed without concealing a valid terminal.

## 3. [P1] Adding STATE_MEMBERS does not preserve state/1 compatibility

**Confirmed code:** exchange `STATE_SCHEMA` is
`baton.worker-exchange.state/1`. `_decoded` rejects missing and extra members
and allows bounded text, lists of text or null; it rejects an integer even if
the field is added to `STATE_MEMBERS`. `_event` checks exact schema equality.
`observation` currently projects only operation/state from a state document.

Thus section 3's “one bounded member” is a wire/type change, not an existing
compatible periodic seam. Old readers reject new state documents; new readers
requiring the field reject retained old state documents after manager restart.
The design neither resolves describe-versus-work shapes nor exposes the count
through a typed manager read surface.

**Proposed correction:** the separate optional diagnostic document in finding
2 lets old lifecycle documents retain their meaning and absent activity stay
unknown. Define old-manager/new-worker and new-manager/old-worker behavior,
including foreign-entry handling and namespace limits; do not claim invisible
backward compatibility merely because a new file fits an existing mount.
Validate count types in that document's own parser, without relaxing all
existing event parsers. Preserve the existing causal and hostile-input tests.

## 4. [P1] The consumer and bounded teardown are still unspecified

**Confirmed code:** `dogfood_operator._Channel` drives a framed `docker exec`
stream. Its `_activity_observer` synchronously opens/writes/closes ControlStore.
Ordinary file-exchange observation is instead
`single_worker.observed_exchange`, supplied as `observe_exchange` to the Job
composition. The proposed path list omits `v12/python/tools/single_worker.py`.
Removing the old channel callback is needed, but does not wire activity into
that serving path. A pure status read must not gain writes as a side effect.

**Inferred risk:** calling the existing store writer from the manager's sweep
merely moves its blocking latency onto the serving/ending path. Putting a
worker writer on another thread proves only that the pipe drain does not call
it; it does not prove bounded completion/teardown. Joining a stalled fsync
writer can hang, abandoning it without fencing can allow late writes, and
spawning replacements can accumulate blocked publishers and staging files.

**Required revision:** name the serving-loop ingestion hook separately from
the read-only projection, and the owner of each publisher's start, bounded
single-slot/coalescing handoff, cadence, stop, finite shutdown and recovery.
No new publisher per tick and no unbounded queue or per-attempt thread leak.
Publishers must not gate mandatory reads, provider completion or runtime
cleanup; an optional final count may be lost and reported as last observed.
Specify bounded resource use for stale staging files as well as memory.
Explain how a delayed old publication is bound to the old attempt and cannot
freshen a replacement. No daemon-thread assertion substitutes for that proof.
