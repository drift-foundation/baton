## P1 — modification time cannot reconstruct the pre-launch byte baseline

The new section1 replaces a synchronous baseline with a scan after launch and
classifies an entire file as new when its mtime is after launch. That loses the
very baseline the count must exclude. **Reasoned counterexample:** a reused or
restored file contains1000 bytes at launch; the provider appends10 bytes before
the first tick. The scan sees1010 bytes and a new mtime, so this rule reports
1010 bytes of invocation activity instead of10. Neither inode identity nor a
launch timestamp reveals the old length. This is ordinary append behavior,
not a clock-skew edge case. It contradicts the retained baseline semantics.

Remove the timestamp reconstruction. The previously proposed admission rule
still works: use a positively completed pre-launch baseline without making the
provider wait for it; otherwise disable optional activity for that operation.
A simpler valid positive path is a construction-proven fresh, unrestored home
with no pre-existing matching native files, whose baseline is known empty
without scanning. In current source _scratch creates a new directory unless
_home is injected, while _prepared_home uses exist_ok=True and does not by itself
prove emptiness. Carry actual freshness provenance from creation, and identify
any pre-provider writers/restoration before relying on it; injected/reused/
restored or otherwise unproved homes stay unknown unless a real baseline is
already available. Do not silently treat them as empty or reconstruct from mtime.

Choose the concrete admission variant and describe its normal positive case.
Acquiring a directory identity with a new stat is also filesystem work; use
already-held construction facts on the launch path, not an extra diagnostic
lookup described as free. The bounded scan itself stays off that path. Add the
existing-file append-before-first-tick case to planned acceptance, alongside
the already-selected blocked-scan/non-delayed-provider case. No runtime probe
was run for this counterexample and no new live experiment is needed.

## P1 — registry and root binding must match one worker serving many attempts

Sections2 and3 currently specify different ownership units: section2 constructs
one ingestion worker per deployment, while section3 admits a worker per
`(control store path, attempt_id)`. A deployment is composed before its future
attempt ids are known, and it serves several attempts. An unresolved helper
for attempt A does not occupy the proposed slot for B, so a new composition
can create another helper for B despite the retained no-replacement rule.
The64-entry registry caps that growth but does not preserve one helper per
deployment or make the second composition ingest nothing as acceptance3 says.

Use a stable deployment/store ownership key for the helper admission slot;
keep attempt identity in individual requests. Conservative one-helper-per-held-
control-store identity suppression is one bounded implementation direction
within selected scope. Specify one shared registry owner used by both factories,
atomic nonblocking acquisition, no registry lock held during I/O, and release
only after positive helper termination. The selected64-slot registry bound can
remain; distinguish it from the unrelated64-file accounting bound. Test distinct
compositions with different attempt ids as well as the same id. True process
exit and same-process recomposition are different lifetimes; no cross-process
exclusion guarantee is inferred from a process-local registry.

The same unit mismatch affects section4: one root handed to that worker once at
deployment construction cannot locate each future attempt's delivery. My prior
review required a root to stay manager-local, **not** that a trusted root be
absent from an in-process queue. Keep one worker, and associate each request
with its own already-composed root capability plus the six expected identity
fields, either directly or via a bounded registration map populated when the
actual delivery is created. The document never supplies that root. Reuse held
delivery operands and avoid diagnostic adoption; suppress when not available.
Revise acceptance4 from "enqueue carries no root" to "no root from the wire
and no synchronous diagnostic adoption". Do not add a worker per attempt or
place a host path in activity.json to resolve this composition contradiction.

Pin partial-construction unwind with the selected closer map: register cleanup
before later construction can fail; on stop timeout keep admission held and do
not close a handle still in use. The ingestion thread closes its own SQLite
handle when it actually exits. The serving closer requests stop and waits only
its bound; it does not close that thread-owned handle cross-thread after timeout.
These specify the existing independent-handle/lifetime rule, not extra scope.
