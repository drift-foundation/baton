## R2 — new count conversion can crash an accepted snapshot (P2)

v12/python/tools/job_viewer.py:_activity accepts every positive integer, while
_bytes_seen converts it through floating-point division. A5659-byte otherwise
ordinary status JSON with `bytes_observed=10**400` passes read_snapshot and then
render_list raises **OverflowError**. The integer itself is valid JSON well
within the4MiB input bound. The prior constant-UNKNOWN rendering handles this
same snapshot. This is an introduced consumer failure, not an observed producer
emission: the trusted producer's own count ceiling excludes such a value.

JobViewer.refresh therefore installs the malformed new snapshot, and rendering
runs outside its last-good-snapshot handler. main catches ViewerRefusal only,
so the ordinary command can exit with an uncaught exception instead of treating
invalid activity as unknown. The new owner slice explicitly requires invalid
counts to remain unknown, and the existing viewer already validates shapes it
consumes to avoid this failure pattern.

Bound accepted activity integers before conversion using the selected count
domain, or otherwise guarantee safe bounded formatting while rejecting invalid
counts as unknown. No additional backend read or producer edit is needed. Add
the huge-integer case through JSON read_snapshot and ordinary render/refresh,
alongside bool/negative/zero/type cases and the largest valid producer count.
Keep snapshot staleness and historical receipt semantics unchanged.
