## [P1] A synchronous sweep step is still blocking

Section5 calls a file read and observe_activity synchronously inside the sweep
and asserts a slow store delays that step alone. Current
`job_manager/manager.py:sweep` executes its passes serially; `_refresh` iterates
live stages serially before projection, adoption, delegation, launch and
conversation. An added synchronous hook blocks whatever passes follow it and
the next tick. It can therefore delay another stage and required cleanup even
though it is no longer on the stderr drain.

ControlStore uses `_BUSY_TIMEOUT_MS = 5000`. Moving that write into a sweep
does not make it nonblocking; neither a read nor filesystem I/O is made bounded
by calling it a step. The packet still identifies no exact hook/owner for its
new ingestion capability beyond the containing file.

**Required correction:** make the sweep's diagnostic contribution a bounded
nonblocking handoff only. Name the actual hook and the resource owning off-loop
file observation/store publication, its independent store handle, finite
admission and shutdown, and no-replacement policy while an earlier publisher
remains live. Use a bounded latest-count slot per admitted observation identity
with an explicit total resource cap; drop optional updates when capacity is
unavailable. An alternative is acceptable if it proves the same nonblocking
serving/cleanup property; the current synchronous call does not. Enumerate any
required composition path beyond the five proposed paths before implementation.

## [P1] Identity correlation neither stops a writer nor expires its authority

Section4 abandons a stalled writer after an unnamed finite wait. Section2 only
compares immutable identity fields. After the work operation ends, its attempt,
session, sequence, command digest and operation id still match the retained
delivery. There is no terminal/eligibility predicate or publication-generation
revocation in the proposed consumer. A late write can therefore still be read
for that same finished operation. `observe_activity` itself accepts a greater
total for an existing attempt without checking a live execution state.

Discarding a foreign identity protects a successor's counter; it does not prove
the writer stopped, prevent retained-root writes, release descriptors or bound
the number of abandoned writers. Starting one publisher per operation after
abandoning its predecessor can overlap writers. Two writers then share
`.activity.json.tmp`: they can collide, or one can rename staging bytes the
other still writes. A single-slot queue does not make those two writers one.
Wholesale root teardown is not a substitute for proving the writer excluded,
and a directory deletion does not close its open descriptors.

**Required correction:** select one publisher lifetime for the entire delivery
(prefer work-only activity for the current provider), not a new publisher while
the prior one is unresolved. Specify exact finite stop/grace bounds and what
positively proves exclusion. A supervised helper process is one possible
implementation direction when potentially blocking I/O must be off-thread;
ordinary runtime exclusion must still report uncertainty honestly if it cannot
end. Suppress further diagnostics instead of accumulating replacements. Do not
claim that arbitrary blocked filesystem I/O can always be cancelled by a flag.

Specify when the manager stops accepting an operation's diagnostics and how
that decision is enforced against a delayed observation/store write, including
restart. If final delayed counts are intentionally allowed for the same attempt,
say so and preserve receipt-time semantics; do not claim every dead-turn write
is discarded by identity equality. Keep exact binding as the cross-attempt
defense, separate from lifetime and stale-publication rules.

The fixed temporary name also needs explicit exclusive/no-follow creation and
stale-temp recovery after the previous publisher is proved gone. Existing
`baton_worker._publish` already writes a unique temporary file then replaces the
published name; it has no remove-then-rename gap to correct. The selected atomic
replacement pattern stands, but neither a stale fixed-name wedge nor a staging
symlink/overlapping-writer workaround should be introduced by the revision.

## [P2] Correct the source derivation and make cumulative counts coherent

**Confirmed source:** ClaudeAgent.__init__ assigns `_home` only from its `home`
test seam. `_scratch` returns that injected path if present; otherwise it creates
and returns a new directory without assigning `_home`. The packet's claim that
production scratch is cached across describe/work is false. `baton_worker.handle`
answers describe without calling ClaudeAgent or starting a provider. A default
fresh provider home and an injected/restored/reused home must not be conflated.
`_prepared_home` uses exist_ok and does not prove a reused home contains exactly
one entry. The fresh production directory is a useful invocation boundary;
the broader claim that all such directories have one exclusive writer is not
established by0700 or that helper alone.

**Proposed corrected source rule:** bind the scanner to the exact provider HOME
created for this invocation; take its baseline after preparation/restoration and
immediately before provider launch. Observe only beneath that directory, with
no-follow checks for every traversed component, regular-file metadata and fixed
depth/entry/time bounds. A bounded *.jsonl metadata scan is a proposed
layout-independent observation rule supported by the retained native-JSONL
experience, not proof from `_prepared_home` that every matching file is a native
session. Label this distinction and declare the supported provider boundary.
No fresh live-provider run is a blanket condition of this review.

The formula `sum(max(0, current-baseline))` is not monotonic as specified. For
baseline0, observations100 then80 pass the stated “shrinks below baseline”
guard yet report100 then80. With baseline50, observations100 then80 report50
then30. Renaming/deleting a previously counted file also needs an explicit rule.
The count owner refuses a decrease, so it cannot repair this source account.

Track each observed identity and its last size, not only its initial baseline.
Freeze further observation as unknown/last-observed on any decrease, disappearance
or identity replacement (including device and inode), rather than silently
clamping/restarting. Keep memory/scanning bounded and define overflow behavior.
Reconcile per-operation counts with the attempt-wide cumulative API: select
work-only activity now, or define durable cumulative composition across any
multiple supported producer operations. Do not reset a positive attempt counter
when starting another operation. Depth, entry cap and finite stop limits remain
unnamed in the packet and should be numeric in the revised design.

## Compatibility can be specified now from code

`exchange.MAX_EVENT_ENTRIES` is64. `_foreign` reports unknown names without
opening them; it does not silently ignore them. Four lifecycle documents plus
activity.json plus one activity staging entry consume six entries before any
concurrent lifecycle staging or historical leftovers. Exceeding64 makes the
whole observation unreadable. Preserve a bounded staging/leftover account and
state the margin; no engine experiment is necessary to read these constants.
Old readers may expose the activity/temp filenames as foreign diagnostics while
retaining lifecycle semantics. New readers of old workers see absence. Malformed
optional activity must remain isolated from receipt/state/terminal validation.
