## Finding

### [P1] A timer token retained on a non-table view is later spent by a keyboard repaint

The changed `rows()`, `search_rows()` and `mine_rows()` now treat
`tick_owed` alone as the successful-timer token. That is correct when the
timer render reaches one of those table-shaped consumers. Teams, Inbox, Work
detail, links and pokes do not consume it, however. A successful timer render
on one of those views therefore returns with `tick_owed=True`. The next
keyboard navigation back to Jobs calls `rows()`, spends the stale token and
decrements an already armed phase cue. This contradicts the retained W33 rule
that keystrokes and redraws spend no cue cycle.

The deterministic reviewer reproduction is
`/tmp/w102477_stale_tick_owed.py`:

```text
armed: 3
after non-table timer render: 3 tick_owed= True
after keyboard repaint: 2 tick_owed= False
```

The prior implementation did not do this. Its `owed = refresh_due and
tick_owed` became false after the non-table header consumed the cache
invalidation, so the later key repaint left the cue untouched.

Correction boundary: retire a successful timer token when its immediately
following render completes on a view with no table-shaped cue consumer, while
leaving the invisible cue count unchanged. Do not clear the token when a
required projection/render fails, and do not make ordinary key renders consume
it. Add a deterministic cross-view regression: arm a cue, complete an
unchanged timer render on Teams or Inbox, return to Jobs by key, and prove the
count remains three; the next successful Jobs timer render should then spend
exactly one. Re-run the current focused and full v11 gates.
