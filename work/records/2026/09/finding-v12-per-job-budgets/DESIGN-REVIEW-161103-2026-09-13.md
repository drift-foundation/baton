# Independent design review — managed, relocatable integration

baton.claude under claim 161103, 2026-09-13. Reviewing
`MANAGED-INTEGRATION-DESIGN-2026-09-13.md` (baton.codex, claim 161035) against
the current tree at `HEAD f3fc9e12cc89bebf9524cd173103df7af67d5212`.

**Read-only.** No source was edited, no test was run, and no implementation is
started. Every claim below is checked against the code named beside it; where I
could not check something I say so rather than agreeing with it.

## What I accept

**The boundary statement.** Running the coordinator in a container does not
satisfy "integration execution runs in managed Docker", and host paths, device
and inode pairs and engine IDs are local capabilities rather than content
identity. Both are correct and both are load-bearing for the rest.

**The separation of untrusted worker evidence from owner adoption.** A process
exit, a provider report, a frozen artifact or a prepared tree granting nothing is
the same rule this Work's accepted host-failure contract already runs on.

**The refusal that copying a parent assignment cannot activate a child.**
Verified: `attempts.activate_assignment` reads the attempt's own committed claim
and refuses when it has none — *"a live assignment elsewhere in the authority is
not evidence that this attempt's offer claimed it"* — and then compares the
claimed assignment against the expected one member by member.

**The per-boundary defaults.** Verified in
`job_manager/execution_limits.py`: `host_verification` 300 and
`integration_verification` 1800, both mapped onto
`verification_command_seconds`, so one explicit Job override does reach both and
relocation must not silently change an omitted setting.

**Preserving `_current`'s refusal.** Verified: a reconciled result reaching the
direct model path returns an **integrity** refusal that blocks the target and
keeps the lease, deliberately rather than terminally refusing. The design's
"do not feed a derived proposal through the direct-source validator and bypass
its refusal" is right, and I would strengthen it: the derived case should be a
*separate admitted case*, not a relaxation of that comparison.

## P1 — "charged to the parent allocation" is not representable today

This is the proposal's central orchestration claim and the one gate I cannot
affirm as written.

`scheduler.reserve` writes one `stage_allocations` row keyed by
`assignment_id` — the stage attempt's own id — and `allocation_of` reads by that
key. **There is no column, relation or query in which one attempt draws on
another attempt's allocation.** "Subordinate execution charged to the parent's
already-reserved integration capacity" therefore has no representation in the
owner that accounts for capacity; today it can only be a sentence in a document.

The two shapes actually available both break a stated requirement:

- **Child takes its own allocation.** `reserve` computes `live` as every
  allocation in `('reserved', 'recovery-required')` and excludes both occupied
  `worker_id`s and occupied `canonical_principal`s. With one configured
  integrator participant the child cannot reserve while the parent's allocation
  is live; it gets *"every effective worker/principal capacity is reserved or
  recovery-required"*. This Work has already measured that exact sentence from
  the other side (`PROGRESS` claim 160341, the third Job deferred behind a
  blocked result), so it is not a hypothetical.
- **Child takes no allocation** — the `JudgmentExecution` shape, whose own
  docstring says it is "not a Job stage or pool allocation". Then it is invisible
  to that accounting, which is exactly the hidden integration capacity the
  proposal forbids.

Also concrete: `scheduler._lane` maps **every** non-review kind to the
`implementation` lane, and `reserve` selects from `pool_workers` filtered by
lane, profile name, profile digest and `eligible_kinds`. A new preparation kind
is therefore not free — it needs pool configuration and it contends in the
implementation lane with producers, not in some separate integration lane.

**Required before implementation:** name which of three the design chooses, and
carry its cost.

1. An explicit scheduler relation — the child allocation records its parent, the
   occupancy query excludes a child that names a live parent from counting
   twice, and the release rule releases the parent only when every execution
   naming it is proved excluded. This is a `stage_allocations`/`scheduler.py`
   change, i.e. one of the paths the proposal lists as *not silently included*;
   it needs its own reviewed scope.
2. Preparation on the parent's own attempt, which contradicts "the parent stage
   attempt is reserved for apply" and must be withdrawn if chosen.
3. An unaccounted child, stated as such, with the capacity consequence written
   down rather than described as "charged".

I recommend (1) and I do not think (3) is acceptable given the proposal's own
rule about hidden capacity.

## P1 — portable custody: the node-local members are named, and they are load-bearing

The proposal says "the local-path fields in existing records remain historical".
They are not only historical today; they are **read and used**:

- `reconciliation.result_of(...)["workspace"]["path"]` is what
  `StageDeployment.judge_result` clones the judgment snapshot from;
- the target record's `target_source["path"]` and `target_reference` are what a
  reader runs `rev-parse` against — this Work's own post-import regression does
  exactly that;
- `integration/oci_delivery` proves no-overlap, no-follow and writable-target by
  device and inode on the node it runs on.

So a collected phase report adopted on another node cannot carry those members
forward at all. **The versioned portable record is a prerequisite of slice one,
not a later refinement**, and its rule should be stated positively: a phase
report carries content identities only — commits, trees, path-set and content
digests, harness identity and digest, the applied bound, and the closed
observation or tagged no-status failure — and every capability (repository root,
reference, mount) is resolved by the node that holds it. Existing rows stay
readable as history; nothing is reinterpreted.

## P2 — the target-owner publication boundary is affirmable, and its adapter gap is exact

I affirm the boundary the proposal asks about: compare-and-swap of the reference
and receipt settlement are bookkeeping over already-authorized content, not
execution of candidate code, and keeping them as trusted target/integration-owner
acts after positive stop does not contradict the owner's "integration execution"
ruling.

The gap is in the signature, and it is exact. The finalization owner in
`integration/execution.py` takes `target_root`, `reference` and `source` — local
filesystem paths — and drives Git through its injected runner; it re-reads the
live grant immediately before the first byte moves and refuses on drift through
Git's own compare-and-swap against the **admitted** old revision rather than
whatever the reference says now. That design is right and should not be touched.
But it means the act is only performable **where those paths resolve**. For a
coordinator on A and a target owner on B, slice one needs a target-owner
entrypoint that accepts *(canonical target, entry, lease, fence, accepted old
revision, authorized candidate)* and resolves `target_root`/`source` locally on
B. That entrypoint does not exist; it is the "exact adapter gap" the proposal
asked to have identified rather than invented. Until it exists, a correct
implementation is single-node and must say so.

## P2 — what the first slice changes in this Work's own test module

The proposal schedules "bounded updates" to
`v12/python/tests/tools/test_execution_limits.py` and asks for existing
expectation changes to be enumerated by method. Mine, precisely — every one of
these asserts a **coordinator-local** subprocess and cannot survive the managed
path unchanged:

- `_watching` itself, which intercepts `subprocess.run` inside the integration
  root and is the discriminator for every host case below;
- `test_the_composed_causal_owner_runs_under_the_jobs_ceiling`,
  `test_a_causal_overrun_is_retained_and_blocks_the_result`,
  `test_the_post_import_verification_uses_the_jobs_ceiling`,
  `test_a_post_import_overrun_runs_once_and_defers`,
  `test_a_post_import_start_failure_is_the_same_shape`;
- the four phase cases `test_a_base_observation_that_never_finishes` /
  `_never_starts` and `test_an_isolated_observation_*`;
- `test_the_retention_key_distinguishes_its_operands_at_the_unit` and
  `test_the_retained_failure_is_keyed_by_the_work_it_is_about`, which are about
  an in-process memo that a managed execution replaces with collected output;
- the scratch lifecycle pair and `test_the_failed_scratch_is_disposed_of`, which
  are about a coordinator-local temporary tree;
- `test_a_post_import_hold_is_not_reachable_by_the_supported_recovery` and
  `test_a_blocked_result_holds_the_only_integrator_and_job_c_waits`, which stay
  valid as *recorded owner behaviour* and should be preserved as such.

Recommendation: keep them as explicitly labelled legacy coverage, and require
each managed replacement to assert **the same fact** through the collected phase
report — same bound, same command, same harness digest, same completed-prefix
and not-run-suffix — so the relocation is proved to preserve meaning rather than
to have quietly dropped a check.

And a note in the proposal's favour: verification gate 2 asks for an instrument
that fails the test if the coordinator runs candidate verification locally.
`_watching` already is that instrument, and reusing it as the negative check is
cheaper and more honest than writing a new one.

## Smaller points

- "Serial phases share one principal-capacity reservation; no simultaneous
  parent and child runtime may use it" needs an **enforcement point**, not a
  statement. With shape (1) above the occupancy query is that point; without it
  nothing refuses a concurrent pair.
- The proposal's own rule that a `TimeoutExpired` in a child subprocess is not
  proof that a container stopped should be carried into the phase-report schema
  as a *required* distinction between "no report collected" and "report says the
  command produced no exit status". This Work's accepted contract already makes
  that distinction; the managed path must not lose it.
- "Do not add nullable lease fields to assignment/1" is right and I would add:
  do not add a nullable `parent_attempt_id` to `stage_allocations` either
  without the occupancy query that reads it, or the column will be documentation
  rather than accounting.

## Disposition

The architecture is sound and the reuse map is accurate where I checked it. **I
do not approve the orchestration gate (P1) as written**, and the portable-custody
prerequisite should move into slice one. The target-owner boundary is affirmed
with its adapter gap named. No implementation should start until the capacity
representation is chosen and scoped, because every later slice's "charged to the
parent" language depends on it.

No source file, product or test was changed by this review. No runtime
verification was run: nothing here needed a measurement that the existing
retained evidence and the source itself could not answer. Author spending is
unchanged at 246 runs / 2530.5844189850177 s plus the four disclosed unknown
activities.
