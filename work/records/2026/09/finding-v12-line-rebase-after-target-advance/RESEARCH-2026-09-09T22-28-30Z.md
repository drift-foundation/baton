## Confirmed

The shared-base two-Job traversal encounters a real missing capability. W131187
returns capacity; it cannot make the other candidate current.

The schema's integration_eligibility relation is unique per line. A target
advance must explicitly retire current eligibility while retaining historical
checkpoint/verdict/publication evidence. An old accepted verdict must never be
relabeled as changes-requested or rewritten to approve rebased bytes.

## Clarifications to the filing

1. The three directions are not three interchangeable complete fixes. Same-line
   base advancement and an ordinary target-driven round are complementary.
   Neither alone completes two already accepted Jobs.
2. A new deployment generation does not, by itself, solve an existing Work's
   immutable line collision. It would require a new Work/line/store or a new
   accepted lifecycle operation. Calling this a no-new-operation solution for
   the same persisted Work is unsupported.
3. The demonstrated failure is a shared-original-base sequence where A changes
   the target. The statement that exactly one Job can ever integrate in every
   deployment generation is broader than the proof (for example a no-change
   target does not demonstrate this mismatch). No general throughput limit is
   inferred beyond the reproduced condition.
4. The retained test calls published_proposal after A completes. That helper
   invokes retain_proposal again, which rechecks today's target. Its refusal
   does not prove B never published earlier: end_implementation publishes before
   fencing and finishing the producer. Reading an already committed publication
   is a different question from offering it against today's target. Even a
   historical-publication lookup repair would leave resolved_account's correct
   stale-target refusal, so it cannot satisfy this prerequisite.
5. The advanced revision must be available as actual nominated target content.
   A canonical target digest is an identity, not proof that B's isolated source
   repository contains that object. Blindly materializing at that hash is not a
   sufficient transfer or rebase design.

## Proposed product decision

Keep both-terminal ordinary traversal in W130224 and final joined acceptance in
W119405. Make W131409 their explicit prerequisite; do not close the consumer as
accepted merely because it now faithfully demonstrates a second blocker.

Prefer automatic target-driven rework of the SAME Job/Work and persistent line,
with an explicit base-advance lineage and fresh producer/review evidence.
Preserve the original creation operands and immutable historical checkpoints.
Keep the stale-target guards at publication, admission and Authority integration.

This is a lifecycle addition, not an instruction to edit the declared_base
column or widen the existing verdict-only correction operation. Initial creation
base and a later effective round base must remain distinguishable. Historical
create/recover and checkpoint audit must still mean what they meant before.

Recommended conflict policy: clean replay/transplant may prepare a new round;
an unresolved conflict or missing target object holds explicitly and preserves
the old candidate and proof. Never discard B's changes, manufacture a verdict,
automatically accept rebased bytes, or silently substitute another Work. Even a
clean rebase requires new required-test evidence and independent review.

## Proposed contract boundaries, before implementation

1. **Custody and content.** An exact operation binds Authority/Work/line, old
   checkpoint/digest/base, current target revision with its owner provenance,
   profile and nominated source/target content. It verifies old immutable
   evidence and line object, excludes active writer/reviewer/integrator access,
   and holds exclusive mutation authority before any checkout changes. Profile
   owns Git commands against the held private checkout object; no manager Git.
   Retain old refs and history. Return a typed operation record and distinguish
   prepared, committed and conflict/held outcomes. Do not reuse materialize
   as if detaching to the new base preserved the old delta.
2. **Scheduling.** A target-change round consumes that typed custody record,
   not a forged review verdict or bare target hash. It cross-binds the Job's
   actual stage/episode/attempt identities and creates fresh producer/reviewer
   attempts. Retire old current eligibility; do not carry old accepted review,
   test, proposal, approval or integration evidence onto the new candidate.
   Resolve the integration episode explicitly: in the existing repro it already
   owns capacity and may own a claim. It must be canonically excluded/settled
   before a replacement round, never simply overwritten or SQL-released.
3. **Composition.** Read effective round base through the owner. Keep configured
   creation identity stable on reopen. Bind each fresh worker's task/input,
   manifest/result base, publication, checkpoint, target and integration port to
   that same round. Detect target drift before reserving/launching stale work
   when possible; a later target race still refuses through existing owners
   and must not leave a fake completed attempt.
4. **Replay and concurrency.** Stable operation identity derives from fixed old
   checkpoint and intended target, with complete signature. Same retry returns
   the same result; foreign old checkpoint/target/assignment collides. Define
   recovery at filesystem-before-store and custody-before-Job-store cutpoints.
   Concurrent target change or attachment cannot grant two writers, release
   another allocation, or report a partially rebased line as ready.

## Acceptance and verification proposal

Retain the exact public stale-target negative and capacity-positive fixture.
The positive must show A's actual terminal receipt advancing the target, B's
old candidate still refused, B's same-line rework onto actual new target content,
fresh matching task/input and immutable checkpoint, fresh review/required tests,
and B's own terminal handoff through ordinary ticks. No manual manager transition
or stale-target policy waiver. Final tree must preserve both Jobs' intended
nonconflicting changes; a target-hash-only assertion is insufficient.

Provider controls: wrong Work/line/checkpoint/target/profile; tampered/missing
old checkpoint or target objects; active writer/reviewer/integration attempt;
dirty/moved/symlink checkout; conflict preservation; missing/foreign custody
record; duplicate/reordered replay; reconstructed readers and each cross-owner
commit cutpoint. Verify old checkpoint audit and original create/recover still
work, new round rejects old accepted evidence, and a second target advance
cannot slip past any stale-target guard. Reuse existing custody, principal and
capacity tests rather than rerunning unrelated suites.
