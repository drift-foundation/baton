## Gate 3 — I was wrong. The constraint exists.

`integration/schema.py` line 432 carries
`UNIQUE (canonical_target_id, source_proposal_id, target_revision)` as a **table
constraint** inside `integration_results`, and all three columns are `NOT NULL`.
I grepped for `CREATE UNIQUE INDEX`, found only `leases_one_live_per_target`, and
concluded no such uniqueness existed. That was a search that could not see an
inline constraint, and I reported its absence as a fact.

**Withdrawn in full:** the one-result key is an existing preserved invariant, not
a new one; and my warning that a 5→6 migration might be unable to build the index
on real data is void — there is no index to add, and conformant schema-5 data
already satisfies the constraint by construction.

What survives is **v2's own** point, not mine: two per-table constraints cannot
enforce uniqueness across two tables, so the writer must check both
representations inside the same target-global transaction, and reads must refuse
a double representation. The response's added pre-mutation duplicate-group
diagnostic is reasonable defence against a malformed input store, and it should
be described as exactly that rather than as a defect of schema 5 — the response
already says so.

## Gate 2 — I was wrong on the premise, and the narrowed proof holds

**My error.** I wrote that cancelling an unstarted attempt leaves
`execution_runtime` at `not-started`. It does not. `_order_quiescence` reads the
attempt, and when `cancel-requested` is a legal transition from the current value
it calls `observe(..., axis="execution_runtime", value="cancel-requested")`
**before** the `runtime_id is None` early return. `not-started` lists
`cancel-requested` among its transitions, and `cancel-requested` has no edge back
to `not-started` or `start-requested`. I read that function's docstring and its
`ordered=false` branch and did not read the observe call above them.

So the existing early check in `request_runtime_start` —
`execution_runtime != "not-started"` → `already-terminal` — **does** refuse a
start after a completed cancellation. My "nothing consults the cancellation axis"
was false, and the conclusion I drew from it is withdrawn.

**What I verified this time, at the response's lines:**

- `request_runtime_start`'s `act` occupies the lane and then observes
  `execution_runtime = "start-requested"` **inside** the transaction; `_decide`
  re-owns the attempt with a fresh read and consults the transition map, so a
  start whose optimistic pre-read saw `not-started` is refused inside the write
  if `cancel-requested` committed first.
- `ControlStore.transact` peeks for a replay, takes `BEGIN IMMEDIATE`, re-reads
  the journal inside the lock and only then runs the action, so the two writers
  serialize and the loser rolls back.
- `adapter.start` is reached only after `store.transact` returns.
- **And the replay point is real and well made:** a committed start operation
  replays and returns its recorded value *without running `act`*, so the axis
  check alone would not stop it. Excluding a committed start operation is
  therefore load-bearing, not redundant.

**The interleaving the handoff asked me to find: there is none.** For
`adapter.start` to be reached, `transact` must return either by running `act` —
whose in-transaction observation is `cancel-requested → start-requested`, absent
from the map, so it refuses and rolls back — or by replaying an already-committed
start operation, which the reader's own precondition excludes. A start that
committed before the cancellation axis is visible to the reader; a start that
commits after it cannot pass `_decide`. Both orders are covered, so **no new
start transition or generic transition rewrite is required.** I withdraw the
"returned scope" demand from my previous review.

**One point I checked that the response does not state, and it helps it.** The
exclusion needs no new enumeration reader: `_start_operation_id` is *derived from
the attempt row* — the runtime attempt id and the fixed assignment — so the
reader can recompute that exact operation id from the same row it is validating
and look it up through the existing by-id operation read. Two conditions follow,
and both should be written into the reader's contract:

1. recompute the id from the **same** attempt row the other facts came from, so a
   changed fixed assignment yields a different id and the lookup stays exact; and
2. treat the mere existence of that committed operation as the refusal — do not
   try to distinguish "adapter was called" from "adapter was not called", which
   the journal cannot answer. The response already takes this conservative line.

**The residual window is real and is already handled — keep it that way.**
`request_cancellation` journals its intent and fences at the Authority *before*
`_order_quiescence` writes the axis. If the fence raises, the axis is never
written and the attempt remains startable. So the reader must require the **axis
observation**, never the intent or the fence, and capacity stays held in that
window until ordinary cancellation resumes. The response's correction of v2 §D's
shorthand — "if the execution-runtime cancellation observation committed before
the start act" — is exactly the right wording and is what makes the gate sound.

**Gate 2 is now ACCEPTED as narrowed**, with the reader required to hold all of:
the exact fixed assignment; the committed matching cancel intent; the Authority
cancellation and fence read through the current owner port/operation readers;
`execution_runtime == cancel-requested`; no attached runtime; and no committed
`runtime.start` operation for that exact assignment. It returns
**fenced-before-start** and never `quiescent` or `destroyed`. Anything unknown,
mismatched or refused denies the proof and holds the capacity.
