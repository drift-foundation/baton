## The shape, as the owner selected it

**ONE monotonic decreasing allowance**, not a value copied per vector. It is a
capability the caller hands in — a deadline, read as "seconds left" at each
boundary — so sequential acts consume ONE budget and no step restarts it:

  1. the caller supplies a deadline; `None` preserves today's behaviour
     exactly and every existing caller is unchanged;
  2. each supported boundary takes `min(remaining, its existing maximum)` —
     so a bounded caller can only ask for LESS than the package's own limit,
     never more;
  3. **waits and margin are accounted, not asserted away.** Store transactions
     and the readback consume the same clock; the allowance reserves a stated
     cleanup margin so a timeout at the last boundary still leaves time to
     record what happened;
  4. **a timeout is a supported failure path, not an abandoned thread** —
     and the second half of what I wrote here is **WITHDRAWN**. I said the
     port's contract ("has terminated AND REAPED its child before it
     answers") means there are no continuing background effects. Review
     [R2]: that contradicts this package's own `custody._recovered`, which
     says it in as many words — "Docker is client/server…
     `subprocess.run(timeout=)` terminates and reaps the local CLI, which is
     all it can do and all this module ever had a right to claim; the
     daemon's already-accepted request is a different process and may still
     create the derived name afterwards", with W44342 named as carrying the
     missing capability.

     SO REAPING THE CLIENT IS NOT SETTLING THE REQUEST. A timed-out act may
     leave a helper the daemon creates afterwards, which is exactly why
     `custody_act` answers UNRESOLVED rather than absent and why the derived
     identity exists for a later manager to reclaim. What the durable state
     gives is a resumable record, not a proof that nothing is running.

     WHAT I WROTE NEXT WAS ALSO WRONG, and claim 257091 withdraws it. I
     named "a provider that can settle or CANCEL the engine-side operation"
     as the precise prerequisite and cited `custody._recovered`'s assignment
     of it to W44342. Review 2026-09-24T11:10:32Z read the canonical record:
     W44342 is open, **PARKED**, routed `baton.decide`, and its own
     2026-08-30 and 2026-09-05 rulings accept fail-closed UNRESOLVED for the
     pilot and SUPERSEDE the durable provider as the default next solution.
     A source comment does not select a dependency, and mine revived
     something this Work had already decided not to depend on. The parking
     stands.

     WHAT WAS SELECTED INSTEAD, by owner 257086: a bounded stopgap for this
     packet. An uncertain custody settlement is reported held and unresolved,

## What this claim DID, and the two things measuring it found

The allowance is threaded and enforced: `custody.allowed` clamps, the adapter
clamps its removal and its observation, `oci.normalize_directory` wraps the
engine port when bounded, `intake.abandon_attempt` carries it to the removal
and to BOTH custody acts, the two compositions forward it, and the supervisor
supplies `total - elapsed` as one callable so every boundary reads the same
decreasing budget.

**A regression I introduced and corrected in the same claim.** Applying the two
new ceilings unconditionally made an UNBOUNDED observation carry 120 seconds
where it had carried `None`. That is a changed existing caller, which the
owner's constraint forbids. An unbounded call now passes `None` exactly as
before, and a case asserts it rather than a comment claiming it.

**Three vectors still run unbounded inside a bounded ending.** Measured with a
costing boundary, a bounded ending asks
`[60, None, None, 57, None, 55, 54, 53, 52]`. The `None`s are the pre-core
credential recovery and adapter internals the owner's own list names. That is
stated as a failing expectation —
`test_every_vector_of_a_bounded_ending_carries_the_allowance` — rather than
described in a plan, so it reports an unexpected success the day it closes.

What IS proved: the allowance decreases across the boundaries that carry it,
never rises, never exceeds the package's own ceiling, and an unbounded ending
is byte for byte what it was.
