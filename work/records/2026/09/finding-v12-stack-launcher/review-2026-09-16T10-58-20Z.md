## F1 — bootstrap reports success before validating the deployment (high)

`v12/python/tools/bootstrap.py:112` validates a few wrapper fields;
`prepare:396` creates the Authority/Works/grants and writes deployment.json
without calling the accepted configuration validator. The nested worker
`deployment` merely has to be nonempty. Missing runtime profile, adapter,
credential selection, workload, workspace and launch fields are neither
reported by name nor refused before durable setup, contrary to PLAN/runbook.

Confirmed with the author's Fixture.document and real bootstrap/Authority APIs:
prepare returns success, creates the Authority and configuration, then
`stage_execution.held_configuration` rejects the result for22 missing worker
fields. These include adapter_name/digest, profile_name/digest, input_manifest,
task_document, workspace_storage/group/capacity, launch_home/contract and
review_route. No production value is needed to reproduce the missing validation.
This is a malformed deterministic input accepted as prepared, not evidence about
whether a real image or credential is fit for production.

The same boundary also selects `/1` solely by Job count, even though `/1` permits
only one worker per role. One Job with a multi-worker pool therefore passes this
helper's checks but emits the wrong variant (static finding). Either select the
accepted variant from both pool and binding shape, or refuse an unsupported
combination before mutation; do not write a configuration the manager rejects.

Correct within the bootstrap boundary: derive the intended worker identities and
external paths, validate the resulting document through the existing accepted
configuration rules before durable mutation, and convert malformed inputs into
operator-facing refusals. Keep explicit production selections explicit; do not
invent them to obtain a pass. Do not duplicate the deployment contract in a
second permissive validator. If deriving a principal requires an Authority read,
separate non-mutating derivation/validation from durable composition as needed.

Add at least one valid deterministic generated deployment that passes the real
`held_configuration`, alongside missing/malformed nested members, independent
identities, and supported one/multi-worker schema cases. Verify routes/grants
through public Authority APIs. No real provider/engine or production installation
is needed. Existing launcher composition evidence does not validate this new
producer of configuration.

## F2 — repeated bootstrap can silently replace existing bindings (high)

`conflicts:361` treats corrupt/unreadable configuration as absent. `_bindings_of`
uses None for `/1` and Job IDs for `/2`, then checks only overlapping keys in the
*new* map. Existing bindings removed from the new map are never checked.

Two confirmed offline cases using disposable real v12 Authorities:

1. Replace deployment.json with malformed JSON and repeat the same bootstrap:
   success, prior bytes overwritten. The old configuration's identity is unknown,
   not proven absent. File read errors follow the same branch (static).
2. Bootstrap the author's two-Job document, then repeat with one Job that changes
   job-a's declared base and target: success, `/2` becomes `/1`, job-b disappears,
   and job-a is rebound. Comparing None to the prior Job keys misses everything.

Preserve existing bindings across schema representations and account for removed
Jobs. Refuse corrupt/unreadable/unsupported existing configuration before opening
or modifying the Authority, rather than overwriting uncertain state. Preserve
an existing configured root on a conflicting repeat. Normal repetition must
remain idempotent. Publish configuration atomically so an interrupted write does
not turn a known configuration into partial JSON (current direct write is a
static observation; no interrupted-write experiment was run).

Regression boundary: identical repeat, corrupt/read-denied existing record,
changed/removed binding, and one-to-many/many-to-one schema transitions. Exercise
the real final bytes and public Authority state, not only helper dictionaries.
A generic migration or live reconfiguration feature is not selected: refusing
unsupported changes is sufficient.

## F3 — input selections can be silently discarded (medium)

`held:112` never closes the input member set; `configuration:193` copies a short
optional-field list. Confirmed: adding `integration_preparation: true` is accepted
by held but absent from configuration output. The serving deployment's
`_prepares` defaults its absence to false, so the operator's requested managed
preparation is silently disabled. Unknown misspelled fields are likewise ignored.

The helper may explicitly support and validate this accepted option, or refuse
it as unsupported. It must not accept a selection and silently drop it. Close
the documented bootstrap input contract, including its nested wrappers, and test
supported option preservation and unsupported/unknown-option refusal before
mutation. This is not authority to broaden product behavior or enable optional
provider-context reuse.
