## D1 [P1, C2] Include the admitted manager before its next fallible record write

stack.py:_start_admitted around678–683 calls _spawn, then writes the manager
record again to add incarnation, and only THEN appends it to started. When this
second write fails, the BaseException handler runs _unwind with an empty list.
The controlled reproduction used real _spawn with an owned sleeper and failed
only that second write: the original OSError escaped, the manager remained
live, and the retained record lacked incarnation. This is a recorded half-start,
not an unrecorded orphan, but it still bypasses the promised rollback.

Register ownership for rollback immediately after spawn, before any further
fallible operation, or have spawn publish the complete identity in one owned
transaction. Cover all record publication boundaries in this small transition,
including the final serving_acknowledged write currently outside the protected
block. Any failed start must stop/reap its admitted processes or explicitly
retain and report unresolved ownership. Preserve the original error if cleanup
also fails; do not let cleanup of one process prevent accounting for the others.
Add focused write-failure cases without weakening the existing unknown-ownership
regressions.

## D2 [P1, C3] Require evidence for an existing manager before declaring readiness

stack.py:_start_admitted around664–670 returns0 immediately if both PIDs are
LIVE. If only the publisher needs replacement, expecting stays empty because
only a newly spawned manager is added. Neither path checks that the existing
manager actually completed acknowledgement. The assumption that an earlier
start already proved it fails after an interrupted start or unsuccessful unwind
that deliberately retained live processes.

Two controlled recoveries reproduce this with an existing, owned, unacknowledged
manager and a valid fresh snapshot:

- Both processes live: start returns0 and prints already running twice.
- Publisher absent: replacement starts, start returns0 and prints ready.

In both cases observe simultaneously says the manager is unacknowledged. These
are process-boundary stand-ins, not a claimed deployed-manager failure. The code
paths are the actual start/observation paths. The current publisher-replacement
test starts from serving_acknowledged=True, so it proves reuse of established
evidence but misses recovery when no such evidence was ever obtained.

Reuse a persisted acknowledgement only when it is valid for that live manager's
identity, or obtain its matching acknowledgement before returning ready. An
unacknowledged existing manager must remain unacknowledged/refused or enter a
bounded wait; liveness alone must not make it ready. Apply this to both-live and
publisher-replacement paths. Preserve no-duplicate behavior and avoid requiring
new initialization of an already acknowledged manager. Update the runbook's
assumption that every earlier start necessarily proved readiness.
