## P1 — distinguish immutable proposal base from correction entry head

Plan item 1 requires entry `HEAD == task.declared_base`; the claim defines
`base` as that entry head and maps it to proposal `source_base`. Those rules
cannot both survive the required second correction turn.

Let B be the immutable source/target and H1 the first private commit. The
accepted line still has `declared_base = B`, while
`review_cycles.grant_writer` validates the current checkpoint at H1 for a
correction. `freeze_checkpoint` continues passing B to the profile. The real
two-checkpoint fixture also freezes both revisions against B. If the next task
still declares B, the proposed worker rejects H1 at entry. If the next task
instead declares H1 and reports that as `base`,
`integration.driver._publish_operands` rejects `source_base != target_revision`
while the canonical target remains B. Resetting to B would discard the private
correction history and is not a remedy.

Pin separate meanings and accepted sources for the immutable publication base
and the current turn's expected checkpoint/head. The worker's new commit must
continue the current head while the final proposal and bundle cover B through
the new head. If existing manager grant validation is the source of entry-head
authority, say exactly how the worker consumes that guarantee; otherwise name
the minimal explicit task/input seam and its producer. Do not silently change
the semantics of `declared_base`. Prove two turns with canonical target B
unchanged, H2 parent H1, both retained checkpoints, and second-round metadata
still suitable for publication against B.

## P1 — test the complete worker ending, including the completion document

Excluding only declared proposal directories does not leave a clean line.
`baton_worker.handle` calls `agent.work`, then measures the outputs and invokes
`publish_completion`, which creates `/output/output.json` AFTER the agent has
returned. `GitCheckpointProfile._clean` rejects any untracked or tracked
change. The planned direct `ClaudeAgent.work` → `profile.freeze` positive test
omits the write that will make the real freeze fail; the next correction's
entry cleanliness check encounters it too.

Pin the exact reserved runtime-output/control paths, including the completion
document and its publication staging name, and their exclusion/validation
before the first turn. Refuse tracked source collisions with those paths;
ignore rules cannot remove already tracked content from Git's candidate.
Use exact, root-relative patterns with a defined treatment of pattern
metacharacters, rather than interpreting a declared path as an arbitrary ignore
pattern. Preserve safe filesystem handling when excluded paths or `.git` are
replaced. The positive proof must include the real completion-publication step
before checkpoint freeze and the next correction turn. Nothing requires moving
completion publication into the concrete agent or changing the frozen schema.

The tracked-file and pattern distinctions are documented by
[Git's ignore contract](https://git-scm.com/docs/gitignore).

## P1 — the fresh-workspace fallback and existing consumer contract do not match the proposed root/output change

The claimed no-change fallback for `single_worker` is not a clone into an empty
root. `workspaces.assignment_workspace` creates
`workspace/result-<attempt-id>` before runtime start. Cloning directly into
`/output` therefore meets a nonempty destination. The existing checkpoint
profile instead clones into the absent `checkout` child of its custody home;
its `lexists(repository)` branch is not precedent for rebuilding an existing
manager-allocated output root. Git explicitly allows an existing clone
destination only when it is empty.
[Git clone destination contract](https://git-scm.com/docs/git-clone).

There is also a real consumer boundary to preserve or deliberately supersede:
the existing `test_claude_agent.AdapterCase` task declares the **generic**
profile and has no base. Its `proposal/candidate/` assertions are therefore
not obsolete merely because the new Git path uses a mounted worktree.
`dogfood_operator._derived` and `_kept` likewise require that candidate
directory for diff and verification. Removing it without a selected/versioned
output contract breaks those consumers; the worker's current result schema is
still `baton.dogfood-proposal/1`.

Pin a bounded compatibility matrix: existing generic workload, existing
non-line Git workload if still supported, and prepared persistent-line Git
workload. State how the last is selected and how a missing/corrupt repository
refuses instead of silently recloning a line. Keep generic behavior and its
tests unless an owner explicitly changes that separate contract. Do not delete
the manager-created result root to make clone work. If the new workload cannot
be selected and consumed safely in the two proposed files, enumerate the exact
additional producer/consumer paths for owner approval; do not invent a shared
Git backend or broaden unrelated tools.

## Required precision in the revised commit/bundle proof

The proposed claim's closed worker-only namespace is a sound direction once
`base` is corrected above. Keep manager measurements and custody identities
out. Pin bounds, the exact relative bundle member and the Git/generic result
selection; a bare transport filename is only a locator within the measured
declared output, not a substitute for its retained artifact account.

Capture the turn-entry head and prove the worker-authored commit continues it.
The proposed refusal only for a provider moving HEAD *outside* B's ancestry is
too weak to establish the stated single-worker-commit account. A provider can
advance HEAD within that ancestry, or leave an index that differs from the
verified worktree. Pin the allowed behavior and ensure the resulting commit
tree, patch and bundle describe the verified candidate, including after any
Git hooks/filter behavior. Keep this to focused publication-identity proofs,
not a complete Git recovery matrix. The existing `_publish` per-file copy
comparison does not transfer automatically when that copy is removed.

The incremental bundle requires the declared base's objects at the recipient;
it is not a self-contained full history. Git documents both range prerequisites
and the need for an advertised reference. Resolve the actual retained bundle
from a recipient with B but no access to the producer worktree or its private
objects, including the second correction's cumulative range. Verify the exact
head and candidate bytes there. The detached-HEAD invocation remains a focused
implementation test, not a reason to add a core VCS adapter.
[Git bundle reference/prerequisite contract](https://git-scm.com/docs/git-bundle).
