## Finding

### P2 — the candidate promises two observations its own regression does not make

The operator documentation at `v12/python/DEPLOYMENT.md:247-249` says a dead
daemon socket is reported as `uncertain / engine-unreachable`, and the source
comment at `v12/python/tools/single_worker.py:1196-1201` says a dead daemon
socket reaches `subprocess.run` as `OSError`. That is not the production path.
`subprocess.run` returns the Docker CLI's nonzero result; `OciAdapter.list`
turns it into `ContractRefusal("policy", "denied", ...)`; and
`_SingleWorker.refresh_runtime` deliberately does not translate that refusal.
The manager therefore reports the stage with `state: null` and
`detail: {"category": "policy", "code": "denied"}`. Runtime state is left
untouched and exchange observation continues, so the implementation still
meets the accepted containment boundary, but the documented operator result is
false.

An independent production-composition probe drove the W85500 faulted-terminal
fixture, replaced the engine answer with Docker's ordinary nonzero
`Cannot connect to the Docker daemon` shape, and observed exactly that
`policy / denied` refresh detail. Correct the documentation and source comment
to promise only what this boundary distinguishes (a runner invocation raising
`OSError`, and a runner deadline raising `TimeoutExpired`), unless a separately
designed typed adapter failure is intentionally added and pinned first. Do not
wrap every OCI `ContractRefusal`: that category also owns policy and integrity
refusals which are not evidence that the engine was unreachable.

The new test class has the same kind of contradiction at
`v12/python/tests/tools/test_single_worker.py:2181-2185`. It says the case's
agent produces `fault_code: output` and exactly reproduces run6, while its
`Silent.work` raises and the assertions correctly require `fault_code: agent`;
the following `Silent` docstring itself explains why this case does not drive
`output`. Make the class-level description agree with the actual regression so
future reviewers do not mistake a correlated-fault projection proof for an
exact reproduction of run6's output-publication failure.
