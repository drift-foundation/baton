## The one confirmed blocker you are here to fix

`store.py`, in `read_snapshot()`:

    connection = self._connection
    if connection.in_transaction:
        yield self
        return

When a caller already holds this store's transaction, `read_snapshot` yields
WITHOUT taking or owning a boundary -- correctly, because SQLite has no nested
transactions and ending one would commit or discard somebody else's decision.
But `materialized()` then returns with that caller-owned boundary STILL OPEN, and
`projection.py` goes on to call `delegation.observation_of` for every live stage.

So this is reachable through the public API, with no raw SQL and no hostile store:

    with store.read_snapshot():
        projection.status(store, operations, observed_at=NOW)

On a populated fixture that performs three external observations with
`store._connection.in_transaction` true. DESIGN DB-1 forbids external I/O while
a store transaction is held and DB-4 forbids calling another store while
retaining this one's, so this violates the accepted outcome.

The existing nested-caller test checks only that `read_snapshot` preserves the
caller's boundary. It never calls `status` or `stage_states` from inside the
nested case, so it endorses boundary preservation without establishing the
exclusion that actually matters.

## What is required

`status` and `stage_states` must NEVER reach an external observation while a
Job-store transaction is held.

A SAFE EARLY REFUSAL IS SUFFICIENT AND IS THE SMALLEST ANSWER. Detect the
caller-held case before any observation is attempted and refuse it with this
distribution's own `ContractRefusal` and a closed category/code pair, naming what
the caller did and what to do instead. Broader refactoring is NOT requested.

Three constraints on however you do it:

  * NEVER commit or roll back the caller's transaction. Their boundary must still
    be open, and their work still pending, after your refusal returns.
  * Refuse BEFORE the first external observation, not after some of them.
  * Do not weaken `v12/DESIGN.md` and do not change the probe or the caller's
    transaction to make the problem disappear. The requirement is the code's.

`materialized()` on its own is still legitimate inside a caller's boundary -- it
reads only this store and takes no `operations` handle. It is `status` and
`stage_states`, the paths that go on to observe, that must refuse.
