# Proposed bounded prelaunch reconciliation and installed consumption

baton.codxpc, claim353886, 2026-10-22. Preparation under owner353807 and review353883 only. No product implementation, product execution, installed mutation or live evidence collection. This proposal replaces the unresolved choice of installation strategies in OPERATIONAL-CONTINUATION-353809; it does not authorize that document's conditional commands.

## Decision-ready outcome

Reuse existing cancellation and preparation owners; add a narrow **validated prelaunch cessation result** to managed recovery, then a **drained, exact-manifest offline update of the existing fixed-root installation**. Preserve its identity pool, credentials, storage and every consumed run. Do not create another installation, reset C, fabricate a workspace token, or build a general rolling upgrade framework.

There is no existing end-to-end CLI operation that supplies this result. Existing `recover` rejects the missing-token branch. Existing `unstarted_cancellation_of` supplies part of the proof, but not host preparation cessation or complete resource-owner inventory. The missing capability is bounded below. Historical C qualifies only if its owner records pass these checks when subsequently inspected through the supported implementation. Nothing in the retained reports establishes that they will.

## Capability A: owner-validated prelaunch cessation

Proposed API boundary (names are proposals, not available calls): `attempts.reconcile_prelaunch(control, port, *, attempt_id, recovery_id, owner_exclusion)` returns an exact, journalled `prelaunch-ceased` record or a typed held result. A workspace-owner reader supplies validated preparation endings; a resource-owner reader supplies a complete recovery inventory. The orchestrator must use these public owner APIs, never reach into their SQLite tables. Reuse existing cancellation records/operations rather than minting a parallel authority fence protocol.

1. **Exclude physical and admission writers first.** Hold the installation's existing broker lock, nonblocking old manager instance guard and exact protected allocation binding. Verify the entire exclusive uid's real/effective/saved/fs uid process inventory on the host before and after owner work; denied/incomplete visibility refuses. The updater's known inspection child is accounted explicitly, not globally ignored. Old consumed selection prevents another dispatch, broker lock excludes an in-progress privileged dispatch, and the manager guard excludes another serving manager. No selected stop/kill is implied. Any active or delayed preparation subprocess keeps the operation held. Do not accept a different process namespace's empty listing.
2. **Freeze the owner scope.** Read every attempt in the isolated control store, including attempts not linked to the selected Job. Bind the inventory to the store/authority identity, all fixed assignment generations, all preparation ownerships and all resource domains/generations/launch or activation intents. Include unlinked tokens and other resource holds; the current attempt-only workspace-token projection is insufficient for this negative proof. Unknown or orphaned records hold the whole allocation. Hold admission excluded and revalidate the same inventory at settlement; no external I/O inside a DB transaction.
3. **Require positive preparation endings.** For each admitted attempt require either its correctly bound completed preparation or validated release of every admitted preparation ordinal. Also require no standing allocation/adoption/removal/cleanup/restoration writer. Validate source-line preparation records and preservation bindings without resuming materialization. An admitted-but-unreleased window remains held even if the host now appears empty; this proposal deliberately does not add dead-writer takeover. No preparation record at all is not a substitute for an ending for an already activated C-like attempt. A truly empty pre-admission allocation can continue through the existing empty-inventory path only after complete owner inventory and exclusion checks.
4. **Establish the exact authority fence.** If the compatible owner journal already contains the full cancellation, use `unstarted_cancellation_of`. If cancellation is partial or absent, resume the existing exact cancellation operation under its original operands and authorized participant-bound port, using the standard capability implementations. Before this branch require no committed start, no attached or token-bound runtime, and no resource acquisition/launch/activation record; a concurrent changed record refuses. A recorded prior reason must be reused, not changed to force replay. If old authority state/grants cannot support the owner cancellation, hold and report that exact refusal. No fake port or worker-supplied fence. Never turn an old `requested:true` JSON field into a committed cancellation.
5. **Prove the negative resource branch through the resource owner.** In the same stable owner scope, require the positive fenced-before-start result plus absence of any start act and any resource reservation, launch, bound runtime, unsettled activation or writer. These negative facts become usable only alongside positive original preparation endings and current physical/admission exclusion. A token present, returned or not, selects the ordinary token/runtime branch rather than this shortcut. Missing/stale/conflicting records refuse. No token is created or marked returned to represent work that never acquired one.
6. **Commit one cessation disposition.** Journal a new versioned result binding recovery_id, original run/packet/consumed hashes, authority/Work/generation, attempt, exact cancellation result, validated preparation-ending identifiers and resource inventory revision. Revalidate expected facts transactionally before commit; re-read the external authority fence and process exclusion outside transactions as needed, then compare recorded versions. If any cross-owner step becomes uncertain, preserve a partial recovery intent and keep the allocation held. Record controller halt through its existing operation only under these exclusions; never remove the consumed fence. The result means no execution/resource writer remains admitted for this attempt, not that source materialization succeeded or that old candidate/cleanup reports were correct.
7. **Retain ordinary cessation.** For any committed start or token, use the existing runtime/resource-owner reconciliation and returned-token plus exact absence proof. An unknown engine reply, unattached token-bound runtime, pending create/start or outstanding activation cannot fall back to prelaunch-ceased. This proposal neither forces destruction nor expands the owner-selected live operation. It returns the exact blocker for separately selected standard reconciliation.

`next_run_recovery` should consume the two typed results (ordinary runtime cessation or new prelaunch cessation) and retain both in its existing recovery intent before allocating a fresh identity. No change to old reports, no claim old cleanup completed retrospectively. A materializing line and partial files remain retained and excluded from reuse; no normalization, delete, clone or fixture repair is part of this operation.

**C-specific feasibility:** the original finally path may already have recorded the required preparation release; subsequent cancellation may already have fenced its generation. Those are hypotheses to check via the new validated owner reader. If either is absent or cannot be proved, this design holds C. It does not promise universal crash recovery or permit inventing historical proof. The held outcome must expose the missing record and exact blocked continuation; any additional dead-writer capability would be separate bounded work.

## Capability B: one drained fixed-root adoption

Choose one offline update of `/opt/baton-next-run`, not a second root. The current entry and client hardcode that root, and repeated account/credential provisioning on recovery would conflict with OBS-0a. Keep the existing four account reservations, credential files, broker-lock inode, storage and runs. This is a code-version adoption, not a store migration or routine setup step.

Proposed protected tool `tools.next_run_adopt` exposes `check --manifest FILE --sha256 DIGEST` and `apply --manifest FILE --sha256 DIGEST`. These names are a finite interface proposal, not executable commands today. The eventual tool must be shipped as an independently reviewed digest-bound protected artifact, never imported as root from this mutable checkout. No archive or tool has been built this turn; deployment selection waits for those real bytes.

The closed adoption manifest must contain:

- Fixed installation root; expected old entry/client/installation.json/READY digests; complete old payload inventory and selected supported schema versions.
- Complete exact new payload inventory and digest-bound source/runtime artifact; no opportunistic inclusion of W333486 or unrelated current-tree changes.
- Expected allocation/run set, exact consumed and prepared receipts, old packet hashes and account/credential **metadata** bindings. Secret contents are neither serialized nor logged.
- Allowed per-run old source generation, store identities and the compatible recovery-reader version; exact changed paths and retained-history destination derived from old inventory digest beneath the protected installation.
- One operation identity and fixed receipt location; no caller-selected Python, environment, source path traversal, arbitrary root or shell command.

`check` validates the entire manifest/custody, reads owner state without reconciling and lists prerequisites. It does not claim cessation from process absence, write side effects into application stores, or create identities. `apply` revalidates, takes the existing broker lock and all old instance guards, and refuses any active uid or any unconsumed prepared allocation. Unconsumed packets pin old code and cannot silently become launchable under new imports. Preserve/refuse such allocations rather than discard them. Require every consumed allocation to have compatible owner cessation from Capability A or the existing ordinary branch before changing installed product bytes. No new accounts, credential copies or database schema migration.

Under the same lock, preserve the exact old payload, installation.json, READY and entry/client bytes in a protected immutable history generation. Hash/type/mode-check all copied bytes and record their original logical paths; preserve original runs/packet files and operational roots in place. This retained generation is data and provenance, never implicitly executed under new authority. Failure to retain any original byte refuses before replacement. An existing history generation must match exactly for replay; never overwrite it.

Publish an adoption intent before replacement. Build all new bytes and the new full installation inventory out of view. Atomically withdraw READY to its already retained historical generation before modifying active payload; old entry then refuses new requests. A request that already passed entry checks must still contend on the same broker lock, and changed new/old inventories must cause revalidation/refusal after lock acquisition; implementing this lock-time generation check is required, not assumed of current code. An interrupted update remains unavailable/held and only the identical reviewed adoption operation may resume it. Publish new installation.json then READY last after all exact bytes/modes are verified. No deletion of history or old receipts. This is fail-closed multi-file publication, not a claim of atomic filesystem replacement.

**How old C is consumed after adoption:** ordinary `status C` continues to return original receipts. Old `start C` must refuse on its immutable consumption before any staging effects or legacy validation branch. New `recover C < new-task` uses the new current reader but verifies C's original packet/source/controller hashes against the retained old generation with an explicit logical-original-path mapping; it must NOT pass the old packet to `verify_imported_sources` and pretend new imports equal old code. Validate current recovery code independently against the new inventory; validate old provenance against the archived old inventory. Original config/store/authority/account bindings stay unchanged and are accessed only through version-compatible owner APIs. Do not rewrite the packet or relabel it as new. A missing archive member, schema mismatch, changed old receipt or current-code mismatch refuses. Existing identical recovery receipts retain their original source generation; no reinterpretation.

Fresh allocations bind only the new current inventory. Recovery still allocates a never-used identity and records original C plus its cessation record and source-generation mapping. This handles fixed-root entry/client admission and retained old pins without introducing arbitrary multiple installations or permitting an upgrade over active work. It is intentionally unavailable until *all* existing allocated work meets the drain requirements; do not claim this host currently does.

## Finite acceptance before installation selection

Use disposable stores and real owner APIs with fake engine/provider boundaries when separately assigned. This turn executes none.

| Case | Required result |
| --- | --- |
| Real pre-runtime profile refusal, original finally releases preparation, cancellation fenced, no start/resource intent | Typed prelaunch-ceased, partial line retained, fresh recovery prepared once; no fake runtime/token, no provider or engine launch. |
| Released preparation but missing/wrong-signature/foreign generation cancellation, authority unreachable or contradictory live assignment | Held; no adoption publication or allocation. |
| Cancel intent committed but axis not yet changed; cancellation reply lost | Resume identical owner operation; proof only after complete positive fence/axis; changed reason refuses. |
| Suspended original preparation writer, live child, unknown uid visibility, held manager guard, standing preparation/allocation/adoption/removal/restoration | Held; resuming original writer cannot race replacement. Missing release after crash is held, not retroactively minted. |
| Attempt unlinked from Job; orphan resource token; workspace token bound before attempt attachment | Included in inventory and blocks shortcut; ordinary exact-runtime reconciliation remains required. |
| Committed start before cancellation; late create/start/activation reply | No prelaunch proof; hold until normal owner settlement. Empty labels/null attachment do not release. |
| Ordinary returned token and exact container absent; stopped-only or engine unknown | Existing successful cessation retained; stopped-only/unknown still holds. |
| Foreign/stale inventory, changed token revision, concurrent old request paused before broker lock | Commit/revalidation refuses; no stale proof publication or old dispatch during adoption. |
| Replay/crash after fence, before cessation, after cessation, after retained archive, during payload publication, before/after READY, after recovery intent/allocation | One attributed result or held continuation; old receipts intact, no duplicate launch/account use. Same op/changed manifest refuses. |
| Wrong installed root, unconsumed prepared allocation, active unrelated pool uid, mismatched old/new digest, schema incompatibility, unsafe archive node or target mode | Whole adoption refused before active-byte mutation; no chmod/replacement workaround. |
| Accepted offline adoption then old status/start/recover and new prepare/check | Old evidence readable and hash-identical, old start always refused, supported old-generation recovery, new packet bound to new code, existing accounts/credentials unchanged. |

Required meaningful race test: suspend a would-be launcher after initial validation but before broker-lock acquisition; finish adoption or retain its interrupted intent, then resume that request. It must refuse/revalidate and cannot dispatch old code into a new generation. Preparation/start checks, callback activity and external I/O must remain outside DB transactions; use existing owner exclusion semantics rather than a transaction held across Git, Docker or filesystem work.
