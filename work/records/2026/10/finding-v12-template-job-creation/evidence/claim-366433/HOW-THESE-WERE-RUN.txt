THE OBS-0 INTERVAL, STATED HERE AS WELL AS IN THE SUITE

  OPENS when the operator's selection arrives: a task id, a statement,
  acceptance criteria and a selected work scope. Nothing else is supplied --
  no digest, no manifest, no submission document, no launch packet, no path --
  and test_the_measured_path_required_no_authored_procedure reads that off the
  recorded resolution rather than describing it.

  CLOSES when the assigned agent ENTERS work() inside its own runtime. The
  producing agent stamps time.monotonic() there itself, so the endpoint is the
  agent's own rather than this fixture's guess about it.

  INSIDE, all of it: the installed worker configuration read and proved; the
  whole creation (template resolution, full-resolution digest, identity
  reservation, Work authorization, deployment binding published and prepared,
  per-Job task composed, submission admitted); every scheduler tick that
  follows (offer, claim, principal allocation, writer grant, input root
  composed and frozen, launch document, credential delivery, runtime start);
  and the in-image startup (launch adoption, exchange, worker preflight).

  OUTSIDE, and OBS-0a is why: the one-time install and the deployment's own
  start -- opening the stores, validating the configuration, certifying the
  checkpoint profile, minting the session and activating the pool. That is
  `just start`, performed once per deployment and not once per task, and
  SCH-2's scheduler is persistent by design. NOTHING PER-RUN IS OUTSIDE.

  THE CORRECTION ROUND IS MEASURED AS A ROUTINE START TOO, from the recorded
  verdict to the second agent's own work() entry, because OBS-0a names retries
  as routine.

  WHAT THE FIGURE IS NOT. The container engine and the provider inside the
  workload are this suite's declared seams, so it contains NO image pull, NO
  container start, NO provider authentication and NO model latency. It is the
  product's own routine path and is reported as exactly that. The supported
  environment is the one this suite runs in: a prepared local deployment on
  one host, local SQLite stores, the deployment-configured checkpoint profile
  with no version control behind it, and no network.

  AND THE SUITE'S OWN DURATION IS NOT THE MEASURE. joined-workflow.txt reports
  ~34s of wall clock for 15 cases, each of which installs its own disposable
  deployment and runs two or three real worker turns. That number is not a
  startup figure and is not offered as one.

WHAT WAS NOT RUN, AND WHY

  NO VERSION-CONTROL OPERATION OF ANY KIND, and this suite PROVES it rather
  than asserting it: every case calls `no_version_control()`, which replaces
  subprocess.run and subprocess.Popen with wrappers that raise AssertionError
  on any argv whose program is `git`. A case that spawned one would fail, so
  15 passes is the evidence. The checkpoint profile is
  tests.job_manager.test_review_driver.Profile, the deployment-configured
  profile with no VCS behind it.

  This is also why the repository's existing full-lifecycle harness
  test_stage_execution.ComposedOneJobCase is NOT used for the workflow: its
  setUp runs `init`, `add` and `commit` against a real repository. Standing
  policy forbids an agent performing a mutating version-control operation and
  does not scope that to the working tree, so the joined path is driven on the
  no-VCS composition this Work's own children established instead. Only
  ComposedOneJobCase.quiescing -- its multi-container engine double -- is
  borrowed, and it performs no version control.

  No live provider, no model, no container engine, no deployed-instance
  mutation, no install, no migration and no cutover. Every destination is a
  disposable root outside the checkout.
