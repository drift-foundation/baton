THE THREE DEFECTS THIS CLAIM FIXED
----------------------------------

All three were invisible to every fixture that composed the creation ports
itself, and all three were found by running the supported command against a
really installed instance.

1. `install-inputs.json` WAS NEVER WRITTEN BY ANYTHING.
   `fresh_attempt_ports._install` reads it and its docstring already said
   "`bootstrap.install` writes it beside the configuration" -- nothing did.
   So on a real install EVERY additive binding (an ordinary creation's and a
   fresh attempt's) refused:

       install-inputs.json does not exist; an additive binding is prepared
       from this instance's own install document and there is nothing here to
       add to

   The two suites that exercise the additive path write the file themselves,
   which is why no test could see it. Fixed in `tools/instance.py` (the
   layout names it) and `tools/bootstrap.py` (the installer writes it under
   the same lock and inside the same unwind as the selector and the justfile).

2. THE DOCUMENT `install` IS HANDED IS NOT ONE `prepare` ACCEPTS. `main` adds
   the resolved `authority_uuid` for the selector, and that member is
   SUPERSEDED as an input -- an input document naming one is refused in as
   many words. Keeping the handed document made the first additive binding
   refuse with "nothing reads authority_uuid". What is kept is now the
   document `prepare` accepted moments earlier.

3. THE SERVABILITY QUESTION WAS ASKED WITHOUT THE JOB'S OWN TASK. A Job
   created against a deployment that composes a per-Job task submits that
   task's Job-scoped input identity, and the selector derives a worker's
   compatibility from the document it would serve the Job under -- composed
   from the task it reads out of the `template_jobs` row. That row is written
   by the same operation, AFTER this question. So every configured worker was
   judged against the installed identity and the creation refused:

       this deployment configures no worker that can serve the
       'implementation', 'review' stage of the Job this request creates, so
       nothing would ever run it

   for a pool that serves it perfectly well. Fixed by passing the derived task
   document through `creation._servable` and the port's `serving` into the
   selector, which already takes it. The test fakes implement that contract
   and were updated with it.

What the new suite proves
-------------------------

  * A REAL INSTALL leaves a preparable input document, and says where.
  * THE SUPPORTED COMMAND, entered with an operator's argv, creates one Job:
    every digest derived (the operator names none), the binding published into
    the configuration with the derived producer, the Job entry appended to the
    install document beside the one the install already named, the submission
    admitted, the Job's own task document written and both resolved stages
    servable by a named worker.
  * TWO ordinary creations bind two Jobs with two distinct tasks.
  * REPLAY: the same argv again answers the same Job and the same resolution
    digest, publishes nothing twice, and leaves one created-Job row.
  * CHANGED INTENT under the same Job refuses and leaves the first creation
    untouched.
  * INTERRUPTION BEFORE THE PREPARE leaves the harmless direction -- the
    install document names the Job, the configuration does not bind it, and
    no submission exists -- and the same command again finishes it without a
    second entry. INTERRUPTION AFTER THE BINDING leaves the binding published
    and no submission, and the same command finishes it. Neither leaves a
    stage a scheduler could offer.
  * REFUSALS: an unsupported source selection, a template this build does not
    carry, an override value nothing can mean, and a Job store belonging to
    another deployment. Each leaves the configuration and the install document
    exactly as they were, and the foreign store is never created.
  * PACKAGED RESOURCES: the template the answer names is the one this build
    carries, with the roles the submission's stages were resolved from; and
    the selector the install emitted carries the runtime digest and the schema
    assets the admission reported, read back off the instance.

WHAT STANDS IN, NAMED. The one-folder RUNTIME is `test_bootstrap`'s stand-in
directory and nothing here executes it; `_identity_of` is patched exactly as
that suite patches it. The CONTROL STORE is created by one
`ControlStore.open`, which is what a deployment's manager does on its first
run; the creation opens it read-only and reads only the instance guard. No
container engine, no provider, no serving loop, and no version control:
`--no-repositories` is passed and the installed workers' sources are
directories.

AND THE CLI'S REFUSALS ARE EXCEPTIONS, not exit codes: `job_manager.main`
parses, dispatches and catches nothing, for every command. The suite asserts
the typed refusal rather than a surface this CLI does not have.
