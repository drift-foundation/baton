===================================================================

The canonical tree is not edited, so every run is on a disposable scratch root
built from the canonical bytes at the accepted base 19f02ce1 with the
candidate overlaid. The base root is built the same way with no overlay, so a
base/candidate diff compares BYTES and not environments.

  base root       /tmp/w361912-base
  candidate root  /tmp/w361912           (candidate-362657 overlaid)

Each root is <root>/v12/python + <root>/v12/worker + <root>/v12/DESIGN.md and
the v12 JSON files + <root>/AGENTS.md + the one published result-manifest
vectors subtree under <root>/work/records/2026/08/... that
tests/manager/test_output.py and tests/job_manager/test_review_driver.py read
by `parents[4]`. Keeping the `v12` directory level matters: without it the
repository root resolves one directory too high and ~354 suites fail on a

What was NOT run, and what is NOT proved
----------------------------------------

Read this beside PROGRESS.md's "Remaining scope" section, which states the
same limits as scope rather than as test selection.

No provider, no container engine, no Authority, no installed instance and no
deployment. The Job stores these cases open are the disposable SQLite files
tests/job_manager/fixtures.JobManagerCase creates under a temporary directory;
the Authority, the host guard and the deployment binding are stand-ins that
record what they were asked. The compatibility generation is moved with
unittest.mock.patch in the test process only. No Git operation of any kind, in
the repository or in the scratch roots.

Specifically NOT proved by anything here:

  * `creation_ports.NewJobBinding.create_binding` is not driven against an
    installed instance. It composes `bootstrap.prepare` through the inherited
    `DeploymentBinding` writer lock and atomic install write, and the whole
    tests.tools.test_bootstrap suite runs beside it with no added failure --
    but no case here installs an instance and then creates a Job in it end to
    end. `DeploymentDerivation` IS driven against a real owned deployment
    document; this half is not.
  * the connected implementation -> independent review -> changes-requested
    correction -> failed/held result cycle for a CREATED Job. The cases stop
    at a recorded, bound, servable Job whose review stage the real projection
    reports `blocked` behind its implementation.
  * the OBS-0 input-to-substantive-simulated-work interval. Nothing here
    measures it and no figure is offered.
