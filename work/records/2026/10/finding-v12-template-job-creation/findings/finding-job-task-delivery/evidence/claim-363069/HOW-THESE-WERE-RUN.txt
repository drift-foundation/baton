What is proved here, and what is not
------------------------------------

PROVED. The composition and the identity, which are the two halves the
parent's R3 showed must move together:

  * each created Job's own `baton.dogfood-task/2` document, composed from the
    installed one with exactly `task_id` and `instructions` substituted —
    `verification`, `source_root`, `source_profile` and `declared_base` travel
    as the deployment wrote them, asserted member by member;
  * the per-Job input manifest whose `human_contract` names those bytes, with
    `manifest_digest` recomputed by §12's rule and the whole document proved
    by `check_manifest_structure`; no digest check is weakened anywhere;
  * the Job's `input_digest` IS that manifest's Job-scoped identity, so the
    two agree by construction, and `creation._task_agrees` refuses inside the
    operation before anything is reserved if they ever do not;
  * two distinct tasks on one pool get two distinct identities, neither of
    them the installed one, and BOTH stages of each are servable — asked of
    `stage_execution.servable_workers`, the scheduler's own function, which
    the parent's R3 proved impossible before this;
  * determinism, so `single_worker._proved_task`'s restart comparison is a
    comparison of one rendering;
  * a Job with no own task still serves the installed one, asserted rather
    than assumed.

NOT PROVED, and this is the gap that remains open — see PROGRESS.md, which
names the exact code points. `stage_execution` composes
`single_worker.worker_operations(one["deployment"], ...)` ONCE PER WORKER for
the implementation and review roles (line ~6656), not per bound Job. So the
`_SingleWorker` that runs those stages still holds the INSTALLED `task_bytes`
and `input_manifest`, and `_input` publishes the installed task into the
attempt's input root. The selector now agrees about the per-Job document and
the integration role is composed per bound Job and gets it; those two roles do
not yet. No connected execution rehearsal is claimed and none is run here.

No provider, no container engine, no installed instance, no deployment. The
Job stores are disposable SQLite files under temporary directories; the
deployment documents are tests.tools.test_stage_execution's own fixture, owned
by `stage_execution.held_configuration`. No Git operation of any kind, in the
repository or in the scratch roots.
