## Observed baseline

creation._asked returns the owned full request plus derived Job/submission IDs and digest(taken). create_template_job forms minimal operands {job_id, submission_id, request_digest}; job_signature(CREATE_KIND, operands) is canonical signature text, not that request digest. Completed replay precedes deployment derivation. The three existing cuts are reservation/acquisition, Authority authorization plus deployment binding, and submission/completion. A queue cannot reconstruct its input from the minimal operands or discard partial effects after a crash.

InstanceOwnership.held borrows the counted instance guard; invocation holds a separate per-Job flock, including within one process. Neither says the request is eligible or that a retired identity may execute. DeploymentBinding._publishing already serializes configuration publication across threads/processes via .fresh-attempt.publication. _bind publishes install inputs before configuration; interruption can leave the first ahead of the second. Reading either file without the owner lock does not establish a coherent generation. Manager death cannot be inferred from a released invocation lock.

Worker state-work.json is published as dispatched before handle, hence before possible adapter refusal and before substantive work. STATE_SCHEMA has no timestamp. Query observed_at is not a worker event. Persisting received_at after input/config validation would omit part of OBS-0. These are observed facts, not proposed instrumentation already present.

## 1. Full immutable request and selected snapshot

Retain **the complete creation._asked(request)[request]**, encoded with contracts.canonical_bytes. Preserve presence/absence of optional fields exactly as current ownership does; do not fill a changed default before request identity or silently equate omitted and explicit values. Current closed request/1 contains schema, task, source_selection, scope, acceptance, optional template and overrides. Task contains task_id and statement, optional job_id/submission_id; scope has work/tests. Nested semantics/bounds stay with existing templates/creation validators. Store statements, criteria, scopes and override values, not paths to mutable operator input files. The accepted task/input representation and derived selected source records are retained through the owners below; credentials remain references, never copied secret material.

Definitions, all distinct:

- job_id/submission_id = existing derivation from owned caller identity; create_operation_id unchanged.
- journal_signature = job_signature(CREATE_KIND, {job_id, submission_id, request_digest}); retain its exact current spelling for legacy replay.
- snapshot_bytes = canonical_bytes(snapshot/1 below); snapshot_digest = digest(snapshot). It is provenance, never substituted into the completed-create request signature.

Propose closed `baton.v12.creation-admission-snapshot/1` with exactly schema, instance_identity, configuration, install_inputs, configuration_digest, derivation, resolution, resolution_digest. Each nested object is a full owned copy under its existing reader: instance identity is the existing instance owner identity document, configuration is the complete stage deployment (including approved /3 when selected), install_inputs is the full installed bootstrap selection, derivation is the complete approved derivation/1 or legacy supported response, resolution is full resolution/2 or legacy /1. No new member is inserted into those approved schemas. Configuration digest binds the ordered pair {configuration, install_inputs}, not a wall-clock revision. resolution_digest uses the existing resolution owner. Whole snapshot <=4 MiB UTF-8/depth32, duplicate keys/nonfinite JSON/unknown top-level keys refuse. Apply tighter existing nested bounds too. Hashes are canonical SHA256; none authenticates unreviewed installed capabilities.

Retain complete per-role derivation inputs/manifests and capability documents through the approved derivation/resolution owners. No secondary execution-basis projection is proposed: comparison uses the full captured configuration pair, with only the exact additive-binding exception below. This avoids a new subset that might accidentally omit an admission or launch input. No task/policy defaults are recomputed after enqueue.

Configuration comparison permits only unrelated additive Job bindings to differ from the captured pair. Every non-job-binding member must remain canonically identical for performance. In job_bindings/install jobs, all previously captured entries must remain identical; extra entries may name other Job IDs, while this Job's new entry must equal this request's intended binding. No removal, replacement, worker tuple change, default change, policy change or descriptor change is admitted as “unrelated.” This deliberately conservative rule avoids silently rederiving a queued selection; routine independent Jobs still coexist. A mismatch before any effects is terminal refused; after partial effects it is recoverable-held, never a new derivation or rollback of another owner.

## 2. One stable configuration owner, not a revision label

Extend DeploymentBinding with public `snapshot_for_admission(request)` and `with_publication()` owner APIs using the existing publication flock; do not add a second lock file or config database. The snapshot reader takes the same lock as writers, reads both files once, verifies their canonical consistency and the installed instance, owns immutable bytes and resolves/validates the final task/manifests/capabilities while outside DB transactions. If install-inputs is ahead after interrupted publication, the read path reports configuration-recovery-required; it repairs nothing. The instance-owning performer uses the existing idempotent binding reconciliation to finish that exact recorded publication before accepting new queue work. No half-published pair is called a snapshot.

All supported configuration publishers, including bootstrap/reconfiguration and fresh-attempt/ordinary binding, must take this owner lock. Pure snapshot reads may take an exclusive lock initially for a simpler bounded contract; a future shared-reader optimization is unnecessary. External file edits outside the owner are unsupported and fail digest/type validation. Publication is bounded and cannot invoke provider/runtime launch; no arbitrary callback occurs inside a DB transaction. A routine caller reads and validates before intent insertion, then **keeps this publication lock until the short Job-store enqueue transaction commits**. This bridges validation and effect without a cross-store transaction: publication cannot race the insertion, and the transaction copies already-owned data only. Release immediately after insertion.

Lock order is instance guard (performers only), per-Job invocation (performers only), configuration publication, then short Job-store transaction. Queue-only callers take publication then Job-store, never try to acquire instance guard while holding publication. No DB lock is held while acquiring a file lock or reading another owner. Retirement takes only the Job transaction. Every call site must follow this order; no in-process count is treated as exclusive serialization.

Serving performs at most one admission/recovery invocation per reconcile iteration, through the same in-process execution lane as configuration mutation and dispatch selection. Threaded/direct entrypoints still take the owner locks; “one per tick” alone is not the safety argument. Routine configuration changes while serving are additive binding publications only. Changing workers/capabilities/source/policies requires stopping/excluding serving and explicitly qualifying replacement configuration; do not enable live incompatible config replacement in this Work.

Before offer/allocation and before external launch, use retained resolution and snapshot plus current owner snapshot under that same configuration/execution lane. Revalidate the approved predicate and actual selected worker tuple. Bind the exact compared inputs to the existing allocation/launch intent; after publication lock release, launch consumes these immutable bytes under the existing token/activation ownership checks. Relevant configuration replacement is forbidden while such work is active/in-flight, so no post-check mutation can reinterpret it. Distinct role runtimes remain distinct; shared logical input identity never requires full per-role runtime manifests to be equal.

## 3. Shared direct/queue ledger and linearization

Propose Job-store `creation_admissions`, keyed by job_id with unique create_operation_id. Columns: job_id, submission_id, operation_id, request_bytes, request_digest, journal_signature, snapshot_bytes, snapshot_digest, state, revision, performer, received_at, selected_at, outcome. revision is a nonnegative CAS counter; performer is null or the current incarnation plus invocation ordinal. received_at is optional UTC provenance from the outer CLI receipt (not the OBS-0 stopwatch); selected_at is manager time of first insertion. Neither affects request identity. outcome is null or an owner result/refusal reference, never an independent fabricated completion. States: pending, performing, recovering, completed, refused, retired.

Public creation-owner APIs: `submit_admission(request, snapshot)`, `claim_admission(job_id, expected_revision, performer)`, `resume_admission(...)`, `retire_admission(job_id, request_digest, expected_revision)`, `admission_status(job_id)`. The only effect executor remains create_template_job using the existing cuts. Refactor its entry gate, not duplicate authorization/binding/submission in the CLI. Direct calls must enter this same gate, including legacy public API callers; no hidden direct path may bypass a retired/refused row.

1. Own caller request and check completed CREATE journal replay before reading current config. Identical legacy completion returns existing result even if configuration is gone; changed request collides. It need not create a queue row. This is history replay, not authority to dispatch. Existing row if present must agree with the journal; inconsistent terminal data is an integrity refusal, not a choice of whichever says success.
2. If no completion, look up admission row. Same digest joins its exact state; different digest under same Job ID collides **even pending**, before any new derivation. Retired/refused returns its stable terminal answer; never reconstruct it as new work. Missing row proceeds to stable snapshot and pure compatibility validation described above.
3. Under publication lock, recheck the CREATE journal and existing admission row inside the same insertion transaction (a concurrent completed result wins), then insert request and full snapshot atomically with pending state after validation. Concurrent insert compares request digest; matching caller joins the winner's snapshot, not its independently computed alternative. Changed caller collides. Every field needed after process death is now durable before queue effects.
4. Performer holds instance and invocation guards, then atomically CAS pending to performing. Retirement atomically CASes pending to retired. Whichever commits first wins; retirement after performing/recovering refuses busy/incomplete even if CUT A has not yet occurred. There is no concurrent retirement rollback of external effects. It may retry only while the row is genuinely pending.
5. Under owner locks the performer validates retained snapshot vs current coherent configuration and approved descriptor predicate, then uses **retained derivation/resolution** for CUT A. Do not call current _resolved again to decide a new contract. Existing template-job reservation is linked to snapshot_digest and must agree; allocation of that provenance is a proposed extension to the creation owner, not an unversioned change to capability/1.
6. Completion is the existing CREATE journal outcome. Row completed is written in the same Job-store completion transaction where possible; after a crash a reconciler derives it only from the exact journal signature/result. Terminal refused is allowed only when no creation reservation/authorization/binding/submission exists and the refusal is definitive (unsupported or changed selected config). Once any cut has effects, row stays recovering with a bounded owner failure reference. No “refused” outcome pretending zero effects, and no ID reuse.

A queue row is a request/eligibility owner, not a second owner of creation success. Retired/refused tombstones are retained permanently by Job ID for this version; no TTL or automatic deletion. For changed intent use a new Job identity. A later direct API sees the tombstone too. Request bytes cannot be edited to “retry with a fix.” Current submission/CREATE signatures remain authoritative for completed legacy requests.

## 4. Stop, timeout and recovery

`create` waits by default for actual completed/refused/retired outcome; proposed `--no-wait` returns an explicit queued receipt, not the current created result. Wait timeout/interruption exits nonzero with stable operation locator and leaves request state unchanged. A failed client reply cannot cancel a committed request. `manager creation-status` is read-only; `manager retire-creation` takes Job/request digest/revision and changes only pending eligibility. Terminal refusal/retirement is durable and distinct from a transient read/lock failure.

The CLI may try the nonblocking instance guard **before** enqueue/performance: if available it can perform directly after submitting through the common ledger; if unavailable it queues and waits. It never polls a PID or interprets guard presence as proof a functioning consumer exists. Manager stopping after enqueue leaves a durable pending request; the caller times out honestly. A later manager or direct caller can take the guard and same invocation lock and continue. A successful `--no-wait` proves durable receipt only. Stopping a manager is not retiring its pending requests.

Recovery does not change performing to pending or erase its snapshot. A new invocation holding the per-Job lock proves only that no *conforming admission invocation* holds that lock. It does not prove the whole old manager died, nor that an external owner effect finished. Only the current instance owner may CAS performing to recovering under an expected row revision, then reconcile exact existing cut records. Old invocation results must carry the current performer/revision CAS when updating the admission row; stale completions cannot overwrite it. Owner effects still replay under their original stable IDs, not performer IDs.

| Durable cut | Recover with original request and snapshot |
| --- | --- |
| Before enqueue | No admission exists; ordinary new submission after validation |
| Enqueue committed, no performer | Pending; same request joins, changed request collides, retirement may win |
| Claimed, before CUT A | Recovering; validate retained config, inspect owner records; do not assume no effects merely from a stale row |
| CUT A reservation/acquisition | Adopt exact existing reservation and retained resolution; no second identity or rederived defaults |
| Authority effect committed, binding absent | Read/replay original authorization operation and binding through their owners; no guessed Authority result |
| install-input published, configuration incomplete | Under publication lock reconcile original binding; block new snapshots/dispatch requiring an inconsistent pair |
| CUT B complete, servability/submission refuses | Keep recovering with exact published facts; no terminal zero-effect refusal or automatic rollback |
| Submission committed, CREATE reply absent | Replay submission and finalize exact CREATE result; never admit twice |
| CREATE committed, row stale/client disconnected | Journal result repairs row/answers caller; current config need not validate completed history |
| Unknown external operation outcome | Held recovering until owner can reconcile; lock release/timeouts are not effect settlement |

A pre-effect configuration mismatch after claim may become refused only after the creation owner proves no reservation/effects exist, including stable journal lookup. Any inability to establish that absence stays recovering. Serial different-Job admissions merge bindings through the same publisher: Job B's unrelated additive binding neither erases A nor changes A's contract. Subsequent dispatch always rechecks retained selection; completed-create replay is not a compatibility bypass.

## 6. OBS-0 whole-path evidence, without false timestamps

Proposed deterministic measurement uses one external monotonic-clock harness; no change to frozen state/1 and no invented worker timestamp. **t0** is immediately before handing the complete task description and selected input-file handles/paths to the supported CLI entrypoint, before opening/reading/parsing files, hashing, importing configuration, validating or queueing. Starting the subprocess inside this interval conservatively includes launch overhead. For API tests t0 precedes the public API's receipt of caller inputs, including serialization required by that boundary. No preparatory parse/hash/cache warming unique to this request is allowed before t0. Report any one-time package installation/image availability assumptions separately under OBS-0a.

**t1** is when the real selected adapter, after input validation and provider dispatch, reaches a task-specific action confirmed by the harness. In deterministic proof the fake provider at its normal boundary signals only when it begins executing the selected first workload action (for example opening the requested source to perform the task), not merely when called, authenticated or sent a prompt. Instrument the fake's actual action, correlate it to exact Job/stage/episode/attempt and request digest, and record t1 on the same harness clock. The real coordination/adapter path must reach it. A negative pre-provider refusal yields no t1. Capture event delivery locally; if delayed IPC is used, the receiving timestamp gives a conservative upper bound, with this method disclosed. Do not subtract UTC worker/status timestamps across hosts.

Report elapsed=t1-t0 including input handling, queue wait, configuration, validation, store admission, serving, allocation and launch. Required target remains <=60s, not a new timeout or a reason to delete requests. Capture wall timestamps for attribution only, monotonic readings for duration. A delayed queue or intentionally stopped manager is still elapsed waiting; report >60s or no endpoint, never reset t0 at claim, retry or manager start. A replay benchmark is labelled replay latency and cannot replace fresh-start evidence. On crash/restart, the original external harness may continue timing; if its monotonic continuity is lost, whole-path result is unknown, not reconstructed from incompatible clocks.

For real providers, t1 requires attributable substantive task activity, e.g. a supported correlated tool/source action actually started. Current state-work=dispatched, receipt, provider process start, first stream byte and status observed_at are **insufficient**. If no suitable observable exists, record endpoint unknown and do not claim live OBS-0 compliance. This proposal adds no product telemetry wire; it recommends external deterministic evidence now and explicit future provider instrumentation selection only if a live-specific question requires it.

A fake provider/engine proof establishes latency only in its declared simulated environment. Record package/source identities, local host, warm/cold caches, CPU/storage, queue depth, image assumptions, provider/engine simulation, exact command/inputs and signal mechanism. It does not certify real engine startup, image pull, authentication/model latency or live task progress. Reuse applicable live evidence, without claiming old dispatch logs supply this endpoint.
