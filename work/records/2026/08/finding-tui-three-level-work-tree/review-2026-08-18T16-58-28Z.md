## P1 — batch the three-level window reads

`projection.tree()` calls `children_of(base)` once per root and then
`children_of(child)` once per visible depth-1 row. The new third level therefore
adds one SQL statement for every visible child on every two-second TUI refresh.
The regression itself currently blesses that growth: after adding a second
depth-1 row, `test_the_window_reads_do_not_grow_with_the_tree` asserts
`small + 1`, contradicting both its name and its claim that the window reads are
bounded by the number of levels.

Fetch each level as one ordered batch, group rows by parent in memory, and make
the regression prove that adding roots, children, or grandchildren does not
grow the window-construction query count. Per-row projection reads are outside
this finding, as the test already notes; the newly introduced per-parent
containment reads are not.

## P1 — make the projection version honest

`jsonapi.py` promises that every response in one projection major is compatible,
yet 10.1 adds a new value (`2`) to the previously consumed `depth` domain and
explicitly acknowledges that a major-10 client may mis-render it. That is an
incompatible consumer-visible change under the file's own rule, regardless of
whether the failure is called a mis-render or a misread.

The repository contains the concrete counterexample:
`tests/work/test_parity.py::_parse_rows` maps only a leading `↳ ` to depth 1
and everything else to depth 0, so the new `  ↳ ` depth-2 row is decoded as a
root. No three-level parity case exercises it. Use an honest new major and
update the readiness consumers in the same candidate, or first establish an
explicit open-ended depth contract and prove every supported major-10 consumer
handles arbitrary non-negative depths. Merely documenting that some old
clients draw the wrong tree does not satisfy same-major compatibility.

## P1 — extend JSON/TUI parity through depth 2

The acceptance contract says canonical `tree` JSON and the TUI expose the same
bounded window. The parity parser cannot represent depth 2, and
`test_containment_children_agree_inline` checks only rows whose JSON depth is 1.
Add a root/child/grandchild/fourth-level fixture that compares identity, order,
depth, title prefix, and `deeper` between both surfaces. This is distinct from
the W155 renderer-only tests: it verifies the promised cross-interface parity.

## P2 — update the live operator and code contracts

Several current sources still state that the main view is two levels:

- `docs/BATON-WORK.md` says the main screen is a two-level tree;
- `Console.view()` and the `u` handler describe a two-level window;
- the `baton_work.tui.app` module description still describes the older drill
  model;
- active TUI/search test descriptions still say two-level.

Historical findings should remain unchanged, but live product documentation,
docstrings, and active test descriptions must describe the three-level model
before this Work closes.

## Disposition

Changes requested. Preserve the working rendering behavior while correcting
the batched read boundary, version contract, parity coverage, and live docs.
