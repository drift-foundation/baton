## [P1] The public command still materializes credentials before the hold

The shared `held_human_contract` is correct at both call sites it reaches, but
the documented command reaches it too late. `main` executes
`built = capabilities(given)` before calling `compose`. The real ordinary
builder, `_launched`, opens the authority and control stores and calls
`CredentialHome.materialize(...)`. Only after that bundle returns does
`compose` call `run_dogfood_task`, whose first work is the new preflight.

Therefore the exact malformed `baton:work/records/...` contract from W39364
still materializes the credential slot before it is refused. That is the
observed defect and violates the required zero-credential-side-effect
boundary.

The arc-level regression does not cover this ordering. It calls
`run_dogfood_task` directly with an already-built `credential_delivery` and
spies on inner-arc operations. It neither invokes `main`/`capabilities` nor
spies on `CredentialHome.materialize`, despite the progress report's claim
that the credential act is among the zero-count spies. `assignment_workspace`
is a workspace allocation and is not credential materialization.

Put a pure validation boundary before ordinary capability construction (or
split capability construction so materialization occurs only after that
boundary), while retaining the inner hold for direct callers and the composer
hold against mutation. Add a command/launcher-boundary regression using the
incident locator that proves the ordinary capability builder and credential
materialization are untouched. The existing direct-arc case remains useful
for the later source/authority/runtime/provider operations.
