## Result

## Findings

### P1 — The two-target template documents a one-target policy installation

`conf/codex-event-bridge.template.json:7-12` shows one generator invocation
with one `participant=<team.member>` and redirects it with `>` into the shared
`execPolicyFile`. The same template configures both `baton.codex` and
`baton.tuner` at lines 28-45. `EventBridge.start()` iterates every configured
target identity and calls `assertPolicyProvisioned()` for each against that
one file (`tools/codex-event-bridge/src/event_bridge.mjs:147-155`).

Following the shipped command once therefore leaves the other target missing
all four rules and startup refuses. Repeating the command as written does not
help: `>` truncates the first participant's rules before writing the second.
A standalone operator still cannot follow this release's own instruction to
produce the policy its shipped configuration requires.

Keep the singular strict generator interface, but document that it is run
once per `targets.*.identity.participant`, with every output combined into one
complete deployment-owned file before installation. Add an actual deployed
artifact regression which generates the combined policy for the template's
two identities and proves the deployed `assertPolicyProvisioned()` accepts it
for both. Prefer staging the complete output before installing it rather than
truncating the live nominated file before operand validation runs.

### P2 — The overwrite regression never checks the existing file's bytes

`tools/codex-event-bridge/test/exec_policy_cli.test.mjs:55-63` writes
`baton.rules` with `untouched\n`, invokes the generator, and then asserts only
that the directory still contains a file with that name. An implementation
that overwrote the existing file in place would pass this test, despite the
test's claim and the dossier's required creates-and-overwrites-nothing
boundary. Read the file back and assert its bytes remain exactly
`untouched\n`.

### P2 — “Same artifact the dispatcher imports” is not the deployed shape

The template says the generator is installed “beside the dispatcher,” and
several new comments/tests claim that the deployed module is the same artifact
the dispatcher imports and therefore cannot drift. The canonical shipped
`conf/infra.example.json` runs the dispatcher from
`<baton source>/tools/codex-event-bridge/bin/codex-event-bridge`; the v11
distribution has no `bin/codex-event-bridge`. `SOURCE_SHARED_GATE` installs a
byte-equal copy under the release's `lib/`, but it is a different filesystem
artifact from the source module imported by that dispatcher.

The byte-parity regression is the correct release boundary. Replace the
one-artifact/beside-dispatcher claims with the confirmed statement: the
release carries a byte-equal immutable copy of the reviewed source helper.
Do not imply that this Work also co-deploys the generic dispatcher.
