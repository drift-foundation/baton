# Review — WS-5 effectively-once retry design, first pass

Date: 2026-08-15T15:27:39Z
Reviewer: `baton.reviewer`
Disposition: design changes requested before product rulings

The design correctly inventories the mutation surface and gives a credible
one-transaction fingerprint/result replay model. P1/P2/P5/P6a/P8/P9/P10 are
real product choices, but three internal contradictions must be corrected
before Slawomir is asked to rule on them.

## R76 — a successful no-op cannot leave its operation identity unused

**Confirmed.** Section 4 says `seen_discussion`'s idempotent/no-advance success
stores no operations row. The same document says an operation identity names
the caller's intended mutation, detects conflicting reuse, and makes the
result recoverable. Those claims cannot both hold: after a successful
no-advance `mark-seen`, the same `(participant, op_id)` could be used for a
different request, or an exact retry after a later cursor advance could return
a different result.

Revise the design so every successful op-id-bearing invocation consumes the
identity and stores its replayable result, including a domain no-op. Preserve
the ruled absence of a duplicate domain event/sequence for an idempotent seen
mark: define whether the operation record may have a nullable domain-event
sequence or another honest locator, and prove its bookkeeping transaction does
not invent a Work/message/seen event. A refusal still need not consume the id.

## R77 — generation-1 init has no participant or existing-authority retry path

**Confirmed.** The proposed primary key is per participant, but current `init`
runs before `_need_participant`; it validates no acting identity. Its lifecycle
also refuses an existing destination before opening it, whereas exact retry
after a lost successful init response must open the published authority and
look up the operation record before returning “already initialized.” Merely
placing a row in the newly created database does not supply either missing
half.

Specify the full init contract: whether init newly requires a participant that
must exist in the generation-1 document, how its fingerprint and actor are
formed before authority publication, and how an existing destination is
validated/bound and checked for exact/conflicting retry without turning an
unrelated database into a replay oracle. If init remains included, cover
concurrent initializers, lost response, mismatched config/authority, different
participant/id, and ordinary existing-destination refusal. Otherwise return
init exclusion as an explicit product choice rather than claiming P9 is
already implementable.

## R78 — the optional guarantee is not visible in the proposed envelope

**Confirmed.** Section 2 says the JSON envelope makes the strong/weak retry
tier visible. Section 6 adds only `already_committed`, whose false value is
shared by both a fresh protected commit and an unprotected id-less call. An
agent therefore cannot tell from its successful result whether the operation
was durably replayable.

Define explicit structured result state—at minimum the accepted operation id
or null plus an unambiguous protected/unprotected guarantee marker. Preserve
the original sequence and `already_committed` replay distinction. Specify the
shape for successful no-ops from R76 and for init/regen from R77. If P2 becomes
mandatory the weak tier disappears, but the accepted id still needs echoing so
the caller can correlate the result it retained.

Revise only `WS5-DESIGN.md` and the design disposition in `PLAN.md`; do not
implement or touch source/schema/tests/PROGRESS. Return the corrected model and
the final concise product-choice list for Slawomir.
