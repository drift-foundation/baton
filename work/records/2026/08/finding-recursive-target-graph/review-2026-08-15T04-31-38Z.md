## Recommended dispositions

1. **Approve D1 Option A.** Creating an exact `@` obligation grants its live
   route handler one narrow authority to accept that request by atomically
   gating exactly the requesting Work on provider Work. It does not move
   Current, grant general consumer ownership, or survive terminal disposition
   of the obligation.
2. **Use the obligation-route gate only for `--into`, plus same-team/open
   provider checks.** Do not also require the actor to be the provider Work's
   Current handler. Incoming bug triage must still converge later reports after

   the provider's current endpoint snapshot for evidence, not as a second

3. **Add terminal obligation status `accepted`.** Reusing `responded` would

5. **Permit optional `--parent`, only when the accepting actor also passes the
   existing live parent-Current handler gate.** The common root case remains
   available when that additional authority is absent; no general containment
   delegation is introduced.

## R47 — acceptance may wake an obligation waiter

The draft says acceptance cannot wake because it adds a gate. That is only true
for a Work waiting on all gates. If the consumer recorded this exact obligation
as its wake condition, terminal `accepted` satisfies that condition just like
`responded` or `disposed`: it atomically wakes to `queued` after the new edge is
installed. The new blocker keeps `ready` false; the consumer then explicitly
decides whether to enter gates-waiting. No automatic conversion from
obligation-wait to gates-wait is permitted.

The implementation matrix must cover both wait types and prove the edge,
obligation terminalization, readiness recomputation, and any wake act commit
as one unit.

## R48 — compound audit ordering must not lie

The draft calls for a nested `create_work` act followed by the primary `accept`
act. The current `_write` allocator assigns the primary act's sequence before
its mutation; an `_emit` inside that mutation necessarily receives a later
sequence. Implemented literally, history would order `accept` before the Work
it claims to accept into.

The implementation plan must choose an honest compound event layout before
coding. The recommended minimal layout is for the primary `accept` act itself
to be the creation act when `created: true`: its sequence creates the provider
Work and its initial provider message, and its payload fully records the
creation fields. A later in-transaction response-message act may carry the
consumer-visible rationale if the two messages require distinct sequence ids.
No redundant `create_work` act is required. Any alternative is acceptable only
if total sequence order says the provider Work exists no later than the act
that associates the consumer with it.
