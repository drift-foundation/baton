## R1 — Thread subject is absent from the effectively-once fingerprint

**Confirmed defect.** `create_thread()` calls `_operation()` before validating
or adding `subject` to the fingerprint payload. Repeating one `op_id` with the
same body/labels/references but a different subject therefore replays the first
Thread instead of refusing a different request. This contradicts the claimed
WS-5 coverage and can silently attach the wrong subject to an agent's intended
operation.

Required correction: normalize/validate the subject before operation lookup
and include that normalized subject in the typed fingerprint. Identical retry
must replay; changed subject under the same participant/op-id must refuse with
no authority residue.

Regression added in `tests/work/test_w31_threads.py`:
`test_the_subject_participates_in_the_effectively_once_fingerprint`.

## R2 — automatically born Threads bypass the subject contract

**Confirmed defect and one explicit product choice.** `create_work()` inserts
its Work title directly as the born Thread subject, while `create_thread()`
requires a normalized, non-empty, single-line subject of at most 80 UTF-8
bytes. Work titles currently permit embedded newlines and values beyond that
limit. The authority can therefore contain a Thread subject which its own
public validator refuses.

Recommended correction: make Work titles pass the same subject validator
before operation lookup and storage, then use that one normalized value for
both the Work title and born Thread subject. This preserves cheap atomic Work
creation without a redundant subject argument or silent truncation. Slawomir's
confirmation of that choice is required before implementation.

Regressions added in `tests/work/test_w31_threads.py`:
`test_the_born_thread_obeys_the_same_subject_contract` for an embedded newline
and an 81-byte value.
