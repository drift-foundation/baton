# W5 review round 4 — storage-change boundary requested

the implementation diff. `schedule_refresh()` is now the one producer hook,
`_cached()` is its one consumer, and repeated requests coalesce. That
architecture is aligned. Two review items remain.

## R7 — Successful verbs are not necessarily storage changes

**Confirmed.** `Console.execute()` schedules based on `code == 0` plus the
parsed verb belonging to `MUTATIONS`. That includes effectively-once operation
replays (`operation.state == "replayed"`) and successful no-op transitions such
as `mark-seen` returning `advanced == false`. The two direct `s` paths likewise
schedule even when their result says `advanced == false`.

The confirmed rule is narrower: commands which change storage schedule an
on-demand refresh. A replay or no-op changes no storage and must leave the
existing timer deadline/cache alone. Have the public command result determine
whether a new mutation committed, rather than inferring it from success plus
verb class. Direct `s` schedules only when it advanced. Add counted-read/due-
flag regressions for an operation replay and an already-seen `s`/`mark-seen`
remaining unscheduled, beside the existing committed-mutation positive case.
