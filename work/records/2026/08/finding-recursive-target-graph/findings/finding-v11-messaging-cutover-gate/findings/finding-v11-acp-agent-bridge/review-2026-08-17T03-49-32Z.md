# Review — W163 distribution round 1 — 2026-08-17T03:49:32Z

## Outcome

Changes requested. The bridge implementation and Slice B boundary remain
signed off, but this handoff does not yet co-deploy a usable bridge through the
actual v11 deployment command.

## R12 — The operator-facing v11 deployer omits the new product

The handoff adds the bridge and examples only to `tools/build_release.py`.
That is not the v11 deployment path. `just deploy-v11 DESTINATION` invokes
`tools/deploy_work.py`, which independently creates only `bin/baton`, `doc/`,
`conf/baton.example.json`, and `tmpl/`. It neither consumes the candidate made
by `tools/build_release.py` nor copies the ACP bridge or its examples.

Therefore the exact command used for every v11 trial would still publish a
release with no ACP bridge. Put the generic bridge, its examples, and its
runtime into the candidate assembled and atomically published by
`tools/deploy_work.py` (or deliberately replace that mechanism and wire
`deploy-v11` to the replacement). Do not certify a packaging path the operator
does not run.

## R13 — Post-deploy `npm ci` contradicts the immutable distribution boundary

The new `tools/build_release.py` comment and handoff explicitly leave
`node_modules` out and require the operator to run `npm ci` beside the shipped
lockfile. That is not a ready co-deployed product: it mutates an exact release
after its atomic publication, depends on npm/network state at the destination,
and makes the deployed bytes differ from the candidate the gate examined.

The pinned W163 boundary requires the generic bridge and its pinned runtime
dependencies to be part of the immutable distribution. Resolve dependencies
during candidate construction, before publication. A staged `npm ci` copied
into the candidate, a self-contained bundle, or an equivalent offline
dependency artifact is acceptable; a manual install in the published target
is not. A missing or unbuildable dependency must fail deployment before the
target becomes visible.

## R14 — No regression exercises the real deployed product

The handoff reports a scratch validation, but there is no committed regression
that runs the actual v11 deployer and proves the resulting release is usable.
Add coverage that deploys through `tools/deploy_work.py` (the mechanism behind
`just deploy-v11`) and establishes at minimum:

- the target exposes stable product entry points for both `baton` and the
  generic ACP bridge;
- Claude and Gemini example configurations are present and inert/non-secret;
- all pinned bridge runtime dependencies are already in the target;
- the bridge can run from the target without the source checkout, host
  `node_modules`, `npm ci`, or network access;
- executable modes and the published layout are correct; and
- incomplete dependency assembly refuses before atomic publication.

The current nested path `tools/acp-baton-bridge/bin/acp-baton-bridge` is a
source-tree snapshot, not a distribution-level product entry point. Use a
stable release layout such as `bin/acp-baton-bridge` plus a private runtime
directory, or pin an equally explicit alternative in the owning finding.

`git diff --check` is clean. Full gates were not rerun because these static
deployment-path contradictions are independently decisive.
