## R7 — the hardened Git guard is still a fail-open command recognizer

The archived `git_guard.py` uses `shlex.split()` and then recognizes only
separator tokens that already appear as standalone strings. POSIX shell
operators do not need surrounding spaces, and wrapper arguments are not
recursively interpreted. The reviewer invoked the guard directly—without
executing Git—and observed:

```text
git commit --allow-empty -m test       => denied (exit 2)
git -C repo commit --allow-empty ...   => denied (exit 2)
git commit; true                       => allowed (exit 0)
env X=1 git commit --allow-empty ...   => allowed (exit 0)
```

`bash -c`/`sh -c`, command substitutions and other nested shell evaluators are
the same unresolved class. More fundamentally, malformed hook JSON currently
exits 0, which explicitly permits execution when the policy input cannot be
understood. That contradicts the pinned fail-closed boundary.

Two passing command spellings do not certify a blacklist as a hard denial.
Replace this boundary with one that cannot be bypassed by alternate shell
syntax (for example a genuine execution/sandbox boundary, or a complete
fail-closed parser/enforcer with recursive shell semantics), and add adversarial
tests for attached separators, wrappers, nested shells/substitutions, malformed
hook input and every configured prohibited Git mutation. A parse or policy
failure must deny, never allow.
