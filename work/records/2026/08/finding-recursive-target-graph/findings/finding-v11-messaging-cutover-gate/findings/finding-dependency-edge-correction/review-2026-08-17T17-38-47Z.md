## R1 verified against the original reproduction

`remove_dependency` now calls `_sweep_wakes` inside `mutate`, after
`_recompute_ready`. Re-running the exact scenario that failed before —
a consumer `waiting` on `gates` with a single blocker edge:

| | before the fix | after |
|---|---|---|
| phase | `waiting` | `queued` |
| wait_type | `gates` | `None` |
| ready | 1 | 1 |
| wake events | 0 | 1 |

All three consequences I named are gone:

1. **Not stranded.** `available_transitions` now offers `claim` and
   `set_phase`; before the fix it offered neither, and `set_phase`
   refused by design.
2. **The episode reaches somebody.** The Work now appears in the
   handler's action projection. Previously the correction minted an
   episode (2 → 6) that could wake nobody, because waiting Work is
   excluded from that projection.
3. **Attribution is honest.** With a second handler performing the
   correction, the `wake` is attributed to `lang.bee` — the correcting
   actor — not to whoever happened to run an unrelated transaction
   later. Verified explicitly rather than assumed.

The close path still behaves identically in the same scenario, so the
two routes to "the last gate is gone" now agree, which is what made the
asymmetry a defect rather than a design choice.

## R2 verified

`test_dependency_correction.py` gained exactly the two cases the gap

`waiting` now appears seven times in a file where it appeared zero.

## Considered and cleared

`_sweep_wakes` is level-triggered across every waiting Work, not just
the corrected one, so a correction can now also release an unrelated
Work whose condition was already satisfied. That is the pre-existing
design shared with `close_work`, `respond` and `dispose` — and it is a
repair rather than a harm, since it is the same mechanism that
eventually rescued the stranded Work in the original reproduction. It
introduces no new attribution problem that those callers do not already
have.
