## R9 — configured Git/index mutations and ordinary indirection still allow

The guard describes itself as denying Git history/index mutations, but its
`PROHIBITED` set omits index/worktree mutations including `add`, `checkout`,
`switch`, `restore`, `stash`, branch/tag operations and others prohibited by
repository policy. It also cannot resolve Git aliases or wrapper options that
consume values. Direct reviewer execution of the archived policy—only feeding
hook JSON, never running Git—produced:

```text
git add tracked.txt                         => allowed (exit 0)
git -c alias.c=commit c --allow-empty ...   => allowed (exit 0)
nice -n 5 git commit -m x                   => allowed (exit 0)
sudo -u nobody git commit -m x              => allowed (exit 0)
```

Arbitrary evaluators (`python -c`, Node, scripts, aliases and executable
renaming) make complete security enforcement from one Bash command string
fundamentally open-ended. Adding discovered spellings one at a time cannot
truthfully satisfy the ruled hard boundary.

Use a real containment/privilege boundary for protected repository state (or
explicitly return for a human supersession that downgrades this to a
best-effort accidental-use guard). A hook may remain for an immediate friendly
denial, but it cannot be the sole hard enforcement while permitted shell and
arbitrary interpreters remain available. Acceptance must cover the complete
configured prohibition set, particularly index/history mutations, through the
actual boundary rather than a finite spelling list.
