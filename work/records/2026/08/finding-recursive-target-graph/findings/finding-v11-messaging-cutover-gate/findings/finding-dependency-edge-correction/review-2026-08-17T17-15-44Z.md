# Review: W122 dependency edge correction

Independent review by `baton.claude` against obligation #131. No
implementation file was edited; the reproduction below runs against the
committed tree from a scratch authority in `/tmp`.

## Result

Changes requested. The contract, authorization, transaction semantics,
retry identity, audit preservation and CLI surface are all coherent and
match the pinned FINDING. One concrete defect: correcting the last gate
of a Work that is explicitly `waiting` leaves it stranded in `waiting`.

## Accepted

- `remove_dependency` gates on the CONSUMER's live Current handler
  through `_handler_gate`, inside the committing transaction, exactly as
  `add_dependency` does. The optimistic pre-reads are all re-checked
  under the lock (Work status, blocker status, edge existence), so a
  stale correction loses honestly.
- The edge row is deleted while the `add_dependency` and
  `remove_dependency` events remain: history says how the mistake arose
  and why it was corrected, which is the point of the finding.
- `rationale` is required on BOTH verbs and carried into the operation
  fingerprint, so a retry that changes the reason is a conflict rather
  than a silent replay. That is the right call — it is what makes the
  correction reviewable rather than bare graph mechanics.
- Discovery is honest: `remove_dependency` is advertised only when a
  live edge with an OPEN blocker exists, which matches the operation's
  own refusal instead of inviting discovery-by-attempt.
- Historical edges (closed blocker) refuse by name rather than being
  quietly rewritten.
- `docs/BATON-WORK.md` states the correction and its historical-edge
  boundary.

## R1 — correcting the last gate strands a `waiting` Work

`remove_dependency` calls `_recompute_ready` but never `_sweep_wakes`.
Closing a blocker runs both (`close_work`), so the two paths to "the
last gate is gone" behave differently, and only one of them releases
the Work.

Reproduction from the committed tree — consumer `waiting` on `gates`
with a single blocker edge:

    before       : phase=waiting  ready=0  wait_type=gates
    after unblock: phase=waiting  ready=1  wait_type=gates
    open gates   : 0
    wake events  : 0

    CONTRAST, closing the blocker instead:
                   phase=queued   wait_type=None

Consequences, all observed rather than inferred:

1. The Work is stranded. `set_phase` refuses by design — *"is waiting on
   its recorded condition; waiting leaves only through the
   condition-bound audited wake"* — and `available_transitions` on the
   stranded Work offers no way out: `['add_dependency', 'classify',
   'close', 'create_child', 'create_trial', 'pass', 'prioritize',
   'request']`. There is no operation the handler can reach that
   releases it.
2. Waiting Work is excluded from the participant action projection, so
   the W49 assignment episode the correction mints (observed 2 → 6) is
   spent on a Work that can wake nobody.
3. It eventually escapes through an UNRELATED transaction. Closing a
   different, unconnected Work later swept it to `queued` — so the
   `wake` event lands in someone else's transaction, attributed to
   whoever happened to run it. The journal then reports a wake caused by
   an act that had nothing to do with the gate.

This is squarely inside the finding's own requirement to "recompute
readiness atomically and mint the ordinary unblock assignment episode
when the last gate is removed". Readiness is recomputed; the release is
not.

Required correction: run the level-triggered wake sweep in the same
transaction as the correction, exactly as the close path does, so a
`gates` condition satisfied by removing its last edge wakes with an
audited `wake` event attributed to the correcting actor.

## R2 — the suite has no `waiting` coverage at all

`tests/work/test_dependency_correction.py` is 7 focused tests and they
pass, but `waiting` appears nowhere in the file. The gap is exactly
where R1 lives: `test_removing_one_of_two_live_gates_does_not_make_work_ready`
covers the *remaining-gate* case, and nothing covers removing the LAST
gate from a Work that recorded a wake condition on it.

Coverage this needs: the last-gate correction wakes a `waiting`
consumer in the same transaction, with the `wake` event attributed to
the correcting actor; and removing a non-final gate leaves `waiting`
untouched.

## Not defects, recorded so they are not re-litigated

- Removing an edge cannot create a cycle, so the absence of a
  `_would_cycle` walk on the correction path is correct.
- Only the consumer's readiness needs recomputation; dependents are
  unaffected by removing `work → blocker`.
- Refusing to "correct" an edge whose blocker is already closed is the
  ruled boundary, not an omission.

## Verification

R1 reproduces deterministically on the committed tree; the contrast case
(closing the blocker) wakes correctly in the same scenario, which is what
makes the asymmetry a defect rather than a design choice. Reproduction
scripts were scratch files outside the repository. No implementation or
test file was modified during this review.
