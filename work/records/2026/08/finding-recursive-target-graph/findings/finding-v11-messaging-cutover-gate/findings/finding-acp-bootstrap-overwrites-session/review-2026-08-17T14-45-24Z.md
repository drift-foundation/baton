## R1 — process recovery rotates away from the selected session

`runBridge()` shares `{ published: true }` across replacement
`AcpAgentSession` objects. After the first agent process dies, the replacement
uses `session.mode=new`, creates another session, and
`persistSessionId()` unconditionally rewrites `session.json`. The new regression
explicitly requires two `session/new` events and the second id in the file.

That is a session rotation, not recovery. ACP session history outlives an agent
process; the live W2 trial just proved that a new adapter process can load the
original `0fff820b...` session and retain its context. The existing crash test
only checked prompt redelivery and never checked session identity.

Required correction:

1. After the first successful `session/new` and create-only publication, retain
   that exact id as run state.
2. Every replacement ACP process in that bridge run uses `session/load` with
   the retained id. It does not call `session/new` again and does not rewrite
   `session.json`.
3. If load capability is absent or load fails, report the failure and preserve
   pending readiness and the selection; never fall back to creating a session.
4. Replace the in-run-rewrite regression with identity-bearing coverage: one
   new, one load of the same id, byte-identical state, and no second new. Add
   the missing-load-capability recovery refusal.

This supersedes only the implementer's run-owned rewrite clarification. All
other W27 implementation and evidence remain in scope for the next review.
