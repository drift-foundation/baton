## Remaining corrections

### R3a — validate every field used to construct trusted instructions

The Work summary prefers `local_id`, interpolates `title`, and branches on
`claimed`, but the validator checks none of them. A malformed action such as a
correct `work:<full-id>` key plus `local_id="W999"` produces a trusted command
instruction for the wrong Work; `claimed="false"` is truthy and falsely says
the Work is already claimed. Validate the fields the trusted summary consumes
(including local-id agreement with the full Work id and boolean claimed), or
construct the command locator only from the already-validated full Work id.
Also require non-negative snapshot sequence and positive obligation/round/
generation integers rather than accepting structurally valid negative ids.
Add focused refusals for these cases. Optional descriptive fields may remain
optional, but if rendered they must have the promised type.

### R5a — make the documented live command true for this deployment

The README command names `/home/sl/opt/baton/v11/825e97d/bin/baton`, which is
the running projection-4.1 trial binary. The new monitor correctly refuses it
because W136's participant actions first exist in projection 4.3. The command
also names target `baton` and socket `/run/user/1000/codex-events.sock`; the
running stack maps this thread as target `baton-reviewer` on
`/home/sl/.local/run/codex-events.sock`. As written, the reviewed live proof
cannot start.

Document that the operator must first deploy a new immutable v11 candidate
containing W136/W148, then use that exact release's `bin/baton`, the existing
stack's configured target, and its configured socket. The concrete command for
this trial must resolve to `--target baton-reviewer` and
`--socket /home/sl/.local/run/codex-events.sock`; do not hard-code the obsolete
release hash as though it could speak the new projection.

Correct the rationale too: v11 `wait` is read-only and level-triggered. Two
waiters do not consume or steal authority state; they can observe the same
action and manufacture duplicate Codex turns. Exactly one readiness path is
still the required operational rule, but duplicate delivery—not destructive
consumption—is why.

Finally, remove or correct the source comment claiming the same wake never
duplicates "across restarts." Restart rediscovery is an explicit W148 feature:
the new process emits the still-current set again (the bridge may suppress a
very recent fingerprint inside its short dedup window). The implementation and
tests already have the right behavior; only the claim is wrong.

No live process should change before these narrow corrections receive
round-three verification.
