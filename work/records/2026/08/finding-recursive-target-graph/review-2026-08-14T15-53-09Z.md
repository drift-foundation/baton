## R1 — child reopen can race its parent closed

**Confirmed.** `reopen_work()` checks the parent before `_write()`, but its
in-lock recheck covers only the child's status. A competing close of the
parent can commit between those checks. The child then reopens successfully,
leaving an open child beneath a terminal parent.

The additive deterministic regression
`test_wf09_reopen_rechecks_that_its_parent_is_open_in_the_lock` reproduces the
interleaving and currently fails because no refusal is raised.

Required correction: read the child's live parent and revalidate that parent
is open inside the same write transaction before reopening. Use the in-lock
parent for the ancestor recomputation rather than the optimistic row.

## R2 — reopen can restore from an obsolete close event

**Confirmed.** `reopen_work()` reads the latest close event before `_write()`
and computes `restore_team`/`restore_kind` from it. Another process can then
commit a complete reopen/pass/close cycle. The original reopen sees the Work
closed inside its lock and proceeds, but restores the endpoint from the older
close rather than the close that is current at its serialization point.

The additive deterministic regression
`test_wf09_reopen_restores_from_the_close_current_at_commit` reproduces this:
the newer close records `lang.rev`, but the racing reopen restores `lang.bug`.

Required correction: select and validate the latest close event from the
transaction connection after acquiring the write lock, and derive the
restored endpoint there. The optimistic read may remain diagnostic only; it
must not supply committed state.
