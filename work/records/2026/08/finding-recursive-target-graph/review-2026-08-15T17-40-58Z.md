## R88 — one-shot multi-file scaffold is not crash-recoverable

The revised R87 rule refuses whenever any of three managed files exists. A
phase-two failure after creating the first file would therefore leave a target
that every retry refuses, even when the remaining bytes are exactly the
release-owned static scaffold. That contradicts the already-required explicit
partial-failure model and turns a recoverable interruption into manual cleanup.

Before Slice B, define bounded recovery without overwriting edited config. One
acceptable design writes fixed, reproducible companions first and the unique
`baton.json` last as the scaffold commit point. A retry may accept byte-exact
fixed companions and continue; if `baton.json` exists it may report the
scaffold complete only under a narrow exact pristine-skeleton recognition rule
(valid generated UUID, generation one, deliberately empty topology, exact
companions, no database). Any edited, conflicting, wrong-type, symlinked, or
unrecognized state refuses untouched. Another design is acceptable if it has
the same crash/retry and non-overwrite properties.

Slice B, including onboarding verbs, resolver/templates/bootstrap, release
assets, WF-14, and WF-15, remains held for its later reviewed correction.
