## [P0] The single mount contains credentials and manager-owned state

The pinned boundary is absence: only the exact attempt workspace/result
directory may be mounted, with credentials, inputs, the repository and
unrelated host paths unreachable. The implementation instead receives a raw
absolute `attempt_root`, applies only `realpath`, and mounts it. Every daemon
call in `test_custody_engine.py` supplies `dirname(roots["workspace"])`, which
is the whole assignment home. `assignment_workspace` provisions that home
with `credential-state`, `credentials`, `custody`, `inputs` and `workspace`.

This is not hypothetical. The implementer's own
`evidence/w36540-probe-2026-08-29.txt` reports those four forbidden sibling
trees in the helper's `inspect` answer. Skipping entries the helper does not
own is not absence; a bug or a different typed operation can still read what
the mount exposes. The daemon-free vector also accepts any raw absolute host
path, so a caller can select a repository, credential root or unrelated
sibling directly.

Required correction: mint a typed manager-owned custody-root capability from
the established assignment layout and make the vector consume it. Mount the
exact workspace or result directory for one act, never their parent. Hold the
boundary with the new forbidden-sibling inspection assertions and a case that
proves an arbitrary absolute path is not a custody capability.

## [P0] A nested mode-zero directory remains outside custody

`CUSTODY_PROGRAM.walk()` uses `os.walk(ROOT, topdown=False)`. It must enter a
directory before the bottom-up yield in which `normalize` changes that
directory. With an outer mode-zero directory containing an inner mode-zero
directory, descent fails and `os.walk` silently omits the subtree; only the
outer directory is later changed. The existing engine matrix puts one hostile
mode on `nested`, so changing that one directory is enough for the manager's
subsequent deletion and the deeper omission remains invisible.

The added daemon-free regression reproduces the omission: after a successful
`normalize`, the inner directory still has no group traversal (`0 != 0o070`).
The added engine case holds the end-to-end deletion boundary once a daemon is
available. Correct traversal must make each owned directory traversable before
descending, remain anchored under the exact mounted root, and never follow a
link.

## [P1] Four advertised operations and the ending composition do not exist

The accepted vocabulary requires inspect, read, hash, archive, normalize and
recursive delete. The program implements only inspect and normalize; read,
hash, archive and discard print `not composed by this build` and exit 3. The
new daemon-free operation matrix fails on exactly those four verbs.

The progress record also correctly states that no cleanup ending invokes even
the implemented normalize operation. This round is therefore useful
mechanism research, not an accepted provider. Implement all six operations
under explicit manager-owned result contracts, then compose the provider into
the fenced, worker-absent ending before returning for review.

## [P1] `--rm` does not establish crash-bounded lifetime

The source and tests claim that foreground plus `--rm` means a manager crash
leaks no capability. The engine's own help defines `--rm` as automatic removal
*when the container exits*. It does not make a running helper exit merely
because the client/manager disappeared. The implementation has no timeout,
durable or derivable act identity, observation path, or restart reclamation.
The current engine test covers only a normally completed `subprocess.run` and
then asks `ps`.

Required correction: make the act bounded and recognizable across manager
failure, and prove that a restarted manager observes and terminates or safely
resumes an in-flight helper before it can leave custody behind.
