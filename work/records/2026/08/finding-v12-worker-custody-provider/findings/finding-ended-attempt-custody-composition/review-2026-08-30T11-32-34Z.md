## Outcome: changes requested; the locator and durable account are not yet
## implementation-ready

The option-(b) applicability ruling is coherent: all three positively absent
endings need accountable normalization, ordinary cleanup may then remove the
attempt home, and the two recordless endings retain it. No production wiring
exists yet, so this pass reviewed the decision and patch boundary rather than
an implementation. Two blocking gaps remain.

### [P0] The helper's `result` root is not the result directory the endings retain

`custody._derived_root(..., which="result")` derives and, when missing,
creates `workspace/result`. The failed-start and refused-session lifecycle
regressions establish the untrusted retained directory as
`workspace/result-<attempt-id>` (`test_failed_start_destroy.py`,
`test_failed_start_destroy_engine.py`, `test_refused_session_engine.py`), in
agreement with `sealing.sealed_result`'s manager-derived
`result-<attempt-id>` identity. Those are different paths.

Wiring the current helper would therefore be able to return an accountable
success for a newly created empty `workspace/result` while leaving the actual
untrusted result tree untouched. It would also mutate an ending by inventing a
directory that did not exist before custody. That cannot satisfy “normalize
both roots,” and it makes the retained-mode caveat apply to the wrong object.

Before implementation, one durable rule must choose the physical result
locator and the missing-result outcome. The recommended rule is to derive the
actual result locator from manager-owned attempt identity, never accept a raw
path and never create a result merely because cleanup asked for custody. If a
result directory is optional, absence needs its own accountable settled
outcome; it must not be represented by creating an empty tree. If the result
directory is mandatory, allocation/start must establish it before worker
execution and cleanup must refuse a contradictory absence. The approver needs
to select which of those two lifecycle contracts is intended because the
current helper and the already-approved ending tests state different ones.

### [P0] `directory_custody` is a noun, not yet a durable receipt contract

The record pins one operation identity per `(attempt, root, verb)`, but does
not define an operation kind, a closed result document, signature operands,
or how the terminal cleanup record binds the two receipts. Reusing only the
outer `runtime.destroy*` journal is insufficient: a crash after one root
settles but before the other would lose the first root's independent durable
answer, and the required changed-signature collision could not be stated per
root.

The implementation-ready boundary is:

1. Use one journal kind such as `directory-custody.normalize`, with an
   operation id derived from the fixed assignment/attempt, root kind and
   closed verb. Its manager signature also binds the custodian image identity
   and the durable workspace-store identity used by W43974, so a changed
   helper or retargeted deployment collides rather than replaying an answer
   about another act.
2. Commit one closed `directory-custody.settled` result per root only when
   `CustodyAnswer.ok` is true. The result must carry attempt, root, verb, the
   accepted custodian account and its operation document. A refused,
   unaccounted or `UNRESOLVED` answer commits nothing and returns the existing
   retryable `cleanup.unsettled` shape.
3. Read each committed receipt back through `store.replay`; do not trust a
   caller-held receipt. Include the two receipt digests (or the complete
   adopted receipt documents) in `cleanup.settled`, so the terminal claim
   preserves which directory acts authorized it.
4. Keep outer cleanup replay first. For a fresh ending, retain the existing
   authority fence, runtime destroy, exact absence and provider-ending gates;
   only then settle result normalization and workspace normalization. A
   positively surviving runtime may still settle `failed` without a directory
   act because no removal or retention claim follows from it.
5. `result` is nested below `workspace`; they are separately attributable
   custody subjects, not two independent deletion trees. Ordinary cleanup
   performs one contained `discard_workspace(storage, attempt_id)` only after
   both receipts. A crash after either helper act replays or re-performs that
   act; a crash after manager removal replays both receipts, observes the home
   already absent, and then commits cleanup. Failed-start and refused-session
   cleanup commit both receipts and retain the home without calling removal.

The call seam also needs to be explicit before code lands. `intake.py` should
not reach through a nominally generic adapter to its mutable implementation
fields (`engine`, `run`, `image_digest`). Either the adapter exposes a typed
directory-custody act that internally calls `custody_act`, or composition
receives a separately owned custody capability. Whichever is selected becomes
part of W43977's receiving-boundary inventory.

## Required regressions for the next pass

In addition to the parent matrix, the implementation must prove the physical
locator distinction directly: put sentinels in both `workspace/result` and
`workspace/result-<attempt-id>`, establish which one is authoritative, and
show that custody neither creates nor mutates the other. Cover missing result
under the ruled contract, result receipt committed/workspace unresolved,
workspace receipt committed/result unresolved, restart after each receipt,
restart after the single manager removal, and outer exact replay after the
attempt home is gone.
