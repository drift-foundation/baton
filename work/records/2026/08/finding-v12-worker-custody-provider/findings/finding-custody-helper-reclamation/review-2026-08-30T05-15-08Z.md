# Independent review — 2026-08-30T05:15:08Z

## Outcome: changes requested

The derived helper identity, exact-name filtering, inspect-time image check,
normal stranded-helper reconciliation and in-custodian alarm are sound and
well covered. The exceptional ending is not yet safe, and the act/reclamation
boundary is not yet bounded by a deadline this manager requires.

## [P0] The manager-side wait and reclamation remain unbounded

`CUSTODY_SECONDS` starts only after the engine has launched the helper's Python
program. It cannot bound an engine call that stalls before that program starts,
loses the result after launch, or never returns. The `except` branch is
reactive: it runs only if the injected `run` capability happens to return or
raise. `_reclaimed` then sends stop, force-remove and inspect through the same
port, with no required deadline on any of them.

The parent enrichment required manager-owned deadlines for both the foreground
act and reclamation. Naming an `EnginePort` deadline out of scope leaves this
child's central bounded-lifetime acceptance unmet. Either make the custody
engine boundary require and enforce finite act/reclamation deadlines, or add
the necessary shared provider as an explicit blocker and complete it before
this child closes. An optional timeout chosen by a test/deployment injector is
not a property `custody_act` currently owns or can assert.

## [P1] A post-invocation `ContractRefusal` skips reclamation

`EnginePort.__call__` invokes `_run(argv)` and only then validates the returned
status/stdout/stderr document. A malformed engine answer can therefore raise
`ContractRefusal` after the helper was launched. `custody_act` currently treats
every such refusal as pre-invocation and re-raises immediately, leaving the
derived helper unreconciled.

The additive regression
`test_a_post_invocation_contract_refusal_still_reclaims_the_helper` demonstrates
the gap: only `ps, run` occur where `stop, rm, inspect` are also required before
the refusal propagates. Preserve genuinely pre-invocation refusals without
misreporting them, but do not use the exception class as proof that invocation
never happened.

## [P1] Exceptional recovery destroys by name before rechecking ownership

For every pre-launch candidate, `_reconciled` correctly treats the derived
name as discovery rather than authority and verifies the exact name and image
before removal. The post-run exception path bypasses that rule and calls
`_reclaimed(..., runtime_id=name)` directly. If the failed run created nothing
and a different-image container acquired that name before recovery, this path
orders stop and force-remove before any inspect identifies it.

The additive regression `test_lost_act_does_not_remove_a_same_name_replacement`
reproduces this race. Exceptional recovery must re-list/re-inspect under the
same closed state table, remove only a candidate identified as this act's
helper, accept positive absence, and refuse contradictory/uncertain identity
without sending `rm`.

The broad `except BaseException` should also be narrowed unless this record
explicitly decides that process-control exceptions such as `KeyboardInterrupt`
and `SystemExit` are to be swallowed into a custody answer.
