## [P0] The timed-out engine call can create after recovery proves absence

`_bounded` starts the injected synchronous call on a daemon thread, waits for
the configured interval, and abandons the still-running thread on expiry. It
does not cancel the call and cannot establish that the call will make no later
engine mutation. `custody_act` then reconciles the derived name, proves it
absent, returns a lost answer — and the original `run --name ...` remains free
to finish an image pull or stalled daemon exchange and create the helper after
that proof.

The additive regression
`test_a_timed_out_call_cannot_create_after_absence_was_proved` makes the race
deterministic: the original run is released only by recovery's absence
inspection. Current behavior returns the lost answer and then the abandoned
call creates the helper. The deadline therefore manufactures exactly the
stranded helper this child exists to prevent.

A daemon Python thread not holding interpreter shutdown is not cancellation of
its engine operation or an OS child it may have started. The same issue applies
to timed-out mutating reclamation calls: stop/remove may still take effect
after the caller has reported their deadline.

Do not use an abandoned thread as the enforcement boundary for a mutating
engine call. The owned engine boundary must provide cancellation/termination
and wait for that termination, or the manager must own a subprocess/process
group it can terminate and reap. After the invocation itself is settled, then
reconcile the derived helper and prove absence. If that requires a shared
engine-provider change, make it an explicit blocker; it cannot be replaced by
bounding only the waiting thread.
