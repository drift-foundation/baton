2. [P1] I QUOTED THE DISTINCTION AND THEN IMPLEMENTED ONE PATH

The comment in the v12 normalizer and the docstring in the model both state
the pinned declaration verbatim -- `kind?: ToolKind` on ToolCall and
`kind?: ToolKind | null` on ToolCallUpdate -- and both then treated null as
absence on either source, which erases the only difference that declaration
states. The v12 absent-case fixture even supplied `kind: null` on `tool_call`
while its own comment said null was the SDK's absence form "for an update".

The rule now implemented in both consumers, and now stated in SPEC 6.2.1 as
well so prose and code finish in one state:

  omitted member          absence on either source
  explicit undefined      absence on either source (TypeScript optionality)
  explicit null           absence on tool_call_update; REFUSES on tool_call
  pinned value            copied on either source
  anything else           REFUSES on either source

The model normalized without any source at all. It reads `sessionUpdate` now,
and a source it cannot see is NOT proof that a null was permitted: absence of
evidence refuses on the strict side rather than defaulting to the lenient one.

DOCUMENTING A DISTINCTION IS NOT IMPLEMENTING IT. That is the actual lesson
and it is the second time in two Works that I have written a rule into a
comment and left one call site outside it.


3. [P2] THE REFUSAL RAN THE VALUE IT WAS REFUSING

Two different mechanisms, one shape:

  JavaScript   `JSON.stringify(update.kind)` in the diagnostic. A BigInt is
               not serializable, so the message construction threw a raw
               TypeError and the closed pair never left the boundary.
  Python       `update["kind"] not in TOOL_KINDS` HASHES the value. A list or
               dict raised a raw unhashable TypeError, and the `{...!r}` in
               the diagnostic would run a caller's `__repr__`.

Both now test the value's SHAPE before its membership, and neither message
names the value. JavaScript reports `typeof`; Python reports
`type(x).__name__`. Neither can run provider code and neither can fail.

Python uses `type(supplied) is not str` rather than `isinstance`, because a
str subclass can override `__hash__` and `__eq__` -- membership of a frozenset
would run them. The pinned wire shape is the JSON string exactly.

This is the same rule I was taught over four rounds on the reconnect
primitive: A REFUSAL MUST NEVER RUN THE VALUE IT IS REFUSING. It applies to
the diagnostic, not only to the check.
