## Findings

### [P1] Initial calls and updates erase the SDK's nullability distinction

The correction accurately records `ToolCall.kind?: ToolKind` and
`ToolCallUpdate.kind?: ToolKind | null`, but both executable consumers treat
`null` as absence without considering `sessionUpdate`. The v12 absent case
even supplies `kind: null` on `tool_call`, while its comment says null is the
SDK's absence form "for an update".

Consequently an initial `tool_call` containing a value its pinned SDK shape
does not admit is accepted and normalized as though the provider omitted the
member. Preserve the source shape: omitted kind is absence on either source;
explicit null is absence on `tool_call_update`; explicit null on `tool_call`
refuses as `integrity.schema`. The executable model must make the same
decision rather than normalizing without its source kind.

This review gives case-specific authority to migrate the existing v12 and
model null-absence fixtures from `tool_call`/unspecified source to
`tool_call_update`, retaining their omission assertions.

Regression:

- `W543 review: null kind is absence only on a tool-call update`
- model `ToolCallKind.test_null_is_absence_only_for_an_update`

### [P2] Some invalid values escape the closed error taxonomy

The ruling says every value outside the pinned vocabulary refuses. In v12,
the refusal interpolates `JSON.stringify(update.kind)`, so a BigInt leaks raw
`TypeError`. In the Python model, list/dict membership against the frozenset
raises raw unhashable `TypeError`. Both consumers must validate the value's
string shape before vocabulary membership and build diagnostics without
serializing rejected caller values.

Regressions:

- `W543 review: an invalid kind always uses the closed error taxonomy`
- model `ToolCallKind.test_an_unhashable_invalid_kind_uses_the_closed_error_pair`
