## R1 — a lease can remain apparently live forever

The finding requires every current runtime fact to carry freshness and says a
runner publishes a bounded lease deadline. `runtime-start expires-at=` is
optional, the schema permits `NULL`, and `_runtime_view()` treats a null
deadline as never expired. A runner or adapter that omits the operand therefore
reports `idle`, `working`, or `waiting-input` forever, even after the process
has disappeared.

Make a bounded deadline unavoidable: require `expires-at=` on lease creation or
derive it from one authoritative configured duration. Define renewal semantics
so an explicit report after an expired deadline cannot update `last_contact`
yet remain `unknown` solely because the old deadline was retained. Add
refusals/derivations for missing, already-expired, renewed, and post-expiry
reports.

## R2 — one launch identity can be reset or resurrected

`_runtime_gate()` correctly says an ended lease must start a **new**
incarnation, but `runtime_start()` unconditionally deletes the current row and
reinserts whatever incarnation the caller supplies. Calling `runtime-start`
twice with the same incarnation resets a live runner to `idle`; calling it
after `runtime-end` resurrects the explicitly ended launch. Both contradict
the contract that an incarnation is one launch, and both bypass the terminal
gate used by `runtime-state` and `runtime-end`.

Refuse `runtime-start` when its incarnation equals the current or ended lease.
Exact transport retries remain the job of `op-id`; a genuine replacement must
name a distinct incarnation. Add live-reset and ended-resurrection regressions
that also prove the lease and journal remain unchanged on refusal.

## R3 — replacement is absent from the runtime journal

The finding requires replacement to be explicit and reasoned and describes
`runtime_events`/`runtime-history` as the append-only incident record.
Replacement currently deletes the lease, puts `superseded` only in the global
event payload, and adds an ordinary `idle` runtime row for the new incarnation.
`runtime-history` therefore shows two timelines but not that one superseded the
other or why.

Record the prior-incarnation relationship and replacement rationale in the
runtime journal itself. A first start needs no replacement rationale; replacing
an existing lease does. Add a projection regression proving that
`runtime-history` alone identifies the superseded incarnation and the durable
reason.
