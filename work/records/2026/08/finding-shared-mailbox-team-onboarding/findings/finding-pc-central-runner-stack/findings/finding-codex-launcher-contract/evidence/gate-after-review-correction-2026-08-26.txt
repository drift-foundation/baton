  [P1] fresh bootstrap renders relative launcher sources as authoritative


THE FINDING, AND IT IS EXACT

  `bootstrapThread` checked only TRUTHINESS for `--baton` and
  `--baton-config`. A relative `bin/baton` is resolved by whatever launch
  context the process happens to have, and a relative config is read from
  whatever working directory it inherits — so the block labelled those
  inferred locations "authoritative; do not infer". The confirmed boundary's
  own rule, broken by the value that states it.

  The dispatcher path was never exposed to this: `validateConfig` has always
  required both `roleInstructions` paths to be absolute. Standalone bootstrap
  never passes through that validator, so ONE contract had TWO admission rules
  depending on which door it came in.


THE CORRECTION, IN THE SAME OPERAND GATE

  Both paths are required to be absolute in the gate that already refuses a
  missing operand — before the instruction read and before any client factory
  is reached. A launcher operand is wrong the moment it arrives, not once
  somebody has tried to use it.

  The renderer is untouched: it still reads nothing, searches nothing and
  defaults nothing. Absoluteness is a property of the operand a launcher
  supplies, which is where the dispatcher checks it too.


AND A THIRD DOOR INTO THE SAME CONTRACT, FOUND WHILE CORRECTING THE SECOND

  `tools/acp-baton-bridge/src/config.mjs` required `baton.binary` and
  `baton.config` to be non-empty strings and NOT to be absolute. Those two are
  the ACP family's half of this same contract — they become `BATON_BIN` and
  `BATON_CONFIG` in the agent's own environment — and the confirmed boundary
  says in as many words that the contract applies to ACP-backed participants
  as well as Codex-backed ones, and that a context must not infer these values
  from repository paths, deployment symlinks or filesystem context.

  So there were three doors into one contract and only one of them was closed.
  It refuses for the same reason as the other two now.

  BEYOND THE REVIEW'S LITERAL ASK, AND FLAGGED AS SUCH. The review scoped its
  required correction to `bootstrapThread` and said to keep the dispatcher
  validation and the renderer unchanged — which this does. It did not ask for
