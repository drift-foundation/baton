## Findings

### P0 — conversation failures still return around the ending

`worker_entry.converse` remains outside `_custody_and_ending`. A non-answered
conversation returns at `dogfood_operator.py:787-793`, and an answered
conversation without a disposition returns at `:794-796`; the only call to
the alleged common ending is at `:798`. Neither branch invokes
`adapter.stop`, `reconcile_runtime`, any manager cleanup operation, or provider
teardown. `_unresolved` still records prose and returns exactly as it did in
the sixth round.

The new additive regression drives `run_dogfood_task` to a named started
runtime with each result and observes zero stop requests in both cases. Move
conversation/disposition handling inside the post-start owner and have one
ending receive an optional disposition/failure, rather than using successful
conversation as the precondition for entering it.

### P0 — the guard's own early returns skip cleanup

Inside `_custody_and_ending`, a stop observation other than quiescent/absent
returns at `:841-847`, and empty custody returns at `:855-857`. The `finally`
at `:901-906` calls only `_observed_after`, whose contract explicitly says it
is a read and never a removal. Therefore the record's claim that “the
manager's own cleanup is attempted, whatever happened” is still stronger than
the code: these paths neither destroy the runtime nor tear down credential and
launch deliveries.

This may require choosing the appropriate existing failed/refused cleanup
operation for paths that cannot produce an intake receipt; it must not be
worked around with a second deployment-owned destroy. If the public manager
surface cannot honestly end one of these states, record that as a manager
finding rather than calling observation cleanup.

### P1 — absent is not a freezeable quiescence proof

The stop branch accepts both `quiescent` and `absent` (`:841`) and proceeds to
`request_freeze`. The freeze contract explicitly accepts only `quiescent` and
states that `destroyed` is not equivalent because the writer was never
observed to have finished (`worker_manager/output.py:273-290`). An absent
runtime must therefore take an unresolved/cleanup ending rather than the
freeze path.

The same guard currently catches every `Exception`, including programming
defects such as `KeyError`, and converts it into an ordinary unresolved result
(`dogfood_operator.py:890-900`). Cleanup must still run after an unexpected
fault, but the fault should then propagate; otherwise an implementation defect
is relabelled as a supervised attempt outcome.
