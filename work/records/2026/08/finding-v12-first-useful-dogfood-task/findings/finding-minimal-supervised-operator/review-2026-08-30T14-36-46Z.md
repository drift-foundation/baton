## [P0] A nonzero independent verification is passed to review

`_derived` records `verification_status`, but `_custody` assigns that document
to `evidence["independent"]` and immediately calls `decide_retention` and
`_passed`. It never requires status zero. A candidate whose frozen task
verification exits 1 therefore receives the exact same successful authority
pass as a verified candidate; cleanup can then mark the attempt resolved.

This contradicts both the acceptance's independently derived verification
boundary and approver ruling M46985, which authorizes preserving and handing
on a *verified* result. Recording a failed check is not independent
verification of success.

The additive
`EveryPostStartBranchEntersTheEnding.test_failed_independent_verification_never_passes_to_review`
drives a completed custody path whose independent verification status is 1.
It currently fails because `session.passes` contains the review pass. Require
the exact successful verification result before retention/pass; retain the
failed result as unresolved and still request manager settlement because
intake committed.

## [P0] The approved narrow retry has no operator entry and trusts presence

`retry_handoff` is callable only by importing this module with five live
objects plus the in-memory evidence dictionary. `main` supports only the
whole-attempt path. The documented command has no retry mode, reads no retained
evidence and cannot reconstruct the exact handoff after the original process
exits. Since exact whole-attempt replay deliberately refuses at staging, an
operator encountering the later pass/settlement failure has no documented
way to perform the narrow retry M46985 requires.

The function's trust hold is also only truthiness of
`worker_disposition`, `intake_receipt`, `custody` and `independent`. It accepts
an arbitrary truthy disposition and an independent document whose
`verification_status` is nonzero. Its positive test supplies the fixture word
`succeeded`, while the real worker vocabulary reports `completed`, `unable`,
`plan-rejected` or `cancelled`, and therefore does not prove the trusted real
state.

Expose one documented retry entry that consumes the retained evidence and
original durable grants, reconstructs only the capabilities necessary for the
same pass/settlement identities, and refuses anything except the exact
completed, frozen, independently successful result. Prove it across a fresh
process/capability construction and assert zero restage, reassignment, runtime
start, provider turn, worker conversation, freeze and rederivation.

## [P1] The command hides its required credential source

`__main__` first strips an additional `--credential-file` through a private
pre-parser and then calls `main`, whose help consequently omits it. Running
`python3 tools/dogfood_operator.py --help` displays no credential operand even
though `_provider` refuses without it when a slot is materialized.

The prose also says the grants file is the whole of what the operator decides,
but its example omits the now-required `authority_store`, `incarnation`,
`credential_home`, `credential_slots` and `credential_profile` members. The
real-Docker test does not close this gap: it invokes `run_dogfood_task`
directly with a test-built adapter and supplied engine/channel functions;
`_launched` itself has no test.

The additive
`TheDocumentedCommandIsOneGrantsFile.test_help_names_the_credential_source_the_launcher_requires`
currently fails. Make the one public parser and the command documentation name
every required operator input, and add a positive launcher-boundary case so
the real seven-capability construction is exercised rather than only the
missing-grants error.
