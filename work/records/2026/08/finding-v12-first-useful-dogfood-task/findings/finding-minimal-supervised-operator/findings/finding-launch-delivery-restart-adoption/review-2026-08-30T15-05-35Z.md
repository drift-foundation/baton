# Independent launch-adoption review — 2026-08-30T15:05:35Z

## Outcome: changes requested; shape agreement is not delivery identity

The seam belongs in `launch.py`, returns the existing typed delivery rather
than making the deployment mint one, uses a bounded document read, and is
composed into W39358's retry adapter. The original 28 focused launch tests
pass.

The adopted document is held only to member names and schema. Its member
values are not validated and nothing ties its bytes to the session, contract
and role this attempt was actually launched with. The root is likewise not
held to the exact entry set `materialize` created. Adoption therefore accepts
state this component did not produce and later authorizes `launch.discard` to
delete a foreign entry.

## [P0] Another delivery's valid document is adopted as this attempt's

`adopt(storage, attempt_id=...)` has no expected launch values or durable
document identity. A valid four-member document copied from attempt 2 into
attempt 1's root passes every current check and is returned as attempt 1's
`LaunchDelivery`. Schema equality proves only that both are launch documents;
it does not prove which delivery this is.

The additive
`test_a_well_formed_document_from_another_delivery_is_refused` fails. Give
adoption the manager-owned expected session/contract/role (or an equivalent
durable identity), author the expected document through `launch_document`,
and require the exact canonical bytes this component would have written.

## [P0] Closed shape is mistaken for the document's value contract

`boundaries.document(... required=LAUNCH_MEMBERS)` holds the member set, not
the members. A document with integer `session` and otherwise correct shape and
schema is adopted, although `materialize` refuses it before writing. The same
gap admits empty/NUL/over-ceiling values and bypasses the authored document's
whole-document secret check.

The additive `test_adoption_applies_the_member_value_contract` fails. Reuse
the authoring owner rather than copying its individual rules; exact comparison
with the expected `launch_document`/`_bytes` result closes both identity and
value drift.

## [P0] A widened root authorizes deletion of a foreign entry

`materialize` creates exactly one entry. `adopt` checks that entry exists but
does not refuse any siblings. `OciAdapter._launch_ended` later calls
`launch.discard`, which removes every name in the adopted root. An extra file
there is therefore accepted now and deleted later even though this component
did not create it.

The additive `test_adoption_refuses_an_extra_entry_it_would_later_delete`
fails. Prove the root contains exactly the fixed launch-document basename
before returning the capability.

## [P0] W39358 must not treat absent as ordinary after a runtime ran

`adopt` returning `None` is correct for the generic component: some attempts
have no launch delivery. It is contradictory in `_for_retry`, whose retained
evidence says this dogfood attempt started a runtime only after
`launch.materialize` completed. The composition currently passes `None` into
the adapter and recreates the original `not-delivered` settlement if the root
is unexpectedly absent. Require a non-null adopted launch delivery in this
retry path before opening the handoff.

## [P1] Check-then-open does not preserve the no-follow proof

The path is checked with `islink`/`isfile`, then mode-checked with `lstat`, and
finally reopened with ordinary `open`. A replacement between those operations
can make the bytes come through a symlink the earlier checks did not inspect.
Open the root and its one entry through no-follow directory-relative
descriptors, and derive the type/mode/read from those same identities.
