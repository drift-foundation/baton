## Findings

### P0 — the assignment manifest fabricates claim evidence

`submit_claim` is called and its result discarded at
`dogfood_operator.py:699`. The manifest is then populated from `accepted`, the
`offer.accepted` document (`:705-710`). That document has neither an authority
claim event nor a receipt digest. `_claim_receipt` therefore writes the all-zero
digest and `_claim_event` writes `1` (`:919-926`). The manager's public
`submit_claim` answer does carry the authority's exact assignment, claim event
and decision. The operator must bind the manifest to that actual result (and
revalidate the contract's receipt-digest derivation); a syntactically valid
placeholder is invented authority evidence.

### P0 — the interactive runtime is never made quiescent

The accepted transport deliberately starts the container interactive so idle
PID 1 keeps running while the worker-entry program is invoked through
`docker exec`. After the conversation the new arc only calls
`reconcile_runtime` and immediately requests freeze (`:788-797`). Reconciliation
observes; it does not stop. `request_freeze` requires the execution-runtime axis
to be exactly `quiescent` (`worker_manager/output.py:273-290`). Consequently the
nominal path reaches freeze with a running runtime and refuses. Compose the
existing public control boundary that orders and positively observes
quiescence before freeze.

### P0 — cleanup is called while the authority assignment is still live

Nothing between `submit_claim` and `authorize_cleanup` ends or fences the exact
assignment. `authorize_cleanup` deliberately refuses when
`port.assignment_of(...)` still equals the attempt's assignment
(`worker_manager/intake.py:1101-1122`). The current cleanup lambda at
`dogfood_operator.py:802-804` is therefore unreachable on success. This also
exposes a missing recorded decision: the deployment facade carries only the
manager port's six delegated operations, none of which expresses the normal
successful handoff. Before coding, pin whether a supervised result passes the
Work to review or uses another authority ending, and make that exact transition
an explicit operator operand/capability.

### P0 — post-start failures bypass the required cleanup path

An unnamed runtime raises before the evidence object exists (`:741-747`), and
a lost/faulted conversation or missing disposition returns directly
(`:771-780`). Any transport exception, freeze/intake refusal, verification
timeout or verification launch error likewise escapes without a common ending.
The parent acceptance requires success and every post-start failure to destroy
the exact runtime, prove absence and tear down both credential and launch
deliveries, preserving `unresolved` whenever a proof is missing. One guarded
ending path must own all of these branches; `_unresolved` alone records prose
and performs no cleanup.

### P1 — public evidence and explicit launch operands are bypassed

The intake receipt already returns each artifact's public `custody_locator`
(`worker_manager/intake.py:706-736`), but `_derived` reaches through the
adapter-private `_custody` method (`dogfood_operator.py:851-868`). That
contradicts the function's public-operations claim and unnecessarily couples
the deployment to OCI internals.

The signature also accepts `run` and `labels` without using them, and the
factory call receives neither engine, resolved image digest, network nor those
values (`:626-633`, `:727-729`). The input/evidence can therefore name one
image/network while an unchecked closure constructs an adapter for another.
The documented operator must construct or hold the adapter against the same
explicit launch grants it records.
