## [P0] Retry rematerializes the credential delivery before it can pass

`main(... --retry-handoff)` calls the same `capabilities(given)` builder as a
new attempt. The real builder is `_launched`, and `_launched` always calls
`CredentialHome.materialize`. That operation deliberately refuses a
pre-existing root because an existing root is a live delivery or orphan that
must be adopted, never overwritten.

The primary approved retry case is a refused or uncertain pass after committed
intake. Manager settlement is requested and refuses while the assignment is
still live, so the credential root remains. The next process therefore fails
inside capability construction with “credential root already exists” before
`_retried` can issue the exact pass. Calling
`workspaces.assignment_workspace` from `_retried` also performs an allocating,
mode-adopting filesystem operation even though this mode promises only pass
and settlement.

Build a retry-specific capability path that adopts the durable existing
credential lifecycle and proves existing assignment roots without creating or
re-adopting them. Add a public-command regression starting from an actual
failed-handoff record and existing delivery; it must reach exact pass and
settlement with no provider callback, credential materialization, workspace
allocation, engine/channel construction or worker-side operation. The current
suite has no test of `_retried` or `--retry-handoff`.

## [P0] Retained evidence is neither safely read nor bound to the grants

`read_evidence` checks JSON object shape and member names only. Unlike
`write_evidence`, it performs no whole-document secret sweep and no byte
ceiling. A registered bearer inserted into an allowed member can therefore
reach authority/manager operands and refusal surfaces before the final writer
gets another chance to reject it.

More fundamentally, `_retried` does not even require
`evidence.attempt_id == grants.attempt_id` before opening stores, allocating
roots and constructing an adapter. It takes the pass assignment from grants
but the pass operation id, runtime and settlement attempt from evidence. The
evidence schema carries no exact assignment/work/generation binding, so a
closed valid result record can be paired with another assignment's grants.
Member presence does not establish provenance.

Two additive witnesses expose the immediate boundaries:

- `test_a_live_bearer_in_a_retained_record_refuses_before_retry` fails because
  `read_evidence` returns the secret-bearing record;
- `test_the_narrow_retry_refuses_evidence_for_another_attempt_first` errors on
  `capabilities["open_store"]`, proving the mismatch is not checked before
  external capability use.

Apply the write boundary's secret/size holds on read, bind every retained
identity needed for handoff to the same grants and durable manager/authority
facts before any outward act, and add negative cross-attempt, cross-generation,
cross-work and changed-image/network cases. A digest stored only beside the
editable record is not independent provenance.
