## [P0] Assignment-label filters still hide contradictory same-attempt state

`_CANDIDATE_LABELS` is derived as every runtime label except the three labelled
resolved-identity digests (`oci.py:172-173`). That leaves
`runtime_attempt_id`, `authority_uuid`, `work_id`, `participant`, and
`generation` as exact engine filters. This still asks the engine to
pre-compare facts the adapter must observe to reject contradictory state.

The additive
`OneDeliveryCarriesOneResolvedIdentity.test_a_stale_assignment_runtime_is_not_filtered_into_a_duplicate_start`
models a real engine applying those filters. A runtime carries the requested
attempt id but generation 0 while the request says generation 1. Because the
requested generation is an exact filter, the engine returns no row;
`OciAdapter.start` reads absence and reaches `run`. The case fails because no
`ContractRefusal` is raised and the recorded vectors contain the create.

The post-read half is incomplete as well. `OciAdapter.list` parses the complete
label record at `oci.py:739`, but then compares only the engine-reported image
and `_LABELLED_IDENTITY` at `oci.py:754-776`. It never compares the returned
attempt/authority/work/participant/generation values with the request. The
additive
`test_a_returned_candidate_must_match_the_requested_assignment` supplies a
candidate with the requested attempt id and contradictory generation. Current
behavior adopts it rather than refusing. Engine filters can select candidates,
but engine-side selection is not proof that a returned record has the values
requested; accepting it also contradicts the acceptance requirement to reject
contradictory engine data.

Candidate enumeration must therefore use the minimal stable ownership key
needed to find this attempt, then compare the complete returned label record
with the requested record in process before adoption. A contradictory row is
wrong, not absent, and must stop `start` before `run`. Preserve the independent
engine-image and resolved-digest comparisons and the existing ambiguity
behavior.

The current five-label expectation in
`test_the_listing_selects_candidates_and_never_pre_compares_identity` pins the
remaining unsafe pre-comparison. This review gives explicit case-specific
confirmation to revise it to the corrected minimal selector while retaining
complete input-label validation and complete post-read comparison.
