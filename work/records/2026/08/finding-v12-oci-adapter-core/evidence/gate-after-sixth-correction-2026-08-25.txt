  [P0] exact resolved-label filters hide stale runtimes before comparison

[P0] DISCOVERY HAS TO BE BROADER THAN COMPARISON

  `list_vector` asked the engine to filter on all EIGHT runtime labels,
  including the three resolved-identity digests. A real engine applies every
  filter before it returns a row — which the review's fake reproduces exactly
  — so a runtime from THIS attempt running under an old policy never appeared
  in stdout, never reached `_labels_of` or the identity comparison, and
  `start` read the empty candidate set as "nothing exists" and created a
  second runtime for one attempt.

  That is the state the acceptance says no later reconciliation can undo, and
  the module docstring had claimed the opposite all along:

    "A stale identity ... is refused rather than filtered away, because it is
     not absent, it is WRONG, and dropping it leaves a mislabelled runtime
     running."

  It was true of everything except the query that finds the runtime.

  THE SPLIT, derived rather than listed. `_CANDIDATE_LABELS` is every member of
  the frozen label set that is NOT part of the resolved identity — the attempt
  and the four parts of the assignment. Those are the filters. The three
  digests are compared IN PROCESS after the read, where a mismatch is refused.

    _CANDIDATE_LABELS = tuple(name for name in documents.RUNTIME_LABELS
                              if name not in _LABELLED_IDENTITY)

  Derived so a label added to the contract tomorrow becomes a selector or a
  comparison by which list it belongs to, rather than by somebody remembering
  to add it here.

  NARROWING THE FILTERS DID NOT NARROW THE OWNERSHIP. `list_vector` still owns
  the WHOLE label set through `_labels` before the engine is asked anything, so
  an invented member, a missing member or a text-shaped digest still refuses
  before a query is composed. Only which of those proved values become filters
  changed, and a case pins that.


[P1] THE SPELLING IS CHECKED BEFORE `normpath` CAN ERASE IT

  `_mounts` normalized the target and only then looked for `..` as a segment,
  so the check could never see traversal that normalization had already
  consumed. `/workspace/../etc` was accepted and emitted as

    type=bind,source=/srv/a-1/workspace,target=/etc,readonly=false

  moving the assignment's WRITABLE bind over the image filesystem.

  The raw spelling is checked first now — the rule `_canonical` already
  followed for a host source and that this side was missing — and only the
  canonical spelling reaches the engine. The source/target asymmetry is
  unchanged and is still stated at the site: a source is a HOST path the engine
  will resolve, so it is resolved here; a target is a path inside a container
  that does not exist yet, so it is normalized as text and never resolved
  against this host.
