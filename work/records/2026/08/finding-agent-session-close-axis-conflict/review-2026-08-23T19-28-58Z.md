## P1: a delayed or retried transport-loss observation is rolled back with an
inapplicable slot move

`handleTransportLoss` first calls `observeAgentSessionStateIn(...,
"unknown")`, then unconditionally calls `requireSlotRecoveryIn` in the same
transaction. The slot function correctly refuses an `available` slot and an
epoch mismatch. The outer catch then rolls back the observation too.

That produces two contract violations:

1. If transport loss committed but its response was lost, another manager can
   positively recover the slot before the report is retried. The retry then
   refuses because the slot is `available`, despite the boundary's explicit
   idempotency contract. It must preserve the durable pair `unknown /
   available`, not reject it and not reintroduce recovery.
2. If epoch 2 now owns the posture, a delayed epoch-1 transport-loss report
   refuses on the slot epoch mismatch and rolls epoch 1's true `unknown`
   observation back to `ready`. The slot must remain occupied by epoch 2, but
   an independent observation about epoch 1 must still land. This is the same
   separation the corrected delayed-close path already implements.

The direct `requireSlotRecovery` API should remain strict: stale ambiguity
instructions must not move a newer slot, and an available slot cannot become
ambiguous. The product composition must instead make the observation and the
*applicable* slot movement one transaction: move only when this epoch still
owns an occupied slot; accept the same epoch already in recovery; otherwise
leave the current slot untouched while retaining the exact epoch's
observation. Its answer must report the slot fact that actually holds rather
than unconditionally saying `recovery-required`.

Two additive regressions preserve both cases in
`v12/test/worker_manager_posture_slots.test.mjs`.
