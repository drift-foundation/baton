2. P1 — SLOT MUTATIONS WERE NOT BOUND TO THE EPOCH

Both mutations selected by attempt and posture only. A delayed epoch-1
ambiguity report moved epoch 2 to recovery-required, and a delayed epoch-1
release or close freed epoch 2.

Both now take `sessionEpoch` and compare it with the slot's durable
`session_epoch` inside the write transaction, INCLUDING in the idempotent
branches — "already released" is only an answer to a retry if the release
being retried is the one that happened.

`occupySlot` takes the same operand name, so all four functions in the module
say `sessionEpoch` rather than three of them saying it.


3. P1 — EVIDENCE NAMES WERE ACCEPTED WITHOUT THE NAMED FACT

This is the one worth stating plainly. `RECOVERY_EVIDENCE` is a closed set and
I checked membership in it — the SPELLING of a caller's assertion — and called
that the ruling's "positive evidence". `provider-session-closed` released a
slot whose session was still `ready`, and `runtime-absent` accepted any
non-empty string.

`proveEvidence` reads the fact now. `provider-session-closed` requires the
same epoch's durable observation to BE `closed` — the axis is where that fact
is established and this reads it. `runtime-absent` requires the exact
`attempts.runtime_id`; a missing, foreign or stale identity recovers nothing,
because "some container is gone" is not "the container that held this
assignment is gone". Neither path rewrites the observation.

The proof runs BEFORE the slot state is read, so a caller whose evidence is
not real never learns whether a retry would have answered.


4. P1 — TRANSPORT LOSS LEFT THE SLOT OCCUPIED

`handleTransportLoss` recorded `unknown` and moved no slot, contradicting the
ruling's own transition and bypassing the recovery API.

It composes with `requireSlotRecovery` now, and in ONE transaction. Two
transactions would leave a crash window in which the observation had landed
and the slot had not — a session recorded `unknown` whose posture still looked
live. `observeAgentSessionStateIn`, `requireSlotRecoveryIn` and
`releaseSlotIn` are the in-transaction variants that make that possible; the
store-level functions are thin wrappers, so there is one implementation of
each rule rather than two.

`closeAgentSession` is one transaction for the same reason.


5. AND ONE THING THE REVIEW DID NOT ASK FOR, WHICH ITS OWN CASE REQUIRED

`W771 review: a delayed close cannot release a newer epoch` expects epoch 1 to
end up OBSERVED `closed` while epoch 2's slot is untouched. My first
correction refused the whole act, which rolled the observation back too.

That is wrong and the case is right: epoch 1's provider session really did
close, and that observation is true whatever the posture has done since. The
close now always records the observation and releases only if the slot is
still this epoch's, reporting `releasedSlot: false` when it is not — because
"the close landed and the posture did not move" is a result a caller has to be
able to see.
