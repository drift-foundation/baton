2. [P1] I ASKED WHETHER THE OBJECT LOOKED EMPTY, NOT WHETHER IT WAS THE DOCUMENT

`Object.keys(new Date(0))` is empty and a Date is not the empty JSON document
-- it serializes as a STRING. Counting enumerable members answers "does this
look like {}", and the question this boundary exists to ask is "is this the
document 2.2 sends". Those are different questions and only one of them is
about the wire.

An INERT JSON RECORD is now proved at BOTH levels, and it is four things:

  - an object, not null and not an array;
  - carrying `Object.prototype` or NO prototype, so nothing it inherits can
    decide its wire form -- this is what refuses a Date, a Map, a regular
    expression and every class instance, generically, rather than by a list of
    the exotic types this contract happens to know today;
  - with exactly the expected own keys COUNTING THE ONES `Object.keys` HIDES.
    A non-enumerable `toJSON` is invisible to `Object.keys` and decides the
    ENTIRE serialization of the document it hides in, so own names and own
    symbols are both counted;
  - and every one of those members a DATA member. A getter is a program: it
    may answer one thing to this check and another to the wire, and reading it
    runs the caller's code at the boundary that decides this policy.

`Object.create(null)` remains a valid spelling and member order remains
irrelevant, as the review requires. Both are asserted.

A Proxy over an array whose `getPrototypeOf` trap answers `Object.prototype`
is refused too, because array classification follows a proxy to its target and
the trap does not.


3. [P2] THE REFUSAL SERIALIZED THE VALUE IT REFUSED -- AT THREE SITES, NOT ONE

The review found `JSON.stringify(advertised.terminal)`. The envelope refusal
and the `fs` refusal carried the SAME LINE and the same defect:

  denied(`it offered ${JSON.stringify(advertised ?? null)}`)     <- BigInt
  denied(`fs is ${JSON.stringify(fs ?? null)} ...`)              <- BigInt
  denied(`terminal is ${JSON.stringify(advertised.terminal)}`)   <- reported

A rule applied at one of three sites is not applied. All three name the value
by its SHAPE now, through one helper that runs nothing: `typeof` cannot fail,
`true`/`false`/`null`/`undefined` are single tokens with no caller content in
them, and every object is described from translated reflection.

Member NAMES are still reported, deliberately. A property name is an inert
string, the reviewer accepted those messages, and "which members did you send"
is the whole diagnostic. What is never reported is a VALUE.


4. AND THE ENVELOPE IS PROVED BEFORE ITS MEMBERS ARE READ

The old order read `advertised.terminal` after checking `Object.keys` but
before anything had established that `advertised` was a record at all. Proving
the envelope FIRST is what makes the two member reads inert: a data member on
a plain record runs nothing, and until the record is proved neither of those
facts is known. Mutation Q9 witnesses the ordering.

Q6 is genuinely equivalent, and provably so rather than by observation:
`Array.isArray` throws on exactly one kind of value, a revoked Proxy, and
EVERY reflection on a revoked Proxy throws. The prototype read therefore fails
first and sets `read: false`, and the array line is never reached with a value
that could make it throw. It stays inside the translated snapshot because that
ordering is what makes it safe and ordering is easy to change -- but it earns
no witness and is not counted as a guard. (This is the opposite finding to
W2929's fifth review, where the same operation ran BEFORE the prototype read
and was load-bearing. Same operation, different position, different answer.)

Q8's zero was a MISSING CASE. The descriptor read happens after the record has
otherwise been proved, so reaching it needs a Proxy that answers
`Object.prototype`, answers exactly [fs, terminal], and then throws from the
`getOwnPropertyDescriptor` trap. I built that value, confirmed it reaches the
descriptor read, and added it. Q8 now fails the case that owns it.

A zero is a question, not a result. These two had different answers and I
could not have told them apart without asking.
