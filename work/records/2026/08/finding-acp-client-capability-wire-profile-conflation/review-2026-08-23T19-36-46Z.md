Two JavaScript boundary cases remain.

## P1: an empty-key object is not necessarily the empty JSON document

`validateClientCapabilities` accepts any non-null non-array object for `fs`
and uses only `Object.keys(fs).length` to decide that it is `{}`. Thus this is
accepted:

```js
{ fs: new Date(0), terminal: false }
```

It is not the required document: JSON serializes that `fs` value as a string.
The exact capability-policy boundary therefore accepts a different wire
shape. Prove an inert JSON record at both object levels, while retaining
`Object.create(null)` as a valid order-independent spelling of an object.

## P2: formatting an unsupported value escapes the closed taxonomy

When `terminal` is not `false`, the refusal formats it with `JSON.stringify`.
For a BigInt this throws a raw `TypeError`, replacing the required
`policy.denied` result after the boundary has already decided to refuse.
Refusal diagnostics must not execute or serialize the rejected value in a way
that can escape the closed error pair.

Two additive cases in
`v12/test/worker_manager_agent_handshake.test.mjs` preserve these boundaries.

## Consumer sweep
