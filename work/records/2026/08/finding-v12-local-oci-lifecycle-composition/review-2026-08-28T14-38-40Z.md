## Finding

### [P0] `discard-after-intake` reports delivery without discarding custody

`OciAdapter.retain` validates only the outer command shape and returns
`{"delivered": True}` for every disposition. It performs no operation on the
adapter-owned custody tree. The new arc selects `discard-after-intake`, then
accepts `cleanup=complete`; it verifies that credential and launch roots are
gone but never verifies the custodied artifact. The manager's own settlement
rule says `complete` means nothing was kept, so this is a false clean ending,
not an unspecified retention-policy interpretation.

The daemon-independent reproduction in
`evidence/w6636-review-retention-noop.py` records:

```text
adapter answer: {'delivered': True}
discarded artifact still exists: True
```

W6629 already decided the boundary: `output.retain` is delivered to the side
holding the material because retention decides what happens to that material.
W6636 owns the shared provider crossing. A separate Work is not needed to make
the already frozen `discard-after-intake` command true.

Required correction:

- enact `discard-after-intake` against only the named, adapter-owned custody
  artifacts and establish their absence before returning;
- preserve bytes for `retain` and `quarantine`;
- make exact retry idempotent and refuse unknown, cross-attempt, or otherwise
  unowned artifact identities rather than deriving a caller-selected path;
- add focused positive, keep, subset, invalid-identity, and retry cases; and
- make the real one-container arc assert the discarded custody bytes are gone
  before accepting `cleanup=complete`.

## What is accepted in this slice
