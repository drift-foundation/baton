# Independent review — security and orphan slice

This pass is bounded to the four cases added after
`review-2026-08-28T15-18-37Z.md`. It is not integration signoff for W6636.

## Accepted partial evidence

The mount cases ask the daemon about the created container rather than reading
the adapter argv. They pin the exact target set, each source, the one writable
workspace, read-only input and provider deliveries, and the absence of any
additional host bind. The applied configuration also pins no network,
unprivileged execution, all capabilities dropped, no-new-privileges, a
positive PID limit, a read-only root filesystem and the fixed non-root user.

Those are useful real-engine assertions. The two findings below prevent this
slice from closing the process-domain and orphan-recovery requirements.

## [P1] The orphan case bypasses production recovery

`test_orphan_recovery_cannot_delete_a_siblings_delivery` materializes two
roots and then calls `CredentialHome.discard_orphan(mine)` directly. It never
calls `OciAdapter.recover_credentials`, so it cannot catch the integration
error this requirement exists to exclude: the adapter choosing assignment-wide
`discard_orphans` or otherwise applying evidence about one attempt to its
sibling.

`evidence/w6636-review-orphan-seam.py` disables
`OciAdapter.recover_credentials` completely and runs the case without a
daemon. The case still passes. The component suite already exercises this
production seam with a fake engine; a composition regression must drive that
seam with the two real deliveries and prove only the attempt selected by the
recovery evidence is removed.

## [P1] The process-domain assertion admits a sibling namespace

`test_the_runtime_boundary_is_the_one_the_launcher_composed` asserts only that
`PidMode` is not the literal `host`. Docker also admits
`container:<runtime>`, which joins another container's PID namespace and is
not the attempt-owned process domain carried in from W28681.

`evidence/w6636-review-security-shape.py` supplies the otherwise expected
inspected configuration with `PidMode=container:sibling-runtime`; the case
passes. Pin the engine's private/default namespace answer (with the explicit
Docker/Podman representation if they differ), rather than excluding only one
unsafe value. The fixed PID limit should also be asserted exactly if this case
continues to claim it is the boundary the launcher composed.
