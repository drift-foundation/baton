## Findings

### [P0] A keep disposition succeeds after the custody bytes are already gone

The `retain` and `quarantine` branch returns
`{"delivered": True, "discarded": []}` without observing any named custody
tree. If custody disappears after intake and before retention, the manager
journals the keep disposition and later derives cleanup `retained`, even though
the material whose continued existence distinguishes that ending is absent.
This is the keep-side equivalent of the false clean ending from the prior
review.

Require every named `retain`/`quarantine` tree to be positively present at its
derived adapter-owned location before returning. Missing or invalid custody
must refuse before the manager journals the retention decision. Add both keep
dispositions as absent-custody regressions.

### [P1] An unknown disposition falls through to destructive discard

`retain` checks only whether the value is one of `retain` or `quarantine`; every
other string takes the discard branch. A typo or future vocabulary value such
as `not-a-retention-disposition` therefore removes the named custody and
reports success. The manager currently emits the frozen three, but this adapter
boundary owns a destructive command and must fail closed rather than making
unknown mean delete.

Validate the disposition against exactly `retain`, `quarantine`, and
`discard-after-intake` before any filesystem mutation. Add an unknown-value
regression that proves the bytes remain.

Both behaviors are reproduced by
`evidence/w6636-review-retention-fail-closed.py`:

```text
unknown disposition answer: {'delivered': True, 'discarded': ['proposal']}
unknown disposition destroyed custody: True
retain over absent custody answer: {'delivered': True, 'discarded': []}
retained custody exists: False
```
