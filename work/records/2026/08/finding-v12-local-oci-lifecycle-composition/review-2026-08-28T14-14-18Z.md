## Accepted corrections

### Provider applicability/omission

The destroy answer is now closed: `credentials` and `launch` are required on
every adapter answer, and `not-delivered` explicitly represents an
inapplicable provider. Manager-generated no-runtime answers carry the same two
endings. An omitted provider is therefore a schema refusal rather than
evidence that no teardown is owed.

The restart regression drives the required sequence: runtime absent plus
launch unresolved leaves cleanup pending; the manager is reopened; an answer
omitting provider endings refuses and remains pending; only explicit terminal
endings complete cleanup. This satisfies the prior review without introducing
new manager persistence.

### Fault-created runtime reconciliation

Typed refusals and ordinary adapter faults now use one
`_settle_failed_start` boundary. Both reconcile exact adapter state first,
attach and observe a matching created runtime, and fall back to durable
`uncertain` only when reconciliation cannot answer. The non-contract fault is
re-raised unchanged. The regression confirms one runtime identity and
`running` durable state for both failure kinds, and retains the unanswerable
fault fallback.

## P2 — the new shared-boundary test leaks registered resources

`test_both_kinds_of_failed_start_take_one_settlement_boundary` constructs a
fresh `TestCase`, calls `setUp()`, then invokes `case.tearDown()` in `finally`.
The fixture owns its temporary directory and `ControlStore` through
`addCleanup`, so `tearDown()` does not execute either cleanup. The focused run
emits implicit `TemporaryDirectory` cleanup and unclosed SQLite connection
`ResourceWarning`s at process cleanup.

Use `case.doCleanups()` (or an equivalent fixture boundary that actually runs
registered cleanups) and make the focused run warning-clean. This does not
invalidate the accepted runtime behavior, but a regression that leaks its
manager/store resources cannot be left as the durable gate for that behavior.
