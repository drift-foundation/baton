## Changes requested

### P0 — omission still erases a known unresolved provider

The prior review explicitly required that a missing provider member must not
erase a known outstanding provider and that provider applicability survive a
manager restart. The correction re-asks the adapter, but the destroy contract
still makes both provider endings optional and the manager remembers no
applicability or prior unresolved ending.

Consequently, a first answer of runtime `absent` plus launch `unresolved`
leaves cleanup pending, but after reopening the manager a second runtime-
`absent` answer that omits `launch` records cleanup `complete`. The adapter was
called; what was lost is the knowledge that launch teardown was required.
`OciAdapter` currently always answers both members, but the manager contract
admits the unsafe answer and `authorize_cleanup` is a public generic manager
boundary. The durable invariant cannot depend on one implementation's current
habit.

Preserve provider applicability/outstanding teardown durably, or close the
destroy-answer contract so every applicable provider must answer on every
retry (with `not-delivered` as the explicit no-provider ending). Add a restart
regression: unresolved first, omitted second must refuse or remain pending,
and only an explicit terminal ending may settle.

Evidence: `evidence/w6636-review-provider-omission.py`.

### P0 — a non-refusal start fault does not reconcile a created runtime

The new non-`ContractRefusal` catch calls `_settle_unknown_start` directly. It
never invokes `reconcile_runtime`. If the adapter created a runtime and then
raised a driver/transport fault, the manager records `uncertain` with no
runtime identity even when `list` and exact `observe` would immediately find
and identify that runtime. The runtime is left unnamed and cannot enter the
ordinary destroy crossing.

A fault says less about the start result than a typed refusal, but it does not
make exact reconciliation less necessary. Use the same reconciliation-first
settlement boundary for both while re-raising the original non-contract fault
unchanged. Add a case where `start` raises after creation, `list` returns the
matching runtime and `observe` says running; the durable row must attach that
identity. Retain the current `uncertain` fallback when reconciliation itself
cannot establish an answer.

Evidence: `evidence/w6636-review-fault-created-runtime.py`.
