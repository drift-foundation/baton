## [P1] Constructor assertions still execute or carry rejected values before §13

There are three manifestations of one remaining ordering/ownership defect.

1. `if category not in _PAIRING` and `if code not in _PAIRING[category]`
   perform mapping/set membership before `_rejected` runs. A malformed operand
   with a caller-controlled `__hash__` therefore executes caller code and can
   raise an exception containing the live bearer; an unhashable operand escapes
   as `TypeError`. The promised assertion taxonomy is never reached.
2. `_rejected` checks whether an exact string operand carries a live value, but
   does not prove the replacement text it composes. A valid 32-character live
   bearer equal to a substring of its fixed redaction sentence leaves verbatim
   in that sentence—the exact containment error sixth review found in
   `SECRET_LEAK_MESSAGE`. The inert type-name branch has the same content gap:
   a build-owned class name can itself equal the currently live bearer and is
   returned inside the assertion.
3. The message-type and durability-type assertions later in `__init__` still
   use `type(value).__name__`. This module already owns `type_name_of` because
   ordinary `__name__` lookup consults a caller-controlled metaclass. Both
   sites can run that code and can emit the complete live bearer it returns.

Thus the implementation has not established the decision it records as
“every diagnostic in this constructor is now behind the same rule.” The
central `ContractRefusal` message guard cannot sanitize an `AssertionError` or
raw exception that already escaped.
