  [P1] the constructor's pair assertions quote live operands before §13


THE FINDING, AND IT IS THE LAST DIAGNOSTIC IN FRONT OF THE GUARD

  `ContractRefusal.__init__` owns its category and code with construction-time
  assertions, and those assertions ran BEFORE the §13 message guard and
  rendered the rejected operand with `repr`. A live bearer supplied as an
  invalid category or code therefore escaped in an `AssertionError` the
  crossing never saw:

    'bearer-9999999999999999999999999999999999999999' is not one of the
    frozen error categories

  Classifying an invalid pair as a raising-site defect is right and is
  unchanged. It does not make an assertion carrying a live secret safe.

  THE SAME SHAPE, FOR THE SIXTH TIME IN THIS WORK: a diagnostic standing in
  front of the guard. A manifest door, a row boundary, two document owners,
  thirty public surfaces, the substitute itself -- and now the two checks that
  run before the message is even looked at, in the very function the crossing
  lives in.


THE CORRECTION: PROVED, NOT SUPPRESSED

  `_rejected(value, live)` names a rejected category or code without ever
  carrying a live value, and the ordinary case is untouched:

    not text            -> `a <type name>`, read without metaclass dispatch
    a live-carrying str -> "a string §13 will not let this build quote,
                            because the registry says it is live"
    anything else       -> `repr(value)`, exactly as before

  A misspelled `integrty` is still quoted verbatim, because that is the whole
  use of this message. Only a value the registry says is live gives way, and
  it gives way to a sentence that says so rather than to silence: a reader has
  to be able to tell a redaction from a missing value.

  ONE SNAPSHOT FOR THE WHOLE CONSTRUCTION. The registry is read once at the
  top of `__init__` and the same view answers the pair assertions and the
  message guard, so two reads cannot disagree about one value inside one
  construction.

  AND A DEFECT THE CORRECTION CLOSES THAT THE REVIEW DID NOT NAME. `{value!r}`
  runs `__repr__`, which is caller-chosen code, inside a diagnostic. The
  module's own `name_value` has refused to do that since W6782 -- "a refusal
  never RUNS the value it refuses" -- and these two assertions were doing it.
  A pair operand with a raising `__repr__` replaced the assertion with an
  exception of the caller's choosing; it is named by its type now.
