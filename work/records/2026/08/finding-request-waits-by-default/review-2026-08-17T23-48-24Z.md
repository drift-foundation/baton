## R1 — invalid `wait=` can replay a valid plain post

`post_thread` computes the effective `blocking` value and consults
`_operation` before it rejects `wait=` without `request=`. For a plain post the
effective value is false whether `wait` is absent or explicitly supplied.
Consequently:

1. a valid plain post commits with `op_id=X`; then
2. the same post retried with invalid `wait=true`, still without `request=`,
   is accepted as a replay instead of refusing.

The additive regression
`tests/work/test_w159_request_waits.py::test_wait_without_a_request_cannot_replay_a_valid_plain_post`
currently fails exactly this way: 15 focused tests pass and this one reports
`DID NOT RAISE`. Validate the conditional grammar before replay lookup, while
retaining omitted-versus-explicit-true equivalence for an actual request.

## R2 — the new default has no packaged public workflow proof

The focused tests exercise the transition API. The collateral sweep then adds
`wait=false` to every existing public workflow. Most notably,
`test_ws3_wf01` and `test_ws3_wf02` still describe consumers that "ask and
wait", but now explicitly publish asynchronously and invoke the retired second
`phase ... wait=<obligation>` command. Those tests preserve the defect W159
removes rather than test the replacement.

Add a source-and-built-artifact JSON-CLI workflow that:

1. creates and claims the consumer Work;
2. sends `say ... request=... on=...` with omitted `wait=` (and covers explicit
   true where useful);
3. proves one sequence atomically publishes, creates the obligation, enters
   the exact wait, and releases the claim without moving Current;
4. accepts/responds/disposes through the public surface and proves the one
   exact wake; and
5. covers `wait=false` as the intentional asynchronous contrast.

Migrate at least the WS3 acceptance workflows whose prose explicitly says the
consumer waits; do not leave them as a two-command compatibility simulation.
Audit the remaining mechanical `wait=false` additions and retain the override
only where asynchronous behavior is genuinely the scenario under test.
