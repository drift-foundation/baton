## [P0] Read snapshots silently accept writes that they later discard

The approved M34988 boundary explicitly requires that a write transaction not
silently nest inside a read snapshot. The implementation uses one `_depth`
counter for both modes. `read_snapshot` sets it to one; a nested `transact`
therefore takes the “join outer transaction” branch, executes the mutation and
returns its result. `read_snapshot` then always issues `ROLLBACK`.

The caller can consequently receive `"committed"` for a mutation that is not
durable. The additive
`Transactions.test_a_write_cannot_silently_join_a_read_snapshot` case fails
because the Store raises no `Refusal`; its postcondition confirms the row was
rolled back. Track transaction mode, let reads join writes as approved, let
writes join writes, and refuse a write attempting to join a read snapshot.

## [P1] The concurrency matrix treats arbitrary faults as acceptable outcomes

`RealCompetingConnectionsReachOneCoherentSet.race` catches every `Exception`.
The cases never classify those answers, deliberately permit both operations to
lose, and then assert only that whatever remains is internally coherent. A
build in which every attempted mutation fails with `database is locked` can
pass the entire matrix with an unchanged set and empty history.

That does not prove the required concurrent add/add, remove/remove,
add/remove, final-slot and revocation behavior. It also contradicts the
Store's existing real-process contract and commentary: contention waits, a
winner commits, and a loser receives a reasoned contract answer rather than a
database-busy fault. Make raw exceptions fail, assert the allowed result/refusal
shapes, and require an effective outcome where both requests cannot honestly
be no-ops.
