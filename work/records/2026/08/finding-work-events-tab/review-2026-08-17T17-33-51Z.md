# Review: W123 Work Events play-by-play

Independent review by `baton.codex` after the implementation handoff at v11
sequence 146. The focused implementation suite reports 25 passing tests. The
review used fresh scratch authorities and did not edit implementation files.

## Result

Changes requested. The principal architecture is sound, but four typed
relationships/duration requirements are missing and the public documentation
retains one statement superseded by W76.

## Accepted

- `work-events` is a bounded Work-relative projection over the immutable event
  ledger; it does not duplicate event storage.
- Association is explicit by event kind rather than a heuristic search through
  arbitrary JSON strings.
- Dependency addition/removal projects the same authoritative event to both
  consumer and blocker with opposite roles and the rationale intact.
- Pure discussion and personal seen movement stay out while workflow-bearing
  message acts remain discoverable without copying message bodies.
- Forward/newest/older event paging uses a proof row, returns canonical
  ascending JSON, and presents newest-first in the TUI.
- Messages/Events are visible tabs, both bracket keys switch globally within
  Work detail, the footer advertises navigation, and each tab owns independent
  pane/selection/page/reader state.
- Closed claim intervals attach to both boundary events; heartbeat, pass,
  close, waiting/parked entry, and invalidating gates have focused coverage.

## R1 — reverse creation projections omit the created Work identity

Direct child and follow-up creation events are associated with the parent or
predecessor, and their roles correctly say `parent` or `predecessor`. However,
`related` is empty because `_event_related()` looks for a nonexistent
`payload.created`. Direct `create_work` stores the created identity as the Work
row whose `created_seq` equals the event sequence; it is not in the payload.

Fresh-authority reproduction:

```text
parent views child create_work: roles=['parent'], related=[]
expected related=[{'work': CHILD, 'role': 'subject'}]
```

The same failure applies to a predecessor viewing the creation of its
follow-up. Resolve the subject identity through the typed creation relation,
not by inserting/reconstructing a guessed id from free-form payload data.

## R2 — duplicate targets do not receive the terminal duplicate event

`_event_roles()` and `_event_related()` contain duplicate-target logic, but
the SQL association predicate never selects a `close_work` event by
`payload.duplicate_of`. The canonical survivor therefore cannot see which
Work was rejected as its duplicate.

Fresh-authority reproduction closes Work B as `rejected` with
`duplicate_of=A`; `work-events work=A` contains no event at the closing
sequence. Attach that same close event to A with role `duplicate_target` and
related Work B with an explicit `duplicate` (or equivalently ruled) role.

## R3 — open claims have no ongoing Held duration

The confirmed contract says an open claim carries its start and ongoing Held
duration. `_claim_intervals()` leaves `elapsed_seconds=None` until an end event
exists, and the TUI renders only `claim: still open`. Heartbeats correctly do
not restart the interval, but clients still cannot display how long the open
claim has been held.

Fresh-authority reproduction immediately after `claim`:

```text
claim_interval.end_seq=None
claim_interval.elapsed_seconds=None
```

Return a non-negative integer elapsed duration for an open interval using the
read's current instant while keeping `started_at` fixed and heartbeat-neutral.

## R4 — accept-created child providers are absent from their parent

When `accept` atomically creates a provider beneath `create.parent`, the event
belongs to the consumer and provider but not to the parent. The accepted
provider's parent relation exists in the Work row, while the accept payload and
association predicate expose no typed parent link. A fresh reproduction cannot
find the accept sequence in `work-events work=PARENT`.

The parent must receive the same authoritative accept event with a `parent`
role and the created provider in `related`. Cover both `accept into=existing`
(no fabricated creation/parent relation) and `accept create=true parent=...`.

## R5 — public documentation contradicts the preserved W76 behavior

`docs/BATON-WORK.md` now correctly says the Message index opens newest-first,
but a later sentence still says selecting a Thread opens its first
personal-new Message. W76 explicitly superseded the hunt for first-new with a
single bounded newest page. Remove the obsolete sentence so the same paragraph
does not prescribe two different entry behaviors.

## Required regression boundary

Add focused tests for both directions of direct child/follow-up creation,
duplicate source/target projection, open elapsed duration across heartbeats,
accept-created provider/parent projection, and the negative existing-provider
case. Keep exact event identity, roles, related Works, pagination, and message
counts stable. Run the focused suite and the complete v11 gate, then return for
independent re-review.
