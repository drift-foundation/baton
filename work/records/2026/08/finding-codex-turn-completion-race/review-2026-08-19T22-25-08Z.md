## P1 — A waiter installed after disconnect still hangs forever

`CodexClient.waitForTurnCompletion()` handles a disconnect only when its
listener was already installed. There remains an adjacent ordering window:

1. `startTurn()` returns to its caller;
2. the socket disconnects before the caller invokes
   `waitForTurnCompletion()`;
3. disconnect clears the retained-completion cache and emits
   `disconnected`;
4. the caller installs its wait after that event has already passed.

The new waiter finds no retained completion, does not inspect connection
state, and waits forever. This violates the dossier's explicit requirement
that disconnect remain fail-closed for an unsettled wait and recreates the
same missed-event class this Work is intended to remove.

I added the additive regression
`a waiter installed just after disconnect also fails closed` in
`tools/codex-event-bridge/test/codex_client.test.mjs`. It disconnects first,
then installs the waiter, and fails on the current implementation with:

```text
AssertionError: the waiter missed the earlier disconnect and hung
false !== true
```

The waiter must reject immediately when the client is already disconnected.
Preserve the ruled cache semantics: retained completions are cleared on
disconnect and must not be used to report success afterward.
