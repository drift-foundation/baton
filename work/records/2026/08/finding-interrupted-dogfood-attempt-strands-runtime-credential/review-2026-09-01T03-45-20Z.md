## Decision review

**Confirmed:** the implementer's refutation is correct. In a recovery process
the original in-memory `credentials.Delivery` is gone, so the current
`OciAdapter._torn_down` returns `not-delivered` whenever
`credential_delivery is None`. That does not make abandonment unreachable; it
makes the ending falsely claim that no credential was delivered for an
attached attempt whose durable evidence proves otherwise. The recovery builder
must therefore carry a typed credential owner/ending and produce only
`torn-down` after positive absence or `unresolved` when absence cannot be
proved.

**Confirmed:** option (a) is the current credential-home contract. The
operator-granted `CredentialHome` already owns materialization and is part of
the accepted grants/evidence contract. Passing that same validated capability
into `OciAdapter`, `_for_retry`, and the new abandonment builder gives
materialization, lifecycle publication, adoption and teardown one owner.
Option (b) would relocate materialization and change the accepted grants
contract, so it would require a supersession not justified by this defect.

No product decision remains open between these two directions, and no grants
supersession is needed.

## Required implementation clarification

`abandon_attempt` explicitly refuses an attempt with no attached runtime. The
regression matrix also names interruption after credential materialization but
before runtime creation/attachment, which can occur because `_launched`
materializes the credential before `run_dogfood_task` records and starts the
attempt. That pre-attach state cannot be forced through the W44716 abandonment
ending.

The public recovery command must branch on durable manager state:

- an attached runtime uses the existing `abandon_attempt` declaration,
  authority fence, exact removal, provider endings and terminal settlement;
- a pre-attach credential/launch orphan receives exact, bounded, no-read
  cleanup after the public surfaces prove it belongs to no live runtime, and
  records no invented terminal attempt; and
- uncertainty in either branch remains unresolved and retryable.

This is a clarification of the existing patch boundary, not authorization for
a second attempt ending. It is now reflected in `PLAN.md` item 6.

## Acceptance emphasis

- For future attempts, the one-home owner must make a separately invoked
  `discard_orphan` and later recovery distinguish historically delivered from
  genuinely not delivered using durable attempt/runtime/grant facts; absence
  of the in-memory `Delivery` is never enough.
- The legacy run7/run8 split must be handled explicitly by proving both the
  configured granted home and the assignment-derived record location. A raw
  path from the record is not authority.
- Complete-looking workspace output remains open/untrusted: no freeze, intake,
  retention, handoff or acceptance is introduced by recovery.
- Runtime removal precedes credential teardown, and both are positively
  observed before the internal lane or terminal attempt state is released.
