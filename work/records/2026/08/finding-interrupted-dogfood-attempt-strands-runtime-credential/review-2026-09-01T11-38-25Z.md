## [P1] Duplicate observations produce a contradictory per-runtime account

`OciAdapter.observe` correctly makes a multi-document answer for one exact
runtime `uncertain`, but `_observed_runtimes` preserves each document as an
independent candidate and `_zombie_account` emits each one unchanged. When the
engine names the same runtime twice with conflicting `Running` members, the
recovery record therefore contains two rows for the same exact locator: one
`quiescent` and one `running`, both targeted, while the top-level runtime says
`uncertain`.

The retained `/tmp/w55758-round12-probe.py` drives documented `--abandon`
through the durable attached-state fixture with two inspection documents for
`runtime-1`, one `Running: false` and one `Running: true`. It returns status 1
and leaves the credential material untouched, but writes:

```text
runtime.state=uncertain
zombies=[runtime-1/quiescent/targeted, runtime-1/running/targeted]
```

The fail-closed host behavior is sound; the durable operator evidence is not.
M60437 and PLAN item 62 require one exact locator, observed state and reason
per runtime. Two mutually exclusive states under the same locator give the
operator no truthful fact to act on and recreate the zombie-report ambiguity
this round was meant to remove.

Canonicalize candidate observations by runtime identity before composing the
recovery record. Repeated agreeing observations may collapse to one; repeated
or aliasing observations that disagree must produce one `uncertain` entry
whose reason names the conflicting engine account. Preserve the per-runtime
targeted/action fact. Add a command-level regression using the already-recorded
same-runtime-twice shape with conflicting states, asserting exactly one zombie
row for that locator, state `uncertain`, unresolved recovery, and no credential
teardown.
