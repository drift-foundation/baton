## P1 — recovery discards a Work origin already proven by the marker

`#recoverQuarantineIncident` always calls `#fileApprovalIncident` with
`attempt: null`. That is correct for a restored `pending`, `unmatched`,
damaged, or otherwise unknown marker: the dead process can no longer prove an
association it had not settled. It is not correct for an `exact` marker.

An exact marker was written only after the approval request's authoritative
turn id matched an immutable delivery attempt. It durably carries the Work,
episode, and action key produced by that proof. If the incident publication
then fails or the process dies before acknowledgement, restoration retains all
four fields but throws three away when it files the required recovery
incident. The resulting incident is uncorrelated even though the dispatcher
has durable proof of the origin. This contradicts the confirmed boundary that
the incident is Work-correlated when known and uncorrelated only when the
origin cannot be established.

I added `W99: restart retains an unpublished incident's proven Work origin` to
`tools/codex-event-bridge/test/cross_work_fence.test.mjs`. The first dispatcher
binds W30 exactly, attempts an incident publication that returns false, and
leaves an unacknowledged exact marker. The restoring dispatcher recovers the
incident. Current code files it with `work: null`, so the new assertion fails:

```text
restart discarded an origin that the durable marker had already proven
null !== '43c-W30'
```

Recovery should reconstruct the closed action locator from the marker only
when `correlation === "exact"` and its Work, episode, and action key are valid.
It must continue filing without a Work origin for restored pending/unmatched,
damaged, and unknown records. No request body or other unsafe payload is
needed or permitted.
