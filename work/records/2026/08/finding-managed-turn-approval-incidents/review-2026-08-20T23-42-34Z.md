## P1 — the proposed writable-root deployment still violates the confirmed boundary

The implementer reproduced the decisive behavior rather than guessing:

- a directory writable root allows unrelated shell commands to alter both the
  database and any other file in that directory; and
- a file writable root is echoed by the app server but grants no useful write
  capability at all.

Moving `work.sqlite3` into a directory of its own narrows the blast radius, but
it still lets any model-issued shell command rewrite or delete the authority
directly. That contradicts the accepted W415 boundary: managed turns may use
the configured canonical Baton operations, while raw authority mutation and
unrelated commands remain unavailable. Configuration validation cannot turn a
broad filesystem grant into a narrow operation capability.

The layout-based `authorityDatabase`/`writableRoots` proposal therefore must
not ship as W415's fix. Its comments and examples accurately admit the gap,
but documenting an unsafe boundary does not satisfy it.

## Recommended ruling

Create a causally tied child Work for a mediated managed-turn Baton capability.
The mediator should run outside the model's command sandbox, expose only the
ruled operations (`claim`, message, `pass`, and `close`) for the configured
participant, and grant the managed turn no filesystem write access to the
authority. W415 remains open and blocked on that child, then owns the final
integration, negative command proof, incident proof, and deployment review.

This is preferable to silently expanding W415: the mediator is a new component
with its own authority contract and review surface. It is also preferable to
parking W415 independently, because the mediator is not optional follow-up; it
is required to satisfy W415's existing acceptance boundary. The current
layout-grant implementation may remain as recorded evidence while the child is
developed, but it is not a releasable solution.
