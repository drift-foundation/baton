## Findings

### P1 — the writable coordination-home root is a broad shell capability

`codex_client.mjs` gives every managed turn `workspace-write` access to every
configured `roleInstructions.writableRoots` entry. The shipped example tells
operators to put the entire coordination home there. That makes the canonical
Baton write succeed, but it also permits any shell command in the managed turn
to modify or remove `work.sqlite3`, `baton.json`, runtime files, logs, and any
other file below that directory without an approval request.

That contradicts the confirmed boundary: canonical Baton `claim`, message,
pass, and close operations are pre-authorized, while unrelated commands remain
closed and agents never mutate the SQLite authority directly. This is not the
"exact narrow allow rule" in the acceptance text; it replaces an unavailable
capability with general filesystem authority over the store.

The live proof tests only a Baton claim inside the granted root and a Baton
claim outside it. Add the missing negative control: an unrelated direct write
inside the coordination home must not succeed merely because Baton needs to
write there. The implementation needs a mediated Baton capability (or another
narrow execution boundary), not a general writable root containing the
authority.

### P1 — configuration validates that a root exists, not that it is useful or narrow

`config.mjs` accepts any non-empty list of absolute paths. A deployment with
`writableRoots: ["/tmp"]` and a Baton config under `/srv/baton` passes
validation and resume verification, then reproduces the original approval
failure on every Baton mutation. At the other extreme, `writableRoots: ["/"]`
also passes and grants far more than intended.

Fail closed on the relationship between the configured Baton authority and
the capability actually granted. Do not report the dispatcher healthy merely
because the app-server echoed an arbitrary requested root.

### P2 — repeated identical approval reports replay instead of incrementing

`RuntimePublisher.incident()` derives a stable operation id from
`cause`, `category`, `work`, and `episode`. A second approval request of the
same category during the same Work episode therefore replays the first
operation; it never reaches `incident_report()`'s coalescing update and does
not increment `occurrences` or `latest_ts`.

The confirmed model distinguishes transport retry from a newly observed
occurrence. Give each observed approval request its own operation identity,
while retries of that one publication retain the same id. Add an adapter-level
regression that files two same-category approval observations and proves the
authority reports one incident with `occurrences: 2`.

### P2 — the advertised live proof is not wired and defaults to a retired binary

`PROGRESS.md` says the proof runs as `npm run test:managed-write`, but
`tools/codex-event-bridge/package.json` contains no such script. The smoke file
also defaults to `/home/sl/opt/baton/v11/8835cd5/bin/baton`, so invoking it
without a second operand silently tests an old installed release instead of
the build being reviewed. Repository policy requires the deployment
executable and config to be explicit; it must not hard-code a local release.

Wire the documented command or correct the handoff, and require an explicit
candidate Baton executable (or obtain it from an explicit test configuration)
so a green proof is evidence about the candidate.

## Additional observation

When an open incident coalesces after a restart, the implementation updates
incarnation/session evidence but keeps the original `action_owner`. If runtime
configuration legitimately changes the owner, the sticky action remains owed
to the former participant. The correction should either update ownership to
the current gated lease or explicitly rule and test why first-owner retention
is the contract.
