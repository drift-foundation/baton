# Review — cross-Work continuation fence

**Work:** W99  
**Disposition:** decision required before implementation

## P1 — idle clears the only fence and reuses the tainted context

`tools/codex-event-bridge/src/event_bridge.mjs` stores one configured
`threadId` per target. An approval request enters `#denyAndRecover`, which sets
`state.blocked`; `#drain` refuses while that field exists. Both the client
`status` handler and `#turnCompleted` call `#clearBlocked`, however, and the
next drain starts the retained event on that same thread. The regression
"W3243: the turn ending drains everything that queued behind it" requires this
behavior.

That was consistent with the earlier wedge recovery ruling, but it is not a
Work boundary. Turn completion says the old turn stopped. It says nothing
about semantic intent retained by the thread. W30's interrupted Docker test
attempt followed by the W30 cleanup command during W28 is the observed
counterexample.

The minimum v11 correction is a distinct, sticky `tainted`/`quarantined`
target state:

- set it on the first unexpected approval request, before denial or interrupt;
- keep `blocked` for the live turn and its bounded recovery only;
- let idle/completion clear `blocked`, never `tainted`;
- refuse `#drain` and report `deliverable: false`/stack `ready: false` while
  tainted, including the failed Work, action key, turn and restart remedy;
- retain queued readiness events and rely on Baton's level-triggered action
  after a full managed-stack stop/start mints a fresh context; and
- publish the managed target as failed after the turn ends rather than
  presenting an idle-but-undeliverable target as healthy.

The official lifecycle already mints new context ids on every full start and
refuses to adopt an incomplete existing set. A dispatcher-only restart would
resume the same configured thread and is not a valid remedy; diagnostics and
docs must say **full managed-stack stop/start**. In-process replacement is not
a small v11 patch: the dispatcher config has only the minted thread id, while
the lifecycle/bootstrap owns cwd, first-turn durability, role instructions,
rendered locator state and replacement identity. That machinery belongs to
the v12 worker supervisor already under W28.

## P1 — correlation is keyed to mutable current state, not the request turn

The `serverRequest` handler files an incident from
`state.activeTurn?.event?.action`. Only `#blockedTurnId` considers the
request's authoritative `params.turnId`, and it does so after publication for
recovery, not correlation. Two races follow:

1. a request can arrive before the awaited `turn/start` continuation records
   `activeTurn`, producing a locator-less incident while the dispatcher still
   holds the exact event; and
2. a request/local turn-id disagreement is logged, but the incident is still
   attributed to the local action.

Record an immutable delivery attempt before calling `startTurn`, then bind the
returned turn id without replacing the event/action. Select incident origin by
the request turn id. A mismatch must remain visible and uncorrelated unless an
exact retained attempt matches; do not guess. Keep the command body, argv,
environment and filesystem operands out of the attempt and incident.

The active Work fields continue to mean "the readiness turn in which this
approval was observed." Semantic origin from a prior Work is not safely
derivable from an arbitrary command payload. The quarantine prevents the
future ambiguous Work-B case; when an old request's turn id matches a retained
tainted attempt, that observed attempt supplies the truthful Work-A origin.

## Required ruling

The earlier confirmed W3243 decision says retained events drain once the
target is idle and explicitly excludes dynamic v11 context replacement. The
new recurrence invalidates the first clause after an approval failure but
reinforces the second. Before code changes, the approver should confirm:

> An unexpected approval request permanently quarantines that v11 managed
> context for the remainder of the managed-stack start. Ending the turn does
> not restore deliverability. Recovery requires a full managed-stack restart,
> which mints a fresh context; v12 owns automatic replacement.

On confirmation, append a scoped supersession to
`work/records/2026/08/finding-readiness-target-wedged-turn/FINDING.md` and mark
this ruling confirmed here. Do not silently edit the old decision.

## Regression boundary

1. Deliver Work A and make its approval request race `turn/start`; the incident
   still names A from the immutable attempt.
2. Queue Work B, deny and interrupt A, then emit both completion and idle in
   either order. No turn for B starts on A's thread; duplicate terminal events
   do not clear quarantine.
3. A request whose turn id disagrees with the active attempt is reported but
   not misattributed.
4. Status and runtime publication distinguish live `blocked` recovery from a
   terminal but quarantined context and name the full-stack restart remedy.
5. Other targets continue draining independently; no action is rerouted to a
   different participant.
6. Stop cancels recovery timers. A fresh full start with a newly minted thread
   accepts the still-actionable Work B exactly once through canonical
   revalidation/level triggering.
7. Existing denial, never-approve, incident persistence/coalescing, redaction,
   queue bounds and exact execution-policy regressions remain green.

No protocol or application implementation was changed in this review.
