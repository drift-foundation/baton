# Review — cross-Work continuation fence, implementation round

**Work:** W99  
**Disposition:** changes requested

## P1 — a dispatcher-only restart clears the quarantine

The confirmed ruling scopes the quarantine to the managed context for the
remainder of the managed-stack start, and explicitly says a dispatcher-only
restart is not recovery because it resumes the same configured thread. The
implementation instead initializes `state.tainted` to `null` in every new
`EventBridge` object and keeps no fence outside that process. Stopping and
relaunching only the dispatcher against the same rendered configuration
therefore clears the quarantine. Baton's level-triggered readiness then
reoffers the still-actionable Work and the new bridge starts it on the same
approval-tainted thread.

This is not only a crash-durability concern. The documented low-level
deployment exposes app-server, dispatcher and readiness producer as separate
processes, and the connectivity guide already states that a dispatcher restart
loses its in-memory queue while retaining the configured thread. The W99 docs
now correctly warn that this restart is not a remedy, but the implementation
does the opposite.

I added the regression `W99: restarting only the dispatcher does not clear the
quarantine` to
`tools/codex-event-bridge/test/cross_work_fence.test.mjs`. It taints the first
bridge, stops it, starts a second bridge with the same configuration/thread,
and reoffers W28. The test fails because the second bridge starts one turn and
reports the target deliverable.

The fence must survive dispatcher process replacement for the same managed
context and clear only when the lifecycle supplies a freshly minted context.
The exact mechanism should be revalidated against lifecycle ownership, but it
must fail closed across a same-thread restart; process-local `tainted` state is
insufficient. The existing fresh-thread regression must continue to prove that
a full start can deliver the action once.

## P1 — an unmatched named turn is guessed to be the pending Work

`#approvalOrigin` treats every named request as `in-flight` whenever any
unbound attempt exists. It does not establish that the request's authoritative
turn id is the id that `turn/start` will bind to that attempt. A late or
disagreeing request that arrives during `turn/start` is therefore filed against
the pending Work even though the confirmed ruling says a turn-id mismatch is
reported without guessing a Work origin.

I added `W99: a different named turn racing turn/start is not guessed as that
Work`. With W30's `turn/start` pending, a request names
`turn-somewhere-else`; the incident incorrectly carries W30, episode 1 and its
action key. The existing positive race still passes when the request and the
eventual `turn/start` result both name `turn-W30`.

Correlation publication must establish the equality before attaching the
immutable attempt, for example by completing/deferred binding of the pending
request. Immediate quarantine, denial and bounded turn recovery must remain
immediate; only the unproven Work attribution needs to wait or remain
uncorrelated. A named mismatch must never acquire the pending action merely
because it arrived during a start call.

## What passed

The rest of the focused implementation matches the ruled same-process
boundary: the context is quarantined before denial, completion and idle in
either order do not drain W28, duplicate terminal events do not clear the
fence, another target continues independently, shutdown cancels the recovery
timer, a newly minted thread accepts W28 once, terminal runtime state is
`failed`, and diagnostics remain payload-safe.

I changed no protocol or application implementation. The only code-side
review changes are the two additive regression cases above.
