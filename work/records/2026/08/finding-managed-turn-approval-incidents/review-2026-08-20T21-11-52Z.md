## Findings

### P1 — `approvalPolicy: never` does not make canonical Baton operations executable

`tools/codex-event-bridge/src/codex_client.mjs:74-124` declares and verifies a
non-interactive approval policy. Its own contract correctly says that a command
the policy does not permit still fails closed. That is not the acceptance
boundary in this record: the managed reviewer must successfully execute its
narrow canonical Baton `claim`, message, pass, and close operations.

The motivating failure was not an interactive-policy disagreement. Codex
wrapped the Baton command in `/bin/bash -lc`, so the existing raw-executable
allow rule did not match. Setting the policy to `never` removes the prompt but
does not change that argv or make it match the rule. It therefore turns the
same failure into an immediate refusal.

It also removes the only trigger currently used for the durable incident:
`event_bridge.mjs:588-624` files one only after the app-server sends an
interactive approval request. A command refused internally under `never` may
produce no such server request, leaving the Work unclaimed and silent again.

The new tests assert request/response operands against fakes; they never ask a
live managed thread to perform one canonical Baton operation. Add a live or
equivalent end-to-end regression that proves the exact narrow operation
commits without approval. The correction must either provide the ruled raw
argv path or durably report the non-interactive refusal through another
observable app-server outcome; policy declaration alone is not the fix.

### P1 — the production and shipped dispatcher targets have no action owner

`RuntimePublisher.incident()` refuses before invoking Baton when
`actionOwner` is absent (`runtime_publisher.mjs:517-529`). The current live
reviewer projection reports `action_owner: null`, and the rendered dispatcher
configuration has no `identity.actionOwner` for either Codex target.
`conf/codex-event-bridge.template.json:12-27` and
`tools/codex-event-bridge/config.example.json:12-27` omit it too.

Consequently, the deployment which reproduced this defect cannot produce the
sticky incident the patch promises. Carry the action owner through the shipped
configuration/bootstrap path and make its absence fail deployment validation
when durable incidents are enabled; a warning in a background log recreates
the original invisibility.

### P1 — a stale runner may file an incident and choose another owner

Every other runtime write gates the supplied incarnation through
`_runtime_gate`. `incident_report()` only checks that the participant is active
and then reads whichever lease is current (`transitions.py:5285-5296`). A
superseded runner can therefore file with its stale incarnation while borrowing
the current runner's adapter/session facts.

The public transition also accepts `action-owner=` and lets the publisher
override the configured lease owner (`transitions.py:5200-5221`). Thus any
configured participant can create a sticky owed action in any other member's
Inbox. That contradicts the confirmed configured-action-owner boundary and
makes stale publishers authoritative after replacement.

Gate the reporter on the exact live incarnation and derive the owner from that
lease. If an explicit administrative override is desired, it needs a separately
ruled authority model rather than riding the runner verb.

### P2 — restart occurrences do not coalesce under the confirmed key

The confirmed decision says reports for the same participant, Work episode,
and approval cause coalesce. The unique index and lookup additionally include
`incarnation` and `category` (`authority.py:772-778`,
`transitions.py:5297-5304`). A managed-stack restart therefore opens a second
incident for the same still-unclaimed episode and cause instead of incrementing
the existing one.

Incarnation/session remain useful evidence on the incident, but they are not
part of the approved open-incident identity. Align the database key and lookup
with the recorded decision and add a restart-then-repeat regression.
