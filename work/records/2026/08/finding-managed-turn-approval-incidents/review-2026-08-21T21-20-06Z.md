## P1 — recovery rejects an exact turn identity the live path accepts

`EventBridge.#provenAction` sends `tainted.turnId` through the new
`#provenText` helper. That helper requires already-trimmed text. The stated
reason is that the live action normalizer stores trimmed values, but `turnId`
is not an action-locator field and does not pass through that normalizer.

The current boundaries are unambiguous:

- the generated app-server schema types an approval request's required
  `turnId` as `string`, with no trimming, pattern, or minimum-length rule;
- `#bindAttempt` accepts every non-empty string and stores it verbatim;
- `#approvalOrigin` compares the request value to that verbatim map key; and
- `#quarantineRecord` then persists the exact value the live path accepted.

The additive regression follows those boundaries rather than manufacturing a
marker by hand. `turn/start` returns `" turn-thread-codex "`; an approval names
that identical value; the live bridge matches it to W30 and durably writes an
`exact` marker with `incidentFiled: false`. On restart, `#provenText` rejects
only the padding and the recovered incident is filed with `work: null` rather
than the Work origin this dispatcher already proved.

That contradicts the confirmed rule that incident attribution remains
truthful and the round-4 correction that restart preserves a known origin.
Align the two boundaries. Either use the live accepted turn-id predicate for
recovery while retaining the stricter trimmed predicate for Work/action-key
text, or introduce and enforce one explicit turn-id contract at live binding
before an `exact` marker can be created. Do not make a hand-edited-marker test
the authority for a rule the live path does not enforce.

Additive regression:
`W99 review: recovery does not invent a stricter turn-id contract`.
