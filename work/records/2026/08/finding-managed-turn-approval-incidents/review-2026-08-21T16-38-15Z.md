# Review — durable quarantine and deferred attribution

**Work:** W99  
**Disposition:** changes requested

## P1 — damaged quarantine evidence fails open

`QuarantineStore.load` treats every read error except `ENOENT`, and every JSON
parse error, as an absent marker. `#restoreQuarantine` then leaves the target
clean and the restarted dispatcher can deliver Work on the same persistent
thread. A marker at the exact server/thread key is positive evidence that this
context was quarantined. Losing its diagnostic payload is not proof that the
context forgot the interrupted Work.

I added `W99: a malformed marker never makes its context deliverable`. It
writes malformed JSON at the exact quarantine key, starts a bridge with that
same rendered configuration, and reoffers W28. The test fails because one turn
starts. The regression deliberately permits either safe implementation:
startup may refuse with a marker/quarantine error, or the target may load as an
unknown-but-tainted context. It only forbids the current clean/deliverable
result. `ENOENT` remains the legitimate clean-context case; an existing but
unreadable or malformed marker must fail closed.

## P1 — restart can lose the deferred approval incident

The named in-flight correction properly defers Work attribution until
`turn/start` binds. The quarantine marker is committed immediately with
`correlation: pending`, but the incident has not yet been filed. If the
dispatcher stops or dies in that window, `#drain` never reaches its `finally`.
On restart, `#restoreQuarantine` assumes the observing process already filed
the incident, restores the marker unchanged, and publishes no incident. The
context stays fenced, but the confirmed W415/W99 durable operational notice is
lost and its correlation remains permanently `pending` even though the old
attempt can no longer be proven.

I added `W99: restart cannot lose an incident whose attribution was pending`.
It holds `turn/start` unresolved, observes the approval and persisted pending
marker, stops the first dispatcher, and starts a second against the same
configuration. Neither process files the required incident; the regression
fails with zero incidents.

Restoration must recover this window as uncorrelated, after the runtime
publisher can accept the report. More generally, a process cannot safely infer
that a fire-and-forget publication completed before it died. Re-publication on
restore is safe under the already-confirmed incident coalescing boundary; an
equivalent durable acknowledgement is also acceptable. A restored `pending`
origin cannot remain pending because the immutable attempt that could prove it
was process-local.

## Confirmed corrections and non-blocking limit

Both findings from the preceding review are corrected. The original
same-thread restart regression now shares one rendered configuration and stays
fenced, while a new thread sharing the marker directory remains clean. The
positive and mismatched `turn/start` races now wait only for attribution,
resolve exact versus unmatched correctly, and keep quarantine, denial and
bounded interruption immediate.

I have no blocking objection to leaving old markers unpruned in this bounded
v11 correction. They are small, keyed to contexts that a full start replaces,
and safety favors retention when lifecycle does not yet own an explicit
cleanup boundary. They are operational fence records rather than the durable
decision history; a future lifecycle-owned retention policy can be separate
work if their accumulation becomes material.

I changed no protocol or application implementation. The only code-side
review changes are the two additive regressions above.
