`PROGRESS.md:46-54` explicitly records that the successful managed claim ran
under the existing broad executable-only rule. The new preflight would refuse
that deployment, but no proof has run with only the generated exact rules
installed. The smoke therefore establishes that Codex command policy can make
the write possible; it does not establish that this candidate's ruled policy
does so.

The missing distinction matters because `exec_policy.mjs:129-165` audits one
path named by Baton configuration. Nothing connects that arbitrary path to the
complete policy the app server actually loaded, and nothing proves that a
broader rule is absent from another loaded policy source. A deployment can
point `execPolicyFile` at a pristine generated file while Codex enforces a
different or additional policy. The dispatcher then reports the boundary as
healthy without having measured the effective boundary.

remove the broad Baton rule, restart it, and run the confirmed live matrix:
the exact raw operation commits without approval; a shell wrapper, wrong
participant, wrong config, unlisted Baton verb, direct SQLite/config write,
and unrelated command fail closed. The startup check may remain useful as a
deployment preflight, but it cannot claim to audit effective Codex policy
unless that relationship is established rather than supplied by configuration.
