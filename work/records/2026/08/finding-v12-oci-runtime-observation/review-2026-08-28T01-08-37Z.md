## [P0] A removed known runtime is never observed absent

`reconcile_runtime` calls `_observed` only inside `len(found) == 1`. Once a
real runtime has been removed, `docker ps --all` no longer lists it, so the
function takes the zero-listing branch and records `uncertain` without asking
the adapter about the exact `runtime_id` already fixed on the attempt.

The positive-absence unit case does not reproduce that path: its fake listing
continues to return the runtime while `observe` says it is absent. That race is
possible, but it cannot establish the ordinary post-removal path. The accepted
four-state seam therefore does not actually expose positive absence for a
known runtime in normal operation.

Required correction: when zero candidates are listed and an exact identity is
known from the durable attachment or the current start receipt, observe that
identity. Preserve `absent` and `uncertain` distinctly; only a reconciliation
with no exact identity should remain unable to ask the question.

## [P0] Observation failure preserves stale `running`

`_observed` propagates adapter exceptions and raises on malformed, incomplete,
or unknown answers before any call to `observe(... value="uncertain")`. If the
attempt was previously observed running, the durable row therefore still says
`running` after the exact observation failed.

The Docker case intended to prove the opposite is inverted:
`test_an_observation_the_adapter_cannot_make_is_never_running` asserts only
that the row is not `quiescent`, so stale `running` satisfies it. Its prose
says each failure is a reason to say `uncertain`, but neither implementation
nor assertion establishes that result.

Required correction: make every failed or unrecognized exact observation
produce a durable `uncertain` answer without erasing the exact attached
identity. Add direct assertions that the returned and durable state are
uncertain and that neither remains running.

## [P1] The real-engine proof uses a superseded launch contract

The W26294 lifecycle cases call `request_runtime_start(...,
environment=self.launch())` and rely on the four `BATON_WORKER_*` variables.
The durable v12 ruling supersedes that transport: the worker must receive the
fixed read-only `/run/baton/launch.json` document containing `schema`,
`session`, `contract`, and `role`, with no environment fallback.

Observation is independent of launch metadata, so this does not require
waiting for the whole worker-launch correction. The real-engine proof can use
a bounded container dedicated to running/quiescent/absent observation, or it
can be rerun through the live launch document after W26291 lands. It cannot use
the retired environment seam as acceptance evidence.

## [P2] One attachment constructor violates its new closed document

`documents.CONTRACTS["runtime.attached"]` now requires `observed`, and the
normal `_attach` action supplies it. The same-runtime recovery return in the
`ContractRefusal` branch still calls `documents.runtime_attached` without that
member. Current attachment immutability appears to make the branch unreachable;
that is a reason to remove it or prove it unreachable, not to leave a latent
closed-document refusal.
