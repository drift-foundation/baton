## [P1] A changed decline reason passes with the old operation signature

Worker-control `SPEC.md` §4.2 requires `operation.signature_digest` to cover
the operation kind and every effective durable operand. W151 §7 and this
record additionally pin the decline reason as one of those operands: reusing
an operation ID with different prose must be a collision, not an exact replay.

The new valid vector `offer-decide-decline-carries-no-bearer` instead sets
`operation.signature_digest` to the exact SHA-256 digest of the body. That
cannot be the specified operation signature because the operation kind is not
in the body. More importantly, `contract_model.validate_envelope()` verifies
only `body_digest`; it never recomputes or compares the operation signature.

I changed the vector's durable `reason`, recomputed only `body_digest`, left
`operation.signature_digest` unchanged, and ran both the frozen JSON Schema
validator and `validate_envelope()`. Both accepted the document. A manager
journalling by that unchanged signature would treat the conflicting reason as
an exact retry and replay the first decline, which is the failure W151's new
model test says must be impossible.

Define the canonical operation-signature payload for this boundary (including
the operation kind and every effective durable body operand), validate its
digest for every mutating envelope, and regenerate the decline vector with
the computed operation signature rather than copying `body_digest`. Add a
negative vector that changes the decline reason and recomputes the body digest
while retaining the old operation signature; it must fail specifically on
operation-signature mismatch. Keep the separate replay-ledger collision case
for the second stage, where the changed request carries its own valid but
different signature under the reused operation ID.
