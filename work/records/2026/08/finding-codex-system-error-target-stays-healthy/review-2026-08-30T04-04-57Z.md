# Review — 2026-08-30T04:04:57Z — `baton.codex`

Disposition: **changes requested**. The terminal-status fence correctly keeps
an observed `systemError` sticky, retains readiness identities, publishes
`failed(internal)`, fails control/lifecycle health, survives reconnect through
the authoritative resume status, and leaves failed turns whose thread returns
to `idle` reusable. One refresh-error branch still recreates the incident's
false-idle state.

## Finding

### [P1] A failed status refresh republishes stale `idle` and drains the queue

`#turnCompleted` settles a failed delivered turn and then calls
`readThread()` to distinguish reusable `idle` from terminal `systemError`.
That ordering is the correction's central boundary. At
`event_bridge.mjs:2530`, however, a rejected status read is only logged. The
method then continues to `#publishReusableIdle` using whatever status was
already cached. In the ordinary delivery path that cached value can still be
the pre-turn `idle` state: `activeTurn` prevented delivery overlap, but the
fake and a notification-lagging real server need not have published an
intermediate status update.

The additive regression
`system_error_target.test.mjs:220` makes the post-failure `readThread()` reject.
The bridge publishes `idle`, reports the target ready/deliverable, and starts
the retained next readiness action before it has established whether the
configured context is `idle` or `systemError`. That is the original false-
healthy/never-drains defect with the status read unavailable rather than
successful.

Fail health and delivery closed while the post-terminal status is unknown.
Do not make a transient read error a sticky `systemError`; record an unknown
or retrying status, retain the exact queue/in-flight identities, and reconcile
until an authoritative reusable or terminal status arrives. The same rule
must cover a completion that beats `turn/start`, because its deferred idle
publication ultimately consumes the same cached status.

## Confirmed corrections

- Observed `systemError` and unknown future loaded statuses create a sticky
  terminal failure; later `idle` notifications cannot reopen that context.
- Control status carries participant, configured session, failed turn,
  provider status, current queued-action count and the full-stack remedy;
  `ready` and `deliverable` are false.
- Failed turns whose authoritative refreshed status is `idle` remain reusable,
  and completed turns do not run failed-claim settlement.
- Reconnect re-observes `systemError` from the configured thread and a fresh
  managed-context thread drains the retained offer exactly once.
- The W39868 secondary-claim settlement remains intact in the combined suite.
