2. [P2] AN EXPANDED BRANCH STILL MATERIALIZED PAST THE CAP

My round-2 correction changed `_dependency_edges` from fetch-all to
`COUNT(*)` plus an ordered `LIMIT` — and then `_expand_dependency` passed the
raw expansion value as that limit. So the unbounded read moved one caller up
rather than going away: with 240 direct dependents and an expansion of 250,
the SQL returned all 240 and only the Python loop stopped drawing at the cap.

CORRECTED: the row limit is `min(page, occurrence_cap - occurrences)`. The
exact total still comes from the COUNT, so the omission is disclosed without
having seen the rows.

AND THE FLAG HAD TO FOLLOW. Bounding the limit alone broke
`test_the_occurrence_cap_actually_bounds_an_adversarial_branch`: the loop
could no longer discover the cap for a branch the SQL had already trimmed, so
`capped` stayed false while the view was in fact full. WHICH bound stopped a
branch is the difference between "there is more here, press Enter" and "this
view is full", and only the second is `capped`. The branch records `capped`
when the remaining allowance — not the requested page — is what truncated it.


3. [P2] DEPTH-TWO ROWS MOVED A NODE BETWEEN LAYER COLUMNS

`_layered` indented every downstream edge to the center column and
right-justified every upstream edge to end there, whatever the depth. In
`A --blocks--> B --blocks--> C` centered on A, B was the first row's target at
the center's right edge and then the second row's source at column zero. One
node in two columns is an adjacency list with indentation, not the layered
form the contract approved.

CORRECTED: `_columns` derives ONE start offset per Work from its
shortest-path layer, and every row draws from its source's column with the
arrow reaching the target's. A node's column is now a property of the node
rather than of the row it happens to appear on. Measured on the corrected
renderer:

  [W21 queued] --blocks--> [W18 block]
                           [W18 block]
                           [W18 block] --blocks--> [W19 block]
                                                   [W19 block] --blocks--> [W20 block]

W18 is the center and holds column 25 in both its appearances; W19 holds its
own column in both of its.


4. [P2] OVERFLOW TOKENS WERE OUTSIDE THEIR BRANCH POSITION

`_ordered` emitted both of the center's branch tokens immediately after the
center, so `[+N blockers]` sat between the center and the blockers it belongs
to, and `[+N dependents]` came before any dependent had been drawn. The same
shape at deeper layers.

CORRECTED: a token is placed by its BRANCH, not by the node that owns the
branch. `_edge_rows` builds the ROW_WORK traversal, `_branch_anchor` finds
the last VISIBLE member of each branch, and the list is rebuilt once rather
than inserted into while its indices move. A branch with nothing visible has
no member to follow, so its token takes the slot the branch itself would
occupy — after the owner's row going downstream, before it going upstream,
which is the direction each side reads.

The wide form also puts the token in its SIBLINGS' column rather than its
owner's. They are one layer out, so aligning with the owner would print
`[+2 blockers]` in the center's column, reading as something about the center
instead of one more of the rows above it.

reviewer case and NOT the upstream one, and the reason is structural rather
