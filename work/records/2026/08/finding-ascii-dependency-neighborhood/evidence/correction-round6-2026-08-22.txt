2. [P1] THE PATH GUARD REFUSED AN EDGE THE CAP WOULD OMIT

`_expand_branch` fetches a bounded direct page and then walks its siblings.
An earlier sibling's descendants can spend the remaining allowance between
the fetch and a later sibling's turn — and the loop tested `far in path`
BEFORE testing whether that edge could still enter the response. So a closing
edge raised `GraphInvalid` although the cap would have omitted it and
`_refuse_cycles` would have seen a perfectly acyclic admitted graph.

That contradicts the rule I pinned in round five: a cycle whose closing edge
was cut by the cap or a branch page is not reported, because the graph
actually returned is acyclic. Refusing over an edge the response does not
contain is the same lie as hiding one it does — in the other direction. I
wrote the rule and then left the fast guard running one step in front of it.

CORRECTED, exactly as the review sets out. For an edge not already drawn, cap
admission is decided FIRST: if no occurrence remains, the branch discloses the
cap and the exact remaining direct omission and returns, without inspecting
that edge for a cycle and without recursing through it.

The path guard then applies to an edge that WILL be in the response — either
it is about to enter it, or it is already part of the admitted graph. Both are
edges the operator can see, so refusing over them invents nothing.
`_refuse_cycles` is unchanged.
