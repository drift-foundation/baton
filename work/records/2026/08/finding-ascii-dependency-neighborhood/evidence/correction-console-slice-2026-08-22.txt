2. [P1] REPEATED WORK ROWS TRAPPED KEYBOARD SELECTION

The renderer keeps one row per canonical EDGE, so a shared DAG Work occupies
consecutive rows. Movement stepped by ROW and the anchor resolved to the
Work's FIRST appearance — so from a shared Work, `j` landed on another row
carrying the same id, the anchor did not change, and the next key started from
the first appearance again. Selection was stuck there permanently.

The contract already said what to do and I read only half of it: "`j`/`k` and
Up/Down traverse one deterministic UNIQUE-NODE order" and "all repeated
appearances of the selected ID receive the selection attribute". Those are two
different lists — movement over distinct stops, painting over every
appearance — and I served both from the row list.

CORRECTED: `_graph_keys` is the traversal order, every distinct selectable key
once, in first-appearance order. Painting is unchanged and still highlights
every appearance.


3. [P2] A SHORTCUT LEFT A FALSE DEPTH-FRONTIER TOKEN

`frontier[key]` is recorded the moment a visit runs out of depth. A later
SHORTER path may legitimately reach the same branch with depth to spare and
draw its edges — and nothing cleared the earlier entry, so the graph claimed a
direct dependent was hidden by depth while drawing that exact edge.

That is the same defect class as the shared-branch omissions two rounds ago: a
bound describing something other than what is on screen. I added `frontier`
this slice and did not carry that lesson into it.

CORRECTED: `_expand_branch` clears `frontier[key]` when it expands the branch.


4. [P2] THE APPROVED SEARCH ENTRY WAS ABSENT

Search mode is dispatched to `_search_mode_key` before the table's `b` case
ever runs, so `[b]` on a search result was a no-op. The contract names entry
from the table AND search. `_search_mode_key` opens the graph now, through the
same `_open_graph` the table uses, so the frame, the depth and the Back
behaviour are identical.
