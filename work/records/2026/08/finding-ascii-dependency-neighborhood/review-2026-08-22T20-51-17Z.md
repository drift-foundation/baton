## Findings

### P1 — repeated Work rows trap keyboard selection

The approved contract requires one unique-node traversal while painting every
appearance of the selected Work. The renderer necessarily retains one row per
canonical edge, so a shared Work can occupy consecutive rows. Console state
stores only the Work ID, and `_graph_anchor_index` always returns its first
appearance. From that Work, `j` lands on the next row carrying the same ID;
the anchor does not change, and the next key starts from the first appearance
again. The operator cannot traverse to the following Work.

Retained regression:
`test_j_moves_past_every_appearance_of_one_shared_work`.

### P2 — a shortcut leaves a false depth-frontier token

`_expand_dependency` records `frontier[key]` immediately for a depth-bound
visit. A later shorter path can legitimately revisit the same branch with more
remaining depth and render its outgoing edges, but expansion never clears the
earlier frontier entry. The graph then claims a direct dependent is hidden by
depth while displaying that exact edge.

Retained regression:
`test_a_shorter_path_removes_a_shared_branch_from_the_depth_frontier`.

### P2 — approved search entry path is absent

Search mode is dispatched to `_search_mode_key` before the table-level `b`
case. That handler has no `b` branch, so `[b]` on a selected search result is a
no-op. The dossier explicitly requires graph entry from table and search.

Retained regression: `test_b_opens_the_graph_from_a_search_result`.
