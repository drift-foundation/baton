**Verdict:** changes requested. The snapshotted projection preserves the

## [P1] Deeper layers invent center edges and drop canonical edges

The projection correctly returns directed `{blocker, work}` edges. The
renderers do not render those edges. `_ordered` emits one entry per unique
node, while `_layered`, `_adjacency`, and `_stacked` pair every non-center
entry with `view["center"]`.

For a canonical chain `A --blocks--> B --blocks--> C` centered on A at depth
2, the wide renderer currently emits:

```text
[A]
[A] --blocks--> [B]
[A] --blocks--> [C]
```

It drops `B --blocks--> C` and invents an `A --blocks--> C` relationship the
authority never held. A shared DAG node similarly loses its actual incoming
edge identities. This violates the central guarantee that every rendered
relationship derives from the canonical projection.

The additive regression `test_depth_two_renders_the_edges_that_actually_exist`
fails on the missing B-to-C edge. Render exact projection edges at every
depth and preserve a separate unique Work selection identity where an edge or
node appears more than once.

## [P1] Stacked selection targets a different Work than the row displays

For a downstream entry, `_stacked` attaches the far consumer's `work` field to
the first row but paints the center token on that row; the actual far token is
a non-selectable `ROW_TEXT` row. The future console would therefore highlight
the center while Enter recenters on the consumer.

The additive regression
`test_every_selectable_stacked_row_displays_its_own_work` fails with a
consumer selector expected on a row that visibly contains the center. Every
selectable row must display the selector for its own `work`; presentation-only
rows cannot carry the only visible identity of the selected target.

## [P2] The 200-occurrence cap still materializes unbounded fan-out

`_dependency_edges` returns a Python list containing every direct edge, and
only afterwards does `_expand_dependency` slice it to the branch limit and
stop at the occurrence cap. A center with adversarial fan-out therefore
allocates memory proportional to the entire fan-out even though the response
claims to be a bounded 200-occurrence view. The current cap regression creates
only six consumers and explicitly does not exercise the cap.

Keep exact omitted direct counts, but obtain them with bounded row
materialization (for example a count plus an ordered limited page) and add a
regression that actually crosses the 200-occurrence boundary. Expansion state
must not turn an arbitrarily large branch into an arbitrarily large Python
list before the cap applies.
