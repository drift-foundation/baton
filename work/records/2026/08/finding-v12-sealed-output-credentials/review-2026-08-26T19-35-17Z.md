## Findings

### [P1] The manager receipt binds a caller claim, not a validated completion envelope

`OciAdapter.__init__` accepts `completion_manifest_digest` as an independent
optional operand. `sealed_result` copies that value into `sealed.json` and its
replay binding, but no manager path opens `/output/output.json`, validates its
`completionManifest` shape and semantics, recomputes its digest, or compares
its answers with the exact input manifest.

The progress account says this belongs with W6633 because that Work publishes
the document. That is the wrong side of the boundary. W6633 owns the worker
publisher; W6634's manager owns validation before freeze and the receipt over
what it validated. W14251's third review and thread message 18646 require:
exactly one answer per declaration, no extras or omissions, exact
`name`/`type`/`path`, required outputs never `missing-optional`, standalone
completion semantics, and a receipt binding the recomputed digest.

W14251 itself still has changes requested over that frozen contract, including
whether the receipt digest is mandatory. W6634 must depend on W14251, consume
its settled validator, and derive the digest from the owned worker document.
An optional caller-supplied digest is not evidence that validation occurred.

### [P1] Post-engine answer refusals bypass the credential lifecycle

`start` guards vector composition and handles a non-zero engine status, but
`self.run(argv)` and the returned runtime-id ownership occur after that guard.
The engine may already have created a container when either boundary refuses.
Those exits propagate directly without `_refused_start`, so the caller receives
no explicit `torn-down` versus `unresolved` lifecycle answer and no candidate
probe decides whether the mount is still live.

The additive
`test_a_started_runtime_with_an_invalid_identity_is_explicitly_unresolved`
drives an engine answer carrying text that cannot become a durable runtime
identity. The engine answer refusal escapes unchanged; the volatile root and
live bearer remain, but the refusal does not say `unresolved`. Route every
post-create answer/identity/lifecycle-record failure through a decision that
uses the known runtime identity when available and otherwise probes the exact
attempt candidates before cleanup.

### [P1] Proved failed recovery leaves a record that can never converge

When disagreement recovery proves the runtime gone, `_recovery_failed` calls
`discard_orphan(attempt)`. That removes only the volatile root. The durable
credential lifecycle record remains `live`, still naming the deleted root and
container.

The additive `test_a_proved_failed_recovery_removes_its_stale_record` proves
the root is gone and the record remains. A later recovery reads that record,
finds no runtime, and cannot adopt or reach ordinary absence; with an empty
candidate list `_recovery_failed` also computes `gone=False`, so the stale
state is permanently unresolved. A proved cleanup must remove or durably
settle the exact lifecycle record as part of the same ordered ending.

### [P1] The mandatory boundary inventory still contains six W6634 orphans

The fifth evidence says W6634 has zero outstanding inventory entries and then
lists six of its own orphan owners: `_relative`, `collected_result`, and four
`declared_outputs` boundaries. Being present in an older shared failure does
not make entries in this Work's files someone else's acceptance debt. Resolve
or correctly attribute all six before sign-off; the durable evidence must not
claim both zero and six.
