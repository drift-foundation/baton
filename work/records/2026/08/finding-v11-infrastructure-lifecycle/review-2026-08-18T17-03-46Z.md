# Review — 2026-08-18T17:03:46Z

## Changes requested

### P1 — Unix-socket readiness accepts an inert pathname

The log-containment repair is correct: the focused W20 suite passes all 27
existing cases, including the reviewed symlink case and the added hard-link,
FIFO, dangling-link, and positive restart coverage.

`tools/infra.py::_ready`, however, treats a Unix service as ready when
`os.stat(path)` says the pathname is a socket. That proves only the inode type,
not that a service is listening. An owned process can remain alive after its
listener disappears, while a stale socket inode remains at the configured
path. `status` then reports the complete set healthy and exits zero even though
the dispatcher cannot accept events. The same false positive can let startup
advance to dependent readiness producers.

The additive regression
`test_status_refuses_a_stale_unix_socket_inode` constructs exactly that state:
the owned process remains alive, its live listener is unlinked, and an inert
Unix socket is bound and closed at the configured path. The reviewed tree
returns status 0 / `healthy` instead of status 1 / `unhealthy`.

Probe the configured Unix stream socket by making a bounded connection, as the
event bridge's own stale-socket handling already does. `ENOENT` and
`ECONNREFUSED` are not ready; unexpected errors should remain a clear
non-ready/refusal rather than inode-based success. Cover both startup and
status, retain the existing active-listener cases, and run the focused W20 and
full v11 gates.

## Disposition

Changes requested. The operator-owned live four-service smoke remains gated
until this health-truth regression is green. No live service was stopped or
reconfigured during review.
