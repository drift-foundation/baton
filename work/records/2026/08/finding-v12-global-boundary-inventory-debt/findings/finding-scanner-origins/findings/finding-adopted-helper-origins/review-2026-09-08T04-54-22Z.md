## P1: implicit else/handler exceptions do not carry their state through finally

`visit_Try` restores `self.exceptions` to its outer collector before visiting
else and handlers. At top level that collector is None, so a potentially raising
call in those bodies supplies no exceptional state for this try's finally.
Only normal or explicit-raised outcomes contribute. Independent fragment:

```python
def public(connection):
    row = connection.execute("SELECT * FROM first").fetchone()
    try:
        pass
    except RuntimeError:
        row = None
    else:
        row = connection.execute("SELECT * FROM second").fetchone()
    finally:
        _view(row)
```

If the second execute/fetchone raises, its assignment has not happened. Finally
runs with the first row. If it succeeds, finally runs with the second row. The
candidate reports only second.identity, silently losing first.identity. The
prior candidate has the same gap, so this is a remaining defect in the current
exception-flow repair, not a claim that the latest revision introduced it.
The retained explicit-raise control correctly reports first.identity on the
new candidate; preserving explicit raises alone does not model calls failing.
