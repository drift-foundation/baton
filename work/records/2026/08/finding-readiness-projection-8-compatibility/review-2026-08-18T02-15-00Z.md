## What I checked rather than accepted

**The central claim: the participant-action envelope genuinely did not
change across the bump.** This is what makes accepting 7 *and* 8 in one
validator safe rather than a shortcut. Read from the live projection-8
authority, neither action kind carries a changed field:

    work action:       action_key, claimed, config_generation,
                       episode_seq, kind, local_id, phase, title, work
    obligation action: action_key, completes_by, flavor, kind, kind_name,
                       message_seq, owed_by, seq, status, team, thread,
                       trial, work

No `route`, no `current`. `owed_by` is an endpoint struct that W245 never
touched, and `claimed` was derived from the claimant column before and
after. Nothing the bridge consumes changed meaning, so the two majors are
genuinely the same contract here.

**The boundary is exactly 7.x/8.x.** Probed the validator directly with
`6.2, 7.0, 7.9, 8.0, 8.4, 9.0, 10.0, 80.0, "8", "8.0.1", "", "0.0",
null, 8` — accepts precisely 7.0/7.9/8.0/8.4 and refuses the rest.
`"80.0"` refusing matters: a prefix or `startsWith` implementation would
have let it through.

**One validator, not two.** `baton_readiness.mjs` re-exports the Codex
bridge's `validateEnvelope` rather than copying it, so there is no second
gate to drift. A search for the contract string finds exactly one
implementation.

**Acceptance 6, packaging half — nobody had stated this.** Built a fresh
distribution and exercised the PACKAGED ACP validator directly at
`lib/acp-baton-bridge/src/baton_readiness.mjs`: it accepts 7.0 and 8.0
and refuses 9.0, so the cross-package relative import resolves inside a
release as well as in the checkout.

**Acceptance 6, runtime half.** Live evidence rather than a claim: I am
receiving readiness wakes from this projection-8 authority through the
ACP path, including the one that delivered this review obligation.

**Suites.** Codex bridge 42/42 across all seven files (2+15+2+7+7+6+3);
ACP gate 36/36. The `PROJECTION_VERSION`-tied regression does what it
says: a bump to a major outside the accepted set fails it.

## Non-blocking observations

**1. The refusal message leads with the wrong projection.** It reads

    projection "9.0" does not carry the projection-7 participant-action
    contract (also accepted: projection 8)

Projection 8 is the CURRENT release projection, not an afterthought. An
operator meeting this string on a projection-8 authority reads "the
bridge wants 7", and this is precisely the string read during the outage
this Work exists to prevent. Suggest naming both symmetrically —
"projection-7/8 participant-action contract". The codex test asserts
`/also accepted: projection 8/`, so it moves with the wording.

**2. A dead condition the diff rewrote and kept.** In

    if (!match || ![7, 8].includes(major) || Number(match[2]) < 0)

`Number(match[2]) < 0` can never be true: the regex captures `([0-9]+)`,
so the minor is always >= 0. It was already dead before this change, but
the diff rewrote that exact line and preserved it, which reads to the
next maintainer as a deliberate guard. Either drop it or make it a real
bound.

**3. Out of scope, flagged so it is not lost.**
`tools/codex-event-bridge/README.md:193` still describes the
"projection-5 participant-action contract". That document belongs to W5
(public docs), not to this Work.
