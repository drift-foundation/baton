WHAT THE CORRECTION CHANGED

  [P1] THE ADAPTER IS THE THIRD MUTABLE INPUT. `_ask` validated `agent.probe`
  and `agent.inquire` before `store.transact` could decide replay. The adapter
  is mutable external state and is not a signed operand; replay does not call
  it and does not need it. An exact retry after a restart that left no
  reachable adapter was refused over a capability it had promised not to use,
  with its durable answer sitting in the journal.

  The pair is checked inside the fresh action now, beside the clock and the
  live authority read that the third and fourth corrections moved for exactly
  this reason. `store.transact` returns the replayed value from `replay()`
  BEFORE `BEGIN IMMEDIATE`, so the action -- and therefore the adapter -- is
  never reached on the replay path. That is the mechanism, read rather than
  assumed.

  THE NON-DURABLE HALF IS KEPT AND NOW ASSERTED. A `ContractRefusal` with
  `durable=False` raised inside the action takes `ROLLBACK TO act` and
  `ROLLBACK`, so a fresh request carrying an unusable adapter journals no
  operation and leaves its identity free. The new case proves the freedom the
  way it matters: it re-runs the SAME operation id with a usable adapter and
  requires a fresh commit rather than a replay.

  THE PROPERTY IS STATED OVER ALL THREE INPUTS.
  `test_nothing_mutable_is_consulted_before_the_journal_decides` counted the
  clock and the authority, so its universal name was broader than what it
  proved -- which is what the review found. It counts adapter INSPECTION too,
  through a proxy that records attribute access rather than calls, because the
  protocol check reads the two attributes without calling them and a
  call-counting proxy would have reported zero however early the check ran.

WHAT MOVED THAT THE REVIEW DID NOT ASK FOR: NOTHING, and one consequence

  `_bound_session` stays before the action. The stable signature is built from
  the durable binding, so it has to be read to know which operation this is;
  the fourth correction established that boundary and this one does not
  reopen it.

  Refusal PRECEDENCE changed for fresh requests as a consequence, and it is
  recorded in FINDING.md rather than left to be discovered. The adapter check
  used to run ahead of `_bound_session`; inside the action it necessarily runs
  after. A fresh call carrying BOTH an unusable adapter and an unbound session
  now refuses `refused/precondition` where it used to refuse
  `integrity/schema`. No case asserted the old order and the pairing is closed
  either way, but a caller diffing refusals across builds would read the
  change as a regression if nobody had written it down.
