## [P0] The promised `0444` file becomes `0400` under a restrictive umask

`launch.materialize` passes `READ_ONLY_FILE` (`0o444`) as the creation mode to
`os.open`, but a creation mode is filtered by the process umask. Nothing later
restores the pinned exact mode. A manager running under the common service
umask `077` therefore authors a manager-owned `0400` file. The fixed container
user is uid 65532, so the read-only bind carries a file that worker cannot
read; the positive launch regresses to the original non-runnable worker.

Independent reproduction from `v12/python`:

```text
env PYTHONPATH=src python3 -B -c '<materialize under os.umask(0o077); stat>'
0o400
```

The existing mode case observes only the review process's default umask and
therefore passes. Materialization must establish the exact final readable mode
independently of ambient umask without introducing a writable interval, and a
regression must set and restore a restrictive umask. The positive real-engine
case should run through that materialization boundary as well.

## [P1] The canonical OCI start seam still permits no launch document

`OciAdapter.__init__` defaults `launch_delivery=None`, `run_vector` defaults
`launch_delivered=None`, and both silently omit the fixed mount. The public
`start` path can therefore create the same adapter-started reference worker
that this Work exists to make runnable; only the worker later refuses it. The
boundary inventory explicitly calls `None` a legal answer, so this is current
contract rather than a test-only escape hatch.

The live finding says the manager authors the document and the adapter mounts
exactly that file. Make the canonical reference-worker construction/start
boundary require a materialized `LaunchDelivery` and refuse before the engine
when it is absent. Worker-side missing-document refusal remains valuable
defense and can be driven below or outside the canonical manager start seam.

## [P1] Launch roots are never ended

`launch.discard` exists, and `PROGRESS.md` says the adapter owns both exposure
and teardown, but no production call reaches it. `_refused_start` and
`_undelivered` settle only credentials; `destroy` calls only credential
`_torn_down`. Thus a refused start and a runtime proved absent both leave the
attempt-private `0555` root and world-readable document indefinitely. Besides
retaining session/contract/role metadata, this makes the implementation claim
false and leaves unbounded manager storage behind.

Give the launch delivery one explicit ending: discard it only after the same
evidence that no runtime can hold its mount, and preserve an unresolved result
when absence cannot be proved. Add refused-start, engine-uncertain, and
destroyed-runtime regressions.

## [P1] `describe.launch` contradicts the pinned answer shape

The pinned finding says `launch` is “the sorted member names of the validated
launch document.” That document has exactly `schema`, `session`, `contract`,
and `role`. `launched` strips `schema`, and both unit and real-container cases
currently require only `contract`, `role`, and `session`.

Either report all four pinned member names or obtain and record an explicit
superseding clarification that `launch` means only agent-visible value
members. The implementation comment that schema is the program's business is
a plausible proposal, but it is not the recorded decision currently being
implemented.
