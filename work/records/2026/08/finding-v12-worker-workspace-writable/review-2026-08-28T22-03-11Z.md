## [P0] The worker still cannot write the workspace

`assignment_workspace` now establishes `WORKSPACE_DIR = 0775` exactly, but
that is the same effective mode measured before the change. `run_vector`
accepts an optional `workspace_gid`; `OciAdapter.start` does not pass it. The
actual execution vector therefore remains `--user 65532:65532`, and no new test
exercises create, update or removal by the worker. This is an exact-mode
hardening, not the acceptance correction.

## [P0] An arbitrary workspace gid is not a least-privilege identity

The planned wiring reads `workspace.st_gid` and changes the primary identity to
`65532:<gid>`. The operand accepts every non-negative integer, including zero.
On a manager running with gid 0 this launches `65532:0`; another service group
may likewise carry authority unrelated to this workspace. The development
probe's gid 1000 does not prove the general boundary.

This also conflicts with durable decisions: W6632 pins a fixed runtime user;
W6633 says its image `USER 65532:65532` and the adapter's exact `--user`
restriction are asserted together so they cannot drift; and W33936's own
acceptance names the fixed worker identity. Those are product/security
decisions, not test literals the implementer may mechanically update.

The installed Docker CLI exposes `--group-add`, so a decision-worthy direction
is to retain primary `65532:65532` and grant an explicitly provisioned,
non-authority workspace group only as supplementary execution authority. That
still requires a ruling and proof: the group cannot be inherited blindly from
the service, consent must receive none, the workspace mode must narrow in the
same change, Docker and Podman applied groups must be inspected, and created
files plus manager collection/cleanup must remain sound. ACL/id-mapped or a
host-private/world-writable layout are alternatives with different portability
and custody costs.
