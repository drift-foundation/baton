# Independent review — changes requested

## [P1] Any held service group can stand in for deployment configuration

Approver rulings M34630 and M34916 require one deployment-configured,
dedicated non-authority workspace group and require every other gid to refuse.
The implementation has no independent configured value:

- `workspaces.check_workspace_group(gid)` checks only shape, gid 0, and
  membership in `os.getgroups()`/`os.getgid()`;
- `assignment_workspace(..., workspace_group=gid)` accepts that same raw
  caller operand;
- `OciAdapter(..., workspace_group=gid)` stores the same mutable integer; and
- `run_vector(..., workspace_group=gid)` validates and grants it.

Consequently, if the manager belongs to configured group A and an unrelated
authority-bearing service group B, a caller can supply B at allocation and
launch. The workspace is adopted into B, the pre-launch group/mode proof
passes, and `--group-add B` is composed. Every layer agrees only because every
layer received the same caller-selected value. There is no configuration or
immutable configured-group capability in production or deployment
documentation against which B can be rejected.

Introduce one deployment-owned source of truth and make allocation and launch
consume its frozen answer. Add a negative case where the manager holds both A
and B, A is configured, and B refuses despite being usable by the process.
