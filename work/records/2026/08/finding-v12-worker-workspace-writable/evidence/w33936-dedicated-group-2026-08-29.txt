W33936 — THE RULED ENGINE PROOF, UNDER AN ACTUAL DEDICATED NON-AUTHORITY GROUP
============================================================================

WHY THE DEPLOYMENT MOVED INSTEAD OF THE FIXTURE. The standing review item
requires this matrix to run against "an actual dedicated non-authority group".
This workstation has none and this manager may not create one: `sudo` here is
not setuid ("sudo must be owned by uid 0 and have the setuid bit set"),
`newuidmap`/`newgidmap` are absent, and creating a host group is precisely what
approver ruling M34630 forbids the manager to do. So the group was provisioned
in a DEPLOYMENT IMAGE -- `w33936-dedicated-group.Dockerfile` -- and the manager
was run inside it. Its workers are launched as SIBLINGS on the same real host
daemon, over the same socket, with the same host bind paths, so the engine half
of the proof is unchanged; only the manager's own account and groups moved.

THE PROVISIONED DEPLOYMENT
--------------------------

    uid=1000(batonmgr) gid=1000(batonmgr) \
        groups=1000(batonmgr),119(enginesocket),8291(baton-workspace)

    baton-workspace:x:8291:batonmgr      <- the configured workspace group
    enginesocket:x:119:batonmgr          <- the engine socket group

    BATON_V12_WORKSPACE_GROUP=8291

gid 8291 IS DEDICATED AND NON-AUTHORITY, and both halves are measured rather
than asserted:

  * `getent group 8291` on the host: NONE. The gid names no group here, and no
    account outside the manager image holds it.
  * `find / -xdev -group 8291`: 0 files across the root filesystem. It owns
    nothing until the manager allocates the first workspace.
  * it is not the manager's primary group (1000) and not a service group.

gid 119 IS THE CONTRAST, and it is what makes the negative case mean something.
It is the container engine's socket group -- membership in it is full control
of the daemon. The manager holds it because it must talk to the engine. So
`test_a_second_held_group_refuses_despite_being_usable` now refuses a group
that really does carry authority, rather than a second harmless one.

A CORRECTION TO MY OWN FIRST MEASUREMENT. I first recorded the socket as
`65534:65534` and said membership in 65534 was what granted the engine. That
was this session's own user namespace re-mapping the owner: read from inside a
container the socket is `0:119`, and 119 is the real group. The image grants
119 and the earlier figure is wrong.
