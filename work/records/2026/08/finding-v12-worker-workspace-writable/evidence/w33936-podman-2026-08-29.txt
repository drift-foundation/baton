W33936 — COMPATIBLE PODMAN, RUN RATHER THAN SKIPPED
===================================================

The review is right that a skip cannot satisfy M34630. Podman cannot be
installed on this host -- `sudo` here is not setuid, and rootless podman needs
`newuidmap`/`newgidmap`, which this host does not carry. So the deployment
moved again, exactly as it did for the dedicated group: podman is provisioned
in an image (`w33936-podman.Dockerfile`) and the manager runs inside it.

  podman 5.8.4 (Fedora build), on Docker 29.1.3 as the outer runtime
  the workers are podman containers INSIDE that container rather than
  siblings, which is the honest shape for podman -- it has no daemon to be a
  sibling of, and everything the matrix touches is then one filesystem, so the
  bind paths the manager composes are the paths the engine resolves.

RUNNING PODMAN AT ALL NEEDED `--privileged` ON THE OUTER CONTAINER, and that
is recorded rather than glossed: `--device /dev/fuse` alone, and
`--cap-add SYS_ADMIN --cap-add SETUID --cap-add SETGID` with seccomp and
apparmor unconfined, both failed with `failed to reexec: Permission denied`.

RESULT 2 — ROOTLESS PODMAN: A REAL CONSTRAINT, AND THE MATRIX FOUND IT
-----------------------------------------------------------------------

Under ROOTLESS podman the group is still applied -- the worker really holds
8291 -- but the workspace is not writable:

    running_as [65532, 65532]
    groups [8291, 65532]                  <- applied
    root {'mode': '0o2770', 'gid': 65534} <- NOT 8291
    created False, create_error PermissionError:13

THE GID DOES NOT MAP THROUGH THE USER NAMESPACE. Rootless podman runs the
container in a userns that maps the invoking user's own uid/gid and its
subuid/subgid range; a SUPPLEMENTARY group of the manager -- which is exactly
what the configured workspace group is -- is not in that mapping, so the
bind-mounted root arrives owned by `nobody` and the setgid group the manager
established means nothing inside.

So the ruled mechanism holds on Docker and on rootful podman, and does NOT
hold on rootless podman without a gid mapping this manager does not compose.
That is a deployment constraint rather than a defect in the correction under
review, and it is now written into `v12/python/DEPLOYMENT.md` where a
deployment will meet it. It is reported rather than fixed: composing
`--userns`/`--gidmap` changes the ruled launch vector and is not this Work's
to decide.

WHY THE FULL SUITE IS NOT THE ROOTFUL ARTEFACT. `test_input_delivery` refuses
to run under a root manager -- "these cases establish that ordinary
permissions DENY a write, and root is not denied by them; run them
unprivileged" -- and rootful podman requires a root manager. That guard is
correct and was not weakened. The applied-group PROBE is what runs there
instead: it measures what the WORKER sees inside the exact argv the manager
composed, and the worker is 65532 either way.

ONE FIXTURE CORRECTION THIS SURFACED. The shared composition fixture took the
engine's `image inspect .Id` verbatim; docker answers `sha256:<hex>` and
podman answers the bare hex. The manager tolerates either from an ENGINE and
requires the canonical form for a CONFIGURED identity, so the fixture -- which
stands in for the deployment -- now writes the canonical form. Before that,
every Podman case failed on the digest rule before reaching the group it was
about.
