# Independent review — 2026-08-28T23:37:24Z

Disposition: **changes requested**.

## [P0] The workspace grant is not wired into workspace creation

The approved boundary requires every execution attempt workspace to be put in
the configured group with exact mode `02770`, and requires the adapter to
prove that group before the engine call. The implementation instead leaves
`WORKSPACE_DIR = 0o770`, calls `chmod` with that mode from
`assignment_workspace`, and never calls `adopt_workspace_group` from
production code. Repository search finds that helper only at its definition
and in `test_input_delivery.py`.

Consequently a canonical execution path neither changes the workspace group
nor establishes setgid inheritance. Passing `workspace_group` to the adapter
can add a group inside the container, but it cannot make the host bind writable
by that group. The submitted real-engine case confirms this outcome by
accepting failed adoption and requiring the worker write to remain denied.
That is a useful environment observation, but it is the original defect, not
the acceptance proof.

Required correction: carry the configured group through the canonical
workspace/allocation boundary, establish it on the exact workspace directory,
establish exact `02770`, verify the exact root still has that group immediately
before launch, and refuse before the engine call if any step is unavailable or
mismatched.

## [P0] Execution silently falls back to the unwritable legacy posture

`run_vector(..., posture="execution", workspace_group=None)` composes no
supplementary group, and the new test explicitly accepts that behavior. This
contradicts the recorded rule that there is no default and that, before the
engine call, the adapter proves the canonical workspace root has the
configured group. A deployment that omits the required configuration is not a
valid legacy execution mode: it deterministically recreates the defect this
Work exists to close.

Required correction: an execution start without the configured workspace
group must refuse before invoking the engine. Consent and other non-execution
postures continue to receive no group; they do not justify an execution
fallback.

## [P0] Required acceptance and recovery gates remain unfinished

The progress record accurately says the worker create/update/remove path,
setgid inheritance, manager collection, compatible Podman behavior, and fresh
full `test_oci.py` recertification are not complete. The Docker test currently
passes when adoption fails and the worker cannot write; it therefore is a
negative environment probe rather than the required positive acceptance.
`test_oci.py` still has the 12 known failures even though M34630 and M34916
explicitly authorize fresh recertification.

Required correction: finish that recertification and run the approved positive
and negative matrix in a deployment with the dedicated group provisioned.
Prove applied supplementary group and unchanged primary identity, exact
workspace group/mode, worker create/update/remove, inherited group, normal
collection, owner-only collection refusal without permission widening,
cleanup/retry/sibling isolation, and denial at every non-workspace surface on
Docker and compatible Podman. A missing provisioned group or engine is a named
deployment blocker; it is not a passing substitute for the required proof.
