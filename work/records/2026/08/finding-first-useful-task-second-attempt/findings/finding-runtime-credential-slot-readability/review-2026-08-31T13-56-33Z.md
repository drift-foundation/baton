## Findings

### [P0] Recovery accepts a widened or substituted credential root

The approved security argument has two halves: the slot is group-readable at
`0640`, and the manager-owned root remains `0700` so host members of that group
cannot traverse to the bearer. `CredentialHome.adopt` is the restart boundary
over existing filesystem state, but the implementation only calls
`_proved_slot` for each child. It never `lstat`s the volatile root or proves
that the root is an ordinary directory, mode exactly `0700`, owned by the
current manager, and not a link.

That omission is now material. If the root is widened to `0770`, every host
member of the configured workspace group can traverse to the ruled `0640`
slot. If the root is substituted, recovery's child checks are performed under
a pathname whose custody was never proved. Materialization setting `0700`
earlier is not evidence at restart; adoption exists precisely because this
process did not create the state it is accepting.

Add one root proof before any child or bearer read and translate `lstat`
failures into the bounded adoption refusal. Add negative recovery cases for a
widened root and a symlink/substitution, plus slot mode/gid/owner drift and an
`lstat` race/error. Each must refuse before bearer re-registration. Preserve
the exact positive recovery case.

### [P1] The exported mode constants give two contradictory answers

`credentials.py` exports `RUNTIME_FILE = 0o640` while retaining and exporting
`VOLATILE_FILE = 0o600` as “decision history”; tests explicitly assert both.
`VOLATILE_FILE` was the established public name for the volatile credential
file and now names a mode no live slot uses. A future caller or test using that
apparently authoritative constant will recreate the defect, while the suite
will claim both modes are required.

Decision history belongs in the append-only finding, not as a dead executable
contract. Keep one authoritative exported slot-mode constant. Prefer updating
the established `VOLATILE_FILE` to `0o640` and removing `RUNTIME_FILE`; if a
rename is genuinely required, remove the superseded export and update every
consumer. The literal test should require one mode, not preserve the old one.

### [P1] Required terminal gate evidence is incomplete

`PROGRESS.md` says the boundary inventory was still running when the Work was
passed, but no terminal result is recorded. The real-Docker module also has a
known unrelated global-litter failure, so the prose does not provide a clean,
bounded transcript for the two new positive/negative cases.

On the next round, record the boundary inventory's exact terminal result. Run
the two new Docker cases by exact unittest selectors and preserve their bounded
output in this dossier; they use `--rm` and do not depend on the unrelated
global-litter assertion. Do not remove pre-existing containers. If the
inventory reports pre-existing W43977 debt, separate that baseline from any
new `materialize`/`adopt` operand delta explicitly.
