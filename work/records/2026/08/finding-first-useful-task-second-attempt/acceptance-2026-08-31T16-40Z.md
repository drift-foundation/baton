## Findings

1. **[P1, the frozen task] Its verification command cannot pass inside the
   worker, and nothing told the provider that.** Two pre-existing
   `AnAncestorDecidesReadabilityToo` cases invert when the harness runs as the
   uid that owns the tree, which is exactly the worker's posture. Any correct
   candidate for this task ends `verification-failed`. Either those two cases
   need to be hermetic about who owns the tree they build, or the task's
   verification command needs to select the cases it actually means. This is
   not W51487's to fix and is offered rather than taken.

2. **[P2, the operator] The deployment preparation an attempt needs was not
   written down.** `dogfood_operator.py` opens an authority and expects a
   configured control store, and its docstring calls the command reusable for
   another bounded task — but nothing in the record said where those come from,
   and every earlier attempt reconstructed the step from test fixtures. It is
   now `prepare_attempt.py` beside this record: it mints no identity of its own,
   reads every value out of the grants file, and refuses rather than adopts an
   authority store that already exists.

3. **[P3, `now`] Still clock-relative and still judged late.** Recorded in the
   run2 acceptance as a P2; it cost one refused invocation here too, because the
   grants template was stamped before an intervening preparation step and the
   120-second offer TTL had passed by the time the operator ran. The fix in
   practice is to stamp `now` in the same command that launches. Unchanged as a
   defect; noted so the count is honest.
