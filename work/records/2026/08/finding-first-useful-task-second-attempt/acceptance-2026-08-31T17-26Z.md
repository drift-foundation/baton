It is not run3's. W52800's correction is what lets me say so: `_prepared_home`
now refuses an unreadable slot with a `TaskRefusal`, and a refusal is a
different disposition from `provider-failed`. The disposition we got is only
reachable after the provider process actually ran.

Credential-free probes in the exact posture: the CLI is present and functional,
DNS and TCP 443 work from `--network bridge`, and both "no credential at all"
and "an invented invalid credential mounted as the adapter mounts it" reproduce
exit 1 with `Not logged in`. Metadata only, no bytes opened:
`/run/baton/credentials/claude` is still a regular 509-byte `0400 sl:sl` file
with an mtime of 09:06:32Z — the same file, unchanged, that run4 used
successfully at 16:33Z.

**The leading inference, stated as the inference it is:** the staged credential
is a 09:06Z SNAPSHOT of a document the provider normally refreshes in place.
It is delivered read-only into a container that cannot write a refresh back, so
a snapshot with an expiry stops working while its bytes never change. That fits
every measurement and explains the 16:33Z/17:20Z difference.

**It is not proven.** An account-level refusal — a usage limit, for instance —
exits 1 in the same shape at the same instant, and I cannot separate the two
from outside, because the provider's diagnostic is deliberately unpublished.
Only the operator, who owns the source, can settle it.
