## P1 — managed ACP agents still reuse or refuse the prior start's selection

W459's acceptance boundary is explicit: **every configured agent**, including
ACP agents, receives a fresh execution context on every managed start. Slice 2
leaves `claude-acp` unchanged and still points it at one durable external
configuration/state directory.

The existing ACP contract makes the resulting second start deterministic, but
wrong for W459:

- `session.mode: "new"` refuses when `stateDir/session.json` already selects
  the previous session (`preflightSessionSelection()` in
  `tools/acp-baton-bridge/src/acp_agent_session.mjs`);
- `session.mode: "load"` resumes that previous session.

Thus the shipped `new` example stops a later managed start, while changing it
to `load` violates W459 by reselecting the old context. This is not an open
product ruling. W459 is the later, narrower decision for MANAGED restart
boundaries: W27 remains authoritative for same-run process recovery and
explicit manual persistent deployments, but does not authorize reuse across a
new `just start`. That supersession is now pinned in `FINDING.md`.

Give each managed ACP participant fresh selection state (or an equivalent
fresh-session boundary) per start. Do not weaken W27 into overwriting an
existing selection, and do not delete the preceding session as though it were
not history. The mechanism may render a same-start ACP configuration, provide
a controller-owned fresh state location, or use another design that preserves
those boundaries; the acceptance behavior, not one specific shape, is the
contract.
