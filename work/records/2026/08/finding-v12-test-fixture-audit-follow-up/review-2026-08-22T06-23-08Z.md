## [P1] A deleted registered pathname remains armed for recursive cleanup

`v12/test/owned_roots.mjs:45-88` records only path strings and removes every
record at the suite hook. Six registered placement families—the five changed
successful-tail families plus `entry-unowned`—are still removed directly with
`rmSync` at `placement.test.mjs:167`, `:225`, `:245`, and `:383`, without
removing those paths from the registry. Once a test deletes a root, the suite
no longer owns anything at that pathname. If another process recreates it
before the `after` hook, the hook recursively deletes the new owner's data.

I reproduced this through the public registry: create and register a root,
delete it as the existing test tails do, recreate the same pathname with a
replacement marker, then call `removeOwnedRoots()`. The replacement directory
and marker were deleted. This is the exact path-identity ABA that the finding's
“a matching path is not ownership evidence” boundary is meant to prevent.

Route every registered root's early removal through a registry operation that
removes and forgets it as one synchronous ownership action. For roots deleted
by the product path under test, retire the registry entry at the positively
observed deletion boundary. Add a takeover regression: after an owned root is
removed/retired, recreating its old pathname must survive suite cleanup. Also
pop a registry entry only after successful removal, so a removal error does
not silently discard the ownership record.

## [P1] The failure-path regression cannot read its child report

`v12/test/fixture_cleanup.test.mjs:67-75` spawns
`node --test fixture_cleanup_probe.mjs` and parses `W2907-ROOTS` from that
runner's stdout. On Node v24.14.0—inside the declared `>=22.5` range—the
default test isolation hides the probe file's stdout behind the file-level
test result. Direct execution exited 0 but emitted no root report; adding
`--test-isolation=none` exposed both reports and all three subtests.

Consequently both new parent cases fail with “the probe reported no roots” on
this supported runtime, and the claimed 141/141 gate is not reproducible from
the documented `npm test` invocation. The parent also does not diagnose
`proc.error`, exit signal, or an empty-output child before attempting to parse
reports, which made the managed sandbox's denied nested spawn look identical.

Use a reporter/isolation-independent channel for the exact root report (for
example, a parent-nominated report file inside the review-owned sandbox), and
validate spawn error, status, signal, stderr, report completeness, and the
intended failing assertion separately. Then rerun the literal supported gate,
not one relying on ambient Node options.
