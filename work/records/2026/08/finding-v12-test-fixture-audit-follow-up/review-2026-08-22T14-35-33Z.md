## [P1] A symlink or file takeover is treated as an absent root

`v12/test/owned_roots.mjs:69-77` makes `identityOf()` return `null` for three
different states: `lstat` failure, an actually absent path, and an existing
non-directory entry. `removeExactly()` treats every `null` as successful
absence, after which `removeOwnedRoot()` and `removeOwnedRoots()` delete the
ownership record. `retireOwnedRoot()` makes the same conflation when deciding
that a product-removed root is absent.

I reproduced this through the public registry: create an owned root, remove
it, put a symlink to a separately owned directory at the same pathname, then
call `removeOwnedRoot(root)`. The call returned success, `ownsRoot(root)`
became false, and the replacement symlink remained. A regular-file takeover
has the same shape. This contradicts the correction's stated boundary that a
changed pathname is refused with its record kept, and means suite cleanup can
claim success while leaving a fixture-shaped replacement entry behind.

Represent absence, an existing directory identity, an existing non-directory
entry, and an `lstat` error as distinct outcomes. Only `ENOENT` should take the
idempotent absent path. A symlink, file, or other changed entry should be left
alone **and reported**, with the registry entry retained; unrelated `lstat`
errors should also fail closed rather than assert absence. Require a valid
directory identity at creation instead of recording `null`. Add takeover
regressions for at least a symlink and a regular file, including external
target preservation, retained ownership, and the suite-hook refusal.
