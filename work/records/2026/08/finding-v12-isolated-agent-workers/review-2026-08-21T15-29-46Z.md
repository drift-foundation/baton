# Post-PoC roadmap revalidation

Reviewer: `baton.codex`, current Work `W28` (`43c55d4b-W28`), claimed at
authority sequence 35. Scope: revalidate the accepted `v12/` proof against the
next pending roadmap item and make the next design decision implementation-
ready. No protocol, application, prototype, dependency, schema or product-code
change was made.

## Result

The accepted proof remains green (`npm test` from `v12/`: 78 passed) and its
bounded lifecycle claims still hold. The next roadmap slice must be a design
gate, not an incremental extension of `manager.mjs`: three intentionally
disposable spike choices conflict with the already confirmed production
identity rules.

## Findings

### 1. Current authority references were stale

**Confirmed.** `FINDING.md` named retired `5f717eee-W2` as current while
`PLAN.md` named retired `88990a87-W2`. Canonical detail binds this dossier to
current Work `43c55d4b-W28`; its only message says the schema-27 recreation did
not migrate prior messages or closed children. The finding now carries an
explicit supersession and the plan names W28 as current.

### 2. The PoC does not mint an assignment generation

**Confirmed.** `v12/src/manager.mjs` writes `generation: 1` after every
successful claim. `v12/src/envelopes.mjs` accepts that number but does not
derive or validate it, and the retained evidence uses fresh disposable
authorities where one successful assignment was enough. This satisfied W76's
walking skeleton and must not be mistaken for the confirmed production rule
that every successful claim receives a new monotonically increasing per-Work
generation.

**Confirmed.** V11's nearest identities are not substitutes:

- `episode_seq` is minted when Work becomes newly actionable and the source
  explicitly says claim does not move it;
- the claim event `seq` is authority-derived but globally scoped rather than a
  per-Work generation; and
- runtime incarnation and configuration generation have different owners and
  lifetimes.

**Recommendation.** Make assignment generation a value incremented inside the
same authoritative transaction that commits the claim, returned in the claim
result and claim event, and projected with the live assignment. Its full
identity is authority UUID + full Work ID + participant + generation. Clearing
the Handler invalidates the live identity but never resets the counter.

### 3. Durable envelopes still use presentation-only Work labels

**Confirmed.** The PoC's offer, claim-intent, assignment and result envelopes
carry `W2`-style local selectors. The roadmap already rules that compact labels
are presentation-only and that durable or mutating identity must be full and
structured. Fresh one-authority evidence made the shortcut harmless; a
production manager serving more than one authority could not safely retain it.

**Recommendation.** The state-machine specification should define one shared
structured identity type and require it in every persisted offer, assignment,
activity, result, proposal, review and disposition. Human-facing local labels
may ride beside it but never participate in equality or fencing.

### 4. Offer/token state cannot survive a manager restart

**Confirmed.** `ClaimTokenIssuer` creates a per-process HMAC key and keeps all
issued/spent entries in an in-memory `Map`. A restart forgets both issued and
spent tokens; the manager also creates its Baton client and token issuer in one
constructor and has no reconciliation store for pre-claim offers or claimed
runtime attempts. Again, this is valid for the disposable PoC and is not a
defect in its accepted scope.

**Recommendation.** Persist an offer record containing only a verifier/digest,
the exact full binding, manager-observed expiry, consumption state, runtime
attempt and pinned input/policy digests. Never persist the bearer token. On
restart, an unconsumed offer may expire closed; a claimed attempt may reattach
only after proof of the same runtime and assignment identity. Otherwise fence
publication before recovery or replacement.

### 5. Manager attempt state and Work phase need separate vocabularies

**Observed.** The PoC currently reports `started`, `fenced`, `error`,
`compensated`, `stranded`, `returned`, and `returned-unclean` from one process.
Those are useful attempt outcomes, but the roadmap's state-machine item also
names offer, claim, plan rejection, cancellation, quiescence, proposal and
integration facts. Collapsing those into Work phase would contradict the v11
closed scheduler axis; collapsing them into one flat attempt status would lose
which capability is live and which transition must be fenced.

**Recommendation.** The design slice should model separate but linked records:

- pre-claim offer/token lifecycle;
- live assignment identity and claim capability;
- concrete runtime attempt and quiescence/cleanup state;
- immutable result/proposal and its verification/review/approval disposition;
- canonical Work route, phase and Handler, which remain authoritative and do
  not acquire worker-runtime meanings.

It should publish a transition table with actor, preconditions, atomic writes,
capability gained/lost, retry key, settling observation and failure state for
every transition.

## Proposed first design child acceptance boundary

Before any application edit, produce:

1. a versioned state/identity specification with explicit supersessions;
2. a complete transition table for offer, accept/decline/expiry, claim,
   activation, cancellation, quiescence, result freeze, proposal publication,
   pass/release/close, plan rejection and recovery;
3. invariants proving generation uniqueness/non-reuse, one runtime per live
   assignment, no writable or publication capability before claim, stale
   rejection after every releasing transition, and no phase overloading;
4. restart and ambiguous-result reconciliation for every manager mutation;
5. executable model tests for expired/replayed tokens, competing claims,
   manager restart before and after claim, cancellation races, uncertain
   quiescence, immediate successor claims and stale publication; and
6. an explicit ruling on where the generation counter and live assignment are
   authoritative.

## Open decision for the approver

The recommended placement is the v12 authority's atomic claim transaction.
Another component is viable only if it is explicitly authoritative and can
prove uniqueness and fencing across managers and restarts. A manager-local
counter cannot. Until this is ruled, creating implementation Work would turn a
proposal into an accidental protocol decision.

## Disposition

Return W28 to `baton.ops` for the authoritative placement decision and
approval of the first design-child boundary. The roadmap remains open and no
application implementation is authorized by this pass.
