## P1 — an absent result is not a terminal claim settlement

`Manager.settlement_timeout` now performs one read-only
`Authority.operation_result` lookup and changes the offer from `accepted` to
`settlement-expired` when that lookup returns no committed result. This fixes
the already-committed-before-lookup trace, but not the concurrent boundary.

A linearizable read that reports “not committed yet” proves only its own
instant. A submitter can already have passed the accepted-offer check and
commit the fixed claim operation after that read but before the manager writes
`settlement-expired`. The additive trace commits at precisely that boundary;
the result is again a live authority assignment consuming the participant's
deployment-wide slot behind a terminal control row.

The same gap appears without a timing hook. `Manager.claim` records
`claim-refused` when a competing Handler makes the authority claim refuse,
but `Authority._replay` does not durably bind an ordinary refusal. After the
competitor releases, a stale retry of that SAME fixed operation succeeds and
mints an assignment for an offer the control store already calls terminal.

The timeout needs a stable authority-side settlement, not merely a
point-in-time absence read followed by a separate control-store CAS. The fixed
operation must become durably one of committed, terminally refused, or retired
before the offer may terminalize, with concurrent/stale submitters replaying
that same outcome. The exact mechanism remains an implementation choice, but
no `settlement-expired` or `claim-refused` row may coexist with a claim
operation that can still commit later.

Additive regressions:

- `test_settlement_timeout_cannot_race_a_later_fixed_claim_commit`
- `test_a_fixed_claim_refusal_is_terminal_for_that_operation`

## P1 — intake and cleanup still lack manager operation identities

`SPEC.md` section 7 explicitly says every manager-owned mutation — including
intake and cleanup — carries its own durable operation record. The model adds
`ControlStore.replay` only to cancellation, collection, and freeze.

The missing boundary is observable in both remaining operations:

- A trusted intake disposition commits, its response is lost, and an exact
  retry receives `intake disposition is already recorded` instead of the
  committed result. There is no disposition operation id with which to
  distinguish exact replay from a conflicting second decision.
- Cleanup writes `blocked-on-intake` before refusing. After intake moves, the
  indistinguishable retry changes that committed refusal into success. A new
  cleanup operation should be allowed to re-evaluate; the SAME operation must
  replay the refusal that already wrote durable state.

Add the operation identities promised by the transition table and route both
mutations through the control-store journal. Bind intake disposition in the
signature. Treat cleanup's state-writing refusal as a durable outcome, while
allowing a distinct cleanup operation to evaluate the later intake state.

Additive regressions:

- `test_exact_intake_retry_returns_the_committed_disposition`
- `test_cleanup_retry_cannot_change_a_committed_refusal_into_success`
