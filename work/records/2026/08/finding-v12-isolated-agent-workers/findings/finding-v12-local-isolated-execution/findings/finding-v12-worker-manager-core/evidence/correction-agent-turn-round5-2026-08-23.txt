2. WHY THE STATE MATTERS AT THE START BOUNDARY

Frozen §7.3 draws exactly one edge that starts a prompt:

  not-started -> initializing -> ready -> prompting -> turn-ended -> closed
                                            |
                                            +-> cancel-requested -> ...

So every state other than `ready` is either before a prompt has become
possible or past one. `agent-quiescent` says the conversation is over. §3.3
makes `unknown` and `closed` terminal, and `closed` asserts that a terminal
fact was observed for EVERY turn the epoch started — so an allocation landing
after it does not leave a harmless gap, it makes a durable session assertion
false the instant the row commits. §3.1's reference labels evidence, so a
mismatched provider label sealed at the opening boundary is a false label on
the turn from the moment it exists.

And the timing is the whole point: allocation PRECEDES the external prompt,
while recording FOLLOWS the terminal fact. A check deferred to recording is a
check made after the thing it exists to prevent.


3. THE CHANGE

`TURN_STARTING_SESSION_STATES` is `["ready"]` — a positive set, named the way
the settle set already was.

`admitTurnStart` checks that set and binds the full durable provider-session
reference. It runs inside `allocateTurn`'s existing BEGIN IMMEDIATE and BEFORE
the insert, so a refused opening leaves nothing behind and the state cannot
move between the check and the row.

`admitTurnSettlement` keeps the separate positive SETTLE set and its own
provider binding, exactly as the review requires. The provider comparison is
factored into `bindProviderSession` so the two boundaries cannot drift apart
on that half.

The two sets are deliberately different and both are needed: a turn OPENS only
from `ready` and may SETTLE wherever §7.3 has legally advanced to since,
because the state moves while the agent is working and a terminal fact
arriving in `cancel-requested` is what the graph describes.

The review named the migration and it is exactly right. Two of MY cases now
open while ready and then perturb:

A fixture helper `openTurn(store, at)` makes that explicit: a case that
perturbs the session and then records is describing a turn that opened before
the perturbation, which is what a relay does.
