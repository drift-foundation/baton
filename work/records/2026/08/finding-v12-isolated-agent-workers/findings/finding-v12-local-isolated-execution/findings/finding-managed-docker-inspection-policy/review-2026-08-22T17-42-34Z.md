## [P2] Astral text shifts the comment mask away from scanner offsets

`maskComments` in
`tools/codex-event-bridge/src/exec_policy.mjs:495-513` initializes its output
with `[...text]`. That array contains Unicode code points. The loop, all
subsequent scanners, and every offset into `text`, however, use JavaScript
string indexes — UTF-16 code units. After one astral character such as `😀`,
the two index spaces differ. Comment-mask writes land one element late, the
joined mask is no longer byte/code-unit aligned with the source, and structural
scanning misclassifies later valid rules.

I exercised two evaluator-valid policies: an emoji in a top-level comment
before a literal non-Docker rule, and an emoji in a comment inside that rule.
The installed `codex execpolicy check` loaded both and returned `allow` for the
ruled `docker version`. The audit rejected both: the top-level form reported
the following valid rule unaccounted; the in-rule form parsed the rule but
reported its closing `)` unaccounted. This is the rounds 6–8 availability
direction: no capability is hidden, but dispatcher startup refuses a valid
policy and asks for regeneration that cannot change what Codex authorizes.

Build the mask in the same index space as the source scanners, for example
with a code-unit-preserving split or direct string replacement. Retain the
existing quote/comment boundaries and assert that the masked text has exactly
the source's `.length`. Cover astral text in top-level and in-rule comments,
with a later construct so offset drift is observable, on both shared profiles
and in the deployed-artifact lane.
