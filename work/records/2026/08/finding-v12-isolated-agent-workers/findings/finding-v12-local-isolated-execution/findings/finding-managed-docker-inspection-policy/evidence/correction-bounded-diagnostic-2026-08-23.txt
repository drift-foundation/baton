2. A CAP ON THE PARTS IS NOT A BOUND ON THE WHOLE

I capped each agent message and called the helper bounded. It then emitted
every item type, every message, every command and each full command string,
and concatenated all of them into the summary.

WHAT MAKES IT WORSE THAN AN OVERSIGHT IS WHEN IT FIRES. This diagnostic exists
for the moment a model goes off-script — which is exactly the moment a turn
has a thousand items, and exactly the moment the operator log has to stay
readable. The one input that triggers it is the one input that breaks it.

I also wrote "BOUNDED ON PURPOSE" in the doc comment. A comment claiming a
property the code does not have is worse than no comment: it is the reason
nobody looks.


3. THE CORRECTION

Hard caps on COUNTS as well as sizes: 40 item types, 5 agent messages, 10
commands, 400 characters per message, 200 per command.

THE CAPS ARE PRIVATE AND THE CALLER MAY ONLY TIGHTEN. `limit` clamps downward
through `Math.min` and cannot raise anything — an exported helper that its
caller can make unbounded is unbounded, and "no current caller passes a large
limit" is a property of today's callers.

TRUE TOTALS ARE ALWAYS REPORTED, and every cut list carries an explicit
"… (N more of M)" marker. A diagnostic that silently drops 990 commands is
worse than one that says it dropped them, because the COUNT is often the
finding — eight cases with zero command items is the whole of W2845's current
state.

Unchanged: `reasoning` items contribute their TYPE and nothing else, only
`agentMessage` text is quoted, only this turn is read, and the helper decides
nothing. The matrix still prints it only for a FAILED Docker verdict, and the
strict oracle remains the sole decision.

The same reproduction now:

   "commands":1000},"summaryLength":3095,"wholeLength":6383}

1,029,041 -> 3,095, with both true totals intact.
