## Finding

### P1 — agent cancellation failure suppresses runtime stop after fencing

`orderQuiescence` calls `agent.cancel(...)` and only calls `adapter.stop(...)`
after the first call returns. If the agent boundary throws — for example,
because the provider transport is unavailable — JavaScript exits the function
and the runtime stop is never ordered. At that point the authority has already
fenced and ended the assignment. A failed cooperative cancellation request
must not veto the configured runtime stop/force-stop path; persistent agent
unreachability is a reason to stop the runtime, not a reason to leave it
running indefinitely.

The owning umbrella explicitly orders ACP cancellation/graceful shutdown and
then the configured runtime stop deadline/force-stop. The dossier also
requires injected crashes at scripted runtime/agent boundaries to be
observable. The current new tests cover negative returned settlements, but no
throwing agent boundary.

Preserve the additive regression `W2929 re-review: agent cancellation failure
cannot suppress runtime stop`. Correct the post-fence orchestration so it still
orders runtime stop after capturing an agent cancellation failure, while
preserving the agent-before-runtime call order and making the failure visible
to the caller. Do not turn either boundary's result into positive quiescence.
