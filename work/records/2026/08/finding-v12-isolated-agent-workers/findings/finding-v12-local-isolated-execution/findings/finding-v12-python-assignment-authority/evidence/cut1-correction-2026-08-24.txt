2. [P1 1] THE FACE NAMED A WHILE THE CONNECTION GOVERNED B

`open` validated the read-only probe, validated the live recheck, and then
built the Store from the PROBE's UUID. With the file replaced in the window by
another valid Python-authority store and no expected UUID supplied, both
validations passed and the public `authority_uuid` named a store the connection
was not talking to -- an authority answering to two identities, which is the
one thing §4 says an `assignment_ref` must never be.

The LIVE identity governs now, and a disagreement between probe and live
REFUSES rather than resolving itself: the caller decided to open against what
the probe said, and quietly handing back a different authority answers a
question nobody asked.

The regression asserts both directions -- the swap refuses, and with nothing
swapped the face and the live `meta` row agree -- because a guard that simply
refused everything would satisfy the first half alone.


3. [P1 2] PRESENCE IS NOT VALIDITY

`_check_compatibility` checked that `authority_uuid` EXISTED, and compared it
only when a caller happened to supply an expected one. So a marker-only file
recording `not-a-uuid` was a recognized authority, and opening it grew the full
18-table schema inside it.

The recorded UUID is now held to the same frozen grammar every assignment
identity is held to, on the probe AND on the live recheck, because both go
through that one function. Nothing built from a durable identity can be valid
if the identity is not.

Covered: text that is not a UUID, uppercase hex, a truncated UUID, an empty
string, and an INTEGER -- a foreign store's `meta` is not a STRICT table, so its
value need not even be text. Each asserts the file is byte-identical afterwards
and still has exactly one table.


4. [P1 3] A FAILED OPEN COMMITTED WHAT IT HAD WRITTEN

The `COMMIT` was in a `finally`, so a fault partway through the schema
committed the statements that had already run. A failed open left tables behind
in somebody else's database -- the exact outcome the whole non-adopting design
exists to prevent, reached through the ERROR path instead of the success one.

Commit is on the success path only; every failure rolls back. The regression
also proves the store is USABLE afterwards -- a rollback that left the
transaction open would make the next open fail for a reason that has nothing to
do with the store.


5. [P1 4] AN EXPORTED HELPER IS A BOUNDARY

`is_v12_contract` invoked the caller's `__ne__`. `gate_token` invoked the
caller's `__format__` -- while assembling a value that becomes DURABLE.
`same_assignment` short-circuited on `None` BEFORE validating anything.

I had proved the rule at `own` and not at the doors people walk through. A rule
enforced at the inner function and not at the exported one is a rule with a way
around it, and that is the same shape as every "applied at one of N sites"
finding I have been given this week -- this time between an internal helper and
its own exported surface.

All three prove their operands first. `gate_token` additionally refuses a
separator inside the KIND, because the token is parsed at its first colon and
one that does not round-trip is not an identity.

The new case drives fourteen exported entry points with an object that raises
from `__ne__`, `__eq__`, `__hash__`, `__format__`, `__str__` and `__repr__`.
`parse_gate` is asserted SEPARATELY, on its own terms -- answering "this is not
a gate token" is its whole contract -- rather than being folded into the table
and quietly weakening it.


6. [P1 5] THE DIAGNOSTIC WAS THE ESCAPE

`str()` of an integer is NOT inert in Python 3.13: the interpreter refuses to
render one above 4,300 digits. `check_generation` interpolated the rejected
value and `name_of` stringified every exact int, so a 5,001-digit generation
left as a raw `ValueError` from the MESSAGE after the check had already decided
to refuse it.

The one function whose entire job is to describe a rejected value safely was
itself a way for a rejected value to escape. `bit_length()` runs no conversion
and cannot fail, so an integer too wide to show is named by its SIZE; 64 bits
covers every value this contract can legitimately carry, so nothing valid is
ever reduced to a size. The refusal message is asserted to stay under 300
characters rather than becoming 5,001 digits of somebody else's number.


7. [P2 6] THE LOCK IS CONSUMED NOW, NOT DESCRIBED

The review is right that a lock nobody resolves from is a document about a
build rather than a property of one, and that a test reading its TEXT proves
only that text resembling pins exists.

`just build` resolves it OFFLINE with `--require-hashes`, and with
`--ignore-installed` so every pin is actually fetched and verified rather than

build dependencies, which is exactly what the lock exists to prevent -- imports
the package from OUTSIDE the source tree and asserts it came from

IT REFUSES RATHER THAN SKIPS when the wheelhouse is absent, naming the override.
