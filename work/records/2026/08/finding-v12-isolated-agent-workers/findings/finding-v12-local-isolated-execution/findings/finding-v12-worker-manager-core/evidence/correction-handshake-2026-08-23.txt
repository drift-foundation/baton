2. P1 — I CLAIMED A CLOSED SURFACE AND BUILT TWO DENY LISTS

This is the finding worth stating plainly, because the slice's own header
comment claimed the opposite.

`checkOutboundMethod` rejected the twenty-one names section 2.3 enumerates and
RETURNED EVERY OTHER STRING. So `session/reuse` — the frozen contract's own
example of a capability that does not exist — passed, and so would any method
a future SDK adds, on the day it adds it. `serveClientMethod` had the same
shape over ACP 1.3.0's eight client methods.

That is the inverse of the rule. Section 2.2 says withholding by default costs
nothing while "advertising by default means every future SDK release silently
widens the boundary", and I wrote the widening it describes into both guards
while quoting the sentence three lines above them.

Both are allow lists now:

  checkOutboundMethod   admits only KNOWN_AGENT_SURFACE — the five required
                        plus the three optional, which together are every
                        method that exists in 1.0. Everything else is
                        refused.capability. Whether a particular OPTIONAL
                        method may be used on a particular session depends on
                        its advertisement and the pinned policy, and neither
                        is in hand here; that check belongs to composition and
                        is named as such.
  serveClientMethod     denies EVERY method. There is nothing to enumerate:
                        section 2.2 advertises no client capability at all, so
                        every client-directed call is a call on something the
                        relay structurally withheld, whatever it is named.
  routeAgentOriginCall  NEW, on the review's authority. The closed inbound
                        surface is one name: session/update is the only member
                        of the required five that flows agent-to-client.
                        Everything else is policy.denied.

One function had been answering two questions — which client capabilities are
served (none) and which agent-origin calls are accepted (one) — and the
session/update assertion migrated to the boundary that now owns it rather than
being dropped.


3. P1 — ONE CONSTANT FOR TWO DIFFERENT DOCUMENTS

Frozen section 2.2 says the ACP wire sends exactly `{ "fs": {}, "terminal":
false }`, with both filesystem members ABSENT — the pinned SDK 1.3.0
declaration makes them optional. The frozen agent-session schema separately
records a normalized snake-case SUMMARY with both members explicitly false.

I had one constant for both, so `validateClientCapabilities` refused section
2.2's exact wire document and `negotiateAcp` emitted `read_text_file` and
`write_text_file`, which are not ACP wire field names.

Two representations, two names: ACP_WIRE_CLIENT_CAPABILITIES is what goes out
and what an advertisement is compared against; NORMALIZED_CLIENT_CAPABILITIES
is what the durable profile records. A case asserts they are DIFFERENT
documents, which is the whole finding.

The comparison is STRUCTURAL now. Comparing `JSON.stringify` output had made
member ORDER part of the rule; JSON object member order carries no meaning,
so the same document in a different insertion order is the same document while
a different member or value is a different one.

ABSENCE IS HOW THE WIRE WITHHOLDS, and a case drives the distinction directly:
an `fs` member present AT ALL — even set false — is denied, because it is a
member ACP's optional type did not have to carry and this boundary is the one
place that difference is still visible.

W641 owns the frozen-artifact conflict between the model, the schema and
section 2.2. This slice follows the explicit section 2.2 wire text and the
pinned SDK declaration now, as the review directs, and rewrites neither
artifact.
