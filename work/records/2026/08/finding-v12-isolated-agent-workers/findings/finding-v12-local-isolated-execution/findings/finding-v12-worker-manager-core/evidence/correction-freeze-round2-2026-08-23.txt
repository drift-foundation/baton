2. BEING AT THE NAMED KEY IS NOT BEING THE NAMED THING

[P1] A RETAINED NON-INPUT DOCUMENT WAS ACCEPTED AS THE INPUT DECLARATION.
`loadManifest` parsed the row and handed it back. Nothing said the body was
the KIND the caller needed, so a retained RESULT manifest — a perfectly valid
thing to retain — could be named as an attempt's `input_digest`, and its
similarly shaped output rows were read as trusted declarations. Every public
operation in that sequence is valid on its own; the boundary that had to
refuse the combination did not exist.

I introduced this in the same round that introduced retention: I wrote the
loader as a getter and the validation as something that happened on the way
IN. A guard on the way in cannot see a document put there by a different,
equally legitimate call.

CORRECTED. The definition is REQUIRED rather than defaulted — a caller that
has not said what it expects has not made the check that matters, and a
default would let a new call site silently inherit somebody else's
expectation. The body is validated as that definition, and its digest is
recomputed against the key it was filed under, because a store nobody
validates on the way out is a store where a hand edit outlives every guard on
the way in.

[P1] RESULT RETENTION BYPASSED THE COLLISION REFUSAL. `retainManifest` refuses
an existing key with different bytes; the result path wrote `INSERT OR IGNORE`
and so skipped it. The insert was silently dropped, the `outputs` row
committed a foreign key to the OTHER document's bytes, and the operation
reported the requested result as frozen while a reload returned a document its
digest does not identify.

That contradicts the invariant the previous correction stated in its own
comment. Writing a rule in one function does not apply it to another writer of
the same table; ONE RULE, ONE PLACE, and both writers go through
`retainCanonical` now.


3. THE OTHER TWO

[P1] DECLARED OUTPUT CONSTRAINTS WERE IGNORED. The comparison read names,
types and required status and never opened `expect.constraints`, so a tree far
larger than its declaration froze successfully. Whether the artifact's BYTES
are what it claims is W2930's collection-time fact; the counts, totals and
media type are already inside the document `validateManifest` accepted. A
limit that is decidable here and not decided here is a limit nobody enforces.

`max_bytes` against the content manifest's total (or the artifact's declared
size when there is no tree), `max_entries` against its entry count, and the
media type against the allow-list — LITERALLY, including an empty list, since
an allow-list that permits everything when it names nothing is a fail-open
reading of a rule written to close.

[P1] EXACT REPLAY STILL DEPENDED ON CURRENT RETENTION. Last round moved the
output-axis check behind `store.replay`; the DECLARATION lookup stayed in
front of it. Removing the old input row after the result committed made an
exact retry refuse, although the journal still held the settled identity.

THE SAME LESSON, ONE ROUND LATER AND ONE LINE HIGHER. I moved the check the
review named instead of the boundary the rule is about. The immutable identity
and its signature are computed first, replay or collision is resolved there,
and EVERY check about today — bindings, declaration, axis — now applies only
to a genuinely new record.
