2. P1 — TWO ACP MAPPINGS DID NOT ACCEPT THE FROZEN EVIDENCE

REASONING. I made only `other` contentless. §6.2 marks `agent_thought_chunk`
content "diagnostics; never portable evidence" — the same sentence about a
different member, and I applied it to one row and not the other. A chain of
thought in an event's portable `content` is exactly the durable agent evidence
that row forbids. `agent-reasoning` joins the contentless set; the bytes are
still counted, as they are for every body this boundary declines to carry.

TOOL CALLS. I read `update.toolCall.toolCallId`. The frozen captured trace
carries `toolCallId` and `status` at the UPDATE ROOT:

  {"sessionUpdate": "tool_call", "toolCallId": "tc-1", "status": "in_progress"}
  {"sessionUpdate": "tool_call_update", "toolCallId": "tc-1", "status": "completed"}

So the normalizer refused the exact provider shape it was built to normalize,
and my own fixture agreed with the code because I wrote both. A mapping table
is half the contract; the captured evidence is the other half, and I read the
first without checking it against the second.

THE OPEN CONTRACT INCONSISTENCY, CARRIED FORWARD NOT RESOLVED. §6.2's prose
says `tool_call` "carries the ACP `toolCallId`, `kind`, `status`", and the
frozen `$defs.toolCallView` permits only `tool_call_id`, optional `title` and
`status` with `additionalProperties: false`. Two frozen artefacts disagree.
Per the review, no portable `kind` member is invented here; a case asserts
that the normalized view has exactly `tool_call_id` and `status` even when the
update carries `kind`, so the omission is a recorded decision. THIS NEEDS AN
OWNING RECORD before any implementation relies on that field — raised on the
handoff, since formal enrichment and priority are the reviewer's and
Slawomir's.


3. P1 — OBSERVATION DID NOT ANSWER FROM THE AUTHENTICATED FRAME

§6.4 requires the consumer to answer with the same sealed bytes and to return
owned copies. I returned summary metadata only, and on replay I compared the
indexed digest column and never read the body — so a retained frame that had
become unreadable was reported as a successful replay. The one place a stale
index is most convincing is the place a record is not read.

`authenticateRetained` is now shared by the reader and the REPLAY path: parse,
validate, and bind the declared digest, the recomputed digest, the stored
digest and the sequence the caller asked for. Both answers carry the
document — the first from the authenticated incoming frame, the replay from
durable state.


4. P1 — THE SEALED TURN IDENTITY COULD DISAPPEAR

A separate `turnId` operand defaulted to null, the sealed `turn_id` was checked
only when that operand happened to be non-null, and the OPERAND was what got
written. A frame sealed for a turn therefore became a durable UNBOUND event
whenever a caller omitted the option, losing an authenticated identity member
and giving lateness the wrong subject.

The sealed `owned.turn_id` is the durable identity. A redundant operand may
only AGREE, in both directions — sealed-null/operand-named,
sealed-named/operand-null, and sealed-named/operand-different all refuse
`runtime-observation.identity-mismatch` and write nothing. For a non-null
effective turn the allocation is validated in this session, lateness is
derived from it, and it is persisted.


5. P1 — THE BOUND TRUSTED AN ATTACKER-CONTROLLED MEMBER

I compared `owned.byte_count`, which is source accounting living INSIDE the
untrusted sealed document: a frame may claim 1 while the event is far over the
limit. The frozen model measures `canonical_bytes(event)` and §6.3 bounds
every normalized EVENT, so the thing being bounded is now what gets measured.

`byte_count` keeps its own distinct job — how much SOURCE there was, including
the parts that were dropped — and a case drives the converse the review's case
does not: a frame claiming ten million source bytes whose canonical event fits
is ADMITTED, and the count survives into the row unrewritten.
