1. WHAT THIS SLICE IS

  "Ended-assignment material is sealed/quarantined. Intake changes only its
   trusted disposition and never publishes on the dead generation. Destruction
   waits for the recorded intake/discard policy; cleanup never changes
   authority state."

and from the contract, SPEC 6.4:

  `output.retain`   -> "retained/quarantined locator and deadline; RETENTION
                        IS NOT ACCEPTANCE"
  `runtime.destroy` -> "collection/intake boundary satisfied or pinned discard
                        policy ... cleanup observation only; never changes
                        authority state"

Schema 5 -> 6 adds `intake`, holding the decision, its retention, the locator,
the deadline and the assignment it was decided under.


2. TWO DESIGN DECISIONS, STATED BECAUSE THEY ARE THE SLICE

`recordIntake` IS NOT GIVEN A SESSION. "Never publishes on the dead
generation" is a rule about what intake may do, and the strongest way to keep
it is to hand this boundary no way to reach the authority at all. A handle
that is passed and not used is a rule enforced by good intentions, and this
Work has already found two rules that were only enforced by the writer.

THE DISCARD PATH IS CLOSED. SPEC 6.4 admits destruction under a "pinned
discard policy" as well as a satisfied intake boundary. A policy this function
takes as an ARGUMENT is the rejected `absenceProven` shape a fourth time, so
it is not offered: destruction requires a recorded intake decision, and the
refusal names what would open it. The same closure the retry path already has,
for the same reason.

RETENTION IS TWO FACTS, NOT ONE. Whether intake wanted the material and where
the material went are separate columns, because a REJECTED draft that is
RETAINED under policy is an ordinary outcome and collapsing them would make it
unsayable.


3. THE DURABLE REFUSAL, AND WHY THE IDENTITY IS DERIVED FROM INTAKE

The pinned rule is that cleanup's `blocked-on-intake` refusal "is durable to
its own operation; a later re-evaluation uses a new operation". A counter
would satisfy the words and would be caller-authored.

So the cleanup operation identity is DERIVED FROM THE INTAKE STATE IT WAS
EVALUATED AGAINST. A retry while nothing has changed lands on the same
identity and REPLAYS the same refusal — the store can be asked what happened,
rather than re-deriving it. Once intake decides, the identity moves, and the
new evaluation is a new act. The evaluation is keyed on the durable fact whose
change is what makes re-evaluating legitimate.

The axis moves to `blocked-on-intake` inside that refused operation and the
writes are kept, which is what `store.transact` already does for a durable
refusal.


4. ORDERED, NOT DONE — AGAIN

`requestDestroy` passes the adapter's settlement through uninterpreted and
moves the cleanup axis only on a positive `destroyed` OBSERVATION. An adapter
that returned from `destroy()` has said it accepted the order, which is not
the runtime being gone; positive absence is item 4's certified-adapter
question and is still closed. The cancellation slice's rule, applied to the
boundary that has the same shape.

And destruction WAITS FOR THE ASSIGNMENT TO BE OVER. Destroying the runtime of
an assignment the authority still believes is executing is the cancellation
ordering defect from the other end.
