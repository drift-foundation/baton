2. [P1 1] A FROZEN RESULT IDENTITY NAMED TWO DIFFERENT THINGS

`result_id` had only the text rule, so an identifier with a space was accepted
and -- the part that matters -- the SAME frozen result identity could be
published twice with contradictory digests. Downstream, nothing could tell which
bytes `r1` meant.

It is a `check_opaque_id` now, checked BEFORE the signature and the journal so a
malformed one never consumes an operation identity. And the binding is stable:
a `result_id` already in the proposal table must name the same
`result_digest` and the same full assignment.

CONSISTENT REUSE STAYS PERMITTED, as the review allows: one frozen result may
back several proposals, so the rule is about CONTRADICTION rather than about
reuse. A second proposal citing the same result with the same bytes and the same
producer is accepted; a different digest, or a different assignment, refuses.

The assignment half is worth stating: a frozen result is produced BY an
assignment, and the same identity appearing under a different one is a claim
that two producers made the same bytes -- which this boundary cannot verify and
so must not record.


3. [P1 2] GENERIC STORAGE PLUS A SPECIFIC MEANING

`policy` is deliberately generic: a policy value is any owned JSON document, and
`own` is what makes it safe to STORE. `canonical_target` then handed whatever it
found straight into a durable column.

A dict reached parameter binding as a raw `ProgrammingError`. An EMPTY STRING
was worse: it published successfully, so the proposal was bound to no target at
all and integration would later compare against nothing.

Generic storage with a specific meaning is exactly where the type has to be
asserted, and the semantic accessor is the only place that knows the meaning.
It refuses now, and the refusal covers both side effects -- publication AND
integration, which compares the target and then writes it.
