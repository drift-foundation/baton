## [P1] Mutable assignment identity bypasses the session binding

The generated transition wrappers at
`v12/src/authority/authority.mjs:1189-1218` read
`operands.expect.participant` to enforce the session binding, then pass the
original caller-owned `expect` object into `Core`. The core serializes and
validates that object through later property reads. A getter or Proxy can
therefore answer with the session participant during the wrapper check and the
foreign participant during the authoritative compare-and-swap.

I claimed `full-W2` as `poc.gemini`, built an otherwise exact assignment object
whose participant getter returned `poc.claude` for the wrapper's first two
reads and `poc.gemini` thereafter, and passed it to
`poc.claude`'s session `end`. The call committed: Gemini's assignment ended,
the Work became unclaimed, and the event/result named Gemini. A session holder
can use the same shape on `activity`, `advanceContract`, `cancel`, `end`,
`installGate`, `pass`, `publish`, or `rejectPlan`, defeating the stated rule
that it can act only on its own assignments.

Snapshot and normalize identity operands once at the session boundary. Validate
plain four-part data, compare the normalized participant to the binding, and
pass only an immutable normalized copy into the core; do not validate one view
and execute another. Add a regression with an accessor/Proxy identity proving
a foreign assignment and its journal remain unchanged.

## [P2] Claim silently ignores a supplied identity operand

The custom `claim` wrapper at `authority.mjs:1179` destructures only `workId`
and `operationId`, so `participant` or `actor` operands are silently ignored.
Calling a Claude session with `participant:"poc.gemini"` succeeded as Claude.
This does not impersonate, but it contradicts the correction's explicit rule
that identity-looking operands are refused rather than ignored. Apply the same
strict operand check used by the generated wrappers and add negative cases for
both names.
