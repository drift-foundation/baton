## P1 — replay provenance is inferred from bearer inequality

After `ControlStore.transact` decides the issue, `issueOffer` compares the
returned durable verifier with the verifier derived by this caller
(`offers.mjs:236-263`). Inequality proves this caller lost, but equality does
not prove it won. Two concurrent exact issuers can receive the same injected
bearer: the inner issuer commits, the outer `transact` replays that record,
the verifier comparison agrees, and the transaction loser returns success.

This contradicts the pinned exact-reissue answer and makes effectively-once
provenance depend on probabilistic secret uniqueness. The transaction boundary
already knows whether it executed the action or replayed a committed result;
propagate that fact (or an equivalent deterministic commit marker) so the
loser refuses regardless of bearer value. Do not infer journal provenance from
the operation's payload.

bearer uniqueness`.
