## Finding

### P1 — operation kind reaches comparison and SQL before becoming durable text

`_agreeing` now proves the signature document, but it never proves the separate
`kind` operand. Any JSON value that canonicalization admits can occupy the
signature's `kind`, and the separate operand may be `None`, an integer, an empty
string, or a behavior-bearing object.

This creates three different boundary failures:

- `None` reaches the `NOT NULL` journal column and escapes as raw
  `sqlite3.IntegrityError`.
- Integer `7` commits successfully; SQLite stores it as text `"7"`, so an exact
  retry with integer `7` collides with its own row instead of replaying.
- Comparing the parsed kind with a hostile separate operand invokes the
  caller's `__eq__`, escaping as its `AssertionError`.

An empty string also commits as an unnamed operation kind. Thus agreement and
canonical bytes still do not establish that the value being stored in a TEXT
identity column is durable text.

Validate kind as exact, non-empty, encodable text before parsing/comparison and
before opening the journal transaction. Apply the same rule in the exported
`manager_signature` helper so it cannot manufacture a signature that the store
must refuse. A rejected kind must execute no caller behavior and leave no row.
Retain
`test_an_operation_kind_is_durable_text_before_it_reaches_sql`.
