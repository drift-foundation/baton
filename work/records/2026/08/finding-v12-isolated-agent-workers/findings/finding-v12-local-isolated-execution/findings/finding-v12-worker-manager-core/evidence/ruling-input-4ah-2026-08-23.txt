1. THE QUESTION

Is a section 3.1 agent-session reference, as an IN-PROCESS API OPERAND, the
same exact inert data record the frozen schema describes -- or a structural
value whose four members are read once?

The independent review recommends the inert reading and asks that, if
approved, it explicitly supersede item 4aa's structural one-read boundary and
be implemented through W641's shared `recordFault`.

allowed to be a program".


3. WHAT THE FROZEN SCHEMA SAYS

`$defs.agentSessionRef` is `additionalProperties: false` over exactly
`runtime_attempt_id`, `posture`, `session_epoch`, `provider_session_id`, and
all four are REQUIRED. `provider_session_id` is required-but-nullable:
`oneOf [providerSessionId, null]`.

That is contract evidence for the inert reading. It governs the DOCUMENT form,
and whether the in-process operand must match it is exactly the open question.

5. A THIRD OPTION THE FRAMING DID NOT NAME

Finding (i) exposes a choice hiding inside "inert exact record": whether
`providerSessionId` is REQUIRED AT THE API or OPTIONAL-IN-ABSENCE.

  INERT, STRICT      expected = all four. Faithful to the frozen document,
                     where the member is required-but-nullable. ~168 call
                     sites and fixtures must write `providerSessionId: null`
                     explicitly.
  INERT, ABSENCE     expected = three required plus one optional; an absent
  MEANS NULL         member still means the null the document requires. The
                     168 vanish. Every container change in (iii) still holds.
                     The in-process operand and the durable document differ in
                     exactly one stated way.
  STRUCTURAL         today's boundary, made explicit rather than implicit --
  (the status quo)   the API accepts any container and reads each member once.
                     Then item 4aa stands as written and the Proxy asymmetry
                     in section 2 should be stated as deliberate.

I am not recommending one. What I can say from the measurement is that the
cost people would associate with "inert" is almost entirely the
provider-member question and not the container question, and those are
separable.
