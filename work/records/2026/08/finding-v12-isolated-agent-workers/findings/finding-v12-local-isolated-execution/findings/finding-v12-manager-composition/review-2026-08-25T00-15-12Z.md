## [P1] An old journal result is replayed after its certification was replaced

`certify_agent_session_profile` derives its operation identity solely from the
profile digest and uses the general effectively-once manager journal. That is
safe for an immediate retry while the effect remains current, but not after a
later certification replaces that profile ID's bytes.

The failing sequence is:

1. certify bytes A under one `profile_id`;
2. certify different bytes B under that same ID;
3. certify A again.

The third call replays A's old success and skips the upsert. Its answer says A
was certified, while `certified_agent_session_profile` still returns absence
for A because B remains in the `profiles` row. This contradicts the public
operation's stated effect and the schema's explicit model that recertifying the
same profile ID under new bytes changes one current profile.

Preserve journal history, but do not use a historical result as proof that a
replaceable state-setting effect is still current. Revalidate the operation
identity/lifecycle against the frozen unjournalled certification path and the
manager's effectively-once contract before choosing the correction.

The additive
`test_recertifying_prior_bytes_makes_them_current_again` demonstrates the gap.

## [P2] The public module narrative names the superseded rule placement

`handshake.py` still says the §2.2 check is reached from the certification
path. The implementation, PROGRESS finding, and current PLAN place it at
emission in `negotiate_acp`. Update the module contract so a reader sees one
current placement rather than two contradictory ones.
