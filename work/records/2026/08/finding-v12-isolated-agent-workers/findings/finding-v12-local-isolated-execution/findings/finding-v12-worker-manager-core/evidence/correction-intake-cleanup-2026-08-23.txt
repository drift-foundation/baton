2. THE ONE THAT INVALIDATED MY OWN FIXTURE

[P1] INTAKE COULD DECIDE WITH NO SEALED MATERIAL, AND RECORDED NO MATERIAL
IDENTITY. `recordIntake` required only a fixed assignment and stored an
unbound locator, and the `intake` row carried no result digest. So THE
SLICE'S OWN `ended()` FIXTURE — which created no output row and no retained
result manifest — accepted, rejected, retained and quarantined material THAT
DID NOT EXIST. Every positive case in the suite was about nothing.

A LOCATOR IS WHERE SOMETHING IS. It is not which immutable result was judged,
and a restart holding only a locator cannot say what the decision concerned.

CORRECTED both ways: intake requires a sealed output for the attempt and binds
the decision to that output's result-manifest digest, with a foreign key to
the retained bytes. And the fixture drives the REAL freeze path now — a real
declaration, a real sealed result, `requestFreeze` — so the positive cases
decide the fate of material this manager actually sealed.

The quarantine manifest for material with NO frozen result is not
implemented, and the refusal says so rather than pretending the sealed path
covers it.


3. THE OTHER THREE

[P1] INTAKE PROSE BYPASSED THE DURABLE-SECRET BOUNDARY. `reason` went straight
into SQLite. The shared transaction guard scans the serialized RESULT, and my
result deliberately omitted `reason` — so a live bearer passed as prose
committed verbatim. A SUMMARY THAT OMITS A COLUMN IS NOT A GUARD OVER THAT
COLUMN. The exact durable record is assembled and scanned before any of it is
written.

[P1] POSITIVE RUNTIME ABSENCE BYPASSED THE INTAKE GATE. `settleCleanup` asked
only whether the runtime was `destroyed`, so a caller could complete cleanup
with no intake decision at all. ABSENCE DOES NOT DECIDE POLICY: an observation
proves the runtime is gone and says nothing about whether the ended
assignment's material was retained or quarantined. The policy gate is checked
first, and the destroyed observation is still what makes cleanup complete —
two gates, not one gate doing two jobs.

[P2] THE RETENTION DEADLINE ACCEPTED ARBITRARY TEXT. The interface and the
contract both call it a deadline and the STRICT column constrained only the
storage class, so the literal `tomorrow` was durable scheduling state. It is
validated against the contract's canonical timestamp form. No expiry policy is
decided here; a deadline is simply a deadline or it is not one.
