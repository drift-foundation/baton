WHAT THIS SLICE IS

  The rest of the frozen `attempts.mjs`, and the ordering IS the content:

    request_runtime_start   commits a fully signed `runtime.start` operation and
                            hands its identity to the adapter, so the adapter
                            and a restart settle the same act
    reconcile_runtime       decides what exists by IDENTITY and by the FULL
                            labels; mismatch or multiplicity CANCELS rather than
                            starting another
    request_cancellation    fences at the authority FIRST, then orders the agent
                            cancelled and the runtime stopped -- and never
                            claims either of them happened

  Two injected capabilities enter: the runtime adapter (start, list, stop) and
  the provider agent (cancel). What a conforming one must BE is still a later
  item's to pin, which is why POSITIVE RUNTIME ABSENCE cannot be proven here and
  the retry path stays closed and says so. A proof a caller can write is not a
  proof, so this takes no `absence_proven` operand.

  STILL ABSENT RATHER THAN STUBBED: output freeze, intake and cleanup, then the
  agent state machines and the public manager composition.

THE ORDERINGS, AND WHY EACH IS THAT WAY

  JOURNAL BEFORE THE ADAPTER. An axis label is not an effectively-once act: a
  journalled operation is what a restart replays and what the adapter can be
  asked about, while a state column records only that somebody once intended to
  start.

  THE MINTED RUNTIME IS CHECKED BEFORE THE FILTER. A runtime this call started
  carrying labels for a different assignment is not ABSENT, it is WRONG, and
  this call caused it -- filtering it out would leave a mislabelled runtime
  running with the manager waiting for news.

  FENCE, THEN STOP. Until the generation is fenced the assignment is still live,
  so a runtime stopped first would be a worker torn out from under an assignment
  the authority still believes is executing. The manager's own intent is
  journalled BEFORE the authority is asked, for the same reason runtime start
  journals first: a crash between two boundaries must be answerable.

  THE AGENT BEFORE THE RUNTIME. An agent told to stop after its runtime is
  already going away never hears the order, and the cooperative shutdown is the
  whole point of asking it. A FAILED COOPERATIVE REQUEST DOES NOT VETO THE STOP:
  by that line the authority has already fenced and ended the assignment, so
  persistent agent unreachability is a REASON to stop the runtime rather than a
  reason to leave a fenced one running.

  ORDERED, NOT DONE. Both settlements ride back UNINTERPRETED and un-normalized.
  Reaching a boundary is not evidence of its effect, and collapsing "the
  boundary returned nothing" into "it returned null" is a smaller version of the
  same mistake.

TWO DELIBERATE DEPARTURES FROM THE ORACLE, BOTH REPORTED

  1. THE CANCELLATION ANSWER IS NESTED, NOT MERGED. The frozen host spreads the
     intent, the fence and the quiescence answer into one object, so its member
     set depends on which branch ran. Three named members always present is a
     document the next receiver can own, which is what the outbound constructors
     exist for.
  2. THE LOST-RACE CATCH IS NARROWED to the compare-and-swap's own refusal. The
     oracle catches every contract error there, which swallows an operation
     COLLISION and answers it as a cancellation -- so a wrong operation identity
     would be invisible. §4.2's collision is the caller's to see. This is what
     makes the per-runtime attach identity OBSERVABLE, and the mutation table
     below shows the two are complementary.

WHAT THE INVENTORY REQUIRED, AND WHAT IT FOUND

  The adapter and the agent are capabilities, so their calls are injected
  crossings and their answers are entries. That surfaced a modelling gap I had
  to fix rather than declare: `cancel` exists on the authority session AND on
  the provider agent, so a member name alone stopped identifying a crossing. For
  those two capabilities the holder's name is now part of the member's identity
  -- two crossings that share a verb are still two crossings.

  Owned at the crossing: the adapter's start answer and every listed runtime,
  because the manager COMPARES their ids and labels. Stated with the pinned
  reason: the two settlements, which it forwards uninterpreted.

  Three derived identities (`_start_operation_id`, `_cancel_operation_id`,
  `_authority_cancel_operation_id`) are PRIVATE, for the reason
  `_fixed_assignment` is: each projects an attempt row this build has already
  adopted, and an exported projector over an unowned dict is a boundary nobody
  owns. They become public when a restart needs to name the act.
