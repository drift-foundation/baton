2. THE FINDING

[P1] AN AGENT CANCELLATION FAILURE SUPPRESSED THE RUNTIME STOP. `agent.cancel`
was called and `adapter.stop` followed it on the same straight line, so a
throwing agent left the function before the stop was ever ordered — WITH THE
AUTHORITY ALREADY FENCED AND THE ASSIGNMENT ALREADY ENDED. An unreachable
provider therefore left a fenced runtime running indefinitely.

The correction I made last round created this. I added the agent boundary in
front of the runtime stop and did not ask what happens when the boundary I put
first fails.

PERSISTENT AGENT UNREACHABILITY IS A REASON TO STOP THE RUNTIME, NOT A REASON
TO LEAVE IT ALONE. A cooperative request is the polite path, not a
precondition for the forceful one. The failure is captured, the stop is
ordered anyway, and only then is the failure re-thrown UNCHANGED — it is the
caller's to classify, not this boundary's, and the order stays
agent-before-runtime.

WHEN BOTH FAIL, NEITHER HIDES THE OTHER. An `AggregateError` carries both, in
call order. Letting the runtime's failure propagate alone would have been this
boundary silently choosing which failure the caller is entitled to see, which
is the same shape as summarizing a settlement.

Because of that, one of my case titles was overclaiming — it said "reports no

Plus two of mine:

  - a failing runtime stop does not hide a failing agent — both boundaries

  - a failed agent cancellation is re-thrown UNCHANGED, after the stop — not

5. WHAT IS STILL NOT DURABLE, AND SAID PLAINLY

A failed agent cancellation is visible to the CALLER and is not recorded in
the store. There is no agent-session evidence table yet — item 7 of the pinned
store surface, owned by item 4 — so a manager that crashes right after the
throw learns nothing about the failed cooperative attempt beyond the committed
`attempt.cancel` intent. That is a gap in coverage, not a claim that it does
not matter.
