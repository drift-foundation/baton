1. [P1] I STATED THE RULE IN ONE PLACE AND CALLED IT FROM ONE SITE

Cut 3's own evidence says I put the opaque-id rule in one place "so a second
boundary cannot reach a different conclusion about the same string". I put the
RULE in one place. I called it from `Store.replay` and nowhere else.
`settle_operation`, `operation_result` and `operation_record` kept the weaker
text check.

So a one-million-character id was still a durable primary key -- and the review
found the worse half: SETTLEMENT COULD RECORD AN INVALID IDENTITY AS RETIRED,
and a claim under the same id then refused on SHAPE before ever reading the
retirement. Two authority paths disagreed about whether a durable identity
existed, and the bound retirement reason was never replayed. That is not a size
problem; it is two answers to one question.

`check_opaque_id` now serves all four paths. Writing a rule down is not applying
it, and this is the third time this week I have made that exact mistake in a
different shape -- documented-but-unimplemented, implemented-at-one-of-two-sites,
and now stated-once-called-once.


2. [P2] THE RACE CHILDREN WERE READING THE SOURCE TREE UNDER THE INSTALLED GATE

Both child scripts began with `sys.path.insert(0, <repository src>)`. Under the
installed gate the parent used the wheel and every child ran source code, so the
five subprocess race cases proved something about `src/` while the gate claimed
to exercise the whole installed layout. A packaging skew in claim, replay or
settlement would have passed it.

The children are told the store path and NOTHING about imports now. They inherit
the gate's own environment -- `PYTHONPATH=src` for the source stage, an empty one
plus the venv interpreter for the installed stage -- and each REPORTS the
directory it imported `baton_v12.authority` from. The parent asserts child and
parent origins agree, so the claim is checked rather than assumed.

MEASURED: with the child's `sys.path.insert` restored to the real repository
path, `just build` FAILS with four failures -- the origin assertion firing in
every race case. The guard detects exactly the skew that was there.


3. THE SETTLEMENT SIGNATURE CAP, NOT INVENTED

Accepted as ruled: settlement must compare the exact canonical signature the
authority itself produced, including every durable operand, and the contract has
no system-wide text bound -- so a settlement-only limit could reject a legitimate
signature. The code now says so where the check would have gone, and points at
the broader operand/signature ruling as the only place it could change.
