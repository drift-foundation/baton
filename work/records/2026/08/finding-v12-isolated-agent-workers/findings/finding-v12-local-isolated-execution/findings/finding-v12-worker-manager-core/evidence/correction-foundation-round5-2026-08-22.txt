2. [P1] THE JOURNAL VALIDATED A DIFFERENT OBJECT FROM THE DURABLE JSON

`transact` walked the action's result and then called `JSON.stringify`
separately for the row. Two observable reads of a value the manager did not
construct: a `toJSON` method returns `{diagnostic: <bearer>}` while
`Object.entries` shows only the method, so the walk passed and the raw bearer
committed.

The durable boundary is the SERIALIZED REPRESENTATION, not the object it came
from. `_durable(value, where)`:

  const bytes = JSON.stringify(value ?? null);
  assertNoDurableSecret(JSON.parse(bytes), where);
  return bytes;

Serialized ONCE. The parse of those exact bytes is what gets walked —
`JSON.parse` runs no user code, so the walk sees precisely what will be
stored — and the SAME bytes are recorded. It does not reserialize after
validating, which would reopen the identical gap for a stateful `toJSON` or
getter; a regression counts the reads and asserts exactly one.

Both durable surfaces go through it: the committed result and the sealed
refusal.


3. [P1] SECRET SCOPES RELEASED VALUES THAT WERE STILL LIVE

Two defects in one `Set`, and the Set is why:

  - A `Set` records PRESENCE, not ownership. An outer owner holding a bearer
    and an inner `withSecret` on the same value are two registrations of one
    value; the inner `finally` deleted the outer owner's still-live entry. A
    scoped use of the seeded golden bearer could delete the seed itself.
  - `withSecret` released as soon as the act RETURNED. A provider act
    naturally returns a Promise, so the bearer was unregistered while the
    work was still pending — precisely the call shape the orchestration slice
    will use. Returning a pending Promise is not completion.

CORRECTED with TWO REGISTERS, because two different lifetimes were being
conflated:

  _PINNED   what this BUILD knows at rest: the golden conformance bearer.
            Never released, because nothing acquired it and so nothing may
            hand it back.
  _live     a REFERENCE COUNT. A value stays live until its last owner
            releases it. An unbalanced release of a value nobody holds
            changes nothing rather than going negative and swallowing the
            next registration.

`withSecret` now transfers ownership to the continuation when the act returns
a thenable, releasing in `.finally` so an awaiting caller sees the value
released and a pending one still sees it held. A synchronous throw still
releases immediately.

THE REVIEWER'S ALTERNATIVE — remove the scoped API until its real
orchestration caller can define the lifetime — was considered and not taken.
The API is what makes the boundary usable rather than a convention to
remember, and both of its failure modes are now regressions rather than
possibilities. If the reviewer would still rather it wait for its caller,
deleting it is a small change and I will make it.
