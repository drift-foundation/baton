2. [P1] THE FIRST COMMITTED RESULT WAS NOT THE DURABLE RESULT

Round 5 made the journal record `_durable(result)` — the exact serialized
bytes — and left `transact` returning `result` itself. So a `toJSON` gave the
first caller the caller-owned source object and an exact retry the parsed
journal: two different answers under ONE operation identity, for an act that
ran once. The dossier pins a byte-stable operation result AND says returned
values are copies rather than caller-owned aliases; that path satisfied
neither.

CORRECTED: `_durable` returns `{bytes, committed}` from the ONE
serialization. `committed` is the parse of exactly those bytes, and it is
what every caller is told — first call and replay alike. It is nobody's
alias, so a caller that mutates what it was handed cannot change what the
next caller is told, and no caller behaviour is invoked a second time.


3. [P1] THENABLE CLASSIFICATION CONSUMED A DIFFERENT CONTINUATION

`withSecret` read `outcome.then` to decide whether ownership transfers and
then handed `outcome` to `Promise.resolve`, which reads `then` again —
assimilation may read it further. A stateful thenable exposing its
continuation on the first read and `undefined` afterwards was classified
asynchronous while the continuation was never called: the wrapper settled
immediately and released the bearer with the represented act still pending.

This is the same shape as the round-5 serialization finding, one level down.
A read that DECIDES something must be the read that is USED.

CORRECTED: the continuation is captured once and THAT callable is
assimilated, with its original receiver:

  const continuation = outcome?.then;
  if (typeof continuation === "function") {
      transferred = true;
      return new Promise((resolve, reject) => {
          continuation.call(outcome, resolve, reject);
      }).finally(() => forgetSecret(value));
  }

A THROWING `then` getter lands in the existing `finally` with `transferred`
still false, so the synchronous cleanup covers it — which the review requires
explicitly, and which now has its own regression: a value whose
classification failed was never handed to anyone, so nothing else would ever
release it.

The review also confirms the scoped API does not need removing. That closes
the question I raised last round.

5. REGRESSIONS — 236 (231 before)

The reviewer's two are retained unchanged. Added five:

  - a throwing `then` getter releases synchronously (the review's explicit
    requirement, and unwitnessed until now);
  - a thenable that REJECTS through its captured continuation releases — a
    provider act ending badly is the likeliest way to strand a registration;
  - a non-callable `then` is ordinary data and releases synchronously, since
    treating it as asynchronous would strand the bearer forever;
  - the committed answer is one canonical value everywhere: not an alias at
    the top level or nested, and mutating the first answer does not change
    what the retry replays;
  - an action returning nothing answers `null` on the first call as well as
    the replay, because `undefined` has no durable representation.
