## [P1] The journal validates a different object from the durable JSON

`ControlStore.transact` walks the action's result and then separately calls
`JSON.stringify` for the operation row. Those are two observable reads of an
arbitrary result object. A `toJSON` method can return
`{diagnostic: GOLDEN_BEARER}` while `Object.entries` exposes only the method;
the guard passes and the later serialization commits the raw bearer.

The durable boundary is the serialized representation, not the pre-encoding
object. Serialize exactly once, validate the exact resulting plain value or
JSON text against known bearer values and secret field names, and record those
same bytes. Do not reserialize after validation: stateful `toJSON` methods or
getters would reopen the same time-of-check/time-of-use gap. Retain the
additive store regression and require `integrity.secret-leak` with no operation
row.

## [P1] Secret scopes release values that are still live

The registry is a `Set`. If an outer owner calls `rememberSecret(value)` and
an inner `withSecret(value, act)` uses the same value, the inner registration
adds nothing and its `finally` deletes the outer owner's still-live entry.
This also means a scoped use of the seeded golden bearer can remove the seed.

`withSecret` additionally releases as soon as an act returns a Promise. Its
synchronous `finally` runs before the asynchronous continuation, leaving the
bearer unregistered while the provider act is still pending. That is exactly
the call shape the not-yet-landed orchestration and adapter slice is likely to
use.

Preserve overlapping ownership, for example with reference counts or opaque
registration handles, and make scoped release Promise-aware while retaining
synchronous throw cleanup. Alternatively remove the scoped API until its real
orchestration caller can define the lifetime; an API that advertises “exactly
one act” may not end the scope at Promise creation. Retain both lifecycle
regressions.
