## Findings

### P1 — concurrent first openers race initialization into raw SQLite faults

`ControlStore.open` decides that a schema is empty before acquiring the write
lock. `_initialize` then takes `BEGIN IMMEDIATE` but does not re-read ownership
inside that lock. When several managers observe one fresh database as empty,
the first creates the schema and every waiter resumes by running the same
`CREATE TABLE`, escaping as `sqlite3.OperationalError: table meta already
exists`.

The reviewed contract explicitly permits a manager to start at an absent path,
and multi-process managers coordinate through this shared store. Initialization
must therefore re-check under the lock: initialize if still empty; validate and
adopt if another opener created the exact compatible store; otherwise refuse a
foreign shape without mutation.

Regression:
`tests.manager.test_store.OwnershipBeforeAdoption.test_concurrent_first_openers_adopt_one_initialized_store`.

### P1 — an unrelated table named `meta` escapes the refusal taxonomy

The optimistic object check treats the mere name `meta` as permission to run
`SELECT key, value FROM meta`. A foreign database with `meta(id INTEGER)` then
raises raw `sqlite3.OperationalError: no such column: key`. The stated
empty-or-ours rule covers every foreign schema, including one that happens to
reuse a generic table name. Probe/validation errors must become the closed
`integrity/schema` refusal while preserving the database bytes.

Regression:
`tests.manager.test_store.OwnershipBeforeAdoption.test_an_unrelated_meta_table_is_still_a_closed_refusal`.

### P1 — replay ignores the recorded operation kind

The journal stores `kind`, and `manager_signature` includes it, but
`ControlStore.replay(operation_id, signature)` compares only the caller-supplied
signature. Reusing an operation id with the same signature argument and a
different `kind` therefore replays the first success instead of raising
`refused/operation-collision`. The store accepts two caller-controlled accounts
of the kind and proves neither agrees with the other.

Bind kind once: either derive the signature inside the store from kind and
owned operands, or validate the supplied signature's canonical content and
compare both stored kind and signature on replay. A first write with mismatched
kind/signature must not create a contradictory row either.

Regression:
`tests.manager.test_store.OneAtomicBoundary.test_the_operation_kind_is_part_of_the_collision_identity`.

### P2 — the schema does not enforce one sealed outcome per journal row

The `operations` table constrains `state` but not its payload columns. It accepts
a committed row without `result`, a committed row carrying `refusal`, a refused
row without `refusal`, and a refused row carrying `result`. `_record` currently
writes coherent rows, but every action receives the same connection and future
cut code will add more writers. The durable store should reject impossible
state rather than leave replay to fail later or reinterpret SQL null.

Require exactly one shape: committed has non-null JSON result and null refusal;
refused has null result and non-null sealed refusal. JSON `null` is stored as the
text `"null"`, so it remains distinct from SQL null.

Regression:
`tests.manager.test_store.OneAtomicBoundary.test_the_journal_schema_requires_exactly_one_sealed_outcome`.

## Accepted in this round

- The manager store is separate from authority state and carries an explicit
  product kind before schema version.
- A genuinely foreign schema without manager metadata is refused unchanged;
  compatible reopen adds no tables.
- Transactional action writes and the journal record commit together; ordinary
  refusals and faults roll back, while durable refusals keep their writes and
  replay the complete closed pair.
- Committed JSON null is distinguished from absence, results are owned before
  journalling, projections are fresh, and settled instants use the injected
  clock.
- Exact retries, operation-id collisions on changed signatures, restart replay,
  and the initialized-store four-process race are covered.
- The frozen Node oracle remains untouched.
