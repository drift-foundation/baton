2. [P1] THE CHECK OUTSIDE ANSWERS; THE LOCK DECIDES -- AND I APPLIED THAT TO
   ONE OF THE TWO PLACES THAT NEEDED IT

`transact` re-reads inside the lock, and I wrote a comment saying why: two
managers can pass the optimistic peek concurrently and a read-then-write check
outside would let both through. `open` did the same thing and did NOT re-read:
emptiness was decided before the lock, so when several managers observed one
fresh database as empty the first created the schema and every waiter resumed
into the same `CREATE TABLE`.

The same sentence, the same file, applied at one of two sites. That is the fifth
time this campaign, and the first time I had already written the rule down in the
module where I then failed to follow it.

Initialization now re-reads under the lock: still empty -> create; already ours
-> adopt by exactly the rule any other existing store is adopted by; foreign ->
refuse untouched.


3. [P1] A NAME IS NOT PERMISSION

The mere name `meta` was treated as licence to run `SELECT key, value FROM meta`,
so a foreign database carrying `meta(id INTEGER)` escaped as a raw SQLite error.
The empty-or-ours rule covers EVERY foreign schema, including one that happens to
reuse a generic table name -- so the probe runs inside the taxonomy rather than
in front of it, and a caller reading our refusals does not have to know SQLite's
error vocabulary to learn their database is not ours.

The two foreign shapes are told apart, because "no metadata at all" and "a meta
we cannot read" are different facts and the second message is wrong about the
first. Measured: removing the first branch still REFUSED, with the wrong reason.


4. [P1] TWO CALLER ACCOUNTS OF ONE FACT

The journal stores `kind`, `manager_signature` puts the kind INSIDE the
signature, and `transact` took both from the caller and compared neither. So a
first write could record a row whose two accounts of the kind contradicted each
other, and a retry with the same signature and a different kind replayed the
first success instead of colliding.

Bound at the write, so a contradictory row cannot exist to be replayed, AND
compared at replay, so a row written by another writer or an older build still
collides. Both, because unreachable is not the same as unnecessary -- the
write-time check makes the replay comparison unreachable from the public path,
and a store is not the only thing that writes to a store.


5. [P2] IMPOSSIBLE STATE, REJECTED BY THE STORE

`state` was constrained and its payload columns were not, so the table accepted a
committed row with no result, a committed row carrying a refusal, a refused row
with no refusal, and a refused row carrying a result. `_record` writes coherent
rows -- and every action receives the same connection, and later cuts add writers.

One CHECK, and JSON `null` stays the TEXT "null" so it remains distinct from SQL
NULL, for the same reason `replay` answers presence separately from value.

THE VERSION WENT TO 2 WITH IT. A store written under the weaker table cannot
satisfy the rule this build enforces, and keeping the number would have let this
build adopt one -- which is the "does not guess across versions" rule applied to
my own change instead of somebody else's.

AND THE INVARIANT CAUGHT MY OWN TESTS: two fixtures wrote committed rows with no
result as side-effect markers. That is the argument for putting the rule in the
schema rather than in the writer.

THE FIRST LOCKED DOWNLOAD AFTER THE RULING WAS REFUSED, and that is the finding
worth recording. `pip` and `setuptools` were hashed from DEBIAN'S REPACKAGED
WHEELS in /usr/share/python-wheels, because under the offline arrangement those
WERE the artifacts. The index serves different bytes for the same version, so
`--require-hashes` stopped the build and named pip's expected and actual digests.

The mechanism worked exactly as intended. A hash is a fact about BYTES, and the
bytes changed when their source did -- so both were re-measured from the index's
artifacts rather than carried over. Had the flag been advisory, the build would
have silently installed something the lock did not describe.
