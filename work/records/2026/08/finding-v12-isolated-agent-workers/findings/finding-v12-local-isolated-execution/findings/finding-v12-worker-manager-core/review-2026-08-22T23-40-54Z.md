## Findings

### P1 — the completed cancellation slice omits required agent cancellation

The owning acceptance boundary says that only after `session.cancel` fences
the generation does the manager order **agent cancellation and runtime stop**
(`FINDING.md`, Runtime, cancellation, output and cleanup). The implementation
has one post-fence outside call, `adapter.stop`, and the test trace can observe
only `authority.cancel` followed by `adapter.stop`. There is no agent-session
handle, agent cancellation operation or agent-side trace anywhere in this
slice.

`session.cancel` is the assignment-authority fence; it is not the provider
agent cancellation required after that fence. Deferring the provider-neutral
adapter contract to item 4 is reasonable, but then item 3k is only the
runtime-side portion of cancellation ordering and cannot be marked done. Keep
the acceptance item open until a minimal injected agent-cancellation boundary
is ordered between the authority fence and runtime stop, or obtain and append
a confirmed superseding decision that moves that required act to item 4 and
makes 3k a partial slice. Add the ordered trace regression once that interface
exists.

### P1 — calling `stop` manufactures a positive stopped fact

`orderStop` discards the result of `adapter.stop(...)` and unconditionally
returns `{stopped:true}` whenever the call returns. A cooperative adapter can
return `{stopped:false}` and the manager nevertheless reports the runtime as
stopped while its durable axis remains only `cancel-requested`. This confuses
an order issued with a positive observation, precisely where the quiescence
gate requires positive absence and the dossier says the gate is not satisfied
here.

The additive regression `W2929 review: ordering a stop is not proof the
runtime stopped` drives that result and fails. Preserve it. The correction may
report an explicit `stopOrdered` fact, propagate a defined adapter settlement,
or otherwise use the item-4 contract, but it must not manufacture `stopped`
from reaching the call boundary.

### P2 — the durable plan contradicts implementation and tests on retry

Plan item 3k says, “The stop order is not repeated for a runtime already
`stopping`.” The implementation calls `adapter.stop` in that state, and
`W2929: an in-flight stop is re-ordered without rewinding the axis` requires
that repeat. The handoff evidence also describes re-ordering. Reconcile the
current plan with the chosen retry rule; the plan and executable acceptance
cannot leave opposite live requirements.
