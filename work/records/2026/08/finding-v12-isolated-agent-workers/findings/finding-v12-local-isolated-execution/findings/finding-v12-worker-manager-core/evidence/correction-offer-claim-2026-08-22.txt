2. THE SIX

[P1] THE SETTLEMENT COULD NOT NAME ITS OPERATION. `acceptOffer` stored
`claim_signature = NULL` and settlement passed `undefined`, so a real
committed claim read as an operation collision and retirement could not write
the authority's NOT NULL column. The acceptance transaction now freezes
`V12Authority.claimSignature(workId, participant)` beside the intent, and
every settlement uses that exact value. It is IMPORTED rather than restated:
a third copy of a signature rule is a third thing that can drift, and this one
decides whether a settlement is recognised at all.

[P1] THE ASSIGNMENT SHAPE. `V12Session.claim` returns the assignment
DIRECTLY and both recording paths read `result.assignment`, so the authority
held a live generation while the manager durably recorded `assignment: null`.
A record that disagrees with the authority is worse than none, because a
restart trusts it. Both paths record what the authority returned.

[P1] THE PARTICIPANT IS THE SESSION'S BINDING. `issueOffer` took it as an
independent operand and never compared it, so the offer, verifier and intent
could name B while `submitClaim` necessarily acts as A. A session with no
binding is refused outright; an operand that disagrees with the binding is
refused before entropy; otherwise the binding is what is stored.

[P1] EXPIRY IS A SETTLEMENT, not only a refusal. It threw and left the row
`issued` with an unspent verifier holding the per-Work slot — so the Work
could never receive another offer and the bearer stayed replayable against
the pinned single-use rule. Expiry now CASes to `expired`, consumes the
verifier, keeps the row visible and releases the slot; the caller's refusal
is still raised, because their decision did fail.

[P1] STALE TERMINALIZATION. `settleTerminal` updated `issued` OR `accepted`
rows while both callers act from an earlier `issued` read, so a stale decline
or abandonment could destroy the authorization and fixed claim identity that
acceptance had just frozen. Every issued-only transition CASes from `issued`
alone and reports the winner's state without rewriting it.

[P1] CERTIFICATION WAS OPTIONAL. The comparison was conditional on the
argument being supplied, so omitting it skipped the check entirely — and my
happy-path fixtures omitted it throughout, which is how it survived. The
control store's own `profiles` row is the stronger fact and is preferred; an
explicit assertion is accepted otherwise and may not CONTRADICT the store;
absence of both is refused before entropy. `certifyProfile` records one.

[P1] ISSUE REPLAY. The signature covered three operands, so a changed policy
digest replayed the first offer as the same request — an operation identity
that ignores operands is not an identity. It now covers every effective
durable operand. And the replay is checked BEFORE entropy: the bearer exists
only in the process that minted it, so a second call cannot reproduce one and
refuses rather than returning a secret that does not derive the stored
verifier.
