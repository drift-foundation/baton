## Findings

### [P1] Intake can decide without any sealed material and records no material identity

`recordIntake` requires only a fixed assignment, then stores an unbound
locator (`intake.mjs:86-119`). The `intake` row has no result-manifest digest
or output foreign key (`schema.mjs:202-217`). Consequently the slice's own
`ended()` fixture, which creates no output row or retained result manifest,
can accept or reject and retain or quarantine material that does not exist.

This contradicts the pinned `output.retain` precondition of the exact attempt
**and material**, and leaves restart unable to prove which immutable result
the decision concerned. Require a sealed output for the exact assignment and
bind the decision durably to its result-manifest digest. Update positive
fixtures to create real frozen material; do not make an unbound locator stand
in for it.

Regression: `W2929 review: intake cannot decide before material is sealed`.

### [P1] Intake prose bypasses the durable-secret boundary

`reason` is inserted directly into SQLite at `intake.mjs:109-118`. The shared
transaction guard scans only the serialized result returned by the action
(`store.mjs:258-282`), and that result deliberately omits `reason`. Passing
the live golden bearer as `reason` therefore commits it verbatim.

Validate the exact durable intake record, including nullable prose and
deadline fields, with the shared secret guard before any row is written. A
summary that omits a column is not a guard over that column.

Regression: `W2929 review: intake prose cannot persist a live bearer`.

### [P1] Positive runtime absence bypasses the intake gate

`settleCleanup` checks only `execution_runtime === "destroyed"` and then moves
cleanup to `complete` (`intake.mjs:236-244`). A caller can therefore complete
cleanup with no intake decision and no pinned discard policy. The runtime
observation proves absence; it does not decide whether the ended assignment's
material was retained or quarantined.

Require the recorded intake boundary (or a future durable pinned discard
policy) before cleanup can become complete. This does not require a redundant
destroy order when positive absence is already known; it requires the policy
gate that destruction and cleanup are specified to respect.

Regression: `W2929 review: a destroyed runtime does not bypass intake`.

### [P2] The retention deadline accepts arbitrary text

The interface and frozen contract call `retainUntil` / `retain_until` a
deadline, but `recordIntake` stores any value and the STRICT table constrains
only the SQLite storage class (`intake.mjs:86-118`, `schema.mjs:209-216`). The
literal `tomorrow` is accepted as durable scheduling state.

Validate a non-null deadline as the repository's canonical timestamp form
before deriving or committing the operation. No expiry policy is requested
here; this finding is only that a deadline must be a timestamp.

Regression: `W2929 review: a retention deadline is a validated timestamp`.
