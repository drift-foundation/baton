## P1 — ACP wire capabilities are replaced by the durable profile shape

Frozen §2.2 says the ACP wire sends exactly
`{ "fs": {}, "terminal": false }`, with both optional camel-case filesystem
members absent. The pinned SDK 1.3.0 declaration confirms `readTextFile` and
`writeTextFile` are optional wire members. The frozen agent-session schema,
by contrast, records a normalized snake-case document with both members
explicitly false.

`MINIMAL_CLIENT_CAPABILITIES` copies that durable document into the transport
boundary. `validateClientCapabilities` refuses §2.2's exact wire document and
`negotiateAcp` emits `read_text_file` and `write_text_file`, which are not ACP
wire field names. Its `JSON.stringify` equality is additionally sensitive to
object member order, although JSON object equality here is structural.

Separate the two representations. At the ACP transport boundary accept and
emit only `{ fs: {}, terminal: false }`, reject all additional members, and
compare the document structurally rather than by serialization order. Keep a
distinct, explicitly named normalized durable representation only where the
agent-session schema requires it.

The pre-existing frozen-model/schema/spec conflict is now independently owned
by W641 at
`work/records/2026/08/finding-acp-client-capability-wire-profile-conflation/`.
W4 should follow the explicit §2.2 wire text and pinned SDK declaration now;
W641 must correct the owning frozen artifacts without silently rewriting
their history.

Case-specific authorization: migrate the existing focused assertions that
currently require `MINIMAL_CLIENT_CAPABILITIES` and `negotiateAcp()` to carry
the durable snake-case shape, only as needed to distinguish the literal wire
document from the durable normalized profile summary. Preserve their exact
withholding and fresh-copy assertions under the corrected names.

## P1 — both claimed closed method surfaces default open

`checkOutboundMethod` rejects only the 21 methods known to the current
negative list, then returns every other string. It therefore permits the
explicitly nonexistent `session/reuse` and any future vendor method. That is
the inverse of §2.3's version-owned closed surface: only the five required and
three optional methods exist, with an optional method usable only after its
advertisement and profile pin are established at composition.

`serveClientMethod` has the same negative-list shape. It rejects today's eight
enumerated client methods but serves any future method by default, even
though §2.2 advertises no client capability and §4.4 makes every call to an
unadvertised client method a `policy.denied` failure. This recreates exactly
the silent future-SDK widening §2.2 was written to prevent.

Make both guards allow-list boundaries. The outbound guard may admit only the
version-known required/optional agent surface, leaving optional advertisement
and profile-pin enforcement to its named composition boundary; everything
else is `refused.capability`. A boundary dedicated to client-directed calls
denies every method in 1.0 because none is advertised. If this helper remains
a generic inbound classifier, it may pass only the closed known agent-origin
surface (including `session/update`) and must deny every unknown name as
`policy.denied`. Preserve the existing `session/update` routing assertion
under whichever named non-client boundary owns it, and retain the enumerated
set tests plus both unknown-method regressions.

Case-specific authorization: if `serveClientMethod` becomes a truly dedicated
client-call boundary, migrate the existing `session/update` pass-through
assertion to the generic/agent-origin routing guard that now owns it. Do not
drop the assertion or make `session/update` a denied client capability.
