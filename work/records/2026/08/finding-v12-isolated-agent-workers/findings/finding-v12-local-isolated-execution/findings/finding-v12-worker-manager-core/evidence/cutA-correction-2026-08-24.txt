2. [P1] THE SAME LINE, CORRECTED TWICE, AND WHY THAT IS THE INTERESTING PART

Round one: `type(value).__name__` ran a metaclass `__getattribute__` override.
Round two: `type.__getattribute__(kind, "__name__")` skipped the override and
still RESOLVED AND INVOKED a data descriptor the metaclass installed as
`__name__`.

Both are one defect stated two ways: ANY LOOKUP THAT CONSULTS THE METACLASS
CONSULTS THE CALLER. I corrected the mechanism I had been shown instead of the
rule underneath it, which is the same mistake as fixing the one site a review
names rather than sweeping for the rule -- and I have now made that mistake at
the level of a single expression.

The name is bound from `type.__dict__["__name__"]` directly, so the metaclass is
not consulted at all: the only description of a class this package accepts is the
one `type` keeps about it.

MY OWN PREVIOUS CASE WAS SUPERSEDED BY THE FIX and is strengthened rather than
deleted. It asserted the two descriptor shapes produced the "will not name
itself" fallback, which was true of the weaker mechanism. The property now is
that a metaclass descriptor NEITHER RUNS NOR CHANGES THE ANSWER, and the case
asserts that instead.

5. [P2] ONE RULE, TWO PUBLIC DOORS, ENFORCED AT ONE

`own` enforced the frozen depth and width; the canonical surface is public too
and enforced neither, so a document `own` refuses could still acquire bytes and a
digest by going straight to it.

That is the shape this repository has now caught me in five times: a rule stated
once and applied at one of N sites. The bounds live WITH THE CANONICALIZER now,
beside the recursion that has to respect them, and `pod` takes them from there --
one definition, both doors.

Depth is checked DURING the descent, not before it: a document deep enough to
matter is one whose depth cannot be measured without descending, and letting it
escape as a raw `RecursionError` would be a fault leaving a boundary that had a
refusal ready.
