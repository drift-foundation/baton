2. THE CODE I ADDED TO MAKE REFUSALS BETTER BECAME THE ESCAPE ROUTE

`describe()` did not exist before the previous round. I added it so a refusal
would not read "{} is not an options document" when a caller passed a Map. It
did two things a refusal must never do:

  JSON.stringify(value)          throws a raw TypeError on a BigInt
  getPrototypeOf(v).constructor  a property an untrusted prototype may define
                                 as a throwing getter, whose arbitrary Error
                                 then escapes

So at the exact moment the boundary had DECIDED to refuse, it ran the rejected
value's behaviour and lost the decision. That is the same shape as the two P1s
it was written alongside — an operand reaching a boundary that had not proved
it — with the aggravating detail that this operand had already been proved
unacceptable.

A REFUSAL MUST NEVER RUN THE VALUE IT IS REFUSING. Diagnostics are the one
place it is tempting, because a better message needs to know more about the
value, and knowing more means touching it.


3. THE CHANGE

`describe` is built from inert facts only: `typeof`, `Array.isArray`, and a
prototype comparison. Nothing is serialized and no property of the value or
its prototype is read. The prototype comparison is wrapped, because
translating an unavoidable reflection failure is cheaper than proving no host
or Proxy object can make `getPrototypeOf` throw.

The result is deliberately COARSE — "a bigint value", "an array", "a plain
object", "an object with a prototype of its own". A diagnostic that has to be
exactly right about an untrusted value is a diagnostic that has to touch it.

The member refusal uses the same helper instead of serializing the member.


4. MUTATIONS — FOUR PATTERNS, WITH TWO MEASUREMENTS

  U1 the rejected value is serialized again        3 cases fail
  U4 the member refusal serializes the member      3 cases fail
  U2 the prototype constructor is read again       masked by the wrapper
  U3 the reflection wrapper is removed             0  UNREACHABLE
  U2 + U3 together                                 3 cases fail

MEASURED, and both directions matter here. Removing the wrapper ALONE fails no
case, because `getPrototypeOf` does not throw on any ordinary JavaScript
value — it is defence against host and Proxy exotica and is not counted as a
guard. Re-adding the constructor read alone is caught BY that wrapper, which
translates the getter's Error. What the cases witness is the pair: read the
constructor and remove the wrapper, and three fail including the review's own.

That is worth stating plainly rather than reporting "4 witnessed": the guard
that actually carries the finding is not reading the constructor, and the
wrapper is a second line that no ordinary value reaches.
