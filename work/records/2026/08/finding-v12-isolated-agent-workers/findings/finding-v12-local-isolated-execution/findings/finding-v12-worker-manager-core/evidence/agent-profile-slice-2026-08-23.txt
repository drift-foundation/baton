0. THE SIGN-OFF'S CLARIFICATION, CLOSED IN CODE

The sign-off recorded that my wording — "writer and reader build the record in
one place" — was NOT LITERAL: the writer assembled its own operand object
beside `intakeRecord`, and the invariant was true of the signature FORMULA
rather than of the code.

The reviewer was right to record it rather than let the stronger claim stand,
and the honest response is to make the claim true rather than to weaken it.
`recordIntake` now builds its operands THROUGH `intakeRecord`, so adding a
column changes both sides or neither. A claim that is only true of the formula
is one an edit can quietly falsify.


1. WHAT THIS SLICE IS

  "The core certifies one exact profile by composing shape, document seal and
   policy checks IN THAT ORDER."

SHAPE FIRST, because every later rule reads members, and reading a member the
schema has not established is how the worker-control entry's round-2 bypass
happened. SEAL SECOND, because a policy decision about a document whose bytes
do not match its own digest is a decision about something nobody agreed to.
POLICY LAST, and only the rules the schema CANNOT state.

The frozen `agent-session-1.0.schema.json` is placed under
`src/worker_manager/schema/`, for the same reason the worker-control schema
is: a manager that read a schema out of another Work's dossier at run time
would be certifying against a document somebody else may edit.


2. THE FIXTURES ARE THE DESIGN MODEL'S OWN, AND THAT WAS MEASURED

The two profiles in the suite are copied verbatim from the ACP boundary's
`evidence/traces.json`, INCLUDING their `document_digest`. Those digests were
computed by that Work's model, and both RECOMPUTE EXACTLY under this manager's
RFC 8785 canonicalization — measured before the suite was written, not assumed.

So the seal these cases check is not a number this suite produced and then
agreed with. It is the design's, and two independently written boundaries
arrive at it. They are embedded rather than read, because `v12/` is
self-contained and a test reaching into another Work's dossier at run time
would be the same mistake the module refuses.


3. WHERE THE DECIDING GUARD ACTUALLY IS, MEASURED

The policy rule I added is that the two postures carry DIFFERENT pinned
policies — a profile in which they are equal is refused at certification
rather than at run time.

MEASURED: THE TWO FAMILIES ARE REFUSED BY DIFFERENT GUARDS. The codex branch
of the schema pins consent and execution to two different policy DEFINITIONS,
so equal policies are already unrepresentable and the SHAPE check answers
first. The ACP branch pins both to one definition with a free-form
`session_mode_id`, which the schema cannot compare — and that is exactly the
gap the policy rule exists to close.

My first version of that case asserted `policy.profile-uncertified` for BOTH
and failed on the codex half. The case now asserts what actually decides for
each family, and says why. A rule is needed where the schema cannot state it,
and claiming it decides where the schema already did would have been a claim
about my own code that the schema was quietly satisfying.
