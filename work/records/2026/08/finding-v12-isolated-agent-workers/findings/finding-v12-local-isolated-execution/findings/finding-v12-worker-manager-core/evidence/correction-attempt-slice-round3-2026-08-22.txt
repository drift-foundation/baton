2. THE THREE

[P1] A NO-CHANGE OBSERVATION DID NOT CONSUME ITS SOURCE IDENTITY. When no
prior row existed and today's axis already held the observed value, `observe`
returned success and wrote nothing — so the `(attempt, incarnation,
source_seq)` identity stayed reusable and a DIFFERENT observation committed
under it. The round-2 correction only bit when the first observation happened
to change state.

That made the identity's meaning depend on WHERE THE AXIS ALREADY WAS, which
is the same inversion the last round removed from the other direction. An
accepted sourced observation now consumes its identity whether or not it moved
an axis.

A manager-internal repeat stays inert, deliberately and narrowly: it mints a
fresh sequence at every call, so there is no identity for another caller to
reuse and a row would record nothing anyone could ask about. `observation_seq`
still advances only on an actual change.

[P1] `stopping` STILL DISABLED LATER MISMATCH CANCELLATION. The round-2
comment claimed cancellation was reachable from every nonterminal state, and
`stopping` was the one that was not — so a later inspection that found two
runtimes was refused by the very axis the safety response writes to.

THE FIX IS NOT `stopping -> cancel-requested`. That would move the axis
BACKWARDS to re-announce an intent the runtime is already carrying out. The
DECISION is what the caller acts on; the axis records where the runtime
actually is. `cancel` is idempotent for a stop already in flight — it returns
the cancellation decision and leaves `stopping` alone.

`destroyed` is deliberately NOT in that set and is named as such in the code.
It is terminal, and an adapter still listing runtimes for a destroyed attempt
is a contradiction rather than a cancellation this manager can carry out, so
it keeps refusing instead of being reported as a cancellation that never
happens.

[P2] CONTENTION WAS MATCHED IN APPLICATION PROSE. `isContention` concatenated
the structured fields with the free-form message and accepted any substring
`busy`, so a trigger raising `busy provider invariant` was handed a database
lock's portable meaning AND its retry policy. The message is
application-controlled; the result code is SQLite's own answer.

Measured rather than assumed, against this Node build:

  trigger abort   errcode 1811  errstr "constraint failed"
                  message "busy provider invariant"
  real lock       errcode 5     errstr "database is locked"

1811 is SQLITE_CONSTRAINT_TRIGGER — primary code 19 in the low byte, the
extended reason in the high bits. The classifier reads `errcode & 0xff` and
accepts only SQLITE_BUSY (5) and SQLITE_LOCKED (6). No prose is consulted at
all.
