## [P1] The matrix does not observe command execution

`runCase` returns only server-request method names. A Docker positive passes
when `approvals.length === 0`; a negative passes when it is nonzero. The
compatible operator run produced an empty array for all eight cases. That
proves only that no approval RPC reached the client. It does not distinguish a
policy-declined command from a model that never attempted it.

The same gap exists on the positive side. The matrix calls all four ruled
inspections PASS solely because no approval arrived; it does not assert that
the exact command ran, completed, or exited successfully. The operator's
negative finding therefore exposes a shared oracle defect, not merely a
different expected approval behavior.

The installed app-server's local protocol supplies a direct boundary.
`thread/read` with `includeTurns: true` returns each turn's
`commandExecution` items, including exact `command`, stable item id, source,
terminal status (`completed`, `failed`, or `declined`), output and exit code.
Approval requests carry the same thread id, turn id and item id, so an
approval-mediated denial can also be correlated exactly.

After each turn, read the exact turn returned by `turn/start` and require
exactly one agent command item matching the requested command. A ruled
inspection must be `completed` with exit code 0 and no approval. An unruled
command must either be `declined` directly or have a correlated approval
request which the client denied and a non-completed terminal item. Retain the
no-mutation probe as secondary evidence. Do not treat a bare `failed` item as
policy refusal: an attempted Docker command can fail on its own.

Add deterministic synthetic-turn tests for absent, wrong, duplicate,
completed, failed and declined command items, plus correlated and unrelated
approval requests. Then rerun the complete credential-bearing matrix against
the compatible candidate. Installation and managed-stack restart remain
blocked until it passes.
