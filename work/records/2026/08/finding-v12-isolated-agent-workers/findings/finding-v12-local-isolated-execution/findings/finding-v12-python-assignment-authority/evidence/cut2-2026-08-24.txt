2. THE ONE OPERAND CUT 2 DOES NOT TAKE, AND WHY

Every transition in the frozen host is wrapped in the journal's `replay` and
takes an `operation_id`. The journal is cut 3.

I did not add the operand. Accepting an `operation_id` here and doing nothing
with it would be a claim with no mechanism behind it: an exact retry would
re-perform the act while the caller believed it had been made
effectively-once. That is the same finding the cut-1 review gave me about
`requirements.lock` -- a lock nobody resolves from is a document about a build
rather than a property of one -- and the frozen host states the rule itself: a
caller who supplies an operand and has it ignored believes it chose something.

So the operand arrives in cut 3 WITH the journal that gives it meaning, and
these transitions run in a plain write transaction until then. Cut 3 therefore
changes these signatures, which is stated here rather than discovered there.

4. THREE GAPS I FOUND BY PROBING MY OWN CUT

The cut-1 review's most useful sentence was that my gate passing proves the
rules I thought of. So before handing this over I probed it the way a reviewer
would. All 36 assignment cases passed first time AND the probe found three
things:

  a) `install_gate` with a STALE `expect` on an UNCLAIMED Work was ACCEPTED.
     The frozen host takes the unclaimed branch first and never looks at
     `expect`, so a caller that passed an identity for a Work since released
     got success and believed it had performed a compare-and-swap. A supplied
     `expect` is now always compared. This is a deliberate divergence from the
     frozen host, on the frozen host's OWN stated rule about ignored operands.

  b) A CLOCK ANSWERING `banana` WROTE `banana` INTO A DURABLE `created_at`.
     `_now` validated that the configured clock answered nonempty TEXT, and the
     boundary says timestamps cross as VALIDATED UTC text. "Validated" has to
     mean the shape or it means nothing. The frozen `$defs.timestamp` grammar
     is enforced now, at the one place the clock's answer enters.

  c) A clock that RAISES leaks its exception, and that is left as it is,
     deliberately. The clock is a TRUSTED bootstrap collaborator; an act whose
     failure we cannot describe is not one we may record an outcome for. What
     is asserted instead is that the fault takes nothing with it -- the
     transaction rolls back, no row survives, and the store is still usable.
     Reported as a decision rather than fixed quietly, so it can be ruled
     otherwise.

  M11 and M21 measured zero because the inner compare-and-swap refuses them
  anyway -- with a WORSE message. "This Work has a live assignment; name it"

  and neither does "stale" when the real fact is a foreign authority. So the
  cases now assert the MESSAGE, and both mutations fail. A specific refusal
  that no case distinguishes from the generic one can be deleted without
  anything noticing, which is the same reasoning as keeping cut 1's empty-file
  check for its diagnosis -- except there I reported an equivalence and here I
  could remove it, so I did.

  M24 measured zero because MY MUTATION WAS NONSENSE: it added a key rather
  than caching anything, so it tested nothing. Written as a real cache it fails
  ten cases. That is the fifth instrument error I have recorded this week, and
  the only reason it was caught is that a zero on a freshness property looked
  wrong.

  M2 IS A GENUINE EQUIVALENCE TODAY and is reported as one. The cross-product
  check inside `_end_assignment` runs before the compare-and-swap so an
  impossible outcome refuses without touching state -- but every current caller
  already passes a coherent pair, and `install_gate` checks the same thing one
  frame up. It becomes load-bearing when cut 4 adds `close` and
  `advance_contract` as callers. Kept for the ordering property, not counted as
  a guard.
