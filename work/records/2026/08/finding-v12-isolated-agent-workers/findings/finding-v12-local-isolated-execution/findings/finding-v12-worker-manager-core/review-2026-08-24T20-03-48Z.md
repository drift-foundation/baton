## P1 — lexical pieces do not establish a parseable authority

`_whatwg_authority` finds a substring. `_AUTHORITY` admits a broad RFC character
alphabet. `_check_authority` then treats any decimal port as valid. None of
those operations proves that the frozen reader can parse the host and port.

Measured disagreements:

- `https:x:65536` and `artifact://x:65536` are accepted by Python; the frozen
  constructor refuses an out-of-range port.
- `https:[gg]`, `https:a]`, `https:a[` and `https:%ZZ` are accepted by Python;
  the frozen constructor refuses the invalid host syntax.
- `https:x:`, `https://x:` and `artifact://x:` are refused by Python as a
  nonnumeric port; the frozen constructor accepts them and removes the empty
  port marker.

This also regresses the ordinary-scheme path. Before 4db, accessing
`split.port` validated the range for `artifact://x:65536`; `_check_authority`
now bypasses that accessor and accepts it.

## Required decision before another correction

This is the third review cycle exposing a different edge of the same parser-
equivalence problem. Copying one more WHATWG production into local string code
will not establish the trust boundary. Pin one of these strategies before the
next implementation edit:

1. Use a vetted WHATWG parser in Python and keep the frozen constructor's
   accepted surface.
2. Define one smaller canonical URI grammar that both runtimes enforce, append
   an explicit supersession of the current frozen-host behavior, and drive it
   with shared vectors.

The second is the smaller trust surface, but it changes previously frozen
acceptance and therefore requires an explicit recorded ruling. Either strategy
must preserve the query, fragment, userinfo, malformed-authority, empty-host,
special-scheme shorthand and port regressions already retained.
