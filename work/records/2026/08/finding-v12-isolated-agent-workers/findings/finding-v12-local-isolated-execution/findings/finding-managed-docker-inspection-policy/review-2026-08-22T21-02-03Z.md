## P1 — matching identities do not prove a command approval was denied

The command-item selection closes the prior review: exact command, source,
cardinality, terminal status, and exit code are all checked against the exact
turn returned by `thread/read`.

Approval correlation stops one boundary too soon. `runCase` records every
server request and ignores the boolean returned by `respondError`.
`approvalsFor` checks only `threadId`, `turnId`, and `itemId`. The installed
schema defines file-change and permission approval requests with those same
three fields, beside the exact command method
`item/commandExecution/requestApproval`. A request from either other boundary
is therefore treated as command-policy evidence. Likewise, a command approval
that the client failed to answer is still described as denied.

This can falsely accept an unruled case whose command item merely failed — the
specific state the correction otherwise and correctly refuses. The live
matrix is the installation gate, so accepting evidence from a different
request type or an unsent response remains release-blocking.

The synthetic fixture also uses the non-schema spelling
`commandExecution/requestApproval`; method-blind correlation masks that error.

## Required correction

- Correlate only `item/commandExecution/requestApproval`.
- Record whether `respondError` successfully sent the denial.
- For a ruled positive, any correlated command approval request is failure.
- For an unruled approval path, require a successfully sent denial plus the
  already-required terminal non-completed command item.
- Keep direct `declined` valid without an approval and keep bare `failed`
  insufficient.
- Correct the synthetic method spelling and retain the two reviewer cases.
