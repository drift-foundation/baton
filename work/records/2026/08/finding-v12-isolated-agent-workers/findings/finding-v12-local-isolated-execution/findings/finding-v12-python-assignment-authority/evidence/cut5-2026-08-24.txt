1. THE TWO FACES, AND WHY THERE ARE TWO

  Authority   TRUSTED BOOTSTRAP.  It creates, opens, configures, reads and
              MINTS sessions.  A deployment holds exactly one, at start-up.
  Session     the RUNTIME boundary, bound at construction to ONE participant.
              It performs transitions and reads projections.  It holds no path,
              no store and no way back to the authority that made it, and it
              cannot name a participant other than its own.

The frozen Node host carried both on one object and was corrected for it: a
consumer claimed as `publisher`, granted `publisher` the close capability,
closed the live Work as that actor, and moved the canonical target with zero
proposals and zero receipts. A second reproduction simply passed a configured
closer's NAME, because the capability check compared a string the same caller
supplied.

A capability nobody can take away from you is not a capability, and an actor
identity the caller chooses is not an identity. So the actor on every receipt
and the claimant on every claim come from the BINDING, and supplying `actor` or
`participant` is REFUSED rather than dropped -- the frozen host silently dropped
a supplied `participant` on `claim`, so a caller could believe it had been
honoured.

AND THE CLAIM IS THE NARROW ONE, stated in the module rather than implied:
private attributes are not a sandbox. A trusted in-process module can read
`_core` or import `core` directly, and no amount of underscores changes that.
What is enforced is the SUPPORTED, EXPORTED surface and the deployment wiring;
untrusted workers are isolated by process and container, which is a mechanism
that enforces something.


2. THE SURFACE IS WRITTEN OUT, NOT DERIVED

16 transitions and 16 reads, in tables. Deriving them from `Core` would mean
that adding a method there silently widened the runtime boundary; a new
transition is unreachable from a session until somebody puts it in the table
deliberately.

Each transition's table entry also names its WHOLE key set, required and
optional. An operand supplied and ignored is one the caller believes it chose,
so an unknown key refuses by name rather than being dropped -- and the operands
are taken ONCE, as an owned copy, and the caller's object is never read again.
That is not hygiene: the frozen host read `operands.expect.participant` for its
binding check and handed the SAME object to the core, which read it again, so a
getter answering one participant twice and another afterwards passed the check
and then ended somebody else's live assignment. Validating one view and
executing another is the defect.

`close` is deliberately NOT binding-checked. Sec 7 authorizes it by the close
CAPABILITY, and its `expect` is a compare-and-swap operand rather than proof of
authorship: an approver closing a Work somebody else is executing is the
ordinary case, and the exact identity is what stops them closing blindly.

`Authority.close` was RENAMED to `dispose`. `close` is the Baton verb that
terminalizes a Work and cut 4 put exactly that verb on the session; one name
meaning both "release the file handle" and "end this Work with an outcome" is an
API that invites the wrong one, so the collision was removed rather than
documented.


3. THE PORTABLE CATALOG, COMPARED RATHER THAN CITED

The boundary calls the 64 W151 design cases and the 75 frozen Node reference
tests a MIGRATION CHECKLIST. A checklist nobody compares is a list, so
`tests/authority/test_catalog.py` reads the frozen sources: it asserts they are
PRESENT and readable, RE-MEASURES their size rather than quoting it, maps every
frozen file to a named Python counterpart, and checks that no obligation area
has vanished from the suite.

WHAT IT DOES NOT CLAIM, said in the file so a green run is not overread: no
name-for-name equality, because the port is by OBLIGATION and an equality
assertion would either be false or force a bad transliteration; and the area
check catches an area DISAPPEARING, not the quality of its coverage -- a word in
a test name is not evidence of a guard. Review and mutation runs measure that.

Two areas failed on the first run and BOTH were my needle, not the coverage:
`policy_generation` when the case reads "binds the generation it was granted
under", and `adopt` when the cases read "requires absence" and "recognized
store". So each area now lists alternatives, and a rename no longer fails for
the wrong reason. An empty alternative list is refused, because a vacuous pass
is the failure mode of every table-driven check.


4. THE SETTLEMENT-SIGNATURE QUESTION, NOW A NUMBER

Cut 3 raised it and the ruling was: no settlement-only cap, because settlement
must compare the exact canonical signature the authority itself produced and the
contract carries no system-wide text bound. That was reasoning. Cut 5 is where a
participant first supplies the operand, so it is where the measurement belongs:

  a legitimate activity idempotency key       100,000 characters, ACCEPTED
                                              and journalled
  the signature the authority derived         100,185 characters
  settling that signature                     answers `live`, as it must

A cap anywhere below 100,185 would refuse the settlement of an operation THIS
AUTHORITY COMMITTED -- worse than the unbounded operand, because the caller
could then neither submit under the identity nor settle it. The bound belongs on
durable text SYSTEM-WIDE, where those 100,000 characters entered in the first
place, which is exactly the broader operand ruling the decision points at.

The ruling is unchanged and it is now PINNED by a case rather than remembered by
a comment, and the collision rule is asserted at that size too: one character of
difference in a 100,185-character signature is still different operands, so
length is not what makes the comparison work.

The refusal diagnostics are separately safe: `name_of` bounds a shown string at
60 characters, so a 100,000-character operand does not become a
100,000-character message. That is the W1593 shape and it does not apply here.

T8 was first written as `operands.get("who", self._participant)` and measured
ZERO. That mutation did not express the defect: no case supplies a `who` key,
and one that did would be refused as an unknown operand. Rewritten as "claim
uses a name other than the binding" it fails 14 cases. THE ZERO WAS MY
INSTRUMENT, which is the failure cut 3 taught me to check for by hand.

T9 IS GENUINELY EQUIVALENT AND STAYS, reported as defence in depth rather than
as coverage. With `operands = given` the exact-`dict` check still refuses a
subclass at the top level, and a nested behaviour-bearing container is refused
by the core's own `own` a moment later. The session's `own` would only become
load-bearing against a container that CHANGES between the binding read and the
core's read, and no such container can enter, because changing requires an
overridden `__getitem__` and that is a subclass. So the guard is unobservable
BECAUSE the type rules hold -- which is the argument for keeping it, since it is
the guard that stays correct if a type rule is ever relaxed.
