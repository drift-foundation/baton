## Finding

### [P1] Refuse an absent state root on the deletion path

`v12/src/placement.mjs:114-120` rejects a non-`owned` state only when
`existsSync(root)` is true. With `forDeletion: true`, an absent root therefore
returns `{ state: "fresh" }` successfully. Direct, non-mutating reproduction:

```text
assertOwnedStateRoot("/tmp/v12-review-absent-root-8f61c2",
                     { forDeletion: true })
=> { root: "/tmp/v12-review-absent-root-8f61c2", state: "fresh" }
```

The path was absent before and after the call. `placement.mjs state` is the
only value source consumed by `just state-clean`, whose next operations are
`chmod -R` and `rm -rf` (`v12/justfile:50-52`). Returning an absent path is not
a harmless ownership result: another process can create an unrelated directory
at that path after validation and before those operations, and cleanup will act
on it without ever observing a marker. It also directly contradicts the
round-two ruling and the code's own comment that cleanup *requires* `owned`.

Require `state === "owned"` whenever `forDeletion` is true, regardless of
current existence, and emit no path for `fresh`. Setup must continue to accept
`fresh` so it can establish ownership. Add deterministic direct and CLI
regressions using a guaranteed-absent root; both deletion entry points must
refuse without creating anything or printing a removable path. The existing
owned-root positive and unmarked-existing-root negative cases must remain.
