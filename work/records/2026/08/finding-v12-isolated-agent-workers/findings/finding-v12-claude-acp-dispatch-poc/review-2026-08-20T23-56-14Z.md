## Findings

### P1 — a successful handoff can retain the operator credential while reporting `returned`

`Manager.attempt()` passes the Job to review before `dispatch()` calls
`reap()`. If the worker container is proven gone but the consent container is
not, `reap()` correctly retains the credential because both containers mount
it. It nevertheless returns `{gone: true}` based only on the worker, and the
success path leaves the attempt status as `returned`.

The CLI output omits `credentialsDisposed` and `retainedSecret`, accepts
`returned` as success, and exits zero. The Work has already reached review, so
there is no compensation record either. The only indication is a
`credential.retained` line buried in the attempt trace. This contradicts the
round-4 claim that an undisposed credential is named as a recoverable terminal
condition; on this path it looks like a clean return.

Make cleanup part of the success boundary before the authoritative handoff, or
give a retained credential a typed non-success result that is surfaced to the
operator and cannot be mistaken for `returned`. Add the missing regression in
which the execution container is gone, the consent container's absence cannot
be proved, the full credential remains, and the command must not report clean
success.

### P1 — compensation `release` still has no effectively-once identity or reconciliation

Round 3 fixed ambiguous `claim` and `pass`, but the compensation mutation at
`src/manager.mjs:219` still invokes `release` once, without an `op-id`. If the
authority commits the release and its result is lost, `compensate()` catches
the transport error and reports `stranded` even though the canonical Handler
is already gone and the Job is available again. This is the same ambiguity the
claim/pass correction was meant to eliminate, on the path whose sole purpose
is to report whether a claim remains held.

Give `release` a stable per-attempt operation identity and reconcile an
ambiguous result through the public projection before choosing `compensated`
or `stranded`. Add a commit-then-lose-result regression. The recap `say` is
also a manager mutation with no operation identity; a committed message whose
result is lost currently releases the Job and may be duplicated by a later
attempt. Make it effectively-once as well, or explicitly move it outside the
load-bearing return transaction with a ruled failure behavior.

### P2 — the runtime capability fence does not include the live Baton source checkout

The W76 finding forbids runtime imports, symlinks, or mounts back into
`/home/sl/src/baton`. `Manager.forbiddenPaths()` includes the installed Baton
binary, disposable config, its directory, `/home/sl/opt/baton`, and one
versioned coordination home, but not `/home/sl/src/baton` or the live
`/home/sl/baton-v11` alias as such.

The proof's after-the-fact `docker inspect` assertion checks the source
checkout, but `assertNoBatonCapability()` would accept a configuration whose
adapter or another mount resolves into that checkout. A safety boundary must
refuse before launch, not depend on the current sample configuration being
honest and detect the mistake after the worker ran. Add the current source
checkout and live coordination alias to the configured forbidden roots and
cover direct and symlinked mounts.
