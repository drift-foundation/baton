## Findings

### 1. P1 — a failed quiescence check is converted into evidence and execution continues

`src/manager.mjs:319-323` and `src/manager.mjs:367-374` catch every
`awaitQuiescence` error and turn it into `{error: ...}`. The pre-claim path
then validates the intent and may claim Work; the execution path returns to
`collect`, which reads and freezes the writable output. In either case the
container may still be running. Recording a failed fence is not the same as
establishing one.

This contradicts the load-bearing ordering claim that the pre-claim process
is quiescent before claim and the execution worker is stopped before output is
read. Fail closed: a quiescence error, a still-running inspection, or an
unacceptable termination must prevent claim/collection/return. Add focused
tests in which inspection or stop fails and prove that no downstream boundary
is crossed.

### 2. P1 — typed input can escape its bound record and be dereferenced into the worker snapshot

`src/manager.mjs:276-284` resolves `input.source` without checking that the
result remains inside the bound record. `src/manager.mjs:117-119` then copies
with `dereference: true`. A `job.in.json` may therefore name `../../...`, an
absolute path, or a directory symlink that points outside the record. The
materialized manifest sees ordinary files after dereference and accepts them.

A local reproduction using a record-local `input` symlink to an outside
directory produced a valid manifest containing the outside `secret.txt`.
Validate the lexical and real path against the record boundary, reject a
symlink at the source root and anywhere below it, and test traversal, absolute
paths, a root-directory symlink, and nested symlinks. The manager must never
turn an untrusted descriptor into arbitrary host-file disclosure.

### 3. P1 — the declared `job.out` contract is parsed but not bound to the assignment or output

`src/manager.mjs:391-397` validates only the shallow envelope shape and then
ignores `declared.work` and `declared.results`. Collection proceeds against the
manager's hard-coded `/out/index.json`. The following declaration is accepted:

```json
{"envelope":"job.out","version":"0-spike","work":"W999","results":[],"summary":"nothing"}
```

If the expected file happens to exist, that mismatched declaration does not
stop collection. Require exact Work, result count, name, type and path matches
against the assignment and offer before reading output. Add negative tests for
wrong Work, empty/duplicate/extra results, and wrong name/type/path.

The independent checker has the same exactness gap at
`src/fixture_check.mjs:50-80`: it rejects extra fields inside entries but not
extra top-level fields, despite the task requiring exactly
`index_version` and `entries`. A one-line reproduction returns no problems for
`{index_version:"0-spike", entries:[], undeclared:true}`. Close that gap too.

### 4. P1 — “read-only pre-claim” and “no execution or publication capability” are not proven

The pre-claim container has a writable credential bind
(`src/runtime.mjs:96-101`), writable tmpfs, Docker's writable container layer,
bridge networking, and the same `bypassPermissions` ACP posture as the
execution worker. `assertNoWritableMount` excludes the credential mount and
does not inspect tmpfs, the root filesystem, tools, or network. It proves only
that no separate result bind is present.

The strong statements in the dossier that the turn is physically read-only
and cannot execute or publish are therefore false. Either enforce a genuinely
non-executing consent surface (including tool and egress constraints) or
revise the W2/W76 contract and recommendation to the narrower property that
was actually established: the pre-claim agent has no Baton capability and no
accepted result/assignment can be produced before the manager validates the
token and commits the claim. Do not preserve both statements as though they
were equivalent.

### 5. P2 — any post-claim failure strands the canonical Handler

After `src/manager.mjs:219-226` commits the claim, failures in worker startup,
ACP execution, fencing, result validation, discussion publication or pass are
caught only by `dispatch`, which records `attempt.error` and removes
containers. It performs no authoritative release, block, or failure handoff.
The Job remains `active` under `poc.claude` even though the manager reports the
attempt ended.

The narrow acceptance boundary requires only expired/replayed pre-claim
negatives, so this need not become a full production recovery subsystem in the
spike. It must, however, be made explicit and safe: either add a bounded
manager compensation path with tests, or record it as an additional required
W2 recovery contract and make the prototype fail visibly without claiming a
clean end-to-end lifecycle after such a fault.
