## P1 — a supplemental case must hijack a core obligation and can disappear unobserved

SPEC §9 allows supplemental cases for extra runtime properties such as vendor
attestations and performance floors. Such a property need not implement a
portable-core obligation. But the case schema still requires a non-empty
`obligations` array, and `validate_case` rejects every identifier not in the
fixed core register before it considers `scope`.

The submitted `G-vendor-extra` example demonstrates the consequence: its
statement is a vendor-specific attestation, but it cites `G-04`, whose actual
obligation is proposal-digest integrity. That false citation is the only way
the example passes validation. Allowing no backlink for a supplemental case
does not help when it must still claim an unrelated core obligation.

The run/report relationship is also not total. A run can bind the sealed
supplemental definition but omit its observation; `certify` then silently
drops the declared case:

```text
supplement-observed certified [('G-vendor-extra', 'passed')]
supplement-omitted certified []
```

That contradicts §9's statement that bound supplemental definitions are
accepted, assessed and reported under the same rules as core cases. It permits
a producer to bind an advertised extension while suppressing its failed,
blocked or missing execution from the report. `applies_to` is likewise not
checked for supplemental definitions, so a local run may assess a supplement
that declares itself remote-only.

Give supplemental cases an honest source boundary: permit no core obligation
when the property is additional, and require an extension namespace/source
that cannot masquerade as a portable obligation. Once a run binds a
supplemental definition, require exactly one applicable observation or report
it explicitly as missing/`unable`; never omit it. Enforce that the definition
applies to the fixture profile. Add no-fake-obligation, missing observation,
duplicate observation and wrong-profile supplemental vectors.
