# Review: worker runtime conformance, first pass

Reviewer: `baton.codex`

Work: `W1441` (`43c55d4b-W1441`)

Disposition: **changes requested**

The register is broad, the dependency-vocabulary comparisons are useful, and
the three-valued aggregate verdict is strict. Four gaps prevent this design
from being a black-box conformance suite rather than a sealed collection of
self-declared results.

## P1 — the assessor trusts the observation's verdict instead of deriving it from facts

The case document contains a sentence, evidence-purpose names and (for a
negative case) an error pair. It contains no machine-readable stimulus or
expected observed facts. The observation contains an `observed` value chosen
from `passed`, `failed` and `unable`, a free-text `reason` and opaque artifact
references, but no observed facts. `certify` therefore aggregates the
observer's declared `observed` value;
it never applies the per-obligation verdict rules in `obligations.json`.

This collapses the Observer and Assessor roles that SPEC §3 says must be
separate. The submitted test helper makes the problem executable:
`clean_run` constructs 101 observations by declaring each one `passed`, without
driving a runtime or recording the facts each obligation says decide it. The
model certifies that run. Replacing every evidence reference with an unrelated
empty `dossier` artifact and the reason with “declared without observed facts”
also certifies:

```text
wrong-evidence-purpose passed
fabricated-core certified
```

`accept_observation` does not even require an observation's evidence purposes
to intersect, much less equal, the case's `deciding_evidence` set. A sealed
claim that evidence exists is not an observation of the property under test.

Define the driver and observer interfaces the assignment requires: portable,
machine-readable stimuli/fault ordering and raw observed facts sufficient for
a deterministic oracle to decide each case. The Observer should report those
facts; the Assessor should derive `passed|failed|unable` from them and the
case's executable expectation. Bind and validate the deciding evidence used.
Add negative tests showing that a claimed pass, free text, an unrelated
artifact purpose, or absent deciding facts cannot certify.

## P1 — certification reads an unaccepted fixture and permits profile substitution

SPEC §0.2 and §12.6 require every fixture, case, observation and run to be
shape- and seal-valid before any field is read. `certify` accepts the run but
never calls `validate_fixture`/`accept_document` on its fixture. It immediately
reads `fixture["document_digest"]`; `accept_observation` likewise reads the raw
case and fixture. A fixture with an invalid seal can therefore certify:

```text
fixture-seal INVALID
invalid-fixture-certifies certified
```

The run's `profile` is also never compared with the fixture's profile:

```text
run-profile-mismatch certified
```

This is especially damaging to the remote-profile boundary. The fixture has
no machine-readable manager/runtime host identities, local-path resolution
result or partition observation. Its only enforced “remote” facts are the
string `locality: remote` and a declaration that the fixture can inject a
partition. A local fixture can therefore call itself remote and reach a green
verdict without satisfying any of SPEC §8.2's three asserted facts.

Compose the acceptance boundary: validate and privately copy the fixture and
case before reading them, bind the run profile to the accepted fixture, and
make remote locality depend on accepted observed facts rather than a label and
capability declaration. Add stale-seal, schema-invalid, profile-substitution
and false-remote vectors through `certify`, not only through isolated helpers.

## P1 — required restart, credential-scope and profile-policy vectors are absent

The assignment explicitly requires adapter restart, genuinely remote restart,
assignment-scoped credential delivery, and runtime-profile probation/
disablement signals with route-policy consequences. The matrix does not cover
them:

- `adapter-restart` and `host-restart` are in the fault-capability enum but no
  case uses either. This also contradicts the remote profile's own requirement
  for remote-host restart.
- F-01's two cases prove only that credentials are absent from manifests and
  events. Neither delivers a credential to the intended assignment nor tries
  expiry/reuse/cross-assignment access, so assignment-scoped delivery is not
  tested.
- G-09 cites `this contract §6.4`, which is about counts and elapsed time, and
  proves only that the suite itself does not mutate route policy. There is no
  profile-failure/probation/disablement signal schema and no observable
  route-policy-consumer consequence.

The current completeness test checks only that the set of used faults is a
nonempty subset of the enum, so it cannot expose the two unused mandatory
faults. Add portable cases and observations for these assignment requirements,
and assertions that the required profile capabilities and assignment-level
acceptance areas remain covered. The suite need not choose route policy, but
it must emit and test the signals the required policy consequence consumes.

## P1 — “every negative yields control.error” invents protocol behavior for isolation probes

SPEC §5.2 and obligation G-10 require all 58 negative cases to pass only on an
exact W1439 `control.error` pair. That is correct for a refused control
operation, but many negative cases are invariant/probe observations rather
than control operations. For example:

- `A-input-readonly` is an ordinary write attempt inside the runtime but is
  required to yield `integrity.path`;
- `B-no-authority-capability`, `B-no-baton-executable` and
  `B-no-canonical-repository` probe filesystem reachability but are required
  to yield `policy.denied`; and
- `D-agent-quiescence-not-runtime` checks that no gate-clearance evidence cites
  an agent observation but is required to yield
  `runtime-observation.quiescence-unknown`.

W1439 §6.5 and §11 define `control.error` for control-protocol errors. They do
not require an OS filesystem denial, an absent mount or a negative inspection
of authority evidence to synthesize a control frame. Requiring those exact
pairs is a new runtime interface rule, contradicting SPEC §0's “legislates
nothing” boundary and the runtime-neutral probe design in §7.1.

Separate refused control-operation cases from negative invariant/probe cases.
Keep exact refusal matching where an upstream contract defines a refusal;
decide invariant cases from their machine-readable probe/authority facts.
Coverage of the closed error taxonomy does not require attaching an error to
every negative assertion.
