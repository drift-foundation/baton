## P1 — command and file approval replies still omit the response object

`SPEC.md` §10.5, `codex_deny_approval` and
`test_codex_denials_are_typed_per_family_and_never_grant` all treat the result
for `item/commandExecution/requestApproval` and
`item/fileChange/requestApproval` as the bare string `"decline"` (or
`"cancel"` during cancellation).

That is the decision MEMBER, not the complete response. The App Server response
schemas require an object with a `decision` member:

```json
{"decision": "decline"}
{"decision": "cancel"}
```

The current provider interface can reproduce the mismatch without a running
server:

```text
codex app-server generate-json-schema --out <temporary-directory>
command-denial 'decline' provider-schema-valid False
```

The generated `CommandExecutionRequestApprovalResponse.json` and
`FileChangeRequestApprovalResponse.json` both require `decision`. This also
matches the response-object presentation in the official App Server
documentation. The permissions response (`{"permissions": {}, "scope":
"turn"}`) and MCP elicitation response (`{"action": "decline", "content":
null}`) are now shaped correctly.

Return the COMPLETE response object for all four families, including the race
forms, and validate each result against the provider response schema captured
by the certified interface binding. A self-authored equality assertion is not
provider-shape conformance.

## P1 — the event ledger still does not consume or return the sealed schema document

The correction record says `EventLedger` consumes the sealed schema shape and
returns a sealed document. Its implementation does neither:

- the trace runner constructs an event with no `document_digest` and passes it
  directly to `record`;
- `record` silently removes any supplied `document_digest` without verifying
  it, so an already-sealed event whose content was changed without resealing is
  accepted and freshly sealed; and
- the return value adds `replayed` after sealing. That extra member is forbidden
  by `normalizedEvent.additionalProperties: false` and invalidates the digest.

Focused output against the submitted model:

```text
unsealed-input-schema-valid False
record-return-schema-valid False
record-return-digest-valid False
persisted-schema-valid True
tampered-sealed-input-accepted True
```

`evidence/test_acp_boundary_model.py:207-227` therefore still feeds a different
object contract into the model than the schema accepts. The separate
`persisted` accessor happens to contain a valid document, but that does not make
the claimed input/output boundary true.

Choose one explicit boundary and enforce it. For the boundary currently stated
in §6.4 and in the correction record: seal and schema-validate the event before
feeding that SAME object to the ledger; verify its digest before sequence or
duplicate processing; return the unchanged sealed document; and report replay
or drop status out of band rather than by mutating the document. Add direct
vectors for unsealed input, a valid-kind tamper with the old digest, and schema
plus digest validation of every normal and replay return.

## P1 — profile certification does not enforce the policy the profile records

The schema conditions only select ACP-shaped versus Codex-shaped policy
objects. They do not bind either Codex policy to its posture, and
`validate_postures` checks only that the two policies differ plus the two
workspace booleans. Swapping the complete consent and execution policy objects
therefore remains valid:

```text
swapped-codex-postures-schema True
swapped-codex-postures-semantic ACCEPTED
```

That certifies consent with `workspaceWrite` / workspace cwd and execution with
`readOnly` / scratch cwd, the inverse of normative §10.2. The request builders
also accept an arbitrary caller-supplied path without checking it against the
pinned `cwd_role`.

The same profile can claim an arbitrary `required_agent_methods` list. A sealed
ACP profile containing only `["session/new"]` is schema-valid, and
`negotiate_acp` accepts it because it checks a separate hard-coded constant and
never checks that the sealed declaration equals the contract:

```text
missing-profile-required-methods-schema True
missing-profile-required-methods-negotiate ACCEPTED
```

`refused_agent_methods` has the same open shape. A durable certified profile
must not be able to disagree with the policy actually enforced. Add one profile
certification validator used by every trace and negative vector. It must at
least enforce the exact mandatory session capabilities and method sets, the
consent/execution workspace/output invariants, the provider-specific posture
policy (including cwd role and sandbox), and the profile-digest relationship
when validating a session record. Either make the stored method lists exact or
remove them in favor of the version-owned constants; do not preserve two live
sources of truth.

## P2 — four live passages still state the superseded cardinality or consent cwd

`SPEC.md` §3.2 correctly says the old “one fresh session per runtime attempt”
wording is superseded, but live normative text still says:

- §0.2: a session lifetime is one per `(runtime_attempt_id, session_epoch)`;
- §2.4: `session.fresh` is “a new session per runtime attempt”;
- §8.2: the relay journal is for `(runtime_attempt_id, session_epoch)`; and
- §3.2: every `session/new` uses the materialized workspace for the exact
  assignment, although a consent session has neither an assignment nor a
  workspace.

The first three must include `posture`. The last must state the posture-specific
cwd: the empty read-only scratch root for consent and the exact materialized
private workspace for execution. Leaving superseded text live makes the
chronological correction ambiguous to an implementer reading the normative
sections rather than the finding history.
