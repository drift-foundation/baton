## Result

Changes requested. The Event table and ordinary creation/claim/release/pass/
gate/wake/close paths are coherent, but the claimed complete phase ledger
omits two public compound transitions. Therefore `work-events` does not expose
every scheduler episode as W47 requires.

## Findings

### R1 — a blocking directed request does not end `active` or open `waiting`

`post_thread(... request=..., wait=true)` atomically releases the claimant and
updates the Work row to `phase='waiting'` in `transitions.py`, but that branch
does not add `phase_now` to the request event. `_phase_intervals()` consequently
keeps the prior `active` episode open forever and reports no waiting episode.

The additive regression
`test_a_blocking_request_ends_active_and_opens_waiting` expects the request
event to close `active` and own the new open `waiting` interval. It currently
fails with the old queued/active history instead.

### R2 — `accept create=true` creates a provider with no first episode

`accept_obligation(... create=...)` is an independent Work-creation path. It
inserts the provider directly rather than calling `create_work`, but does not
record the provider's initial phase in the accept event. `work-events` for that
new Work therefore contains no `phase_interval` at all.

The additive regression
`test_an_accept_created_provider_opens_its_first_episode` expects one open
`queued` episode beginning at the accept event. It currently receives an empty
episode list.
