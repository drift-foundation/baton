## [P1] Failed revalidation is called retained but is delivered as live

`EventBridge.#revalidate` catches a failed Baton invocation or JSON parse at
`tools/codex-event-bridge/src/event_bridge.mjs:705-710`. Its diagnostic says
“the event is retained,” but it returns `live`. A response with no actionable
array takes the same path at lines 712-715. In `#drain`, `live` is the verdict
that immediately opens and starts the model turn; the event is then dequeued.

Before the claim-slot correction, not dropping an uncertain event was treated
as sufficient and the W1224 tests named this delivery “retention.” Under the
confirmed one-claim boundary, the immediate read has two jobs: prove the exact
episode still exists and prove an unclaimed Work is not waiting behind another
claim. A read that failed proves neither. Starting anyway can spend a model
turn against an occupied slot, while ACP's equivalent failed read throws into
its delivery boundary and retries without prompting.

The additive cross-boundary regression
`an unreadable claim-slot projection is retained without spending a turn` at
`tools/codex-event-bridge/test/claim_slot.test.mjs:277` injects a failed
canonical read. Current behavior starts one turn and drains the queue; the case
requires zero turns and queue depth one.

Add a distinct uncertainty/retain verdict rather than mapping the read to
either `over` or `live`. The drain must leave the exact event and its v11
in-flight identity held, schedule a bounded re-read, and spend no turn until a
successful canonical envelope answers the claim-slot question. Apply the same
rule to invalid JSON and malformed envelopes, validating any fields used to
schedule. Ordinary non-readiness events remain outside this read.

The existing stale-episode cases
`a failed revalidation retains the event rather than dropping it` and
`a reply with no actionable set retains the event` currently assert that a
turn starts. They pin the pre-claim-slot behavior and must be revised, not kept
as contradictory certification. This review gives explicit case-specific
confirmation to change those expectations while preserving their actual
retention requirement.
