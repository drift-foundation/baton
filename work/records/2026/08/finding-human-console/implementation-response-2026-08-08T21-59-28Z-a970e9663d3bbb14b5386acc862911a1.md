# Replies are indented children now

Implemented as ruled. A reply renders as an indented child of the message it
answers, marked `↪` (U+21AA, with `->` where the terminal cannot encode it),
two cells of indent per level. Newest-first ordering and the existing badges
are preserved; nothing about authority order changed.

    >[R] 08-08 21:54 baton.reviewer     R7 review: four corrections
     [Q] 08-08 21:54 to baton.reviewer    ↪ R7 review: four corrections
         08-08 21:54 baton.reviewer     Older thread: protocol-10 inventory

## Two orders, and the choice mattered

Your brief said "preserve newest-first" but not where a THREAD sits, and the
two readings behave very differently:

- **Threads sort newest-first by their most recent member**, which is what I
  implemented. Answering an old message brings the conversation back to the
  top.
- By the ROOT's own timestamp instead, a reply you had just sent would appear
  near the bottom of the list — which is the "I sent it and it vanished"
  failure that unified MESSAGES was built to fix, wearing a new hat.

Within a thread it flips to oldest-first under the parent, because that is the
order the conversation happened in and an indented child that precedes its
parent is not a child.

If you meant root ordering instead, say so and it is a one-line change with
its pin; I have recorded the reasoning in FINDING and PLAN so the decision is
visible rather than buried in the sort key.

## Two boundaries decided rather than left to the code

- **`responds_to` is followed only within the VISIBLE set.** A reply whose
  parent has been collected is a root — indenting it under nothing would show
  a relationship that is not on the screen. Pinned, and verified by removing
  the membership test.
- **The indent lives in the SUBJECT column and nowhere else.** Indenting the
  whole row would move the date and party columns on reply rows alone, and
  every list row lining up is the alignment property pinned in R3. The
  regression asserts the marker is present and indented AND that the date
  column has not moved.

A self-referencing row is treated as a root rather than walked. The schema
should never produce one, but a loop would hang the walk instead of failing
visibly.

## Core change, declared

`list_messages` now reports `responds_to` — the schema's own column, reported
rather than derived. Additive, read-only, no query cost per row, and within
"richer stable inbox rows". Its docstring says so. Nothing else in the core
moved, and parity is unaffected because `list_messages` is a core addition the
oracle does not have.

## Presentation only, pinned as such

The parent still turns `[R]`, the reply is still an outbound `[Q]` with
direction `out`, actionability is unchanged, and `claim`/`wait` still take the
oldest pending message.

## Deliberate-break checks

| Break | What fails |
|---|---|
| flat newest-first list again | three threading pins |
| threads sorted by their root instead of their newest member | the answered-thread-returns-to-the-top pin |
| the indent kept, the `↪` marker dropped | the marker pin |
| `responds_to` followed outside the visible set | the orphaned-reply pin |
