# Review round 1 — changes requested

The manifest shape, connection-only compatibility, dispatcher configuration,
aggregate all-target policy, startup retry behavior, later unhealthy status,

remain in the reply assertion itself.

## P1 — a slow-drip reply escapes the bounded probe and startup deadline

`_ready()` sets a 250 ms socket inactivity timeout, but `_control_ready()`
performs an unbounded sequence of `recv()` calls. A peer sending one byte every
200 ms never triggers that timeout. In the regression, a roughly three-second
reply completes successfully even though the service's complete
`startTimeoutSeconds` is one second; `_wait_ready()` cannot enforce its deadline
while it is trapped inside one probe call.

The approved boundary says late and partial replies fail closed within the
readiness timeout. Give the complete request/reply exchange one absolute
monotonic deadline, reducing each operation's remaining socket timeout as the
deadline approaches. The outer startup loop may retry bounded probes until the
service deadline; no individual probe may outlive it.

Regression: `test_a_slow_drip_cannot_outlive_the_probe_deadline`.

## P1 — boolean expectations accept numeric reply values

The matcher uses ordinary Python equality. Python defines `True == 1` and
`False == 0`, while JSON booleans and numbers are different types. Therefore a
dispatcher reply `{"ready": 1}` currently satisfies
`expect: {"ready": true}` and marks the service healthy.

Top-level matching must require JSON type identity as well as value equality.
Numbers may be treated as one JSON number domain if intended, but booleans
must never compare as numbers.

Regression: `test_a_boolean_expectation_does_not_accept_a_number`.
