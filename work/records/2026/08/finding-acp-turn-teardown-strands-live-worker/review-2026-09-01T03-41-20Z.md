## Decision support

**Proposed:** accept the implementer's W11910 refinement after an authorized
ruling is pinned. A claimed Work whose recovery prompt failed must remain
eligible for redelivery; a claimed Work whose prompt returned was presented
and must not be repeated merely because the claim still exists. In both cases
W55705 still requires `failed`, not `idle`, plus the durable incident. This is
the split already established by W11910's accepted failed/succeeded recovery
tests. It narrows “retain later readiness” to `secondary`, `held`, unreadable,
and drifted claim-slot states; it does not authorize dropping an unspent wake.

at M57668. This review does not turn optional ownership into a startup refusal.

## Findings

### [P1] A newly stranded slot does not stop the rest of the same envelope

The outer fence check runs only once before `for (const action of fresh)`
(`tools/acp-baton-bridge/src/acp_baton_bridge.mjs:315-338`). When settlement of
one action returns `stranded`, both the returned-prompt and failed-prompt paths
set `failed = true` and `continue` the **inner action loop**
(`acp_baton_bridge.mjs:421-427`, `518-525`). Later fresh actions in that same
envelope are still revalidated and may start another ACP turn before the outer
loop reaches the fence check.

This is fail-open for the important unreadable/drift case: the settlement read
can fail, creating a stranded fence, while the next action's independent
pre-turn read succeeds. The bridge then delivers after it has just concluded
that the participant's claim slot cannot be proved safe. Break out of the
action loop immediately on `stranded` and retain every remaining action; add a
multi-action case where the first settlement read is unreadable and the second
action is otherwise live.

### [P1] Recoverable retries re-mint the fence and lose its authority/incident fence

For an existing `claimed` fence, `AcpSettlement.settle` saves only the boolean
`incidentFiled`, sets `this.fence = null`, recursively performs the canonical
read, publishes/files against a newly minted fence, and only then copies the
old boolean into memory (`tools/acp-baton-bridge/src/acp_settlement.mjs:247-259`).
That ordering has three concrete failures:

- `#read` can no longer compare the new answer with the old authority, so a
  retry silently accepts authority drift.
- A previously acknowledged incident is filed again before the old boolean is
  restored.
- If the retry is now a successor fence and its incident publication fails,
  the old fence's `true` acknowledgement is copied onto the successor in
  memory, suppressing the retry for the wrong Work/episode.

**Observed probe:** two exact reads against authorities A then B returned
`recoverable` both times, filed two incidents, and saved B as the new authority.
The probe is `/tmp/w55705-review-probes.mjs`. Preserve a stable fence identity
through the read; compare authority before replacement; serialize incident
publication; and apply a late acknowledgement only when authority, Work,
episode and action key still identify the same fence. A genuine successor must
mint its own unfiled incident state.

The same identity rule is needed during periodic reconciliation. A fence for
W1/episode 11 followed by a canonical secondary W2/episode 22 currently stays
filed against W1 and emits no incident for W2 (`acp_settlement.mjs:424-440`).
The probe confirmed the saved record remained W1 with `incidentFiled: true`.

### [P1] A restored recoverable marker can deliver before authority drift is checked

`restore()` loads the recorded authority, but `fenced()` deliberately returns
false for correlation `claimed` (`acp_settlement.mjs:164-166`). The bridge
therefore skips `reconcile()` at startup and can process the first fresh action
from the newly configured authority before any settlement read compares it to
the marker. The later retry path then clears the fence before its comparison,
as above. A dispatcher restart pointed at another authority can therefore
deliver despite the record's explicit fail-closed authority-UUID boundary.

Restoration needs a pre-delivery canonical comparison even when the eventual
verdict is `recoverable`; only the matching exact claim may enter the W11910
redelivery path. Missing or drifted authority stays fenced. Add restart cases
for a matching authority, changed authority, missing/malformed canonical read,
and the same Work under a newer episode.

### [P1] Marker persistence failure is recorded and then ignored

The initial synchronous `store.save()` result is assigned to
`this.fence.durable`, but neither verdict nor caller behavior depends on it
(`acp_settlement.mjs:295-300`). The incident acknowledgement save is also
unchecked (`acp_settlement.mjs:416-418`). If the state directory is unwritable,
the current process looks fenced but a bridge restart finds no marker and
delivers into a still-occupied slot. If only the acknowledgement save fails, a
restart files a duplicate incident.

The reusable store returns a boolean specifically so callers distinguish an
in-process fence from a restart-durable one. Fail closed on an uncommitted
marker before any ordinary delivery can continue, and preserve the distinction
in runtime/operator evidence. Do not report an incident acknowledgement
durable until the matching marker update commits. Cover initial-save,
acknowledgement-save and clear failures across restart.
