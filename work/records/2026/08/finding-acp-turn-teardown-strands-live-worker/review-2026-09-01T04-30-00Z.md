## Findings

### [P1] A recoverable fence detects authority drift only after spending the next turn

`AcpSettlement.fenced()` returns false for a durable, verified `claimed`
fence. `runBridge` therefore skips `reconcile()` and proceeds through
revalidation and `promptText`; only the post-prompt `settle()` compares the
new canonical answer with the fence's recorded authority
(`tools/acp-baton-bridge/src/acp_baton_bridge.mjs`, outer fence check and
returned-prompt settlement; `src/acp_settlement.mjs`, `fenced` and `#read`).
The read eventually reports drift and strands the lane, but one action from
the new authority has already reached the model.

**Observed reproduction.** `/tmp/w55705-return-review-probes.mjs` ran one
bridge over a claimed recovery action from authority A followed by the same
action from authority B. It recorded two prompts, then retained A in the fence
and recorded B as drift. The second prompt is the forbidden side effect: the
approved split retains authority-drifted readiness, and authority identity is
a pre-delivery fence, not a post-turn diagnostic.

**Required correction.** Before any action is delivered while a settlement
marker exists, compare the current validated authority with the marker and,
where needed, perform the canonical reconciliation. A matching exact claim
must retain W11910's recoverable redelivery; a changed or unnamed authority
must retain the whole envelope without starting a turn. Add an end-to-end
single-bridge A-to-B case proving only the A prompt is spent.

### [P1] The mandatory incident owner may still be the fenced runner itself

The startup gate checks only that `runtime.actionOwner` is a nonblank string
(`tools/acp-baton-bridge/src/acp_baton_bridge.mjs`, `runBridge` startup).
Configuration therefore accepts
`runtime.actionOwner === baton.participant`. In a secondary, held, unreadable,
or drifted settlement the bridge retains every readiness action, including
the incident obligation addressed back to that same participant. The one
durable notice is then not actionable by the recovery/operations participant
the ruling requires; it is queued behind the fence it is supposed to resolve.

This is the same self-addressed deadlock the approved action-owner rationale
rules out. Explicitly spelling the runner instead of inferring it does not
change the scheduling result.

**Observed reproduction.** The same probe passed a validated configuration
with both fields set to `baton.claude`; startup completed instead of refusing.

**Required correction.** Refuse an action owner equal to the runner
participant before role loading, runtime-lease publication, or the first
wait. Add a startup-order regression beside the absent-owner cases. This does
not require inferring an owner or validating a different participant's remote
capabilities; it closes the locally provable self-owner case.
