## [P1] Source checkout mtimes remain part of the image identity

`_normalized_layer` at `v12/python/tools/worker_image.py:178-191` copies every
member's mtime and replaces it only for directories. It explicitly treats a
regular file's build-context mtime as content. Git carries file bytes and the
executable bit, but not file mtimes; two fresh checkouts of the same revision
can therefore present identical `baton_worker.py` bytes with different ambient
filesystem clocks.

The additive daemon-free
`TwoBuildsReachOneIdentity.test_source_checkout_mtime_is_not_part_of_the_image_identity`
constructs two otherwise identical OCI layouts whose one worker file differs
only in mtime. Current normalization returns
`sha256:57bea3a2…` and `sha256:05f1817c…`, so the image identity depends on when
the checkout was populated. The existing real-engine test builds twice from
one context and consequently reuses the same source mtimes; it cannot establish
reproducibility across independent checkouts.

Normalize the ambient mtime of every member in recipe-owned layers, not only
directories, while retaining the bytes, mode, link target and other semantic
filesystem content. The current
`InsideTheRewrittenLayerOnlyDirectoryTimesMove.test_a_file_keeps_the_mtime_it_came_in_with`
pins the defect as an expectation. This review gives explicit case-specific
confirmation to revise it to the reproducible member-time contract.

## [P1] Refused stage cleanup is silently reported as a successful build

`build_worker_image` removes its allocated staging image in `finally` at
`v12/python/tools/worker_image.py:353-356`, but discards the subprocess result.
After a successful build, save, normalization and load, an engine refusal from
`image rm --force` is ignored and the function returns the pinnable identity at
line 357. The mutable unnormalized image may remain under a readable staging
tag even though the module and dossier say the stage is removed on every path.

The additive daemon-free
`TheBuildVectorIsClosed.test_a_failed_stage_removal_cannot_report_a_successful_build`
drives the successful path with a cleanup result of status 1. Current behavior
raises nothing. A positive sweep after an ordinary green daemon run does not
cover this branch: it neither forces removal refusal nor runs when class setup
fails partway.

Check the removal result and do not return an identity when cleanup was
refused. If an earlier build operation also failed, preserve that primary
failure while retaining actionable cleanup evidence; cleanup must not silently
turn either path into a success.
