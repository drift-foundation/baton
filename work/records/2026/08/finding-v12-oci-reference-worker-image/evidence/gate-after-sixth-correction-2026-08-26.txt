[P1] ANCESTRY IS AN ORDERED PREFIX, NOT SET MEMBERSHIP

  `_base_facts` returned a `frozenset` of the base's diff ids and
  `normalize_layout` called every diff id found in that set a base layer. A
  built layout carrying ONE of two claimed base layers and not the other was
  accepted, its remaining layers rewritten, and a digest returned as though
  the pinned base had been established.

  That contradicted the correction's own central claim. An image descends from
  a base by carrying that base's layers, in that base's order, at the FRONT;
  anything else is a different image that happens to share bytes.

  So the base's layers come back as an ORDERED SEQUENCE — the engine already
  reports them in order, and keeping that order is the whole of the fix — and
  the built image must begin with that exact sequence, with at least one
  recipe-owned suffix layer, before anything is rewritten:

      base = tuple(base_layers)
      if not base:                              -> refuse
      if tuple(diffs_now[:len(base)]) != base:  -> refuse
      if len(diffs_now) <= len(base):           -> refuse

  The recipe's layers are then the SUFFIX, taken by position. That is stricter
  than set membership in a way membership could never be: a recipe layer whose
  digest happened to equal a base layer's is still the recipe's, because of
  where it is.


[P1] THE STAGE IS ALLOCATED, NOT DERIVED

  `staging_tag` returned `<target>-unnormalized` from the destination alone,
  so two simultaneous builds for one destination shared one mutable tag:
  either could save the other's un-normalized image, and either `finally`
  could delete the tag before the other had saved it.

  The docstring claimed the opposite — "so two builds running at once do not
  stage over each other" — and the claim is what made it easy to miss. It is
  unique per invocation now, with the destination still in the readable prefix
  so a leftover stage says which artefact it was on its way to being.

  AND IT IS THREADED, which is what the uniqueness is for. `build_vector` takes
  the stage as an OPERAND rather than deriving it: a vector that allocated its
  own would name a reference its caller could not save, remove or read back,
  which is the shared-tag defect wearing a different hat.
  `build_worker_image` allocates once and uses that exact value for build,
  save and cleanup.
