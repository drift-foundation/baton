[P1] THE MTIME RULE WAS A DECISION I WROTE AND DEFENDED, AND IT WAS WRONG

  `_normalized_layer` replaced the mtime of directories only, on this
  reasoning, which is quoted from the code it justified:

    "A regular file's mtime came out of the build context and is content."

  The build context is a CHECKOUT, and a checkout does not pin mtimes. The
  version-control source carries file bytes and the executable bit and nothing
  about when a working tree was populated — so two fresh checkouts of one
  revision present identical worker bytes under different ambient clocks, and
  the reproducible identity this whole step exists to produce depended on when
  somebody cloned.

  I drew the line between "the copy created it" and "the context supplied it".
  THE LINE THAT MATTERS IS WHAT THE SOURCE OF TRUTH PINS, and it pins neither.

  Every member time in a recipe-owned layer is normalized now. Bytes, mode,
  link target, ownership ids and member order are content and survive; the
  mtime is a clock reading whatever member carries it. The module docstring
  records the old rule as SUPERSEDED with its reasoning, because the
  distinction it drew is the instructive part.

  AND THE REAL-ENGINE CASE COULD NOT HAVE CAUGHT IT. It builds twice from ONE
  context, so both builds see one set of source mtimes. That is worth naming:
  a daemon-backed gate is not automatically the stronger evidence, and here
  the daemon-free fixture is the only thing that can vary a checkout.


[P1] A REFUSED CLEANUP CANNOT REPORT A SUCCESSFUL BUILD

  The staging removal ran in `finally` and discarded its result, so an engine
  that refused `image rm` left the mutable un-normalized image under a
  readable staging tag while the function returned a pinnable identity — which
  makes this module's own remove-on-every-path guarantee false, in the same
  docstring that states it. **That is the second time in this Work a comment
  has asserted a property the code did not have**, and the first was the
  shared staging tag one correction ago.

  The result is checked now, and the raise is placed AFTER the `finally` on
  purpose: a build that failed and then could not clean up is reported as the
  build failure it is, with the cleanup evidence in the log rather than
  replacing it. Only a run that got all the way through — build, save,
  normalize, load — turns a refused removal into its own failure, because that
  is the run whose success would otherwise be a lie.
