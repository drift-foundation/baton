WHAT IS ACTUALLY VOLATILE — THE RECORD'S MEASUREMENT WAS INCOMPLETE

  The record said two `--no-cache` builds differ only in the config's wall
  clock, with "all six RootFS layers identical". Measured again here on docker
  29.1.3 with no buildx, two builds differ in FOUR places:

    1. config `created`                    the build clock
    2. `container`, `container_config`     the intermediate container id
    3. `config.Image`                      the parent chain id
    4. THE RECIPE'S OWN LAYERS

  (4) is the one the record missed. `COPY x /opt/baton/x` writes a tar
  carrying the DIRECTORY ENTRIES the copy created, and their mtime is the
  build clock:

    == build a
       4125fffca90e 'opt'                        mtime=1787702374
       4125fffca90e 'opt/baton'                  mtime=1787702374
       4125fffca90e 'opt/baton/baton_worker.py'  mtime=1787650104
    == build b
       93ab6c47621e 'opt'                        mtime=1787702375
       93ab6c47621e 'opt/baton'                  mtime=1787702375
       93ab6c47621e 'opt/baton/baton_worker.py'  mtime=1787650104

  The copied FILE keeps its source mtime. The two directories do not, and the
  resolution is ONE SECOND.

  SO THE EARLIER READING WAS AN ACCIDENT OF TIMING: two builds that start
  inside one wall-clock second have identical layers, and two that straddle a
  second do not. That also explains the interaction the previous correction
  reported and could not attribute — two container cases passing alone, in the
  locked build and beside the engine gate, and failing in a full source run.
  A full run is slower, so the two builds straddle a second more often.


THE CORRECTION: THE RECIPE HAS A DETERMINISTIC OUTPUT STEP

  `v12/python/tools/worker_image.py`. The engine builds with `--no-cache`; the
  saved OCI layout is normalized; the normalized layout is loaded back, and
  the identity of THAT image is the one the manager pins.

  ONLY THIS RECIPE'S OWN WORK IS TOUCHED, and the boundary is DERIVED from the
  pinned base rather than counted:

    a layer is the recipe's when its diff id is not one of the base's;
    a history entry is the recipe's when it is newer than the base's Created.

  So the base image's layers and provenance travel byte for byte. A normalizer
  that rewrote them would describe a different base from the one the recipe
  pins, which is what the digest pin exists to protect.

  INSIDE A REWRITTEN LAYER, ONLY DIRECTORY MTIMES MOVE. A regular file keeps
  the mtime it had in the build context, because that is content the recipe
  carries rather than a clock reading.
