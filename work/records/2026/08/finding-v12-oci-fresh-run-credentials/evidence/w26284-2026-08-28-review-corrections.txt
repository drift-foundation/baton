--- 2. THE TWO [P1] FAILURES THE 2026-08-27 MEASUREMENT DID NOT CATCH

Section 6 reports nineteen mutations, all caught. That measurement was
honest and it was not sufficient, and the reason is worth stating plainly
because it is a property of how the mutations were chosen rather than of how
many there were.

  THE FAILED-MATERIALIZATION MUTATIONS WATCHED A SUCCESSFUL REMOVAL. Both
  existing ones either removed the `_discard` call or swapped it with the
  forgetting. Neither drove `_discard`'s explicit FALSE answer, which is the
  one the operation exists to return — so nineteen of nineteen could be
  caught while a filesystem refusal left bearer bytes on disk with the
  registry disarmed. A third mutation now makes the proof vacuous the same
  way ignoring the boolean did.

  THE ARGV MUTATION REMOVED THE SWEEP FROM THE ONE VECTOR THAT HAD IT.
  `run_vector` swept the argv it composed; `start`'s duplicate probe reached
  the engine first and unswept. The case that existed chose the `participant`
  label specifically because it is NOT a candidate filter, so it proved the
  late sweep worked and said nothing about the early leak. The sweep now has
  one owner at `EnginePort.__call__`, which is what every vector actually
  passes through, and the mutation removes it there because that is the only
  place it exists.

--- 3. THE REAL-ENGINE TEARDOWN CASE WAS OUT OF SCOPE

Section 6's real-engine pass included
`test_teardown_forgets_only_after_the_bytes_are_proved_gone`, which started a
real container and then called `CredentialHome.tear_down` directly. Removing
a host pathname is not proof that a bind-mounted runtime cannot still hold
the inode, and this finding keeps the shared quiescence/removal/settlement
crossing explicitly outside this provider.

The review offered two resolutions and the finding's own boundary chooses
between them: this suite stays inside fresh-run delivery and failure. The
case now tears down a delivery that never launched — a real ending this
provider owns — and a new case exercises the one runtime-absence question it
does own: a start the engine refused settles through the adapter's real `ps`
against a real daemon before the delivery is released. The post-runtime
crossing remains W6636's.
