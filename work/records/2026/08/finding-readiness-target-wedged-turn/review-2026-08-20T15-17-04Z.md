# W3243 review — changes requested

The non-interactive denial, unhealthy status, retained queue, and identity
boundaries are directionally sound. Two recovery defects remain.

## P1 — interruption ignores the authoritative request turn

The generated app-server schema requires `params.turnId` on
`item/commandExecution/requestApproval`. `#denyAndRecover`, however, stores
`state.activeTurn?.id`, which may still be null when the server request races
the continuation that records the accepted turn. The blocked diagnostics then
lose the exact turn and the bounded recovery calls `turn/interrupt` with a
null `turnId`.

Use and validate the request's required `params.turnId` as the authoritative
blocked-turn locator. Reconcile it with a non-null local active turn rather
than silently preferring either if they disagree. The additive reviewer case
`W3243 review: recovery uses the approval request's authoritative turn`
reproduces the current failure.

## P2 — the recovery timer survives a clean stop

`stop()` clears `retryTimer` and `reconcileTimer` but not `blockedTimer`.
Consequently a callback can run after the bridge has disconnected and after
the runtime publisher reported a clean shutdown, attempt an interrupt through
the dead client, and publish/log a failure that happened only because shutdown
did not cancel its own timer.

Clear every target's `blockedTimer` during stop. The additive reviewer case
`W3243 review: stopping cancels the pending recovery timer` reproduces the
current failure.

## P2 — a drain assertion is tautological

The recovery/drain test contains:

```js
assert.equal(status.ready, false || status.ready, "");
```

`false || status.ready` is `status.ready`, so the assertion can never fail.
Replace it with the exact ruled post-recovery expectation and independently
assert the target's deliverability/blocked state as appropriate.
