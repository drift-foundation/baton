## [P1] A positional continuation silently skips actionable Work

The approved contract calls `next_after` opaque. The implementation instead
returns `start + len(page)`, validates `after` as an integer, slices the newly
derived current set with `rows[start:start + size]`, and documents examples
such as `after=25`.

That is not merely a representation difference. If a row before the offset is
claimed or rerouted between pages, every later row shifts left and the next
slice begins one row too late. The retained reproduction creates W2–W5, reads
W2/W3 with limit two, claims W2, then follows `next_after=2`; page two returns
only W5 and never exposes still-actionable W4.

This race is ordinary on a shared Route: another handler can win a claim while
the viewer is paging. It violates the feature's central promise that every
participant-actionable Work is discoverable.

Required correction: use an opaque stable continuation over canonical
`WORK_ORDER` rather than a positional index, and treat it as pass-through in
the CLI and TUI. Add an inter-page removal/reroute regression proving later
actionable rows are not skipped. An earlier insertion must likewise not repeat
an already-returned row; deliberate refresh remains the path for restarting at
the current first page.

Evidence: `evidence/w26328-review-pagination.py`.

## [P2] The too-narrow refusal understates the required width

`Mine` correctly joins the mandatory layout allocation, but the refusal path
still computes `need` with `id_width` rather than the full `mandatory` width.
It omits at least the Mine heading and its separator, so an operator can widen
to the reported minimum and receive the same refusal again.

Required correction: calculate the diagnostic from the same complete fixed
allocation used by `layout_fits`, and add a boundary case proving the stated
minimum is sufficient.
