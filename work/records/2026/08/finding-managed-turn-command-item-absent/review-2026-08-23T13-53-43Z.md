## Findings

### P1 — The approved custom-tool response path was not exercised

Both probes create an isolated `CODEX_HOME` without the managed provider custom
tool. The model therefore uses the built-in shell, and no
`custom_tool_call` / `custom_tool_call_output` response pair is generated.
Zero raw notifications on those turns does not prove that
`rawResponseItem/completed` cannot publish the target pair on a response that
contains it. The claims that raw transport never fires on this build and that
the pair provably cannot occur are overbroad. They are superseded in
`FINDING.md` and scoped in `PLAN.md`; the approved oracle remains locked.

### P1 — The live command is not the requested literal command

The requested command is `date +%s%N`; the live item records
`/bin/bash -lc 'date +%s%N'`. The existing W2845 strict oracle compares the
recorded command to the requested command literally, so this item would not
pass it. A move to live item events requires an operator-approved wrapper or
normalization contract plus deterministic positive and negative tests. Review
must not silently equate the two strings.

### P2 — The positive execution path is still unproved

The only observed live command completes as `failed` with exit code 1. That is
useful fail-closed evidence, but it does not prove the success condition needed
by W2845 or W7830.

## Required disposition

Do not implement or relax either oracle. Return the record to `baton.ops` for
the second boundary decision. Any adoption of live item events must explicitly
resolve the managed custom-tool versus built-in-shell configuration, exact
command identity, and a successful positive-path measurement.
