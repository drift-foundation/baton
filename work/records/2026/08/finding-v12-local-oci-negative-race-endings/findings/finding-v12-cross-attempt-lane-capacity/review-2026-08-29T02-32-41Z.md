# Independent review — changes requested

## [P1] Adopted split lane identity is projected as free

`runtime_lanes.lane_id` is derived from the stored `authority_uuid`, `work_id`,
`principal`, and `effective_scope`, so those five values are one persisted
relation. `_holder_of` and `_work_lanes` currently apply
`RUNTIME_LANE_COLUMNS` only: each independent value is owned, but the relation
between them is not.

When an adopted row retains its holder and four identity parts but its
`lane_id` is changed to another well-formed identity, `_holder_of` misses it by
the recomputed key. `_work_lanes` finds it by Work, then `runtime_lane` excludes
it from `blocked_by` because its holder is the queried attempt. The public
projection consequently answers `holder=None`, `held_by_this_attempt=False`,
and `blocked_by=[]` while the capacity row still exists. An operator is told the
lane is free rather than told the store is internally inconsistent.

The additive
`TheProjectionExplainsTheHolderAndTheBlocker.test_a_persisted_lane_must_derive_from_its_stored_identity`
is the regression and currently fails. Validate the derived/stored relation on
every adopted lane row before either read path uses it, returning the manager's
closed integrity/schema refusal rather than choosing one side of the split
identity. Extend the corruption coverage to the shared relation owner rather
than adding unrelated independent-column checks.

## Acceptance correction and added coverage

The reported inability to drive a real successor offer was incorrect. The live
offer index covers only `issued` and `accepted`; a claimed predecessor has
already released that slot. I added and passed a public
`issue_offer`/`accept_offer`/`record_attempt`/`submit_claim`/
`activate_assignment` successor case. It proves the held predecessor lane wins
before input-root authorization and before the runtime adapter.

I also added and passed a race between two successor attempts with different
principals. Their lane ids differ, so one winner proves the decisive per-Work
interlock runs inside the serialized transaction rather than relying on the
lane primary key.
