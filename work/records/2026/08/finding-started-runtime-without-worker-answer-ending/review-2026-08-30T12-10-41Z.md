## [P0] Reconciliation can revoke the positive runtime observation while the fence is in flight, but removal still uses the stale pre-declaration row

`abandon_attempt` now correctly rereads `cleanup` after the destroy replay
miss, but it then tests `attempt["execution_runtime"]` from the snapshot taken
before `_abandon_intent`, the destroy replay, and `AuthorityPort.cancel`.
Reconciliation is an independent manager operation. If it records
`execution_runtime = "uncertain"` while the authority call is in flight, the
abandonment still calls `adapter.destroy_abandoned` from the stale `running`
snapshot. Settlement only discovers the conflict afterwards, when it refuses
the `uncertain -> destroyed` state regression. By then the destructive runtime
boundary has already been crossed.

The additive witness
`TheAbandonmentEndingSurvivesInterruptionAndDrift.test_reconciliation_to_uncertain_while_fencing_prevents_removal`
moves the axis to `uncertain` inside the fence callback. It currently fails:
the public call reports `state-regression` rather than the specified
`quiescence-unknown`, and the recording adapter has already received one
destroy command. This is the dossier's required race-against-reconciliation
row; the static already-uncertain case does not exercise it.

Before runtime control, reread the current attempt and apply the uncertainty
gate to that current row. The same post-fence read should also preserve the
terminal-axis refusal if another ending settles during the authority call.
The committed intent still authorizes an interrupted exact retry: its cleanup
axis remains `pending` or `blocked-on-intake`, while a completed exact retry is
caught by the outer destroy replay.
