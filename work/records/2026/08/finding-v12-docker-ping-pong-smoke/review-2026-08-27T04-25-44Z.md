## Findings

### P0 — arbitrary provider output crosses the no-credential durable boundary

`trial.mjs` writes up to 2,000 bytes of raw agent stdout into
`output.json.result`; on failure it also writes provider text as
`failure_detail`. `trial.py` then copies the complete document into its printed
host report and separately records redacted container stderr. The regular
expression recognizes some familiar token spellings, but the ruling is not
"redact tokens that look familiar": no credential may enter a result, evidence
file or log, and durable evidence records only the provider/method and redacted
failure category.

The additive fake provider returns an arbitrary sentinel shaped like no known
token. It appears verbatim in the host report. A real agent has the mounted
credential and can emit arbitrary stdout; a prompt requesting one word is not
a non-disclosure boundary.

Before mounting any live credential, make durable output an allowlist. For a
successful trial it needs only the exact `pong` fact and correlation. For a
failure retain a closed category, exit state and bounded operational facts,
not raw stdout/stderr or a heuristic redaction of them. Provider text may be
shown only on an explicitly non-durable operator surface if the ruling is
revised to authorize that surface.

### P1 — the host trusts a worker-authored success bit and ignores exit state

The in-container check treats any word occurrence of `pong` as success, so
`not pong` matches. The host does not inspect the text at all: it accepts the
truthiness of `answer["pong"]`. Its final `satisfying` expression omits the
container exit status and the expected spike/provider/closed-document shape.

The additive regression supplies `result: "not pong"`, `pong: true`, matching
correlation and container exit 9. `trial.py` returns success. This contradicts
the pinned requirement that malformed pong fail visibly.

Require an exact textual `pong`, a zero provider/container exit, the expected
provider and spike identity, matching correlation, and one closed result shape.
The host must recompute that verdict from the bounded document rather than
trust the document's boolean claim.

### P1 — cleanup failures can still report `clean: true`

Image removal is unchecked. A refused `docker image rm` followed by an empty
tag lookup reports no surviving image, even though the immutable image may
remain untagged. Staged-root removal uses `ignore_errors=True`, records whether
the root survived, then excludes that fact from `clean` and `satisfying`.

Two additive regressions independently make image removal fail and leave the
staged root in place. Both runs still return satisfying success. Enforce every
cleanup result, query the recorded immutable image identity rather than only
its removed tag, and include positive staged-root absence in the final verdict.
The same fail-closed treatment should apply to timeout container kill/removal.

### P1 — the offered personal credential files are present but not usable by the image user

Both Dockerfiles run as uid/gid `65532:65532`. The two host files offered as a
"one flag away" alternative are owned `1000:1000` with mode `0600`. A direct
read-only bind preserves that ownership and does not grant uid 65532 read
access. Preflight reports presence/mode/size but not this usability mismatch.

Do not nominate or mount those personal files on the current claim. Ask the
operator for a dedicated provider whose ownership/mode is intentionally
readable by the container identity, or record an explicit alternative runtime
identity/delivery ruling. Preflight should distinguish "present" from
"readable by the configured container uid" without opening the secret.
