## [P0] A colliding attempt home can alias a sibling's input root

`assignment_workspace` creates every home entry with
`os.makedirs(..., exist_ok=True)` (`workspaces.py:634-637`). It then resolves
the entry and accepts any resulting path still contained by workspace storage.
There is no exclusive creation of the attempt home and no durable ownership
proof before an existing path is reused.

The additive reviewer case
`TheRuledTrustModel.test_a_colliding_home_cannot_alias_another_attempts_root`
creates a stale second attempt home whose `inputs` entry is a symlink to the
first attempt's input root. The alias stays inside manager-owned storage, so
the current code accepts it and returns the first attempt's root for the second
attempt. The direct reproduction reports `aliases True`; the regression fails
because no refusal is raised.

That contradicts both "unique never-reused per-attempt directories" and
"exclusive creation with collision refusal" in approver ruling M34768. It is
also within the ruled threat model: the case is stale/accidentally corrupt
manager state, not a malicious same-uid host process.

The submitted collision case does not cover this. Despite its name, it calls
`compose_input_root` twice with the same attempt ID and the same already-
published root, so it proves recomposition refusal. A document-exists check at
publication cannot prove exclusive directory allocation; if the aliased root
is empty, the wrong attempt can publish into it first.

Separate exclusive first allocation from authorized same-attempt restart
lookup, or add equivalent durable manager-owned ownership evidence. A
pre-existing or aliased home/root must fail closed unless it is proved to be
the exact existing attempt being reopened. Preserve legitimate restart
adoption, clean concurrent allocations, exact cleanup/retry, sibling isolation,
and all landed readable/read-only input behavior.
