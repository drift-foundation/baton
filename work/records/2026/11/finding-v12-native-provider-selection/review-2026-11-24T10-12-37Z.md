## 2. Required corrections

### R1 — a holder that never started a runtime blocks its Job's home permanently

- **Observed** (probe C6). The home is held at the start of launch, before
  any runtime exists. I refused the launch delivery after that point. The
  stage ended `exceptional`. The home record names that attempt as holder,
  state `ready`. The cessation evidence for it is `runtime: not-started`,
  `cleanup: pending`, `observed_at: None`, and stays so.
- **Why it matters.** `provider_home.ceased` accepts only `destroyed` with a
  recorded observation. A holder that never requested a start can never
  produce one, so every later attempt of that worker for that Job waits
  forever, and by design no owner item is opened. Contract §8.4 says the
  wait ends "once settlement records the earlier runtime gone"; here nothing
  ever will.
- **Not shown.** I did not drive a successor attempt into the wait; the
  harness produced none. The evidence state and the release rule are what I
  observed.
- **Required.** A holder for which the manager's own record shows no start
  was ever requested, and whose attempt has ended, is positive absence and
  releases the home. Alternatively record the holder only when the start is
  requested. Either way: a deterministic proof that a successor attempt
  proceeds after a pre-start failure, and that a holder with a start
  requested and no cessation still waits.
- Where: `worker_manager/attempts.py` `provider_home_cessation_of`;
  `worker_manager/provider_home.py` `ceased`, `acquire`;
  `tools/single_worker.py` `_hold_provider_home`.

### R2 — proof 39's test fails wherever the temporary root lies under a directory named `home`

- **Observed.** `test_39_crash_after_record_before_home_creation_replays_same_holder`
  fails with "HomePending not raised" when `TMPDIR` is under `/home/…`, and
  passes under `/var/tmp`. Its patched `os.mkdir` raises for any component
  named `home`, so the ancestor walk fails before the holder record is
  written and the crash point it means to test is never reached.
- **Why it matters.** Disk-backed `work/scratch/` is where this repository
  directs temporary test storage, and on this host that is under `/home`.
- **Required.** Make the injected failure specific to the home directory
  being created (the `dir_fd`-relative final creation), and rerun the module
  with a temporary root under `/home`.

## 3. The September participation evidence

**Finding: the retained evidence does not satisfy the approved provenance
rule as written. It is sufficient for what the contract actually permits in
this slice.**

- **What the rule requires.** Addendum §2.1: a participation source traces
  to "output already retained in a dossier from a real run of that exact
  build", by path and digest, or to a selected provider qualification.
- **What is retained.** The raw file was never promoted to the dossier. The
  September review left it at `/tmp/w177936-canary-234686`, which no longer
  exists; no file under `work/records` has its digest (`defc5df0…`). What
  remains is an independent reviewer's written account of it: the result was
  `type=result`, `subtype=success`, `is_error=false`, had no direct `model`
  member, and `modelUsage` held exactly two keys, the selected model and one
  other. The run's CLI was 2.1.247 (`MODEL-SELECTION-234686.json`).
- **So:** an attested description of exact-build output, with the digest of
  bytes nobody can now produce. That is not retained output.
- **My error.** Addendum §2.2 said retained exact-build evidence "does
  exist". I wrote that without checking, and flagged it as unchecked in its
  §6. It was wrong.
- **What the contract permits.** §7 marks the Claude list as "drafted from
  the September output" and unproved until qualification confirms it against
  real output. A drafted list is what the candidate has. No test claims a
  real shape: every fixture is synthetic and labelled.
- **Direction of the risk.** If the real shape differs, results are
  `missing` or `conflicting` and are held. The one way a draft can accept
  wrongly is a usage key for a model that did no work; the contract already
  lists that as unresolved.

Consequences I am applying:

1. The list is **drafted and unqualified**, and the documentation must say
   so in those words (R4). No code change.
2. Native use stays behind qualification, as already selected. The
   qualification that confirms the list must retain the raw output in the
   dossier by path and digest, so this cannot recur.

**For the owner to confirm:** keep the drafted list until qualification
(my recommendation), or empty it now so every Claude result under the new
composition is `missing` until then. The second is stricter and means a
source change, a rebuilt image and a second qualification after the first.
