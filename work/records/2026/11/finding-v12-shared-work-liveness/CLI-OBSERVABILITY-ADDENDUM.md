## Why Claude streaming is a separate bounded change

`_provider_document:5282` rejects partial/oversized data and parses exactly one complete JSON object; `MAX_PROVIDER_RECORD` is 64 KiB. Multiple JSONL objects are rejected. `_context_result:4329` independently parses that terminal record, requires the expected session_id, successful result shape and process status, and binds the record digest. `_provider` verifies context argv_digest. Changing only the output flag could therefore lose diagnostics, invalidate invocation bindings and fail reuse receipts even if the CLI performs useful work.

If selected later, implement a provider-owned, bounded JSONL decoder once: keep raw stdout byte-identical in private evidence, validate complete lines, extract safe event summaries and exactly one valid terminal result, and retain partial/malformed/oversize/duplicate-terminal distinctions. Feed a documented terminal-record representation into both diagnostic and context-result parsers. Specify its digest separately from raw stream digest; update approved invocation/profile digests and versioned fixtures. Preserve process exit, timeout/drain grace, interruption, retained evidence and session-continuity checks. An observed result event alone never settles a Baton attempt. Do not weaken completeness to accept a stream that lost its end.

Native transcript parsing is an alternative without CLI flag changes, but requires an exact-build decoder and stricter uncertainty. Completed framed records may expose message/tool kinds; guessed regexes over prose, unfinished JSON or file names do not. Match source session and command/attempt binding before attributing events. Resumed histories must not replay old events as new activity. Unsupported schema yields parser-unsupported, not “no tool calls.” Until that evidence exists, byte growth is the supported useful signal; semantic tool state remains unknown.

## One collection/interpretation boundary, bounded options

**A — recommended first slice (about 1–2 implementer-days plus review):** keep status.json job-status/9 and worker-visibility/1 contracts unchanged; reuse their existing facts. Extract/share a pure presentation projection for activity, attribution, outcomes and freshness between status and monitor. A future TUI calls that same projection. The existing publisher and worker mailbox remain the collectors. Add no HTTP service, state database, new on-disk envelope, host transcript tailer or CLI flags. Centralize freshness in the shared presentation policy; do not silently change worker-visibility/1's documented unknown freshness output. Proposed policy remains snapshot stale at >=15 seconds, with activity age separate; needs owner selection. Keep service-health behavior unchanged in this small slice and explicitly defer its full consolidation: this is useful Job activity delivery, not a claim that every monitoring source already has one collector.

**B — optional next increment (about 2–3 days plus review, assuming known log locators):** one backend collector uses existing capture metadata/bounded reads to summarize stdout/stderr/native stream growth and capture completeness, if existing activity is too often unavailable. No per-UI parsing. This needs an explicit versioned additive observation contract; do not cram stdout growth into the existing native-byte counter. It can distinguish “stream grew” from “no usable stream” without interpreting content. Metadata is insufficient for exact provider operation. Existing reused-HOME activity limitations remain until an exact baseline/source-generation design is approved.

**C — richer CLI event increment (roughly 3–5 days for Claude parser/recovery changes plus review, pin evidence dependent):** choose documented stream-json after exact-build verification, or a version-pinned native-transcript decoder. Reuse existing drain/capture and publish only normalized metadata. Prefer streaming for a longer-lived event contract; prefer no flag change only if native decoder support is actually proved. Codex production adapter delivery is separately estimated after selection, not included in this range.

These are planning estimates, not measured promises. A is smaller than the original 3–5-day envelope migration. None claims CPU/memory, complete file-change counts, provider tool queries or accepted useful progress. The original broad envelope remains an architectural option when new sources justify it, not a prerequisite imposed now.

For B/C, collector cursor is bound to instance/attempt/operation/provider version/session/source generation and byte offset. On restart resume only against matching source identity; otherwise establish a new generation and report a gap. Bound bytes per poll and maximum line size, buffer incomplete UTF-8/JSON lines, discard neither capture errors nor rotated/truncated history silently, and expose lag/backlog rather than declaring current. A candidate limit is 64 KiB per stream per poll and one-second local polling, subject to deterministic cost validation; fair per-instance scheduling prevents a noisy stream starving others. Never rescan whole transcripts every refresh. Coalesce safe counts/kinds/times, omit prompts, output, commands, arguments, paths and arbitrary tool names. Worker occurrence time, collector receipt time and source observation time are distinct. Quiet remains inconclusive. No extra prompts, status queries, SDK or App Server are required.
