## Required before approval

**G1 — Retained-byte trust root.** Section 2 allows "an explicit typed
retained-evidence reference" that binds the failed execution "to the copied
manifest". For W385624, the copies under
`finding-v12-retained-recovery-admission/evidence/output-limit-recovery-20261122/`
were made by an agent. Their manifest is a coordinator assertion, and the
failed exchange recorded no output digest or custody. The contract must state
the authoritative source:

- the original attempt's output, as the host owner holds it, read through
  the host owner with exclusion;
- dossier copies are acceptable only when they byte-match that original;
- if the original is gone or unreadable, the case HOLDS, and an
  agent-made copy is never the sole trust root.

Otherwise REC-9's own sentence, "a copied log or owner assertion alone is
not proof", is undercut by its own admission path.

**G2 — Trust and meaning of "valid verification".** The retained
`verification.txt` is written by the adapter (claude_agent ~5440), not the
provider, and states: "Rerun the command yourself, from the collected
candidate tree, outside the worker. The acceptance already says that rerun
and not this file is what an operator trusts." The in-worker verifier ran
provider-edited code with the credential mount readable. It is producer
evidence, not acceptance.

REC-9 must define:
- "valid" as adapter-authored attribution (argv from the read-only task, exit
  status from `wait`) bound to the exact candidate;
- that reusing it means only that the recovery pipeline does not re-execute
  it;
- that it is never presented as acceptance.

Today the text reads as if the evidence substitutes for verification.

**G3 — Reviewer's required verification versus "no verifier call
permitted".** Section 3 says: "legacy verification ceiling 900s (no verifier
stage/call permitted)". The owner's M385703 ruling covers the "entire
recovery reviewer invocation including its tests". The approved Stage 1 profile
also marks `verification_command.includes_required_review_verification`.

The contract must say plainly that the 900 s per-command ceiling applies to
the reviewer's own required verification and tests. The prohibition applies
only to the recovery pipeline re-running the producer's verifier, never to
the substantive reviewer. As written, a strict implementer could forbid the
reviewer's tests, which would contradict M385703 and G2.

**G4 — A new stage kind is a vocabulary and scheduling change that is not
named.** `documents.STAGE_KINDS = ("implementation", "review", "integration")`
is closed. `scheduler._lane` maps every non-review kind to the
implementation lane, so an unqualified `publication` kind would take an
implementation worker and capacity. `review_driver` and the review stage
consume an implementation stage's frozen output.

REC-9 and the bundle must name:
- the stage-vocabulary or submission revision, refused by older binaries;
- the publication lane and which configured worker serves it;
- how the review consumer binds the publication output without a fake
  implementation stage;
- the readiness gate, so review cannot be offered before publication custody
  exists.

That last point is exactly the defect found in Stage1-B (T385624 seq 385705,
F1): a dependency-free review stage is queued and offered on the first tick.

**G5 — Fresh Work versus reused Work is inconsistent with Stage1-B and its
servability argument.** Section 4 creates "a fresh recovery Work linked to the
original Work under the same effective scope". Stage1-B deliberately REUSES the
failed Job's Work because `stage_execution._disagreements` compares the
worker's manifest Work with the Job binding, so a fresh Work needs worker
configuration for every recovery.

The contract must either:
- reuse the original Work, with the old claim untouched and new
  attribution through the recovery lineage; or
- justify the fresh Work and name the deployment-binding step that makes it
  servable without per-recovery installation, plus the Authority operation
  that links the two Works.

Two recovery paths with opposite Work rules would be inconsistent.

## Notes (non-blocking)

- **N1.** The 900 s publication sub-bound needs a named enforcement owner.
  job_control has no sub-stage bound; a worker-side command ceiling, like
  ordinary verification, is the natural home. Its origin must be the
  persisted publication-stage start.
- **N2.** Name the mechanism that makes the old attempt's retained output
  readable to the fresh worker: a read-only mount or staging through the
  host owner. The new worker must never get write access to the original.
  This is implied by "host-controlled exclusive preservation" but not
  specified.

  worker, a template and descriptor, and review wiring. Keep the
  "connected acceptance or not delivered" rule. Name 2–3 internal
  checkpoints for review, without delivering partial "resume".
- **N4.** `publication-status` lacks `--participant`. That is fine for a
  read, but it should state that it shows no more than recovery-item-style
  public facts.
- **N5.** On sequencing: apply the eventual Stage1-B gating fix (seq 385705
  F1) and the REC-9 readiness rule from one shared pattern, so the two
  recovery admissions do not diverge.
