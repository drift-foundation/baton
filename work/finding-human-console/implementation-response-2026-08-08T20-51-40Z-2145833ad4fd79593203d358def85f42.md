# R7 stacked layout — implemented, verified, ready for review

R7 was the sole remaining implementation for this commit and it is done. No
protocol, schema or agent-CLI change. The frozen CLI artifact, its manifest,
the oracle and the builder are byte-identical.

## What changed in behaviour

The console was two side-by-side columns: a 40%-wide list beside a 60%-wide
detail pane with a vertical `│` between them. It is now stacked — a full-width
MESSAGES/Sent-filter list on top (~40% of the usable body height), ONE
continuous horizontal `─` rule spanning the terminal (ASCII `-` fallback,
chosen at startup from the terminal encoding), and a full-width detail/composer
below (~60%).

Everything derived from the old geometry was recomputed rather than adapted:

- `pane_widths` is GONE; `pane_heights` replaces it and divides the body
  HEIGHT after reserving the one-row rule. There is no pane-width helper left
  at all, and re-adding one fails a structural test rather than merely sitting
  unused — that was your explicit "no hidden authorities" requirement.
- Wrapping, the detail line count, paging, scrolling, part-header marks, caret
  placement and resize all take the terminal width and the stacked row
  offsets. The caret is placed by its ROW below the rule where it used to be
  placed by a column past the divider.
- The selection highlight covers the whole row, because a stacked list row IS
  the whole row. It still covers nothing else: never the rule, never a detail
  row. Pinned pure and over a real PTY.
- The minimum terminal is unchanged at 40x8 and still draws every region:
  header, a list row, the rule, a detail row, the two-row footer. Pinned,
  because a minimum the layout cannot draw is not a minimum.
- The single-row status bar and the `Send now? [Y/n]` confirmation footer are
  EXACTLY preserved, including the rule that the row the second footer line
  would have taken goes to the panes.
- List column degradation thresholds were re-derived: they were widths of a
  40% column, so at the stacked width the date would have been unconditional
  and the degradation path dead code.

## Two consequences that needed a decision, not an adaptation

1. **The recipient picker is now MODAL and owns the body.** It replaced the
   detail pane when that pane was the whole body height; stacked it is two
   rows at 40x8 and cannot hold a prompt, one recipient and its page footer —
   so a confined picker would offer a letter it could not draw, the exact
   fault the measured-capacity work fixed. Verified by putting it back: two
   supported sizes fail immediately.
2. **`[`/`]` now scroll the selected part header into view.** A 60% pane puts
   the later parts of a multipart message below the fold, and a mark nobody
   can see is not a cursor. Only on the keystroke that moves it — following on
   every redraw would take a reader's `J`/`K` position away, pinned
   separately. `follow_input` became `follow_line` for that second caller.

If either reads as beyond R7, say so and I will narrow it; both were forced by
"recompute picker capacity and scrolling from the stacked geometry" rather
than chosen.

## One latent bug fixed while restructuring

`_detail_lines` filled the part-header `marks` list from message content and
THEN returned the picker's lines when the picker was open, so a picker row
could be styled as a part header. The picker check moved to the top of the
function. Cosmetic, unreported, and declared because it is a change you did
not ask for.

## Existing tests deliberately rewritten

Every one of these described the column layout. Nothing else in the suite was
touched.

`test_tui_render.py`

1. `_draw` helper — now goes through `driver.apply_layout` (the driver's one
   resize helper: layout then follow-the-caret) instead of `layout_for` plus
   `set_viewport`. Calling `set_viewport` alone stopped being what the driver
   does when following moved out of `step`; the stacked layout is what made it
   visible, because a 60% detail pane leaves a draft below the fold.
2. `_detail` helper — the detail pane is now the rows below the rule and above
   the footer, where it was the columns right of the divider. Same purpose:
   keep the ellipsis pins off the list column and the footer.
3. `test_the_caret_lands_on_the_draft_line` — draws first and places the caret
   second (the driver's order), and asserts the caret's ROW is below the rule
   rather than its column being past the divider.
4. `test_the_divider_is_a_box_drawing_character` → renamed
   `test_the_divider_is_one_full_width_box_drawing_rule`; asserts the rule row
   equals `─ * columns` at five widths.
5. `test_the_divider_holds_the_same_column_on_every_row` → renamed
   `test_only_one_row_is_the_divider`; the drift it guarded against is now a
   second rule row or a content row masquerading as one.
6. `test_the_divider_costs_exactly_one_cell` → renamed
   `..._one_row`; also pins that the box and ASCII forms put the rule on the
   same row.
7. `test_the_divider_falls_back_when_the_terminal_cannot_render_it` — expected
   glyphs are now `─` and `-`.
8. `test_the_divider_survives_on_the_highlighted_row` → replaced by
   `test_the_divider_row_is_never_the_highlighted_row`; a rule on its own row
   cannot be "on" the highlighted row, and must never be it.
9. `test_wrapped_detail_never_exceeds_the_pane` — the pane and the terminal are
   the same bound now, and it also pins that the pane got the whole width.
10. `test_panes_split_forty_sixty_with_one_divider` → renamed
    `..._with_one_divider_row`, parametrised over LINES, using `pane_heights`.
    The 3% ratio tolerance now applies only where the body is big enough for
    the split to be a ratio rather than rounding.
11. `test_every_consumer_uses_the_same_pane_arithmetic` — asserts the drawn
    rule sits exactly where `pane_heights` puts it and the caret row is inside
    the detail pane, at five sizes.
12. `test_the_selection_span_covers_the_inbox_pane_and_stops_before_the_divider`
    → renamed `test_the_selection_span_covers_the_whole_list_row`.
13. `test_the_selection_span_ends_exactly_where_the_divider_is_drawn` →
    replaced by `test_the_highlight_never_reaches_the_divider_or_the_detail_pane`
    — the same guarantee, moved from a column boundary to a row boundary.
14. `test_wide_characters_do_not_push_the_highlight_past_the_divider` → renamed
    `test_wide_characters_do_not_push_a_list_row_past_the_terminal`.
15. `test_every_offered_recipient_is_fully_drawn` — entries wrap at the full
    terminal width now that the picker is modal.
16. `test_a_reply_draft_is_never_elided` — reads the detail pane through the
    new helper, sets the caret with the text, and asserts the drawn run is
    lossless rather than counting all 400 characters on one screen (a 60% pane
    holds fewer rows, so "every character is on screen" was a statement about
    the old pane height, not about eliding).
17. `test_a_compose_field_is_never_elided` — same helper change.
18. `test_a_picker_address_is_never_elided` — same helper change.
19. `test_nested_leaves_are_markable` — driven through the real `]` keystroke
    instead of assigning `part_cursor`, because the mark is only visible once
    the pane has followed it. Setting the cursor directly tested the model and
    not the screen.

`test_tui_state.py`

20. `test_the_compose_prompt_says_enter_sends_from_any_field` — locates the
    detail pane below the rule instead of right of the divider. The property
    (prompt in the pane AND in the status bar, checked separately) is unchanged.

`test_tui_driver.py`

21. `test_the_confirmation_footer_is_exactly_one_row_of_exact_text` — counted
    "body rows" as rows containing the divider, which stacked would count as
    one. It now counts the rows between the header and the footer, and
    additionally pins that exactly one row is the rule in both states.

`test_tui_pty.py`

22. `test_the_highlight_stops_before_the_divider_on_a_real_terminal` → renamed
    `test_the_highlight_covers_one_list_row_on_a_real_terminal`; the rule
    character is still what would give away a stripe that spilled.
23. `test_the_divider_draws_as_a_continuous_column_on_a_real_terminal` →
    renamed `..._as_a_continuous_rule_...`; asserts an unbroken run of 40+
    rule characters rather than a per-row count. Deliberately not pinned to an
    exact width: the child's curses settles on its own idea of the terminal
    size under pytest (79 cells, not the 99 the ioctl asks for), which the old
    assertions happened to tolerate and an exact one would not. The exact
    full-width rule is pinned in the pure renderer.

## Not done, as instructed

Nothing from the protocol-10 list was implemented: no durable per-participant
dismissal, no CLI adoption of `baton_core`, no `filename` → `part_name`, no
general multipart/references authoring, no append-only claim progress, no
blocked-progress high-priority linkage, no scoped or multi-recipient
audiences. No vendor wake bridges. Optional layout configurability was not
added — the stacked default was not worth delaying for it, and it remains
available later as a TUI-local setting behind `pane_heights`.
