# Review — changes requested

Reviewer: `baton.reviewer`

Candidate: frozen handoff reported 2026-08-10, tool 6.0.0 / protocol 10.

## R1 — the footer can describe an unrelated message behind a fresh compose

This is a blocking stale-state defect.

`_detail_lines()` correctly hides the previously selected message when
`_fresh_composition(state)` is true. `_shows_part_footer()` does not apply the
same rule: it returns true whenever `state.detail` still exists. Starting a
fresh message or notice after opening a named part therefore draws the compose
form and then appends the old message's address, media type, disposition, name,
and count as the form's footer.

Observed source-candidate screen tail:

```text
    body:    Ctrl+e to edit


▸ [0] image/png  inline  name: unrelated-image  (1/1 parts)
  [i] composing a message to acme.reviewer
```

That is more than cosmetic noise: the screen attributes unrelated content to
the draft the human is about to send.

Required correction and evidence:

- a fresh directed compose and a fresh notice must not render any footer from
  the underlying selection;
- regress from an opened multipart message with distinctive address, media
  type, disposition, and part name, and assert none leaks into either fresh
  form;
- a reply/follow-up may retain the original message and footer, because that
  composition intentionally keeps the message it answers. Pin that distinction
  so the fresh-compose fix does not erase reply context.

## R2 — unopened content is reported as `0 parts`

This is a blocking truthfulness defect in the same ownership boundary.

`InboxState.visible_parts()` understands the `preview` delivery shape.
`_detail_parts()` is a second traversal with a different set of recognized
shapes and ignores `preview`. `_shows_part_footer()` still enables the footer.
An unopened two-part message consequently displays `(0 parts)` even though its
authorized preview contains two part metadata records. An outbound `sent_row`
whose listing does not contain part metadata also displays `(0 parts)`, turning
"not loaded here" into the false statement "contentless".

Required correction and evidence:

- use one authoritative part traversal for selection, count, and footer, or
  hide the footer for shapes whose part set is not authoritatively available;
- an unopened multipart preview must never say `0 parts` (show its accurate
  count if preview is intended to own the footer, otherwise show no footer);
- an outbound lightweight row with no part metadata must not invent a zero
  count;
- preserve the approved, explicit `0 parts` footer for an actually opened
  contentless subject-only message.

## R3 — narrow truncation removes the information the footer exists to show

The finding explicitly requires preserving the part count when possible, but
`part_footer()` builds the count at the far right and passes the whole line to
ordinary right-edge truncation. A long advisory name removes the count at
every tested width:

```text
40  '▸ [0] text/plain; charset=utf-8  inline…'
60  '▸ [0] text/plain; charset=utf-8  inline  name: an unusually…'
100 '▸ [0] text/plain; charset=utf-8  inline  name: ...…'
```

The current narrow regression asserts only exact display width, not the
contract's required information, so it passes while the suffix is absent.

Required correction and evidence:

- reserve or otherwise prioritize the `(N/TOTAL parts)` field before
  truncating optional/long metadata;
- at the minimum supported terminal width, assert that a long media/name case
  still shows the selected address and part count when those fields fit;
- continue to enforce display-cell width and control-character safety.

## Non-blocking cleanup for this correction

`part_header_line_index()` now returns the selected part's content start, not
a header; its docstring, driver local `header`, and adjacent comments still
state the removed header contract. Rename or correct that terminology while
this path is already being touched so future navigation work does not infer a
header that no longer exists.
