## R1 — explicit empty inside an existing quick reply still permits fallback

Severity: **blocking wrong-message path**.

In `MODE_REPLY` with a quick subject draft and no previously imported body,
the editor seed is the original-message quote. Returning exact empty differs
from that seed, reaches the new refusal, and returns `False` before setting
`reply_body_requested`. Because this is Ctrl-E inside an existing composition,
the driver keeps `MODE_REPLY`. A later ordinary Enter/affirmative key then sees
`reply_body_requested == False` and `send_reply()` publishes the quick subject
through its subject-only shorthand.

The human chose the full-body editor and explicitly emptied it; this is the
same “send a different message” failure the first review required the fix to
close.

Required correction: an explicit empty result must preserve the prior buffers,
show the immediate warning, never arm, and preserve full-body intent. In reply
mode that includes keeping `reply_body_requested` protective when no prior body
exists, so every later ordinary send still refuses rather than falling through
to the subject.

## R2 — fresh empty refusal is mistaken for cancellation and loses the draft

Severity: **blocking contract and existing-regression violation**.

From browse, the driver treats every false `edit_body_externally()` result as
“the one action did nothing” and calls `abandon_fresh_reply()`. The new exact-
empty refusal therefore clears the provisional reply/follow-up instead of
retaining the ruled protected draft/context.

The pre-existing
`test_an_empty_body_from_the_editor_refuses_rather_than_sending_the_subject`
used to assert:

```python
assert state.draft == "Deploy", "the draft was lost"
```

That assertion was removed in this correction. The review authorized changing
when the warning is asserted; it explicitly required fresh browse reply and
follow-up coverage with unchanged buffers. Removing the preservation assertion
was neither authorized nor a correction: it adapted the old regression to the
new loss.

Required correction: distinguish at least three transition outcomes—successful
non-empty import (arm), cancellation/unchanged/error (fresh action may restore
browse), and explicit-empty refusal (do not arm or import, but retain protected
draft/context and full-body intent). A small enum/sentinel/result object is
preferable to overloading a boolean whose two callers need different behavior.
Restore the existing draft-preservation assertion and add the missing fresh
browse follow-up case.

## R3 — the new tests do not prove the bytes claimed in their comments

Severity: **blocking regression gap on the wrong-message boundary**.

`test_emptying_the_body_in_the_editor_never_arms` says a later send publishes
the original body, but after publication it queries only the message count and
`subject`. A subject-only fallback has exactly that same subject, so the test
would pass for the defect it says it excludes.

Likewise the three whitespace parametrizations assert the in-memory body before
send and count a later row, but never open the published message/notice and
compare its content bytes. The first review specifically required exact
published bytes.

Required correction:

1. Open the sent message/notice through the public core API and assert the
   inline leaf text is exactly the preserved body or whitespace body after
   publication.
2. Add empty-refusal cases for existing quick/full reply, compose, notice,
   fresh browse reply, and fresh browse follow-up. Assert immediate warning,
   unchanged buffers/context, no confirmation/no write, and then either exact
   prior-body publication or continued refusal—never subject fallback.
3. Deliberately remove the explicit-empty protection and show the named cases
   fail for the actual wrong bytes/disposition, not only for an intermediate
   mode.
