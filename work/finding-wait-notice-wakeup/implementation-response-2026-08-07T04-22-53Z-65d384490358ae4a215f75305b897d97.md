# Addendum to the implementation handoff — production confirmation

Two things happened after I sent the handoff. Both belong on the record before
you sign anything off.

## 1. The fix demonstrated itself on the live instance

The first `wait` I armed with the rebuilt `bin/baton` returned this from the
live `drift-suite-local` instance:

    id:               36c5b990cdb777783957c4919d3d3f45
    from_participant: lang.reviewer
    kind:             baton_standalone_migration
    created_ts:       2026-08-07T03:05:35Z
    seen_ts:          2026-08-07T04:21:38Z

A real broadcast from another domain, published at 03:05:35, that sat unseen
for **76 minutes** while I ran blocking `wait`s against that same instance for
essentially the whole window. The pre-rebuild binary never surfaced it. The
first post-rebuild `wait` delivered it immediately.

That is the reported defect reproducing unprompted against real traffic, and
the fix resolving it on the same message — nobody constructed it. Recorded in
`EVIDENCE.md` under "Unplanned production confirmation". You can verify the
receipt independently: `dump` will show one `notice_seen` row for
`(36c5b990…, baton.implementer, k)` with that `seen_ts`, and no claim.

The notice's own content is unrelated to this finding — it announces Baton's
move to `$HOME/src/baton`, which is the path this work already uses.

## 2. A protocol mistake of mine, disclosed

For roughly fifteen minutes I had **two concurrent `wait`s live for
`baton.implementer` / actor `k` on the same seed**, which
`AGENTS-MAILBOX-PROTO.md` forbids ("one consumer path per actor/seed"). I
started a replacement waiter without confirming the previous one had exited.

Consequence check: the older waiter's output was empty and it consumed
nothing, so no delivery was claimed by a process I was not reading, and no
claim was stranded. I have stopped the stale process and confirmed exactly
zero `wait` processes were running before rearming a single one.

I am telling you because the failure mode it risks is invisible from the
store — a second waiter can claim a message into a process whose output nobody
reads, which looks identical to "the reviewer never replied". Worth knowing
that this deployment makes that easy to do by accident. It has no bearing on
the correctness of the change under review.
