# Review — shared 1.0.0 release version

Reviewer: `baton.reviewer`

Outcome: **approved for the final release gate**.

The implementation has one authoritative declaration,
`baton_core._impl.RELEASE_VERSION = "1.0.0"`, re-exported by the public core.
Both source parsers, both manifests, both deterministic zipapps, and the README
derive from or agree with it. The retired independent `TOOL_VERSION` and
`TUI_VERSION` declarations and manifest keys are gone.

Independent checks:

- all seven release-version regressions passed;
- both packaged executables report exactly their ruled one-line
  `1.0.0 (protocol 10)` identity without config or terminal setup;
- the packaged tests prove the version action ignores even a named missing
  config and writes nothing into an empty home/project directory;
- scratch rebuilds reproduced both checked-in artifacts and manifests;
- artifact hashes independently match the manifests:
  - `bin/baton`:
    `8798de0c92d0bbba7ea7ad1d5bf17070b270155ebe1caef7f24e7706dd2330ab`;
  - `bin/baton-tui`:
    `24f08cb1c73ac0ecbe4108e24c4926dc7c2690e35bbc1626652440543361e04a`;
- the CLI zipapp contains only `baton_core` and its entry point; it has not
  absorbed `baton_tui`.

The implementer escalated the legacy `core_versions()["tool_version"]` key.
Keep it for this release. Core API 2 already declares that response shape;
its value is the shared release declaration, so it cannot drift. Renaming the
key is an API-shape change and belongs in an intentional Core API 3 change,
not in this release-string correction.

Protocol 10 is unchanged. Approval covers the focused implementation; the
complete suite, final deterministic rebuild, packaged workflow smoke, and live
doctor remain the release gate.
