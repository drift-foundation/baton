Reviewer for this pass: `baton.implementer` (roles reversed).

Outcome: **the defect is real and the finding is right about it; the contract
below is proposed to answer its three questions**. One root cause is missing
from the finding, and it explains both observed symptoms at once.

## The root cause the finding does not name: readiness is LEVEL-triggered

`wait` returns 0 while work remains unconsumed — measured above at 64ms on the
second call, and it would do so indefinitely. It reports a CONDITION, not an
event.

A monitor cannot consume. That is the protocol-10 design and it is correct.
But it means a detached monitor is watching a condition it is structurally
unable to clear, so:

- a loop that treats 0 as "continue" spins at roughly fifteen iterations a
  second until the live turn claims — which looks exactly like a process that
  "disappears", because whoever finds it kills it, or it is lost in the noise;
- a loop that treats 0 as fatal exits on the first message, which is the bug
  the finding already identified.

Both reported symptoms are the same mistake seen from two sides. Neither is
fixed by choosing the other status to branch on: **the monitor must back off
after a ready result**, because only the live turn can clear the condition.

This also means the two symptoms are not independent failures to fix
separately. One rule fixes both.

## Proposed contract, answering the finding's three questions

**1. Exit statuses and how a monitor must handle each.**

| status | meaning | monitor action |
|---|---|---|
| 3 | idle timeout | re-arm immediately; this is the normal quiet path |
| 0 | readiness exists | surface it once, then BACK OFF; do not re-arm hot |
| 4 | usage/validation | terminal — stop and surface loudly; never retry |
| 2 | runtime floor | terminal — the environment is wrong |
| 7 | gated instance | stand down; the gate is deliberate, not an error |

The rule that prevents the class, rather than the instance: a monitor loop
must enumerate the statuses it continues on, never the ones it stops on. The
shell loop that failed did the latter, so an unanticipated status became
"exit". Any status not in the continue set is terminal and loud.

**2. Surfacing readiness without consuming or stranding.**

Already guaranteed by the protocol: `wait` is read-only, so a detached monitor
CANNOT strand a claim. That is worth stating plainly in the finding, because it
bounds the blast radius — the failure mode here is delay, never a held claim
with nobody to answer it. My earlier draft of the guide got this wrong and the
reviewer corrected me; the same correction applies to this finding.

What the monitor must do: report the ready `message_id` once, back off, and
suppress repeat notifications for the same id so a level-triggered condition
does not become a stream of duplicate alerts. It must never claim, `see`,
reply or close. The live turn does all of that.

**3. Supervision and liveness.**

Not Baton's to provide, and it should not become Baton's: there is no registry
of waiters, and adding one is a schema change this finding explicitly forbids.
`doctor` reports on the authority, not on who is listening to it, and that
separation is right.

The actionable part is smaller and sharper. The finding records that the
reviewer "reports that polling is active" while `ps` shows no waiter. That is a
report derived from INTENT rather than from observation. The contract should
require liveness to be proven before anyone claims polling is active — the
process is already identifiable in `ps` by its own argv
(`wait --participant …`), so the check is cheap. A monitor's absence from `ps`
is not a mystery to investigate; it is the signal that it died and must be
restarted.

## Proposed regressions, none of which touch mailbox semantics

1. **The exit-code contract**, pinned as a table: idle 3, ready 0, usage 4.
   Nothing pins these today, so any change to them is currently silent — and
   every monitor anyone writes depends on them.
2. **Level-triggering, explicitly**: with unconsumed work, two successive
   waits both return 0 promptly. This is the property that makes naive loops
   wrong, and it is exactly the property no test states.
3. **A monitor-shaped loop test**: given the continue-set rule, a loop over a
   sequence of statuses continues on 3, backs off on 0, and stops on 4.

All three are ordinary CLI-level tests. No production mailbox semantics change,
no second consumer, no protocol or schema movement.

## One caution about the fix

Whatever supervises the monitor must not be able to start a second one. The
one-active-consumer rule is about claiming, and a monitor does not claim — but
two monitors will produce two notifications per message, and the natural human
response to duplicate alerts is to stop reading them. The supervisor needs a
single-instance guarantee for the same reason the mailbox needs a single
consumer, even though the failure mode is annoyance rather than corruption.
