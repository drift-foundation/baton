## R1 — the final publication is still replacing `rename`, not no-replace

Severity: **release-blocking atomic-publication defect**.

`publish()` checks `os.path.lexists(version_dir)` under a cooperative `.lock`
directory and later calls `os.rename(staging, version_dir)`. The lock prevents
two copies of this tool from entering together, but it does not reserve the
final pathname. Another process can create an empty final directory after the
check and before `rename`; POSIX rename then consumes that directory and
publishes successfully over an object the tool did not create.

The reviewer race inserts the empty final directory at the rename boundary.
The expected no-replace refusal does not occur; publish returns success and
the foreign directory is gone. The existing concurrent test only pre-creates
the cooperative lock, so it cannot expose this race.

Required correction: publish with a real atomic no-replace primitive. The
final operation itself must refuse any object at `v<VERSION>`, independent of
the advisory serialization lock. Add the move-boundary race regression and
prove the foreign path survives byte-for-byte.

## R2 — staging is neither uniquely created nor removable after hardening

Severity: **release-blocking failure-cleanup defect**.

The staging name is only PID-derived. If it already exists, `publish()` calls
`shutil.rmtree(staging, ignore_errors=True)`, which may delete an unrelated
directory left by a previous process/PID reuse. That contradicts the ruled
“remove only the staging tree this process owns” boundary.

After `_harden()` changes every staging directory to `0555`, the exception
handler uses the same `rmtree` without first restoring owner-write permission.
An injected final-rename failure leaves the entire hardened
`.staging-v1.1.0-<pid>` tree behind. The current copy-failure test fails before
hardening and therefore cannot exercise this cleanup path.

Required correction: create staging atomically with a genuinely unique name
that this call thereby owns, refuse rather than delete any unexpected
pre-existing object, and use a no-follow cleanup helper that can remove the
owned tree even after hardening. Add both pre-existing-staging and
post-hardening rename-failure regressions.

## R3 — `verify` ignores the required modes and accepts a symlink root

Severity: **release-blocking verification defect**.

The plan explicitly requires verification of permissions and symlink safety.
`verify()` currently checks recorded leaf bytes but never checks modes. Changing
`README.md` from `0444` to `0644` without changing a byte returns no problems;
activation would accept that writable tree. The official tamper test changes
both mode and bytes, so the digest—not the mode—makes it fail.

Direct `verify` also accepts a symlink used as `VERSION_DIR`. Leaf checks do not
see it because `_no_symlink_ancestors` stops before examining the root itself.
Activation has a separate root check, but the public verify command promises
to validate the deployed tree and must not follow a deployment root elsewhere.

Required correction: verify the exact ruled modes (`0555` directories and
`bin/` leaves, `0444` other leaves), lstat/refuse a symlink or non-directory
version root, and add mode-only plus root-symlink regressions. Keep the existing
recorded-leaf symlink and extra-file cases.

## R4 — only the staging root directory is fsynced

Severity: **blocking durability gap in the stated publication contract**.

Every file is fsynced before hardening, then `_fsync_dir(staging)` syncs only
the staging root. The `bin`, `docs`, `dist`, and `examples` directory entries
are never fsynced, and mode changes occur after the file fsyncs. A root-directory
fsync does not make entries in its child directories durable.

The reviewer fsync recorder saw only `.staging-v1.1.0-<pid>` and the destination;
all four nested payload directories were absent.

Required correction: after the payload and final modes are complete, fsync the
regular files whose metadata changed and every directory deepest-first, then
perform the atomic no-replace publication and fsync the destination. Add a
regression that records the directory fds and proves nested entries participate.
