## R1 — the ruled command and payload are not implemented

Severity: **release-blocking contract mismatch**.

Slawomir ruled the soak command shape `just deploy DEST 1.1.0`. The current
recipe is `deploy DESTINATION`; `tools/deploy.py publish` accepts no requested
version and deploys whatever release the manifests happen to name. The human
therefore cannot state or verify the version they intend to install, and the
ruled command with two arguments does not dispatch.

`PAYLOAD` still excludes `examples/baton.json`, while the later ruling requires
that inert template. The focused test positively asserts the superseded
exclusion. `PAYLOAD` also hardcodes `docs/RELEASE-1.0.0.md`, so a 1.1 publish
would either carry the old release announcement or fail after that file is
retired; the release document must be selected from the certified version and
`docs/RELEASE-1.1.0.md` must exist before publish.

Required correction:

1. make publish and `just deploy` require `VERSION`, validate the release
   spelling, and refuse unless both manifests name exactly that release;
2. invoke it exactly as `just deploy DESTINATION VERSION`;
3. include `examples/baton.json` and assert it is a template while still
   excluding every SQLite/live-authority artifact;
4. select `docs/RELEASE-<VERSION>.md` dynamically and fail in preflight if it
   is absent.

Changing the old “no examples” assertion is case-specifically authorized by
Slawomir's explicit payload ruling; retain the authority-exclusion assertions.

## R2 — certification ignores a manifest-pinned deployed file

Severity: **release-blocking mixed-version deployment**.

`DISTRIBUTION.json` records both `protocol_doc` and
`protocol_doc_sha256`. `certified()` validates only each artifact hash; it
never validates the protocol document it then copies into the deployed tree.
Once 1.1 source documentation changes while frozen 1.0 artifacts/manifests
remain, the tool can pair those 1.0 binaries with newer protocol prose and
write `DEPLOYMENT.json` over the mixture. Its later `verify` then succeeds,
because the deployment record blesses the bytes it happened to copy rather
than checking the manifest pin the release already supplied.

The two manifests' protocol versions are also not compared: the loop simply
overwrites `protocol` with the last value while it correctly compares release
versions.

Required correction: preflight every manifest-addressed deployed artifact,
including `protocol_doc_sha256`, and require both manifest protocol versions to
agree. Add a regression that changes only the pinned protocol document and
proves publish leaves no destination version behind.

## R3 — a refused publish leaves a visible, permanently blocking partial version

Severity: **release-blocking publication integrity defect**.

`publish()` creates and fills the final `v<version>` directory incrementally.
It checks each payload file only when that loop reaches it. A missing late file,
copy/write failure, interrupt, or process death therefore exposes a partial
final version. The next invocation sees that version directory and refuses to
repair it under the immutability rule.

Independently reproduced with an otherwise valid certified source lacking only
the final `LICENSE` payload entry:

```text
exit 1: deploy: LICENSE is missing
destination/v1.0.0/ already contained both binaries, manifests, three docs,
and README.md; DEPLOYMENT.json and LICENSE were absent
```

The exact retained repro is under
`/tmp/baton-deploy-review-repro-20260811/` for this review turn.

Required correction: validate the complete source payload first, populate and
verify a uniquely owned sibling staging tree, fsync it, then publish the
complete directory atomically with a no-replace primitive. Any ordinary
failure removes only that exactly owned staging tree and leaves no final
version. Existing final paths are never replaced, including an unexpected
empty directory. Add late-payload, injected-copy-failure, existing-empty-dir,
and concurrent no-replace regressions.

## R4 — “immutable/read-only” and symlink claims exceed the implementation

Severity: **blocking hardening for an externally used release tool**.

The progress record says the deployed tree is read-only except executables.
Measured output has version/directory modes `0775` and executable mode `0755`;
both are owner-writable and the directories are group-writable. Files can be
added and binaries replaced without first changing permissions. `verify()`
also follows symlinks and accepts any regular bytes reached through them; it
does not establish that a recorded path itself is a regular deployed file.

`activate()` uses a fixed `current.staging` name and unconditionally
`os.remove()`s any object found there. It also allows `os.rename()` to replace
an unrelated regular file at `current`. Although activation is explicitly
forbidden for the 1.1 soak and permanent activation remains next-major work,
the shipped command must not delete unrelated destination entries.

Required correction:

- after complete staging, set executables/directories to `0555`, other files
  to `0444`, and fsync before publication; document that filesystem ownership
  still permits a human to deliberately remove a version;
- require deployed payload entries to be regular non-symlink files and reject
  symlink/non-directory ancestors in publish and verify;
- make activation refuse unexpected `current`/staging object types and use a
  uniquely owned staging link rather than deleting a fixed arbitrary path;
  fsync the destination directory after the atomic swap;
- cover symlinked payload, writable-mode, unexpected-current/staging, and
  activation-no-disturbance cases.
