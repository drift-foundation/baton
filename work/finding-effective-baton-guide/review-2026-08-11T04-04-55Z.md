## Required correction — the config ceremony as written is impossible

`docs/EFFECTIVE-BATON.md:29-30`:

> An administrator adds participants or roots through Baton's audited config
> ceremony. Never edit the JSON or SQLite database directly.

The ceremony IS a config-file edit. `regen_instance` reopens the SAME
`config_path`, requires the offered `generation` to be exactly accepted+1, and
requires the `config` capability. So adding a participant means: write the new
config at that path with `generation` incremented by one, then run
`regen --participant <admin>`. A reader who follows "never edit the JSON"
literally has no way to add a participant at all.

Suggested replacement, which keeps the real prohibition intact:

> Config changes take effect ONLY through the audited `regen` ceremony. An
> administrator with the `config` capability writes the new config at the same
> path with `generation` incremented by exactly one, then runs
> `regen --participant <admin>`; Baton accepts or refuses it in one
> transaction. Editing the file alone changes nothing, and the SQLite database
> is never edited by hand.

This is inherited wording, not invented: `docs/AGENTS-MAILBOX-PROTO.md:127-128`
says "direct config/database edits are forbidden" and the guide followed it.
The README is the one that is right, if terse: "`regen` (accept a
generation+1 config; requires `config`)".

**Do not fix the protocol document in this change.** `dist/DISTRIBUTION.json`
pins `protocol_doc_sha256`, so editing it forces a manifest change to a
released 1.0.0 distribution. The artifact itself does not embed the document,
so only the manifest would move — but that is still a released-manifest edit
for a wording fix. Correct the guide now, and log the protocol-document
sentence as its own finding for the next release window.

## Recommended addition — `see` is not targeted

The guide sets up a parallel: for a message, "claim the exact reported id";
for a notice, run `see`. `see` takes no id and consumes EVERY unseen notice
for the participant at once. That asymmetry is deliberate — `wait` reports
`{"ready": true, "channel": "notice"}` and never names the notice — but a
reader following the parallel structure may expect a targeted receipt. One
sentence at line 48-51 would close it, e.g. "`see` has no id: it marks every
unseen notice for the participant seen and returns them together."

## Recommended addition — nothing pins the guide's syntax

This is the duplication risk the brief asked me to attack, and it is not the
duplication itself: a working guide has to show commands, and the guide is
disciplined about not restating the contract. The gap is that no test fails if
a flag it shows is renamed or removed. I checked: no test references
`EFFECTIVE-BATON.md` or `RELEASE-1.0.0.md`, and the documentation coverage
that exists is the extraction-purity grep gate and the distribution-root
contract, neither of which reads these files.

Concrete mitigation, offered rather than done because the document is the
author's: a focused test that extracts every `"$BATON_BIN" ... <subcommand>
... --flag` occurrence from the guide and asserts each subcommand and long
option exists in the real parser. That turns the duplication from a drift risk
into a checked invariant, and it is the same argument the release-version work
used for the manifests — compare the copy against the source, not against
another copy. I will write it on request.
