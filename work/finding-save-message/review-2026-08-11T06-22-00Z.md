# Review — save any message body

Reviewer for this pass: `baton.implementer` (roles reversed).

Outcome: **the need is real, but the finding's premise is inverted and one
requirement as written would break the retention contract.** Recommend
rewriting the premise before any design work, because the current text points
the implementation at the wrong operation.

## The premise is backwards, demonstrated

> `materialize` is currently limited to materializable external content

It is the opposite. `_project_part` writes INLINE bytes and explicitly REFUSES
external ones:

    part '0' of message '…' is externally stored at root:path; it is already a
    file and is not copied into a projection

I ran it rather than reading it. Against a development authority, a claimed
message with an inline markdown body:

    baton materialize --participant dev.reviewer --dir <chosen dir> --part 0 <id>
    -> {"projection": "<dir>/message-2026-08-11T06-20-30Z-<id>.md"}

The file was written, with the body in it. So the motivating sentence — that
there is no direct way to save a large inline body — is not true today, and
the console has had `m` bound to exactly this since the part-footer work.

I am not saying the feature is unnecessary. I am saying that if this text goes
to an implementer unchanged, they will start by adding inline support to an
operation that has always had it.

## What the real gaps are

Having checked the operation rather than the description, these hold up:

1. **No whole-message save.** `materialize` writes ONE leaf per invocation and
   the caller must know the part address. Saving a three-part message is three
   commands and a reading of the manifest. That is the actual missing
   operation, and it is worth having.
2. **No chosen filename.** The caller picks the directory and a `--prefix`;
   the name is generated as
   `<prefix>-<created_ts>-<message_id>[-partN]<suffix>`. The finding asks for
   "an explicitly chosen path", which is a genuine gap — though the generated
   name is doing real work (it is collision-resistant and it says which
   message the file came from), so replacing it should be a choice, not a
   default.
3. **Containers are refused**, deliberately: you address leaves. A
   whole-message save is precisely the operation that would walk the container
   instead, which is the shape the feature should take.

## The requirement that would break a contract

> Humans need a direct way to save the complete content of any claimed message

`materialize` refuses a TRANSIENT message, and says why:

    message '…' is transient; materializing it would create a durable copy
    that defeats the retention contract

"Any claimed message" includes transient ones. A save feature that honours
that word literally is a retention bypass with a friendly name — and it would
be reached by a human pressing a key in a console, which is the worst possible
place for a contract to be quietly undone.

**Recommendation: the save operation inherits the transient refusal verbatim.**
If Slawomir wants transient content saveable, that is a deliberate change to
the retention contract and belongs in its own finding with its own ruling, not
as an implied consequence of a convenience feature.

## Two decisions the contract does not yet make

**External parts in a whole-message save.** They are already files, and their
pin is what gives them integrity. Copying them into a save directory produces
a second, unpinned copy that will drift from the pinned original — so my
recommendation is: do not copy them; write a manifest alongside the saved parts
naming each external part by `root_id:path` and its expected digest. The human
gets a complete record of the message without the tool manufacturing an
unverifiable duplicate.

**Overwrite and filename safety already have a policy** — a strong one, in
`_publish_bytes_at`: scratch write, fsync, no-clobber hardlink, directory
fsync; an existing file with IDENTICAL bytes is accepted as a resume; a
mismatching file is refused; a symlink is refused. The plan's line about
needing an explicit overwrite policy should become "reuse the existing one",
because inventing a second policy for the same directory is how two answers to
"may I overwrite this" end up in one tool.

## On the plan's ordering

Step 4 puts regression coverage before implementation, which is right. But the
first step has to be correcting the premise: every step below it inherits the
inverted description, and a plan whose first line is wrong produces a design
that is wrong in the same direction.

Suggested first step: restate the gap as "there is no whole-message save, and
no chosen output path" — then steps 1 to 4 as written are sound.

# Second pass — the `m` refusal Slawomir hit

Asked to verify the console's claim precondition and explain or fix it.

## What he hit, exactly

`materialize_selected_part` requires `self.opened` to be a ROW_MESSAGE with a
non-null `claim_id`. `_revalidate_action_target` clears `self.opened` as soon
as the row stops being `claimed` — which is what replying or closing does — and
the poll runs every two seconds. So the sequence is:

1. claim and open a message, read it;
2. reply or close it;
3. within two seconds the action target is dropped;
4. `m` now reports "materialize needs a message you hold the claim for; this
   row has none".

The same refusal covers two more cases that are not "you have no claim" at all:
a message the participant SENT (there is no claim; they are the author) and a
seen NOTICE (notices are seen, never claimed).

## It is a real defect, not just wording

The core does not have this rule. The module-level `materialize` authorizes by
sender-or-audience — the participant-scoped reread — and does not ask for an
active claim. Measured against a development authority:

    # message answered and closed by dev.reviewer, claim no longer active
    baton materialize --participant dev.reviewer --dir … --part 0 <id>   -> ok
    # the same message, materialized by its AUTHOR
    baton materialize --participant dev.implementer --dir … --part 0 <id> -> ok

Both succeed. So the agent CLI can save the human's own answered mail and their
own sent mail, and the human console — the thing built for humans — cannot.
The console is strictly less capable than the tool it fronts, for the
participant's own content.

## Why the rule exists, and where it should actually apply

The rule is not wrong, it is over-applied. The preview boundary says: writing
bytes to disk is reading them in the most durable form there is, so `m` must
not turn an UNCLAIMED PENDING message into content on disk without the human
claiming it. That is exactly right and must not be relaxed.

But it only bites on unclaimed pending mail. For a message already answered, a
message the participant sent, or a notice already seen, the content is
legitimately readable — the console itself displays it — and refusing to write
what it is already showing protects nothing.

## Recommended fix

1. `m` uses the participant-authorized path for rows whose content the
   participant may already read: answered messages, sent messages, seen
   notices. The core's own authorization decides, rather than the console
   applying a stricter private rule.
2. The active-claim requirement stays for exactly one case — a pending message
   not yet claimed — which is the case the preview boundary is about.
3. The refusal text names the real rule. "Needs a message you hold the claim
   for" describes neither the core's rule nor the remaining console rule; for
   an unclaimed pending row it should say that opening it is what makes its
   content available, since that is the action the human should take next.

This is console-only. No protocol, schema, authorization or retention change:
the console would call an authorization path that already exists and is already
exercised by the CLI.

# Retention, as asked

Retention is chosen by the SENDER, per message, at publication: `--retention
durable` or `--retention transient` on `send`/`reply`/`close`, defaulting to
durable. It is not a property of the reader, the mailbox or the claim, and no
reader can change it.

A transient message's metadata is garbage-collected under the instance's
`retention_days`, and its content is not meant to outlive that. Materializing
one is refused for that reason — "materializing it would create a durable copy
that defeats the retention contract" — and the refusal is the contract working,
not a limitation to route around. Unchanged by this finding, and a save
operation inherits it verbatim.

# External parts

Confirmed as ruled: a whole-message save retains `root_id`, `path` and digest
references and does not copy the bytes. This matches the recommendation in the
first pass, and the reason stands — a copy of a pinned file is a second,
unpinned artifact that will drift from the original it claims to be.

# Implementation — the `m` fix, 2026-08-11

Approved as console-only. Delivered, with one part deferred for a reason worth
recording.

## What changed

`materialize_selected_part` no longer requires an active claim. It refuses
exactly one thing — a row that positively identifies as an INBOUND PENDING
message — and routes everything else to the core's own authorization
(`authorize_read`) followed by `materialize_part`. The console decides which id
to ask about; the core decides whether the participant may read it, so the
boundary never moves into the front end.

The refusal text now names the action that helps ("Enter opens it, which is
what makes its content available to save") instead of a rule about claims the
human cannot act on.

## Deferred, and why

Saving a SEEN NOTICE still refuses — but honestly, naming `baton materialize`
as the way through. The core authorizes a seen notice for reread; the only
projection method a front end holds, `Store.materialize_part`, resolves
MESSAGES, and the notice-aware path is the module-level entry point that opens
its own instance. Closing that needs a small core addition, which is more than
the console-only fix authorized.

Pinned as a known gap by `test_saving_a_notice_is_refused_with_an_honest_
reason`, which also asserts the core WOULD authorize it — making it visibly a
console gap rather than a limit on the human's authority.

## The mistake I made twice in one day

The first predicate was "not outbound and pending". SENT rows carry neither
`row_type` nor `direction`, so every message this participant had written was
classified as unread inbound content and refused — the exact failure I hit
hours earlier writing the search filter, in the same file, for the same reason.
Both are now default-deny on identity: a row is treated as unread only if it
positively says it is an inbound message.

Recording it because the lesson is not "check direction". It is that this
model has TWO row shapes and the sent one is missing the fields the inbox one
carries, so any predicate that reads those fields must fail closed.

## Evidence

`tests/tui/test_tui_materialize_boundary.py`, 6 tests: an unclaimed pending
message is still refused and nothing reaches disk; an answered message can be
saved; a sent message can be saved; the notice gap is refused with a reason and
a way through; authorization is the core's (a participant who is neither sender
nor audience is refused, while both sender and recipient are allowed); and
saving writes nothing to the authority, compared against a full `dump()`.

Deliberate break: the preview-boundary check disabled →
`test_an_unclaimed_pending_message_is_still_refused` fails.

`tests/tui`: 1620 passed.

# Notice-aware materialization — 2026-08-11, and a consequence

Ruled: anything viewable in full must be saveable, seen notices included.
Implemented as authorized, with one consequence that needs a decision.

## What changed

`Store.materialize_authorized_part(owner_id, participant, target_dir, …)` — the
reread path, extracted from the module-level `materialize` entry point, which
now DELEGATES to it. One implementation, so the agent CLI and the human console
resolve, authorize and name a projection identically; they had drifted, which is
the whole reason this finding exists.

The console calls it for messages and notices alike, so it decides which id to
ask about and nothing else. The preview boundary is unchanged: an unclaimed
pending message is still refused.

Authorization and retention are untouched, and both are pinned: a message needs
its sender or frozen audience, a notice needs its author or a participant who
has already seen it, refusals stay indistinguishable from "no such id", and a
transient message still refuses because a durable copy would defeat the choice
its sender made.

## The consequence: `bin/baton` is now stale against its own source

The CLI manifest pins `source_sha256` of `baton_core/_impl.py`. The `m` fix
required a core addition, so that hash no longer matches and three tests now
fail on one cause:

    TestPackaging::test_distribution_root_contract
    TestPackaging::test_isolated_checkout_runs_full_reusable_suite
    test_rebuilding_reproduces_the_checked_in_artifacts_and_manifests

This is materially worse than the state we agreed to leave red. Before, only the
CONSOLE source was ahead of its artifact. Now the CORE is, which means the agent
CLI every team runs is stale relative to the source beside it — and the CLI
manifest, unlike the console's, records exactly enough to prove it.

I have NOT rebuilt. Rebuilding `bin/baton` would modify a released 1.0.0 artifact
in the released tree, which is precisely what the isolation ruling forbids and
what the branch exists to make unnecessary.

It also sharpens the branch decision: any core change at all desynchronizes the
CLI artifact, so next-generation work cannot proceed much further in this tree
without either a branch or a rebuild of production bytes.

## Evidence

`tests/core/test_core_api.py::TestAuthorizedMaterialize`, 4 tests: it reaches
messages and seen notices while refusing an unseen one; no claim is required and
none is created (full `dump()` comparison); authorization is unchanged, with the
two refusals identical apart from the id each names; retention is unchanged and
nothing is written.

`tests/tui/test_tui_materialize_boundary.py`, 7 tests, including the seen notice
saving and a transient message still refusing through the authorized path.

Deliberate break: the notice branch removed from the resolution walk → the core
test and the console test both fail by name.

Full suite: 2354 passed, 3 failed — all three the staleness above.

# R1 fix — dispatch, 2026-08-11

The reviewer was right and the finding is exact: the model was widened and `m`
still refused, because `_AFFORDANCE` gates it through `affordances()`
["materialize"], which still required an active claim. Every model test passed
while the console stayed broken — the same shape as the packaged Enter defect,
and I should have measured through the key rather than the method.

## Fixed

- `affordances()["materialize"]` no longer asks for a claim. It asks the SAME
  predicate the model asks.
- `unavailable_reason("materialize")` names the action that helps, and
  distinguishes an unopened message from an unseen notice.
- The stale docstring on `materialize_selected_part` is rewritten.

## Two defects the new cross-check found in my own fix

**The affordance over-promised on an UNSEEN notice.** The rule only covered
unclaimed pending messages, so `m` was advertised on a notice the human had not
seen, and pressing it produced "unknown id" from the core. The predicate is now
`_is_unreceived_content`: an inbound message still pending, OR a notice not yet
seen. Both are content this participant has not received; everything else is on
their screen already.

**The rule was reading an identity, not a row.** `self.opened` carries row type,
id and claim — not `state` — so asking it whether a notice had been seen
answered "no" forever. `_action_row()` resolves the actual list row, which is
where state lives.

Found by `test_the_affordance_and_the_model_agree`, which walks every row shape
and asserts the affordance and the write agree in both directions. That test
exists because two places asking the same question is exactly how this defect
happened, and my first fix reintroduced it in a third place — a line-spanning
edit missed the affordance, so it kept reading the identity dict after
everything else moved to the row.

## Evidence

Driver-level, through the real key: an answered message saves; a seen notice
saves; an unclaimed pending row is refused with nothing written and no claim
created; and the affordance/model agreement sweep.

One existing assertion changed: `test_m_on_a_pending_preview_writes_nothing`
pinned the old refusal wording, which the ruling made obsolete. Every
substantive assertion in it — no file, no claim — is untouched; only the string
it matches now describes the current rule. Flagged rather than done quietly.

Deliberate break: the affordance restored to demanding a claim while the model
stays widened — exactly the state reported — fails both key-level tests by name.

`tests/tui` + `tests/core/test_core_api.py`: all passing.
