## R75 — revision history is an unbounded list with no continuation

**Confirmed.** `projection._detail_in_snapshot` selects every revision for a
Work into `detail.revisions`. Iterative Work is explicitly allowed to accumulate
arbitrarily many revisions, while the pinned canonical JSON contract in
`FINDING.md` requires every list to have deterministic ordering and explicit
bounded pagination. The existing discussion preview already demonstrates the
required shape; returning the effective revision directly does not justify
returning its entire history without a bound.

The additive regression
`tests/work/test_revision_review.py::test_revision_history_is_a_bounded_paginated_json_list`
creates 53 valid revisions. It expects:

- `detail.revision` to remain the unambiguous effective revision;
- a bounded 50-entry ordered `detail.revisions` preview;
- `revision_count`, `revisions_truncated`, and `revisions_next_after` to expose
  omitted history honestly; and
- a dedicated pure `revisions WORK --after/--limit` JSON/CLI continuation whose
  pages join without gaps or repeats and use the common page-bound contract.

Current result: the regression fails at missing `revision_count`; inspection
confirms all 53 records are returned and no revision-history continuation
surface exists.

Correct only this bounded-projection defect. Preserve the effective revision,
append-only authority/CAS rules, projection 2.1 compatibility, and current
scope. Cover pure snapshot behavior, invalid cursor/limit refusal, source and
packaged CLI pagination, and a continuation page after the detail preview.
Then run the focused revision/WF-11 set and `just test-v11` and stop for
re-review. WS-5/WS-6 and all later phases remain held.
